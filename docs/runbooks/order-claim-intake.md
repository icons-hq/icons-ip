# 굿즈 클레임 직접 신청과 고객지원 접수

2026-09-09 승인 정책은 [ADR-0017](../adr/0017-order-claim-intake-and-origin-collections.md)을 따른다. 이 문서는 운영 절차이며 production 적용 완료나 법무 검토 완료의 증거가 아니다. 티켓 취소 정책에는 적용하지 않는다.

## 직접 신청 조건

| 주문 사실 | 주문 상세의 직접 신청 | 운영 확인 |
| --- | --- | --- |
| 발주확인 전, `pending`·`paid` | 주문 전체 취소 | 발주확인·발송 이력, 결제 사실, 기존 활성 클레임을 서버에서 확인한다. |
| 발주확인 후, 미발송·배송 중·일부 수령 | 취소·반품·교환 직접 신청 닫힘 | 청약철회 의사를 1:1 문의·고객지원에서 받고 접수 시각을 보존한다. |
| 모든 주문 품목의 수량이 실제 배송 완료, `delivered`·`done` | 주문 전체 반품·교환 | 취소 배송 건이나 누락 품목을 완료로 세지 않는다. 기한·사유·활성 클레임도 작성 시 다시 확인한다. |
| 기존 진행 중 클레임 | 기존 건으로 처리 | 새 요청을 중복 생성하거나 기존 금융 결과·회수 증거를 덮어쓰지 않는다. |

취소·반품의 환급은 기존 주문 결제금액 전액(최초 배송비 포함)이며, 부분 환불을 약속하지 않는다. 반송비 부담과 환급 기한은 기존 공개 정책과 관계 법령에 따른다. 새 수거 수수료, 배송비 공제, 예외 환급액을 이 표에서 정하지 않는다.

## 1:1 문의·고객지원으로 청약철회 의사를 받은 경우

1. **의사표시를 보존한다.** 주문번호·고객 식별자와 문의를 연결하고 원문 및 최초 접수 시각을 남긴다. 기존 문의에 추가로 보낸 의사표시는 해당 메시지의 시각을 확인한다. 단순 질문인지 철회 의사표시인지 불명확하면 확인하되, 원문이나 최초 연락 시각을 새 답변 시각으로 대체하지 않는다. 전화·이메일은 실제 통지 내용·시각·채널과 확인 가능한 근거를 권한 있는 내부 기록에 연결한다.
2. **접수 확인과 처리 승인을 구분한다.** 고객에게 의사표시를 확인했으며 배송·회수 상황을 검토한다고 안내한다. 문의 등록·배정·답변은 환급 승인이나 PG 취소 명령이 아니다. 문의 유형이 일반 문의라는 이유로 명시적인 철회 의사를 무시하거나 직접 신청 버튼만 반복 안내하지 않는다.
3. **배송 건별 사실을 확인한다.** 주문 상세에서 각 출고지의 발주·발송·도착 시각, 실제 수령한 품목과 수량, 기존 클레임·환급 처리 여부를 확인한다. 미발송분이 남아 있으면 물류 담당자와 실제 출고 중단 가능 여부를 확인한다. 문의 생성만으로 출고가 자동 중단되는 기능은 없으므로, 확인 전 중단 완료를 약속하지 않는다.
4. **기한과 처리 방법을 검토한다.** 청약철회 통지 시각과 거래·공급 사실을 함께 담당자에게 전달한다. 앱은 주문 전체 도착 시각의 기한을 사용하므로, 먼저 받은 배송 건·하자를 알게 된 시점·기타 예외를 독립적으로 판정하는 법률 엔진이 아니다. 앱 버튼의 상태나 기한 오류만으로 권리를 거절하거나 전체 배송 이후로 통지를 미루지 않는다. 지원되지 않는 사례의 권리·환급 기한 판단은 운영 책임자와 필요한 법무 검토로 넘긴다.
5. **승인된 처리 경로만 사용한다.** 기존 주문 API를 우회하는 SQL, 가짜 `delivered_at`·회수 시각, service-role 직접 환급, 임의 클레임 생성으로 해결하지 않는다. 즉시 자동 처리할 수 없는 건은 주문/문의 연결과 담당자 메모를 유지하며 검토 중임을 안내한다. 수동 후속이 필요하다는 사실은 기한을 연장하거나 법정 처리 의무를 없애는 근거가 아니다.
6. **종결 근거를 남긴다.** 안내·운영 판단·실제 회수·환급 결과를 구분해 기록한다. 1:1 문의의 답변/자동 종결 상태는 클레임 완료나 청약철회 의사의 철회를 뜻하지 않는다. 진행 중 통지는 운영 담당자가 별도로 추적한다. 공개 댓글·GitHub에 고객 원문, 주소, 계좌, 결제 식별자를 복사하지 않는다.

문의에는 본문/메시지와 서버 작성 시각, 주문 연결, 담당자·내부 메모 기능이 있다. 이를 법정 통지 전용 불변 원장이나 모든 외부 채널의 자동 수집으로 표현하지 않는다. 문의 삭제·자동 종결·보존기간과 법정 증거 보존의 관계는 기존 계정 삭제/개인정보 정책을 따르며, 분쟁이나 보존 필요가 있는 건은 해당 담당자가 검토한다.

## 출고지별 회수와 환급·재출고

반품·교환 승인 시 각 회수 대상의 출고지, 반송 주소, 품목·수량을 확인해 고객에게 안내한다. 운영 설정의 주소를 나중에 바꾸었다고 이미 접수된 건의 회수 안내를 조용히 바꾸지 않는다. 한 출고지에 먼저 도착해도 나머지 회수가 남아 있으면 주문 전체 입고 완료로 표시하지 않는다. 모든 필요한 회수를 확인한 뒤 기존 전액 환급 또는 교환 재출고 절차로 진행한다.

실제 창고 반환 시각과 운영자가 확인 버튼을 누른 시각을 혼동하지 않는다. 입고 기록을 늦게 남겨 법정 환급 기한이 늦게 시작하는 것으로 취급하지 않는다. 수거비, 하자·오배송의 비용 부담, 원 배송비를 포함한 전액 환급과 기존 결제 증거 확인 절차는 이 정책에서 바꾸지 않았다.

교환은 원주문·결제를 유지하고 회수 옵션 복원과 재출고 옵션 차감을 기존 멱등 경계에서 처리한다. 클레임당 재출고 운송장은 한 쌍이므로 혼합 출고지의 개별 재출고가 필요하면 지원 범위를 먼저 확인한다. 환급 중이거나 이미 PG 호출을 시작한 과거 건에도 실제로 확인하지 않은 회수 사실을 소급해 넣지 않는다. 추가 회수가 필요한 과거 건은 실제 입고를 새 근거로 기록하며, 이미 존재하는 입고·금융 결과와 구분한다.

교환품을 재출고한 뒤에는 클레임 상세의 **교환품 배송완료 확인**에서 택배사 조회 또는 고객의 전체 수령 확인 근거를 기록한다. 원주문의 배송완료만으로 교환품까지 도착했다고 판단하지 않는다. 확인 전에는 새 반품·교환 신청이 차단된다. 같은 담당자의 같은 근거 재전송은 멱등 처리하고 다른 근거로 기존 기록을 덮어쓰지 않는다. 확인 시각은 시스템 기록 시각이며, 원주문의 공급 시각이나 기존 신청 기한을 새로 연장하지 않는다. 기존 교환 이력의 배송완료 증거가 없으면 사실을 확인한 뒤 기록하고, 기한 예외는 앞의 CS 절차로 검토한다.

## 승인된 공개 문서와 FAQ의 배포 확인

- 주문 상세는 직접 신청 조건과 1:1 문의·고객지원 통로를 함께 설명한다. ‘발주확인 후 청약철회 불가’처럼 법정 권리 자체를 닫는 문구를 사용하지 않는다.
- 사용자가 공개 변경안과 main 병합·production 배포를 승인하여, `lib/legal/documents.ts`의 배송정책 3·6·10절과 이용약관 제12조·제16조의2를 직접 신청 조건·CS 통로에 맞췄다. 연락처가 비어 있어도 문의로 의사를 전할 수 있게 안내한다. 실제 공개 완료는 배포 뒤 HTTP 본문을 확인한 기록으로 판단한다.
- 승인된 배포일 기준으로 이용약관·배송정책 시행일은 2026-09-09, 개인정보처리방침은 기존 2026-08-22를 유지한다. 배포 날짜가 달라지면 실제 적용일을 다시 확인한다. 제3조의 공지·통지 조건과 제4조의 기존 계약 보호는 변경하지 않았고, 해당 조건의 법률 적용 판정이나 개별 통지 완료를 코드 변경으로 주장하지 않는다.
- 개정 안내와 이전 정책 본문은 같은 공개 법정 문서 화면에서 구별해 열람할 수 있다. `lib/legal/archive/pre-2026-09-09.json`은 이전 production 소스 `7ea5d1fd`의 이용약관(2026-08-22)·배송정책(2026-08-21)을 보존한다. 개인 연락처를 정적 문서에 복제하지 않고 참조로 두며, 열람 시 현재 고객지원 정보를 표시한다고 안내한다. 과거 연락처의 불변 사본이나 개별 이용자의 수락 이력은 아니다.
- 현재 가입 동의는 `profiles.consents`의 boolean과 온보딩 시각이며, 수락한 법정 문서의 version/hash/본문을 별도 불변 원장으로 저장하지 않는다. Git의 과거 본문은 확인할 수 있지만 개별 고객이 그 본문에 동의했다는 증거로 바꿔 말하지 않는다. 이 기존 한계는 법무·공시 검토에 전달하고, 이번 기능이 과거 동의 이력 보존을 새로 구현했다고 보고하지 않는다.
- FAQ 답변은 운영자가 DB에서 관리하는 게시 콘텐츠다. 배포 환경의 공개 FAQ 중 취소·배송·반품·교환 안내를 읽고 개정안과 대조한다. 저장소 수정이나 FAQ CRUD 테스트만으로 실제 게시 답변이 갱신됐다고 판단하지 않는다.

공개 개정안·main/production의 사용자 승인과 실제 공지·시행·필요한 기존 이용자 통지·배포 완료는 구분한다. 배포 후 문서별 시행일과 개정 안내·이전 본문, 실제 게시 FAQ, 주문 연결 문의 경로를 확인한다. 지원하지 않는 부분 환불이나 미확정 비용 예외를 FAQ로 먼저 약속하지 않는다.

## 공식 근거와 적용 한계

2026-09-09 국가법령정보센터에서 시행 2026-07-21, 법률 제21312호의 조문을 확인했다. 제17조는 공급 시점 등의 청약철회 기간과 예외, 서면 통지의 효력을 규정하고, 제18조는 공급 여부와 반환에 따른 환급 및 비용 기준을 구분한다. 제35조는 해당 규정을 위반한 소비자에게 불리한 약정의 효력을 제한한다. 따라서 앱의 발주확인이나 전체 배송 상태만으로 모든 통지·권리를 판정하지 않는다. 이 런북은 개별 분쟁의 법률 판단이나 새 환급 규칙을 확정하지 않는다.
