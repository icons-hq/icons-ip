# 굿즈 클레임 직접 신청과 고객지원 접수

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-09-09 승인 정책은 [ADR-0017](../adr/0017-order-claim-intake-and-origin-collections.md)을 따른다. 사용자 승인 뒤 PR #452의 main `a2d021a`에서 production DB·앱과 공개 정책·FAQ를 반영했고, 최신 main `abed200`의 [Actions 34309609698](https://github.com/icons-hq/icons-ip/actions/runs/34309609698)도 성공했다. 아래 운영 절차를 별도 법무 검토나 개별 고객 통지 완료의 증거로 사용하지 않는다. 티켓 취소 정책에는 적용하지 않는다.

[Production](https://iconsip.com)과 [고정 staging](https://icons-ip-staging.vercel.app/admin)의 배포·로그인 준비는 확인했다. staging은 합성 이력으로 연습하며 실제 PG·창고를 호출하지 않는다. 계정과 다음 main 보존·운영팀 인수 상태는 [staging.md](staging.md)를 따른다.

PR #407의 혼합 출고지 P1은 [승인된 A 계약의 배포·공시 근거](https://github.com/icons-hq/icons-ip/pull/407#discussion_r3964523088)로 resolve했고, 중복 PR #407·#435는 merge 없이 종료했다. 실제 창고의 두 출고지 인수, 일부 배송의 CS 수동 검토 및 단일 교환 재출고 운송장 한계는 [#453](https://github.com/icons-hq/icons-ip/issues/453)에 OPEN으로 남긴다. 이 review 종료나 공개 게시를 운영팀 S1~S5 또는 #410의 사람 S2 완료로 해석하지 않는다.

## 직접 신청 조건

아래 표는 2026-10-16 승인된 [배송 중 접수](../research/smartstore-admin/in-transit-claims.md)를 포함한 릴리스 구현 계약이다. 9월 운영 반영 기록과 구분하며, 이번 기능의 실제 반영 상태는 [어드민 배포 런북](smartstore-admin-rollout.md)의 배포 결과로 확인한다.

| 주문 사실 | 주문 상세의 직접 신청 | 운영 확인 |
| --- | --- | --- |
| 발주확인 전, `pending`·`paid` | 주문 전체 취소 | 발주확인·발송 이력, 결제 사실, 기존 활성 클레임을 서버에서 확인한다. 자동 발주확인이 켜져 있으면 매일 설정 시각(기본 16:30) 실행 전까지다([ADR-0025](../adr/0025-auto-order-confirmation.md)). |
| 발주확인 후, 모든 배송 건이 미발송 | 취소·반품·교환 직접 신청 닫힘 | 청약철회 의사를 1:1 문의·고객지원에서 받고 접수 시각을 보존한다. 아래 **운영자 전액 취소**의 조건을 충족하면 해당 경로로 처리한다. |
| 실제 발송된 배송 중 주문·일부 수령 | 주문 전체 반품·교환 | 전체 품목·수량의 배정과 발송 근거, 이전 교환품 수령, 기한·활성 요청을 확인한다. 미출고 품목이 남아도 전체 요청이며, 모든 회수·창고 보관 확인 전에는 환급·재출고하지 않는다. |
| 모든 주문 품목의 수량이 실제 배송 완료, `delivered`·`done` | 주문 전체 반품·교환 | 취소 배송 건이나 누락 품목을 완료로 세지 않는다. 기한·사유·활성 클레임도 작성 시 다시 확인한다. |
| 기존 진행 중 클레임 | 기존 건으로 처리 | 새 요청을 중복 생성하거나 기존 금융 결과·회수 증거를 덮어쓰지 않는다. |

취소·반품의 환급은 기존 주문 결제금액 전액(최초 배송비 포함)이며, 부분 환불을 약속하지 않는다. 반송비 부담과 환급 기한은 기존 공개 정책과 관계 법령에 따른다. 새 수거 수수료, 배송비 공제, 예외 환급액을 이 표에서 정하지 않는다.

## 판매자 직접 취소·반품·교환 접수 — 2026-10-13 구현

주문 상세의 **판매자 직접 취소 접수**와 **판매자 직접 반품·교환 접수**는 고객과 확인한 주문 전체의 요청을 주문 관리 권한이 있는 매니저가 대신 등록하는 경로다. 아래 설명은 저장소 구현과 격리 로컬 검증 기준이며 운영 배포·실제 고객 접수 완료를 뜻하지 않는다.

취소는 발주확인 전 `pending`·`paid` 주문에서 접수한다. 서버는 현재 상태뿐 아니라 이전 발주확인·발송·배송완료·거래확정 및 출고지시서 출력 이력도 검사한다. 고객 요청 경로·시각·사유·주문 전체 동의를 기록하고 수거 주소/수거 계획은 받지 않는다. 선택 환불계좌는 반품과 같은 private 보관 경계를 쓴다. 접수 후 취소 관리 상세에서 요청과 담당자를 확인하고 기존 승인·결제사 취소/조회·전액 환급 절차를 진행한다. 무결제 주문도 이 버튼으로는 요청만 생성한다.

반품·교환은 다음 순서로 접수한다.

1. 주문과 고객, 전체 품목·수량의 배송 배정, 실제 발송 또는 전체 배송완료, 이전 교환품의 수령 확인 및 진행 중인 클레임을 확인한다. 승인된 배송 중 접수도 허용하되 배정 누락·수량 초과는 차단한다. 서버는 현재 접수 시점의 사유별 신청 기한을 다시 검사하며, 지원 조건 밖의 일부 배송·기한 예외는 아래 고객지원 절차로 넘긴다.
2. 반품 또는 교환, 사유, 고객 요청을 확인한 경로·시각과 합의 근거를 기록한다. 연결된 고객문의를 고르면 문의의 주문과 구매자가 모두 일치해야 한다. 고객 요청 시각은 근거로 보관하고 실제 `requested_at`을 소급하지 않는다.
3. 수거 안내 주소와 모든 출고지의 수거 계획을 기록한다. 구매자가 이미 발송한 건은 택배사·송장번호를, 판매자 별도 수거는 협의 메모를 남긴다. 입력은 택배 예약·입고 확인이나 원주문 배송지·교환 재배송지 변경이 아니다.
4. 고객의 주문 전체 요청 및 수거 계획 동의를 확인하고 접수한다. 반품의 선택 환불계좌는 기존 private 보관·마스킹·파기 경계를 사용한다. 계좌 원문을 합의 근거·운영 메모·감사 로그에 복사하지 않는다.
5. 접수번호와 현재 단계 **접수**를 확인하고 상세에서 담당자·연결 문의·수거 계획을 재조회한다. 응답이 불확실하면 입력과 같은 요청 번호를 보존한 상태에서 저장 결과를 먼저 조회한다. 저장된 요청을 반복 실행해도 새 접수·알림·감사를 중복 생성하지 않는다.

접수는 요청과 근거만 생성한다. 주문·결제·재고·환불·실제 회수 기록을 바꾸지 않으며, 반품·교환은 이후 기존 **승인하고 수거 시작 → 출고지별 실제 입고 확인 → 전액 환급 또는 교환 재출고**를 각각 수행한다. 부분 품목·수량 처리, 환급액 입력, 반품↔교환 전환, 택배 자동예약은 포함하지 않는다. 기존 고객 직접 신청의 무결제 즉시 취소·결제완료 취소 자동승인 경로를 이 버튼에서 호출하지 않는다.

## 결제 취소가 나가는 시점 — 2026-10-12

토스 결제의 취소는 **승인되는 순간** 서버가 토스 전액 취소를 발행하고 결제사 조회로 확인한 뒤 주문 취소·재고 복원·카드팩 회수·환불 원장 기록을 한 번에 끝낸다. 운영자가 결제사 원장에서 먼저 취소하거나 확인할 단계가 아니다.

| 경로 | 결제사 취소 발행 | 실패·불명확할 때 |
| --- | --- | --- |
| 고객이 발주확인 전에 직접 신청한 변심 취소(자동 승인) | 접수 응답 직후 서버(시스템)가 실행 | 클레임이 결제확인필요로 남는다 |
| 클레임 콘솔·주문 콘솔에서 취소 승인 | 승인 버튼을 누른 운영자 계정으로 즉시 실행 | 승인은 유지되고 화면에 오류 코드가 표시된다 |
| 반품 | 모든 회수 확인 → 환불 접수 → **환불 완료 확정**을 누를 때 실행 | 결제확인필요로 남는다 |
| 결제 승인 확인 중에 접수된 취소 | 접수 직후 승인 결과가 나오면 서버가 이어서 처리한다. 승인 결과가 늦게 확정된 건은 자동 승인까지만 되고 결제사 취소는 나가지 않는다(아래 경합 절) | 처리중으로 남으면 클레임 상세의 환불 완료 확정으로 진행 |

- 결제확인필요 건은 클레임 상세의 정합화 오류 코드(주문 통합검색 주문 패널의 취소 요청 영역과 재시도 결과 문구에도 같은 코드가 나온다)를 확인하고 원인을 해소한 뒤 **환불 완료 확정**(또는 주문 통합검색 주문 패널의 **상태 다시 확인**)으로 다시 시도한다(코드별 조치는 아래 "결제확인필요 재시도와 멱등키" 절). 같은 결제를 결제사 상점관리자에서 따로 취소하거나 계좌로 다시 송금하지 않는다 — 시스템이 이미 취소를 발행했을 수 있어 이중 환불이 된다.
- 결제 내역이 없는 주문(결제창만 열렸거나 결제 결과가 아직 정해지지 않은 주문)의 취소는 환불 원장이 없어 클레임 상세에 **환불 완료 확정**이 보이지 않는다. 만료 처리도 처리중 요청은 건너뛰므로, 주문 통합검색에서 그 주문을 열어 **처리 상태 확인**(결제확인필요면 **상태 다시 확인**, Korpay 결제창 주문은 **Korpay 만료·취소 처리**)으로 닫는다.
- 결제 대기 주문의 고객 취소(2026-10-12 QA-1): 결제 시도가 없거나 결제 가능 시간이 이미 지난 결제 준비 시도뿐이면 즉시 취소되고 재고·쿠폰·적립금이 바로 돌아온다. 그 시도는 같은 잠금 아래에서 결제 없이 닫히고(클레임·주문 타임라인 "결제 준비 건 취소 완료 (구매자 취소)"), 늦게 도착한 결제 완료 콜백은 승인 API를 부르지 않는다. 결제 가능 시간이 남은 결제창이나 승인 확인 중이면 요청은 접수 상태로 남고 결제 결과(결제 기한 sweep·승인 결과)가 닫는다 — 운영자가 처리할 건이 아니다. 구매자는 접수 때 "담당자가 확인" 대신 결제 기한 자동 취소·결제 승인 결과 확인 안내를 받는다. 반품·교환과 결제완료 주문의 하자 취소 접수는 종전처럼 "담당자가 확인한 뒤 진행 상황을 알려드립니다"다.
- 토스 결제의 환불 수단은 결제사 취소로 고정된다. 계좌 송금은 무통장 입금 결제와 Korpay 운영 판단에만 쓴다.
- 고객에게는 결제사 취소가 확인된 뒤에만 "결제 취소가 완료됐어요"가 간다. 토스 결제의 환불 접수 알림은 "환불 절차를 시작했습니다"다.
- Korpay 결제는 승인 뒤에도 자동 취소가 나가지 않는다. 클레임 상세의 접수 양식을 이메일로 보낸 뒤 admin이 환불 완료를 확정한다. 무통장 입금 결제도 서버가 자동 실행하지 않는다 — 결제사 취소가 없고 계좌 송금 종결은 아직 시스템 밖이다(아래 "결제확인필요 재시도" 절과 [운영 설정 런북](admin-store-settings.md)의 계좌 설정 선행 조건).

### 결제확인필요 재시도와 멱등키

- 서버의 토스 취소 요청은 결제 시도마다 같은 멱등키(`refund:{결제 시도 id}`)를 쓴다. 토스는 같은 멱등키 요청에 첫 응답을 **15일간** 그대로 돌려주고, 오류가 난 뒤 멱등키를 바꿔 같은 요청을 다시 보내는 것은 위험하다고 안내한다([인증 및 기타 헤더 — 멱등키](https://docs.tosspayments.com/reference/using-api/authorization)). 오류 응답까지 재생되는지는 문서에 명시돼 있지 않다.
- 그래서 결제확인필요에서 **환불 완료 확정**·**상태 다시 확인**을 다시 눌러도 같은 오류가 돌아올 수 있다. 다시 누르기 전에 클레임 상세의 **정합화 오류** 코드로 원인을 먼저 본다. 토스 취소 결과의 코드는 서버 결제 모듈이 정한 사유 코드 그대로 남는다(2026-10-12부터). 그 전에 남은 요청 행은 토스가 확인해 주지 않은 결과가 사유와 관계없이 `provider_cancel_failed`(모호하면 `provider_unavailable`) 하나로 남아 있다 — 그 건은 토스 상점관리자에서 결제 상태를 직접 보고 아래 표에서 맞는 줄을 따른다.

| 정합화 오류 | 뜻 | 조치 |
| --- | --- | --- |
| `provider_unavailable`, `provider_cancel_ambiguous` | 취소 응답이나 결제 조회가 모호했다(시간 초과·일시 오류). 취소가 이미 나갔을 수 있다. `provider_unavailable`은 서버가 결제 시도 기록을 읽지 못해 취소를 보내지 못한 경우와 Korpay 결제에도 남는다 | 잠시 뒤 다시 누른다. 같은 멱등키라 취소가 두 번 나가지 않는다. 계속 같으면 결제 담당 admin이 상점관리자에서 결제를 확인한다. Korpay는 접수 양식 절차를 따른다 |
| `provider_cancel_rejected` | 토스가 취소를 명시 거절했다. 하루·한 달 환불 한도 초과 `EXCEED_MAX_REFUND_AMOUNT`, 환불 기간 초과 `EXCEED_MAX_REFUND_DUE`, 취소 불가 결제 `NOT_CANCELABLE_PAYMENT` 등이다([API 에러 코드](https://docs.tosspayments.com/reference/error-codes)) | 원인을 해소한 뒤 아래 수동 복구 |
| `provider_cancellation_incomplete` | 취소 요청은 성공했는데 조회가 아직 전액 취소가 아니다 | 잠시 뒤 다시 누른다. 계속되면 수동 복구 |
| `provider_payment_not_refundable` | 조회한 결제가 전액 취소할 수 있는 결제완료가 아니다(부분 취소, 입금된 가상계좌, 금액이 원장과 다른 결제 등) | 상점관리자에서 결제를 확인한다. 이 주문 금액 그대로의 결제면 수동 복구로 닫힌다. 금액이 다르면 닫히지 않으므로 개발 담당에게 넘긴다 |
| `provider_configuration_error` | 토스가 키·설정 오류로 조회나 취소를 거부했다 | 결제 담당 admin이 키·설정을 고친 뒤 다시 누른다. 고치기 전에는 수동 복구도 닫히지 않는다 |
| `provider_merchant_mismatch` | 조회한 결제의 상점아이디(MID)가 ICONS 상점(라이브 `iconsi0xvd`, 테스트 `ticonsi0xvd`)이 아니거나 비어 있다. 서버는 그 결제를 취소하지 않는다 | [토스 운영 전환 런북](toss-production-rollout.md)의 상점 불일치 `needs_review` 건 조치를 따른다. 그 결제를 만든 MID의 상점관리자에서 취소해도 다음 조회가 같은 코드라 이 요청은 닫히지 않는다 |
| `provider_payment_not_found`, `provider_identity_mismatch` | 지금 키로 이 결제를 찾지 못했거나, 조회한 결제의 결제 키·주문번호가 원장과 다르다 | 원인이 그대로면 다시 눌러도 같은 코드다. 결제 담당 admin이 상점관리자에서 결제를 확인하고 개발 담당에게 넘긴다 |
| `provider_refund_request_invalid`, `provider_refund_amount_mismatch`, `provider_mismatch` | 서버가 만든 취소 요청이 형식·금액 검사에 걸려 토스에 보내지 않았거나, 토스가 취소를 확인한 결제 키가 원장 키와 다르다 | 다시 눌러도 같은 코드다. 개발 담당에게 넘긴다 |
| `provider_cancel_failed` | 사유 코드가 없거나 형식 밖이라 위로 분류하지 못한 결과다 | 상점관리자에서 결제 상태를 확인하고 그 상태에 맞는 줄을 따른다 |

- **수동 복구**(`provider_cancel_rejected`·`provider_cancellation_incomplete`·`provider_payment_not_refundable`과, 상태를 확인한 `provider_cancel_failed`에만 쓴다): 같은 키로 다시 눌러도 풀리지 않는 거절(예: 한도 초과가 해소된 뒤에도 같은 오류)은 결제 담당 admin이 원인을 해소한 다음 **토스 상점관리자에서 해당 결제를 전액 취소**하고, 클레임 상세의 **환불 완료 확정**(또는 주문 통합검색 주문 패널의 **상태 다시 확인**)을 누른다. 서버는 취소 전에 결제를 먼저 조회하므로 이미 전액 취소된 결제를 보고 그대로 완료로 수렴한다 — 주문 취소·재고 복원·카드팩 회수·환불 원장이 이때 함께 닫힌다. 이 수렴은 조회가 그 결제를 ICONS 상점의 이 주문 결제로 확인할 때만 일어난다. 상점 불일치·결제 미발견·결제 대조 실패·키 설정 오류·요청 검사 실패 코드는 상점관리자에서 취소해도 다음 조회가 같은 코드로 끝나 요청이 닫히지 않는다. 이 건은 결제확인필요로 남고 주문·재고 점유도 유지된다. 앱에는 토스 결제의 취소 요청을 결제사 확인 없이 닫는 경로가 없으므로, 개발 담당이 종결 방법을 정할 때까지 그대로 둔다. 이 수동 복구를 제외하고는 상점관리자에서 따로 취소하지 않는다.
- 결제 시도별 회차 멱등키(재시도마다 새 키)는 도입하지 않았다. 도입하려면 오류 응답 재생 범위를 토스 기술지원에 먼저 확인한다.

### 결제 승인 확인 중에 접수된 취소(경합)

구매자가 결제창 인증을 마친 직후, 승인 응답을 기다리는 몇 초 사이에 다른 탭에서 취소를 누르면 요청은 접수 상태로 남는다.

- 토스가 승인으로 끝나면 결제 원장은 남기되 주문은 결제 대기로 두고(주문 확인 메일·카드팩·발주 큐 없음), 요청을 자동 승인해 서버가 토스 전액 취소를 이어서 발행한다. 클레임 타임라인에 "자동 승인"이 actor 없이 기록된다.
- 승인이 거절되면 요청을 결제 없이 바로 종결하고 재고·쿠폰·적립금 점유를 푼다.
- 승인 결과가 늦게 확정돼(결과 불명 → 웹훅·내부 재정합) 서버 대기 창을 지나면 요청은 자동 승인되지만 결제사 취소는 나가지 않아 클레임이 처리중으로 남는다. 구매자에게는 이미 "결제 취소 처리를 시작합니다"가 갔고 카드 승인은 살아 있다. 클레임 상세의 **환불 완료 확정**으로 토스 취소를 발행한다. 오래 남은 처리중 건을 알리는 자동 알림은 없으므로 취소 관리 목록에서 처리중으로 남은 취소를 매일 확인한다.
- Korpay·무통장 결제에서 같은 경합이 나면 종전처럼 결제확인필요다. 결제사 원장 확인 뒤 기존 수동 절차를 따른다.

## 1:1 문의·고객지원으로 청약철회 의사를 받은 경우

1. **의사표시를 보존한다.** 주문번호·고객 식별자와 문의를 연결하고 원문 및 최초 접수 시각을 남긴다. 기존 문의에 추가로 보낸 의사표시는 해당 메시지의 시각을 확인한다. 단순 질문인지 철회 의사표시인지 불명확하면 확인하되, 원문이나 최초 연락 시각을 새 답변 시각으로 대체하지 않는다. 전화·이메일은 실제 통지 내용·시각·채널과 확인 가능한 근거를 권한 있는 내부 기록에 연결한다.
2. **접수 확인과 처리 승인을 구분한다.** 고객에게 의사표시를 확인했으며 배송·회수 상황을 검토한다고 안내한다. 문의 등록·배정·답변은 환급 승인이나 PG 취소 명령이 아니다. 문의 유형이 일반 문의라는 이유로 명시적인 철회 의사를 무시하거나 직접 신청 버튼만 반복 안내하지 않는다.
3. **배송 건별 사실을 확인한다.** 주문 상세에서 각 출고지의 발주·발송·도착 시각, 실제 수령한 품목과 수량, 기존 클레임·환급 처리 여부를 확인한다. 미발송분이 남아 있으면 물류 담당자와 실제 출고 중단 가능 여부를 확인한다. 문의 생성만으로 출고가 자동 중단되는 기능은 없으므로, 확인 전 중단 완료를 약속하지 않는다.
4. **기한과 처리 방법을 검토한다.** 청약철회 통지 시각과 거래·공급 사실을 함께 담당자에게 전달한다. 앱은 주문 전체 도착 시각의 기한을 사용하므로, 먼저 받은 배송 건·하자를 알게 된 시점·기타 예외를 독립적으로 판정하는 법률 엔진이 아니다. 앱 버튼의 상태나 기한 오류만으로 권리를 거절하거나 전체 배송 이후로 통지를 미루지 않는다. 지원되지 않는 사례의 권리·환급 기한 판단은 운영 책임자와 필요한 법무 검토로 넘긴다.
5. **승인된 처리 경로만 사용한다.** 기존 주문 API를 우회하는 SQL, 가짜 `delivered_at`·회수 시각, service-role 직접 환급, 임의 클레임 생성으로 해결하지 않는다. 모든 배송 건이 아직 발송 전이고 창고 출고 중단을 확인했다면 **운영자 전액 취소**(아래 절)가 승인된 경로다 — staff 세션·사유·감사·결제사 검증을 거치므로 임의 클레임 생성이 아니다. 즉시 자동 처리할 수 없는 건은 주문/문의 연결과 담당자 메모를 유지하며 검토 중임을 안내한다. 수동 후속이 필요하다는 사실은 기한을 연장하거나 법정 처리 의무를 없애는 근거가 아니다.
6. **종결 근거를 남긴다.** 안내·운영 판단·실제 회수·환급 결과를 구분해 기록한다. 1:1 문의의 답변/자동 종결 상태는 클레임 완료나 청약철회 의사의 철회를 뜻하지 않는다. 진행 중 통지는 운영 담당자가 별도로 추적한다. 공개 댓글·GitHub에 고객 원문, 주소, 계좌, 결제 식별자를 복사하지 않는다.

문의에는 본문/메시지와 서버 작성 시각, 주문 연결, 담당자·내부 메모 기능이 있다. 이를 법정 통지 전용 불변 원장이나 모든 외부 채널의 자동 수집으로 표현하지 않는다. 문의 삭제·자동 종결·보존기간과 법정 증거 보존의 관계는 기존 계정 삭제/개인정보 정책을 따르며, 분쟁이나 보존 필요가 있는 건은 해당 담당자가 검토한다.

## 운영자 전액 취소 — 2026-10-12

[ADR-0018](../adr/0018-staff-initiated-order-cancellation.md). 주문 통합검색(`/admin/sales/orders`)에서 주문을 선택하면 열리는 주문 패널의 **운영자 전액 취소** 양식으로 시작한다. "상세 열기"(새 탭)의 주문 상세 화면에는 이 양식이 없다.

- **쓰는 경우**: 품절·출고 불가, 발주확인 뒤 1:1 문의로 받은 취소 요청, 라이브 전환 전 심사용 테스트 결제 정리, 기타(메모 필수).
- **열리는 주문**: 결제완료·발주확인이고 모든 배송 건이 아직 발송 전인 토스 결제 주문(실패가 아닌 결제가 모두 토스 결제완료). 그 밖의 주문에는 양식이 보이지 않는다. 진행 중인 취소·반품·교환 요청이나 미확정 결제가 있으면 열리지 않는다. Korpay·무통장 주문은 기존 수동 절차를 따른다.
- **출고지시 뒤**: 출고지시 파일이 나간 배송 건이 있으면 창고에 출고 중단을 먼저 확인하고, 그 사실을 확인란으로 남긴다. 확인 없이 누르면 거절된다. 양식을 연 뒤 출고지시가 나가 서버가 거절하면 주문 패널이 최신 상태로 다시 그려지고 확인란이 나타난다(입력한 사유·메모는 남는다). 창고에 확인한 뒤 체크하고 다시 실행한다. 확인란이 보이지 않으면 새로고침한다. 이미 발송된 배송 건이 하나라도 있으면 이 경로는 닫히고, 반품 또는 담당자 검토로 넘긴다.
- **누르면 일어나는 일**: 취소 요청이 사유·메모·처리자와 함께 만들어지고 구매자에게 알림이 간다. 서버가 바로 토스 전액 취소를 발행·확인한 뒤 주문 취소·재고·쿠폰·적립금 복원·카드팩 회수·환불 원장 기록까지 끝낸다. 결제사 취소가 확인되지 않으면 결제확인필요로 남고 주문·재고는 그대로다 — 취소 관리 요청 상세에서 정합화 오류를 보고 **환불 완료 확정**(또는 같은 주문 패널의 **상태 다시 확인**)으로 다시 시도한다. 실행 결과(결과 코드·다음 할 일)는 양식이 사라진 뒤에도 주문 패널 처리 버튼 위의 **취소 처리 결과**에 남고, 상태 필터 때문에 목록에서 빠진 주문이면 목록 위에 주문번호와 **이 주문 열기** 링크로 표시된다.
- **테스트 결제 정리 순서**: 라이브 키로 바꾸기 **전에**, 테스트 키가 살아 있을 때 사유 "테스트 결제 정리"로 정리한다. 키를 바꾼 뒤에는 테스트 결제를 조회·취소할 수 없어 결제확인필요에 남는다.
- 같은 결제를 토스 상점관리자에서 따로 취소하지 않는다. 시스템이 모르는 취소가 생겨 주문·재고·정산이 어긋난다.

## 출고지별 회수와 환급·재출고

반품·교환 승인 시 각 회수 대상의 출고지, 반송 주소, 품목·수량을 확인해 고객에게 안내한다. 운영 설정의 주소를 나중에 바꾸었다고 이미 접수된 건의 회수 안내를 조용히 바꾸지 않는다. 한 출고지에 먼저 도착해도 나머지 회수가 남아 있으면 주문 전체 입고 완료로 표시하지 않는다. 모든 필요한 회수를 확인한 뒤 기존 전액 환급 또는 교환 재출고 절차로 진행한다.

실제 창고 반환 시각과 운영자가 확인 버튼을 누른 시각을 혼동하지 않는다. 입고 기록을 늦게 남겨 법정 환급 기한이 늦게 시작하는 것으로 취급하지 않는다. 수거비, 하자·오배송의 비용 부담, 원 배송비를 포함한 전액 환급과 기존 결제 증거 확인 절차는 이 정책에서 바꾸지 않았다.

교환은 원주문·결제를 유지하고 회수 옵션 복원과 재출고 옵션 차감을 기존 멱등 경계에서 처리한다. 클레임당 재출고 운송장은 한 쌍이므로 혼합 출고지의 개별 재출고가 필요하면 지원 범위를 먼저 확인한다. 환급 중이거나 이미 PG 호출을 시작한 과거 건에도 실제로 확인하지 않은 회수 사실을 소급해 넣지 않는다. 추가 회수가 필요한 과거 건은 실제 입고를 새 근거로 기록하며, 이미 존재하는 입고·금융 결과와 구분한다.

교환품을 재출고한 뒤에는 클레임 상세의 **교환품 배송완료 확인**에서 택배사 조회 또는 고객의 전체 수령 확인 근거를 기록한다. 원주문의 배송완료만으로 교환품까지 도착했다고 판단하지 않는다. 확인 전에는 새 반품·교환 신청이 차단된다. 같은 담당자의 같은 근거 재전송은 멱등 처리하고 다른 근거로 기존 기록을 덮어쓰지 않는다. 확인 시각은 시스템 기록 시각이며, 원주문의 공급 시각이나 기존 신청 기한을 새로 연장하지 않는다. 기존 교환 이력의 배송완료 증거가 없으면 사실을 확인한 뒤 기록하고, 기한 예외는 앞의 CS 절차로 검토한다.

## 공식 근거와 적용 한계

2026-09-09 국가법령정보센터에서 시행 2026-07-21, 법률 제21312호의 조문을 확인했다. 제17조는 공급 시점 등의 청약철회 기간과 예외, 서면 통지의 효력을 규정하고, 제18조는 공급 여부와 반환에 따른 환급 및 비용 기준을 구분한다. 제35조는 해당 규정을 위반한 소비자에게 불리한 약정의 효력을 제한한다. 따라서 앱의 발주확인이나 전체 배송 상태만으로 모든 통지·권리를 판정하지 않는다. 이 런북은 개별 분쟁의 법률 판단이나 새 환급 규칙을 확정하지 않는다.
