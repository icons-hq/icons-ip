# 출고지시와 운송장 회신 (#429)

`/admin/sales/dispatch`의 **출고지시 내보내기** 기본값은 **스마트스토어 양식(74열)**이다. 김포를 포함한 출고지에서 같은 양식을 사용하고 `출고지` 열로 구분한다. 다만 내보낼 배송 건이 모두 서원 송장양식 출고지(남양주)이면 **서원 원형 송장양식**이 기본으로 선택된다(10/14 회의 A2). 선택 배송 건이 없으면 목록 위에서 고른 출고지를, 그것도 없으면 출고지별 전체 내려받기 버튼의 출고지를 기준으로 한다. 운영자가 양식을 직접 고르면 그 화면에서는 그 선택을 쓴다. `기존 창고 양식`을 선택하면 출고지 설정의 일반 12열(옵션코드·바코드·ERP 코드·ERP 품명 선택 추가, 최대 16열)·김포 WMS 21열·서원 송장양식(원본 7열 + 받는분성명·배송메시지·배송건번호·옵션명·바코드·ERP 품명 6열)을 쓴다. 저장된 출고지 양식 설정은 자동으로 바꾸지 않는다. 파일 생성·암호화가 실패하거나 배송 상태가 변경되면 출고지시 전달 시각을 기록하지 않는다.

선택 내려받기와 출고지별 전체 내려받기는 화면에서 고른 양식을 함께 사용한다. 고르지 않았으면 출고지 기본 양식(남양주는 서원 송장양식, 그 밖은 암호화하는 스마트스토어 양식)을 쓴다. 발송 대기·발송지연 탭의 출고지별 **새 출고지시 전체 내려받기**는 선택 없이 그 출고지의 발송 대기 택배 건 가운데 아직 전달하지 않은 것을 한 파일로 받는다(`admin_origin_pending_export_ids`). 김포·서원 파일은 품목 한 줄이 한 행이고 회신 업로드가 1,000줄까지라, 한 번에 품목 1,000줄(배송 건 1,000건)까지 고르고 남은 건수를 알린다. 선택해서 내보낼 때도 김포·서원 파일이 1,000줄을 넘으면 만들지 않는다. 취소 진행 중인 건, 예약 재고 미할당 건, 퀵·방문수령 건은 제외한다. 목록 한 페이지(100건)를 넘는 물량도 파일 하나로 받기 위한 경로다. 이미 전달한 배송 건을 선택해 다시 내려받으면 화면이 확인을 받는다. 서원은 같은 파일을 두 번 받아도 걸러내지 못한다(회신 C6).

2026-10-15 확인한 운영 방식은 남양주·김포 담당자가 출고 엑셀을 내려받아 각 창고 WMS에 직접 넣는 방식이다. 어드민은 창고별 양식 출력과 운송장 회신 등록을 제공한다. 운송장 발급·회수 접수·배송추적 API 자동화는 구현 범위에 포함하지 않는다.

## 목록 엑셀 다운로드 (배송현황 53열)

발주·발송관리와 배송현황 관리의 **목록 엑셀 다운로드**는 2026-10-21 제공된 `스마트스토어_전체주문배송현황`의 `배송현황관리` 시트를 따른다. [열·서식 정본](../../lib/admin/smartstore-delivery-format.json)은 고객 행 없이 원본의 53개 열 이름·순서, 너비 28.5, 연보라 헤더, 날짜·금액 서식과 필터 위치만 기록한다. 별도 안내 시트를 붙이지 않는다.

현재 탭과 검색 조건의 전체 결과를 품목 한 줄씩 내보내며 최대 10,000행이다. 신규주문·발송 대기·배송중·배송완료에서 같은 양식을 쓴다. 상품주문번호·주문번호·배송비 묶음번호는 [16자리 날짜형 번호](order-reference-numbers.md), 전화·우편번호·송장은 문자열로 저장한다. 금액은 불변 품목 배분 원장(원장이 없는 계산 버전 1 할인 주문은 74열과 같은 공통 배분), 수취 주소는 운영 배송지에서 읽고, 배송비는 묶음의 첫 행에 한 번 기록한다. 네이버 전용 정보와 기록되지 않은 기본가·옵션가·날짜는 빈칸으로 남긴다.

이 경로는 출고지시 전달 시각과 배송 상태를 바꾸지 않는다. 조회 중 배송 버전·상품 구성·수량이 달라지거나 행이 누락되면 파일을 보내지 않는다. 비밀번호 암호화와 다운로드 감사 기록은 유지한다. 감사 기록에는 원래 화면·탭·검색 조건과 건수를 보존한다.

## 스마트스토어 출고지시 양식 (74열)

2026-10-20 네이버 발주(주문)확인/발송관리에서 직접 내려받은 빈 XLSX를 기준으로 한다. 원본은 고객 데이터가 없는 안내 1행·헤더 1행이며 [고정 원본](../../lib/admin/fixtures/smartstore-dispatch-20261020.xlsx)과 [형식·출처·SHA-256](../../lib/admin/smartstore-shipment-format.json)을 보관한다. `발주발송관리` 시트명, 74열의 이름·순서, 열 너비 28.5, 안내 행 높이 150, `A1:C1`·`D1:F1` 병합, 노란 안내·연보라 헤더와 헤더 필터를 맞춘다. 안내 문구는 실제 ICONS의 회신 절차로 작성했다. 원본이 빈 파일이므로 실제 네이버 고객 행의 값·서식까지 동일하다고 판단하지 않는다.

- 한 행은 실제 `order_items.id`에 연결된 `product_order_number`로 식별하는 상품주문이다. 주문번호는 `orders.order_number`, 배송비 묶음번호는 `order_shipments.shipment_number`를 쓴다. 여러 출고지의 선택도 한 시트에 담고 번호·옵션코드·전화·우편번호·송장은 텍스트로 쓴다. 수량·금액은 숫자, 날짜는 KST로 표시되는 Excel 날짜 값이다.
- 주문 품목·수취 주소는 기존 출고 읽기와 `private.operational_order_address`를 따른다. 구매자명은 기존 관리자 조회와 같은 현재 닉네임, 구매자ID는 ICONS 회원 UUID다. 구매자 연락처의 별도 스냅샷이 없으면 빈칸이며 수취인 연락처를 복사하지 않는다.
- `최초/최종 상품별 총 주문금액`은 불변 품목 배분 원장의 `paid_goods_total`이다. `최초/최종 상품별 할인액`과 `판매자 부담 할인액`은 당시 정가와 판매 단가의 차이, 복수구매·쿠폰·적립금 할인을 합한다. ICONS 적립금은 기존 상품금액 차감 계약을 유지하며 네이버페이 포인트 결제로 바꾸지 않는다. 발송 대기이고 부분취소·부분반품을 제공하지 않는 현재 범위에서는 최초/최종 값이 같다. [네이버 금액 정의](https://help.sell.smartstore.naver.com/faq/content.help?faqId=4499), [할인 구성 정의](https://github.com/commerce-api-naver/commerce-api/discussions/945)를 대조했다.
- 과거 배분 원장이 없는 계산 버전 1 주문은 할인·적립금이 모두 0이면 품목 합계를 쓴다. 쿠폰·적립금이 있던 주문은 주문 당시 쿠폰 기록(대상·대상 품목 합계)과 사용 적립금을 거래확정 엑셀과 같은 공통 규칙(`lib/admin/item-allocation.ts`, 대상 품목 금액 비례·큰 나머지 순)으로 나눠 채운다(10/14 회의 A5). 쿠폰 대상 품목은 주문 당시 사용 스냅샷으로 정한다 — 상품 쿠폰은 대상 상품(그룹상품 포함), IP 쿠폰은 품목의 당시 IP, 카테고리 쿠폰은 품목별 당시 분류 기록이 없어 현재 분류로 판정한다. 쿠폰 기록이 없거나 대상 품목 합계가 기록된 대상 금액과 맞지 않으면(분류가 바뀐 경우 포함) 추정하지 않고 빈칸이다. v2 거래의 필수 배분 원장이 누락되면 파일 생성 자체를 거절한다. 정가 기록이 없으면 총 할인액을 추정하지 않는다.
- `상품가격`과 `옵션가격`은 주문 당시 기본가·옵션가 분리 스냅샷이 없어 빈칸이다. 현재 상품가로 역산하지 않는다. 네이버의 상품종류·배송비 유형에 대응하는 당시 분류가 없으면 빈칸으로 두고 ICONS 굿즈 분류나 현재 무료 여부로 대체하지 않는다. 네이버 전용 풀필먼트·N배송·반품안심케어·수수료·정산예정금액·인증·통관 값도 생성하지 않는다. 발송·결제·발주확인 일시는 실제 해당 기록만 사용하고, 엑셀 생성일을 송장 발급일로 표시하지 않는다.
- 배송비 합계는 해당 배송 건의 선불+착불 금액이며 첫 상품 행에 한 번 쓴다. 지역 추가배송비·배송비 할인은 주문 당시 배송비 구성 원장을 따른다. 선물·착불·합포장은 별도의 `배송 운영 안내`를 함께 확인한다. CSV에서도 같은 74열을 쓰며 필요한 운영 안내가 있으면 ZIP으로 묶는다.

기본 XLSX는 비밀번호·확인 입력 후 ECMA-376 Agile 방식으로 암호화한다. 비밀번호는 URL·로그·브라우저 저장소·서버 저장소에 남기지 않고 입력 필드도 요청 전에 비운다. 파일 생성과 암호화가 끝난 뒤 기존 `admin_mark_shipments_exported`가 조회 버전·배송 상태·합포장 상태를 다시 검사한다. 기존 배송건별 감사는 유지하며 암호문 해시를 새 감사 필드로 저장하지 않는다. `기존 창고 양식`과 CSV의 기존 평문 호환은 유지한다.

## 스마트스토어 양식 회신 등록

1. 기본 XLSX를 Excel에서 열어 실제 발급한 송장번호·택배사를 입력한다. 주문과 상품주문번호는 그대로 유지한다.
2. 파일의 암호를 해제하고, 74열 출고지시처럼 상단 안내 행이 있는 파일만 안내 행을 삭제한다. 53열 배송현황 파일은 첫 행부터 헤더이므로 삭제하지 않는다. 실제 데이터가 있는 시트명을 `발송처리`로 저장한다.
3. `상품주문번호`·`배송방법`·`택배사`·`송장번호` 네 헤더를 각각 하나씩 유지한다. 순서는 자유이며 나머지 70열은 유지하거나 삭제할 수 있다. 배송방법은 `택배,등기,소포`, 택배사는 등록된 이름 또는 코드로 입력한다. 퀵·방문수령·직접전달은 기존 주문 상세의 인계·수령 확인을 사용한다.
4. `엑셀 일괄 운송장 등록`에 올린다. 서버는 16자리 상품주문번호를 저장된 `order_items.id`로 조회한 뒤 `order_shipment_items`로 배송 건에 연결한다. 이전 파일의 전체 UUID도 계속 받는다. 같은 배송 건의 모든 행이 같은 택배사·송장인지 확인하며, 상품주문번호가 틀려 배송 건을 확인할 수 없는 행은 파일 전체를 등록하지 않는다. 연결된 배송 건에 오류 행이 있거나 합포장에 충돌이 있으면 해당 배송 묶음을 등록하지 않는다.
5. 성공한 배송 건마다 발송·메일 대기열을 한 번 처리하고 원본 줄 번호별 결과를 확인한다. 같은 배송의 여러 상품 행을 여러 배송으로 집계하지 않는다. 재시도는 기존 발송·메일 멱등 경계를 따른다.

숫자로 저장된 상품주문번호·송장, 수식, 알 수 없는 상품주문, 비활성 택배사는 거절한다. 기존 일반 세 칸 회신과 김포 원본 회신도 계속 지원한다. 실제 창고 WMS의 새 74열 파일 수용 여부는 별도 인수 확인 대상이다.

## 기존 창고 양식의 제공 원본과 적용 범위

2026-09-08 사용자가 제공한 다음 두 원본을 읽기 전용으로 대조했다. 고객 행은 저장소와 테스트에 반입하지 않았다.

| 원본 | 헤더 범위 | SHA-256 |
|---|---|---|
| `260908_우체국 송장 입력 양식.xlsx`의 `송장양식` | A1:G1, 7열 | `f7442d08afadfd91f403093a7828b0cc3a14f03af384ae572e5c30dcf645b0fc` |
| `20260907_주문서확인처리_김포 물류 송장 출력 전용.xlsx`의 동명 시트 | A1:U1, 21열 | `f9c9e660ebcb82c47fd9e10415b172cf6c4196810cfaed69ad2279792c380a02` |

정확한 헤더 목록은 `lib/admin/warehouse-templates.ts`에 있다. 출력 파일은 원본의 고객 데이터와 빈 추가 시트(Sheet1~Sheet5)를 복제하지 않는다. 식별자·전화번호·우편번호·운송장은 문자열을 유지하고, CSV의 수식 시작 문자는 보호한다.

기존 창고 양식을 명시적으로 선택하고 여러 출고지를 함께 내보내면 출고지별 파일을 ZIP 하나로 묶는다. XLSX·CSV 선택 모두 같은 원칙이며, 각 파일에는 해당 출고지의 행만 담는다. 일반 양식의 헤더·순서 설정은 이 모드에만 적용하고 기본 스마트스토어 74열에는 적용하지 않는다.

김포·일반 XLSX의 식별자·전화번호·우편번호·운송장 열에는 텍스트 형식(`@`)을 적용한다. 김포의 빈 운송장 칸도 입력 전에 텍스트 형식을 갖고 있어 앞자리 0과 긴 번호를 보존한다. 수량·금액은 숫자 셀을 유지한다.

서원 파일만 원본 서식까지 옮긴다(2026-10-12 사용자 요청 "남양주 양식대로 정확하게"). 서원 송장양식은 XLSX 양식이고 회신도 XLSX로만 받으므로, 파일 형식에서 CSV를 골라도 서원 파일은 XLSX로 만든다. 시트 하나의 이름은 `송장양식`이다. 앞 7열의 헤더·순서·열 너비, 헤더 색(노랑=필수, 회색=선택, 초록=피킹), 맑은 고딕 10pt, 전화 칸 텍스트 형식, 수량 칸의 숫자 형식(`#,##0_);[Red]\(#,##0\)`)과 초록 칸이 원본과 같다.

## 값 매핑

- **김포 21열:** 상품·옵션명과 할인 전 단가는 주문 당시 스냅샷이다. `상품명(확정)` 칸만 옵션의 ERP 품명이 있으면 ERP 품명, 없으면 주문 당시 상품명이다(10/27 회의 D10②). `옵션(확정)`·`옵션(수집)`과 앞의 두 조합 열은 주문 당시 상품·옵션명 그대로다 — ERP 품명이 옵션 단위라 옵션까지 바꾸면 중복된다. 열 수·헤더는 그대로다. `주문번호(쇼핑몰)`에는 ICONS 전체 주문 UUID를 유지한다. 수취인명 합성의 쇼핑몰명은 ICONS다. 상품 수량은 숫자로 쓰고, 선결제 배송비는 배송 건의 첫 상품 행에 한 번 표시한다. 신규 출고 파일의 운송장은 빈칸이다.
- **서원 송장양식:** 원본처럼 품목(주문 상품·옵션) 하나가 한 행이다. 우체국 송장 프로그램은 받는 분 이름+전화가 같은 행을 한 송장으로 합친다(회신 C8). 그래서 한 파일 안에서 이름+전화가 같은 **서로 다른 배송 건**이 둘 이상이면 받는분성명 뒤에 배송건번호 순서대로 `01`·`02`…를 붙여(예: `김영생01`, `김영생02`) 송장을 따로 받는다(10/14 회의 A6, 10/7 서원 회신은 접미사를 쇼핑몰 몫으로 적었다). 공백 차이는 같은 이름으로 보고, 주소가 달라도 이름+전화가 같으면 붙인다. 운영자가 묶은 **합포장**은 한 상자이므로 구성 배송 건이 모두 같은 접미사를 쓰고, 그 받는 분의 배송 건이 하나뿐이면 접미사를 붙이지 않는다. 접미사는 **그 내보내기(한 출고지 파일)의 구성으로만** 정해진다 — 같은 배송 건이라도 다른 내보내기에서는 다른 접미사(또는 접미사 없음)가 될 수 있다. 그래서 출고지시 전달 표시와 같은 트랜잭션에서 배송 건별로 그 내보내기 묶음과 접미사를 기록한다(`admin_mark_seowon_shipments_exported`, `private.seowon_export_labels`). 같은 배송 건을 다시 내보내면 마지막 내보내기의 접미사로 바뀐다.
  - 받는분전화번호: `010-1234-5678` 형식
  - 받는분우편번호: 5자리
  - 받는분주소(전체,분할): 기본+상세 주소
  - 수량: 상품 수량을 숫자로 적는다(회신 C4)
  - 품목명: 서원 회신 B2의 예처럼 `상품명_옵션명`이다. 옵션이 없는 단일 상품도 원본의 같은 형식 행처럼 `상품명_`으로 끝난다. 상품·옵션명은 주문 당시 스냅샷이다. 10/27 결정 뒤에도 품목명 칸과 회신 대조 키(전화·주소·품목명·수량)는 바꾸지 않는다.
  - 받는분기타연락처·운임Type: 회신대로 빈칸이다(C4).
  - 원본에 없는 `받는분성명`·`배송메시지`·`배송건번호`·`옵션명`·`바코드`·`ERP 품명`은 7열 오른쪽에 이 순서로 덧붙인다. 서원 회신 C3·C8이 이름을 송장 출력과 합배송 판정에 쓴다고 했기 때문이다. `배송건번호`는 [16자리 번호](order-reference-numbers.md)이며 텍스트 칸이다. 송장은 배송 건 단위로 발급·등록되고 같은 배송 건의 품목 줄이 한 번호를 공유하므로, 상품주문번호가 아니라 배송건번호를 쓴다. `옵션명`은 주문 당시 옵션명(직접 입력 값 포함), `바코드`(텍스트 칸, 앞자리 0 보존)·`ERP 품명`은 아래 식별값 규칙을 따른다. 서원 프로그램이 7열만 읽으면 덧붙인 열은 무시된다. 회신 파서는 덧붙인 열을 헤더 이름으로 찾고, 송장번호 열은 송장 헤더(`송장번호`·`등기번호` 등)로만 찾으므로 새 세 열의 영향을 받지 않는다.
- 김포의 사방넷 주문번호·옵션별칭·공급단가·EA(상품)·두 번째 연락처는 현재 빈칸이다. 존재하지 않는 공급단가를 판매가로 대체하지 않는다. 김포 EA와 공급단가의 의미는 확인 중이다.
- **옵션 식별값(바코드·ERP 코드·ERP 품명, 2026-10-27 회의 D10②):** 2026-10-12 회의의 "출고 파일에는 ICONS 상품명·옵션명만 넣는다"는 결정을 뒤집었다. 서원 회신 B2·C2의 바코드 요청대로 옵션별 바코드·ERP 품명을 출고 파일에 싣는다. 값은 주문 시점 스냅샷(`private.order_item_external_identity_snapshots`, 정산 내보내기와 같은 원천)이 우선이고, 스냅샷 값이 비어 있으면(그 주문 때 아직 입력하지 않았거나 스냅샷 행이 없으면) 지금 상품 옵션에 등록된 값으로 칸마다 채운다. 둘 다 없으면 빈칸이다. 출고 파일은 스냅샷을 읽기만 하고 되쓰지 않으므로 정산 내보내기 값은 바뀌지 않는다. 기존 창고 양식으로 받을 때 파일에 바코드 칸이 있는 출고지(서원 송장양식, 바코드 선택 열을 고른 표준 양식)의 배송 건이 있으면 발주·발송 화면이 내보내기 전에 "바코드가 없는 옵션 N개 — 파일의 바코드 칸이 비어 있습니다."를 보여 준다(`admin_shipment_barcode_gaps`). 바코드 칸이 있는지는 서버가 배송 건 출고지의 양식·표준 열 설정으로 판정하므로, 다른 페이지에 있는 방금 발주확인한 배송 건도 함께 센다. 김포 21열·표준 기본 12열·스마트스토어 74열에는 바코드 칸이 없어 세지 않는다. 경고일 뿐 내보내기를 막지 않는다.
- 기존 창고 양식의 선물·착불 배송에는 별도의 `배송 운영 안내` 시트를 붙인다. 김포 고정 열과 서원의 기본 7열·확정된 추가 전달 열에 금융 안내 열을 끼워 넣지 않는다. 이 시트의 포장 요청·선결제 금액·계약상 착불 금액·수납 주체와 방법을 함께 확인한다. 김포·일반 CSV에 운영 안내가 있으면 출고지시 CSV와 운영 안내 CSV를 ZIP으로 내려받는다. 여러 출고지를 골랐다면 이 출고지별 결과를 다시 하나의 ZIP에 담으므로 필요한 출고지의 결과가 내부 ZIP일 수 있다. 서원은 CSV 선택에도 XLSX를 만들고 필요한 운영 안내는 별도 시트로 둔다. 착불 금액을 김포의 선결제 배송비 열에 더하지 않는다.

**실제 창고 인수 확인은 남아 있다.** 확인할 항목은 빈칸 허용 여부, 단가의 할인 기준, 배송비 행 배분이다. **김포 EMP가 `상품명(확정)`의 무엇으로 상품을 찾는지(H6)는 확인하지 못했다 — ERP 품명을 넣은 뒤 김포 회신 대조나 EMP 상품 매칭이 실패하면 `lib/admin/warehouse-templates.server.ts`의 `gimpoCells`에서 `goodName`을 주문 당시 상품명으로 되돌린다.** 서원 프로그램(위드유소프트)이 덧붙인 여섯 열을 읽는지·무시하는지, 이름 접미사를 서원이 붙이는지 우리가 붙인 그대로 쓰는지, 회신에 배송건번호를 남겨 줄 수 있는지, 실제 회신 파일 모양도 물류 담당자와 확인한다(H1). 합성 주문의 파일 생성·재입력 성공만으로 창고 접수 성공이나 #429 전체 완료를 선언하지 않는다.

## 회신 등록 공통

운송장 가져오기는 발주·발송과 배송현황의 모든 탭에서 열 수 있다. 김포 21열·서원 송장양식 회신은 파일 양식으로 출고지를 찾고, 택배사는 그 출고지의 기본 택배사를 쓴다. 목록에서 고른 출고지가 그 양식이면 그 출고지를 쓴다. 고르지 않았으면 같은 양식을 쓰는 사용 중 출고지가 하나일 때만 그 출고지를 쓰고, 여러 곳이거나 없으면 멈춘다. 기존 일반 3열 XLSX·CSV·붙여넣기도 계속 지원한다. 내용이 있는 시트가 하나면 원본처럼 빈 시트가 붙은 파일도 받는다.

**일괄 등록은 이미 발송된 배송 건의 운송장을 바꾸지 않는다**(`admin_import_shipment_tracking`). 같은 회신을 다시 올리면 아무것도 바꾸지 않고 "이미 발송된 N건은 그대로 두었다"고 알린다. 다른 번호면 `shipment_tracking_conflict`로 그 건을 실패 처리한다. 정정은 감사 기록을 남기는 주문 통합검색의 운송장 수정 폼으로만 한다. 새로 발송처리한 건만 등록 건수와 배송 메일에 들어간다.

## 김포 회신 등록

1. 해당 출고지에 김포 WMS 21열 양식과 활성 기본 택배사를 설정한다.
2. 출고 파일의 `주문번호(쇼핑몰)` 값을 유지한 21열 XLSX 회신을 올린다. 김포 양식 출고지가 여러 곳일 때만 목록 위에서 출고지를 고른다.
3. 21개 헤더를 정확히 인식한 파일에서 주문번호와 운송장을 읽는다. 고객명·주소·행 순서로 주문을 추정하지 않는다. 서버가 선택 출고지의 기본 택배사와 `(주문, 출고지)`에 속한 유일한 배송 건을 확인한다.
4. 같은 주문의 동일 운송장 상품 행은 한 건으로 센다. 서로 다른 운송장이 있거나 같은 주문의 다른 행이 잘못됐으면 그 주문의 모든 행을 고친 뒤 다시 올린다. 실패 보고서는 원본 줄 번호를 유지한다.
5. 성공한 배송 건은 배송 중으로 바뀌고 배송 메일이 대기열에 들어간다. 메일 대기열 경고가 있으면 발송 이력과 배송 상태를 확인한다. 재시도는 기존 멱등 발송·메일 규칙을 따른다.

회신은 XLSX 1MB·1,000행, CSV·TSV·텍스트와 붙여넣기는 256KB·1,000행 한도다. XLSX 압축 해제 후 전체 8MB·개별 항목 4MB 제한을 유지한다. 상품주문번호·주문번호의 정밀도 유실, 수식, 비활성 출고지·택배사, 다른 출고지나 미확인 주문을 거절한다. 아래 서원 계약의 안전한 13자리 숫자 송장 외에는 숫자 변환으로 유실될 수 있는 식별자를 허용하지 않는다. 실제 WMS가 발급한 운송장을 기준으로 대조하며, 연습 파일을 실제 창고나 택배사에 보내지 않는다.

## 남양주(서원) 회신 등록

서원은 주문번호를 돌려주지 않고 송장번호를 따로 준다(회신 D2·D4). 그래서 회신은 **내려받은 송장양식에 송장번호 열을 채운 파일**로 받는다. 덧붙인 `배송건번호` 열이 텍스트 16자리로 남아 있으면 그 번호로 배송 건을 정확히 찾는다. 열이 지워졌거나 숫자 칸으로 바뀌어 자릿수를 잃었으면 번호를 쓰지 않고 아래 내용 대조를 한다.

1. 내려받은 송장양식의 A~G 헤더를 그대로 두고, 오른쪽에 `송장번호` 열을 둔다. 검증된 `배송 운영 안내` 시트와 빈 추가 시트는 유지할 수 있다. `운송장번호`·`등기번호`·`운송장`·`송장`·`택배송장번호`·`우체국송장번호` 헤더도 인정한다.
2. 각 줄에 그 품목이 실린 송장번호를 채운다. 우체국 13자리 번호는 숫자 칸으로 저장돼도 받는다. 앞자리가 0이거나 15자리를 넘는 번호는 텍스트로 입력한다.
3. 받는분전화번호·주소·품목명·수량·받는분성명·배송건번호는 바꾸지 않는다. 배송건번호가 있는 줄은 그 배송 건만 보고, 네 칸이 그 배송 건의 줄과 다르면 등록하지 않는다(없는 번호도 같다). 서버는 회신에 나온 전화번호로 좁힌 남양주의 대조 후보(`admin_origin_tracking_candidates`)를 읽고, 후보가 5,000건을 넘으면 아무것도 등록하지 않는다. 후보는 출고지시를 전달한 발송 대기 택배 건과 재업로드 확인용 최근 45일 발송 건이다. 아직 전달하지 않은 건은 회신에 있을 수 없으므로 후보가 아니다. 회신 줄과 이 네 칸이 같은 배송 건만 연결한다. 우편번호와 공백·하이픈 차이는 무시하고, 받는 분만 같은 건으로 넘겨짚지 않는다.
4. 한 배송 건의 줄은 송장번호가 같아야 하고, 그 배송 건의 품목 줄이 회신에 모두 있어야 한다. 송장번호가 다르거나, 한 줄이라도 오류(송장번호 없음 등)가 있거나, 빠진 줄이 있으면 그 배송 건 전체를 등록하지 않는다. 일부만 출고했다면 그 배송 건은 주문 통합검색에서 처리한다.
5. 배송건번호 없이 받는 분과 품목이 똑같은 발송 대기 건이 여럿이면, 그 줄이 배송 건 수만큼 회신에 모두 있고 송장이 하나(합포장·합배송)이며 회신 접미사가 기록과 어긋나지 않을 때 함께 등록한다. 송장이 따로 나왔으면 회신의 `받는분성명` 접미사를 **마지막 내보내기에서 배송 건별로 기록한 접미사**와 정확히 맞춘다. 접미사마다 기록이 같은 배송 건이 하나(합포장이면 같은 묶음의 구성원)이고 한 내보내기 묶음에서 나온 기록이어야 한다. 기록이 없거나(이 기록 도입 전 내보내기), 맞는 기록이 없거나(취소·다른 파일), 여러 내보내기에 걸치면 남은 후보의 순위로 추정하지 않고 그 줄만 실패로 남겨 주문 통합검색에서 배송 건별로 등록한다. 같은 내용의 발송 대기 건이 하나뿐이어도 회신 접미사가 그 배송 건의 기록과 다르면 다른 배송 건의 줄로 보고 등록하지 않는다. 실패 사유와 등록 결과의 배송 건은 배송건번호로 표시한다.
6. 합포장은 구성 배송 건 모두가 같은 송장으로 회신에 있어야 등록한다. 구성원 줄이 빠졌거나 송장이 갈렸으면 그 합포장만 실패로 남기고 나머지 배송 건은 등록한다.
7. 한 송장번호가 받는 분(전화·주소)이 다른 배송 건에 함께 적혀 있으면 그 배송 건들을 모두 등록하지 않는다. 같은 송장으로 이미 발송된 건은 그대로 둔다(다른 운영자가 먼저 같은 회신을 올린 경우 포함). 기간과 관계없이 이미 다른 배송 건에 등록된 송장번호는 새 배송 건에 붙이지 않으므로, 예전 회신을 다시 올려도 같은 내용의 새 주문이 옛 송장으로 발송되지 않는다.
8. 연결된 배송 건마다 한 번 기존 일괄 등록 RPC로 발송처리하고, 배송 메일을 대기열에 넣는다.

남양주 회신은 XLSX만 받는다. CSV로 올리면 XLSX로 다시 올리라고 안내한다.

회신 파일은 768KB·1,000행 한도다(서버 액션 본문 한도 1MB 안). 김포·서원 출고지시 파일은 회신에 운송장 열을 더해도 들어가도록 512KB를 넘으면 만들지 않고 나눠 내보내게 한다. 숫자로 저장돼 자릿수가 유실될 수 있는 주문번호·운송장, 수식, 비활성 출고지·택배사, 다른 출고지나 미확인 주문을 거절한다. 실제 WMS·우체국이 발급한 운송장을 기준으로 대조한다.

연습 주문으로 창고와 시뮬레이션할 때는 파일을 보내기 전에 모의 주문임을 알린다. 송장 출력·출고 여부도 미리 합의한다. 서원은 출력한 송장을 당일 출고하며, 온라인몰 허위송장 규제를 이유로 들었다(회신 D3). 연습 주문은 운영 DB가 아니라 스테이징에서 만든다([staging](staging.md)). 운영 DB에는 테스트 주문을 걸러내는 표식과 정리 수단이 없다.
