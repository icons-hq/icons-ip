# PG 정산 조회·대조 운영 절차

2026-10-14 구현 기준. 로컬 합성 검증을 완료했으며 실제 PG 연결·운영 적용은 수행하지 않았다. 이 절차의 설정 변경과 운영 수집은 명시적인 운영 승인 범위에서 실행한다.

## 연결 전 확인

1. 앱과 `20261013132500_pg_settlement_ledger.sql`, 정기결제 기반 및 `20261014032236_goods_transaction_settlement_profiles.sql`을 같은 배포 범위로 준비한다. migration은 격리 DB에서 검증하며 기존 개발 DB를 reset하지 않는다.
2. 통합·계정 주매니저의 현재 `sales.manage` 권한을 확인한다. 전환 전 호환 모드에서는 기존 admin 전용이다. 부매니저·운영자에게 메뉴나 엑셀 URL만으로 접근을 열지 않는다.
3. 실제 토스 계약 계정의 MID, 기존 `TOSS_SECRET_KEY`와 `NEXT_PUBLIC_TOSS_CLIENT_KEY`의 같은 모드, 정산 GET 조회 권한을 확인한다. 일반 결제는 기존 주문서형 키를 재사용하고, 정기결제는 저장된 billing profile·MID·환경에 정확히 대응하는 현재 키로 조회한다. 각 계약 계정에서 정산 조회가 허용되는지는 실제 확인이 필요하다. 다른 키를 임의 발급하거나 Preview/로컬에 실키를 복제하지 않는다.
4. 승인된 환경에서만 `TOSS_SETTLEMENT_MID`를 등록하고 `TOSS_SETTLEMENT_SYNC_ENABLED=true`로 켠다. 미설정/`false`는 비활성이며 앱 빌드의 필수 변수가 아니다. live 모드는 `VERCEL_ENV=production`에서만 연결된다. 키·MID·인증 헤더·scope 지문을 문서, 로그, 브라우저나 파일에 남기지 않는다.

토스 테스트 환경의 정산 API는 기록을 제공하지 않는다. 테스트 0건과 합성 fixture의 성공을 실거래 정산 검증으로 보고하지 않는다. [공식 테스트 환경 안내](https://docs.tosspayments.com/guides/v2/get-started/environment).

## 조회와 수집

1. `/admin/settlements`에서 일반 결제/정기결제의 정산 계정과 실거래/테스트, 정산 매출일/지급일, 최대 31일의 범위를 선택한다. 최초 운영 확인은 실제 원본과 대조할 수 있는 작은 기간부터 시작한다.
2. 자료 가져오기는 공급자 `GET /v1/settlements`만 호출한다. 한 단계는 최대 65초·1,000건이며, 한 작업은 최대 20,000건을 허용한다. 범위를 넘으면 날짜를 줄인다. 날짜 경계를 놓치지 않도록 양쪽 하루를 함께 조회하고 요청한 날짜만 보관하므로, 인접 날짜 거래도 조회 한도에 포함된다.
3. 같은 기간을 두 차례 읽어 거래 집합을 확인한 뒤 완료한다. 이는 공급자가 원자적 스냅샷을 보장한다는 뜻이 아니다. 진행 중·실패 자료를 합계로 사용하지 않으며, 이전 완료 자료는 유지된다.
4. 창을 닫거나 ‘현재 조회 후 멈춤’을 누르면 현재 단계가 끝난 지점부터 이어서 수집한다. 일시 장애는 현재 상태 확인 후 재개한다. 응답 불명에서는 같은 요청을 확인하고 새 요청으로 중복 시작하지 않는다. 계정·MID·키 범위가 바뀌어 기존 요청과 충돌하면 ‘저장된 수집 작업 다시 불러오기’로 새 화면에서 기록을 확인한다.
5. 완료 자료의 전체 건수·일별/건별·수수료, 원본 소수 값과 PG 원장을 대조한다. 미수집은 0건이 아니다. 새 수집이 실패해도 이전 완료 자료를 최신 성공 자료로 보여주며 완료 시각을 함께 확인한다.

계정은 무작위 식별자와 안전한 표시명으로 구분한다. 브라우저 URL·화면·파일에 MID나 billing profile ID를 보내지 않는다. 수집 이력과 완료 자료는 연동 종류·계정·환경별로 분리하며, 과거 계정의 키를 사용할 수 없어도 저장된 내역은 권한 안에서 조회할 수 있다. 정기결제 승인·취소 내역은 결제 시점에 저장한 profile·MID·환경 binding과 대조하므로 같은 MID여도 일반 결제 자료로 합치지 않는다. 키 버전 교체는 동일한 정기결제 계정의 읽기 범위를 바꾸지 않는다.

## 대조 결과와 엑셀

- ‘일치’는 수집 완료 시점의 결제·목적·주문/예매·금액·공급자 거래 근거가 일치한 결과다. 은행 입금 완료 판정이 아니다.
- ‘미연결’은 연결할 결제가 없거나 기존 거래 근거가 부족한 경우다. 기존 굿즈 환불 경로에 취소 거래 식별자가 없으면 금액이 같아도 미연결로 남는다. ‘불일치’는 연결 근거가 있으나 금액 등 조건이 맞지 않는 경우다. 자료를 임의 수정해 일치시키지 않는다.
- 완료 자료와 대조 결과는 변경하지 않는다. 이후 원장이 바뀌면 다시 수집해 새 완료 자료로 확인하고 수집 이력에서 이전 자료도 조회한다.
- 엑셀 다운로드는 선택한 완료 자료·검색 조건의 전체 거래를 4개 시트로 제공한다. 자료 ID·완료 시각·파일 생성 시각·지문·행 수를 확인한다. 금액은 Excel의 15자리 제한을 피하는 텍스트 셀이며 승인·취소·통화를 합쳐 순입금액으로 계산하지 않는다.
- 내보내기 직전 현재 권한·완료 자료·지문·행 수를 다시 검사하고 감사 기록을 남긴다. 실패하면 파일을 내보내지 않는다. 파일에는 공급자 키·MID·계좌·고객 연락처가 없다.

## 중단과 미연결 범위

`TOSS_SETTLEMENT_SYNC_ENABLED=false`로 신규 공급자 조회를 막을 수 있다. 이미 실행 중인 한 페이지의 응답은 원장에 기록될 수 있으며, 저장된 자료 조회·내보내기는 현재 권한 안에서 계속 가능하다. 완료 원장을 지우거나 결제·환불·재고를 되돌리는 중단 절차가 아니다.

코페이 정산 원본, 은행 입금 자료, 지급 묶음·지연 사유·보류/조정·우대수수료 환급·수취 세금계산서·부가세 신고자료는 별도 계약 원본이 필요하다. [확인한 공급자 범위와 후속 계약](../research/smartstore-admin/pg-settlement-followups.md)을 따른다. 이 기능은 지급 요청·환불 실행·신고·세금계산서 발행을 수행하지 않는다.

## 검증 기록

[구현 계약](../research/smartstore-admin/pg-settlement-parity.md)에 격리 DB 회귀/동시 처리, 합성 45행·0행, Chrome PC/390px와 실제 XLSX 내보내기의 근거를 기록했다. 운영 활성화 후에는 실제 사용한 기간·모드·완료 자료 ID·행 수·대조 결과와 PG/은행 확인 여부를 별도로 남긴다. 비밀값과 공급자 원문 식별자는 기록에서 제외한다.
