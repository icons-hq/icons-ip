# 주문·상품주문·배송 번호

화면과 ICONS 표준 양식 엑셀은 DB에 한 번 발급해 저장한 번호를 사용한다. 주문 시각 전환을 켠 뒤(아래 '전환 켜는 순서') 만든 주문의 주문번호·상품주문번호는 주문 시각을 넣은 20자리이고, 그 전에 만든 주문의 번호와 모든 배송건번호는 16자리다.

| 종류 | 저장 열 | 주문 시각 형식(20자리) | 16자리 형식 |
| --- | --- | --- | --- |
| 주문번호 | `orders.order_number` | `20261112143510000042` | `2026102110000001` |
| 상품주문번호 | `order_items.product_order_number` | `20261112143520000057` | `2026102120000001` |
| 배송건번호 | `order_shipments.shipment_number` | 없음(16자리만) | `2026102130000001` |

20자리 = 주문일(한국 시간) 8자리 + 주문 시각(한국 시간 시·분) 4자리 + 종류 1자리 + 그날의 일련번호 7자리다. 16자리 = 주문일 8자리 + 종류 1자리 + 일련번호 7자리로, 20자리는 16자리 번호의 날짜 뒤에 시각 4자리를 끼운 모양이다. 종류는 주문 1·상품주문 2·배송 3이고 두 형식 모두 끝에서 8번째 자리다. 서로 다른 종류의 번호가 같아져 잘못 연결되는 일을 막는다. 일련번호는 (날짜, 종류)별 DB 카운터의 원자적 증가로 매기고 각 열의 UNIQUE 제약으로 구별한다. 하루·종류별 9,999,999건을 초과하면 잘린 번호를 만들지 않고 실패한다.

상품주문번호는 주문번호와 짝이다. 주문번호의 앞부분(16자리 주문은 날짜 8자리, 20자리 주문은 날짜·시각 12자리)에 종류 `2`와 그날의 상품주문 일련번호를 붙인다. 그래서 20자리 주문의 상품주문번호는 주문번호와 앞 12자리가 같고, 16자리 주문에 나중에 붙는 품목도 16자리다. 배송건번호는 시각을 넣지 않고 16자리 그대로 발급한다.

기존 주문은 생성일·UUID 순서로 번호를 부여한다. 이 순서는 이전에 발급되지 않았던 표시 번호를 결정하는 기준이며 과거 영수증을 재작성하지 않는다. 새 주문·품목·배송 건은 INSERT 트리거에서 발급하고, 발급 후 번호 변경과 임의 번호 지정은 거절한다. 주문 시각을 넣은 뒤에도 이미 발급한 16자리 번호는 바꾸지 않는다. 화면 순서·엑셀 행 번호·UUID 절삭이나 해시로 번호를 계산하지 않는다.

UUID 기본키, 외래키, URL, 서버 액션·결제 시도·PG 주문번호와 멱등 키는 기존 값을 사용한다. 주문·상품주문·배송 검색은 두 형식의 번호와 기존 UUID를 지원하고, 주문번호 부분 일치라 날짜나 날짜·시각 앞부분으로도 찾는다. 일반 운송장 입력의 기존 8자리 조회는 종전처럼 여러 건이 겹치면 거절한다. 일반 운송장 입력은 배송건번호(16자리)와 배송 건이 하나인 주문의 주문번호(16·20자리)를 받는다. ICONS 표준 양식 회신의 상품주문번호는 전체 번호(16·20자리)가 일치하는 품목만 찾고, 알 수 없는 품목이 하나라도 있으면 발송 전에 파일 전체를 거절한다. 김포 21열·일반 12열 창고 양식의 전체 주문 UUID 식별 계약은 바꾸지 않는다(회신 파서와 김포 WMS 매칭이 그 값을 쓴다). 서원 송장양식은 덧붙인 `배송건번호` 열이 회신에 남아 있으면 그 번호로 대조한다([출고지시와 운송장 회신](warehouse-export.md)).

번호 형식 판정은 한 곳에서 한다 — DB `private.is_commerce_number(값, 종류)`, 앱 `lib/commerce-number.ts`의 `isCommerceNumber`·`commerceNumberPattern`. 회신·검색·입력 검증이 16자리 정규식을 따로 두면 20자리 번호를 거절하므로, 새 화면·RPC도 이 둘을 부른다(`lib/commerce-number.test.ts`와 `supabase/tests/order_number_time.sql`이 따로 둔 16자리 정규식을 찾아 실패한다).

고객 메일(주문 접수·배송 시작·선물 수령인·발송 지연 안내)의 제목·본문·푸터와 어드민의 일괄 발주확인 결과·운송장 수정 영역·서원 회신 결과는 주문번호·배송건번호를 쓴다. 번호가 없는 옛 기록만 UUID 뒤 8자리로 표기한다. 이미 고객에게 보낸 발송 지연 안내 본문은 고지된 기록이라 다시 쓰지 않는다. 무통장 입금의 입금코드는 주문번호에서 만든다(아래 무통장 입금코드).

16·20자리 번호는 Excel의 숫자 정밀도 한도(15자리)를 넘으므로 XLSX·CSV와 화면에서 문자열로 처리한다. 숫자 셀로 바뀐 상품주문번호와 운송장번호는 재업로드에서 거절한다. 주문 당시 기본가·옵션가 분리 기록이 없어 현재 상품가를 대신 넣지 않는다.

## 주문 시각 형식 (2026-11, 1014-116·117)

10/14 회의 요청은 "앞에는 날짜고, … 시간 다음에 일련번호다. 누구라도 이해할 수 있게"였고, 사용자가 11/11 '날짜+시각+일련번호'(새 주문부터, 기존 번호 유지)로 확정했다. 업계 관행(스마트스토어 상품주문번호 16자리 = 날짜 + 순번, 시각 없음)과 다른 원래 요청안이다.

자리수와 범위를 이렇게 정한 이유는 다음과 같다.

- 시각은 시·분 4자리까지 넣는다. 같은 분의 주문은 일련번호가 가르므로 초까지 넣어 번호를 늘리지 않는다. 시각은 주문 생성 시각(`orders.created_at`, 한국 시간)이며 결제·입금 시각이 아니다.
- 종류 자리를 유지한다. 주문번호를 상품주문 양식에 붙여 넣어도 다른 품목을 찾지 않게 하는 기존 안전장치이고, 끝에서 8번째 자리라 두 형식에서 같은 위치다.
- 일련번호는 7자리, (날짜, 종류)별 하루 최대 9,999,999건으로 종전과 같다. 5자리(18자리 번호)로 줄이면 하루 99,999건을 넘는 날 주문이 실패하는 새 상한이 생긴다.
- 고유성은 종전처럼 (날짜, 종류) 카운터와 UNIQUE 제약이 준다. 시각은 정보용이라 고유성에 쓰지 않는다. 전환하는 날도 같은 카운터를 이어 쓰므로 그날 16자리 번호와 20자리 번호의 일련번호가 겹치지 않는다.
- 일련번호를 분 단위로 매기면 자리는 줄지만 하루 안에서 일련번호가 되풀이되어 무통장 입금코드(일련번호 끝 5자리)가 겹친다. 주문번호 + 품목 순번(11번가식)은 상품주문번호 길이가 달라지고 종류 자리 안전장치를 잃는다. 둘 다 택하지 않았다.

### 전환 켜는 순서

`20261112150000_order_number_time`은 전환을 꺼 둔 채(`private.commerce_number_time_switch.switched_at = infinity`) 배포한다. 이 배포로는 발급 형식이 바뀌지 않고(16자리 그대로) 같은 배포의 앱이 두 형식을 읽을 준비만 한다. 켜는 순서는 다음과 같다.

1. 이 변경이 든 main 실행에서 `deploy-supabase`와 `deploy-vercel`이 모두 성공했고, 운영 도메인의 production 배포가 그 커밋 이후 빌드인지 확인한다(GitHub Actions 실행 결과와 Vercel production 배포의 커밋). `deploy-vercel`이 실패했으면 재실행해 성공한 뒤로 미룬다. 꺼져 있는 동안은 기다려도 영향이 없다.
2. AX ERP 읽기(`service_erp_read`)는 주문번호·상품주문번호 열을 그대로 내보내므로 ERP 쪽이 20자리를 받는지 확인한다.
3. 후속 migration(별도 PR, 이 변경과 같은 배포에 넣지 않는다)으로 켠다. 그 migration을 적용한 시각 이후(이상)에 만든 주문부터 20자리다. DB가 앱보다 먼저 바뀌어도 그때 운영 앱은 1에서 확인한 두 형식 앱이라 배포 순서 창이 없고, 그 PR의 앱 배포가 실패해도 마찬가지다.

   ```sql
   begin;
   update private.commerce_number_time_switch set switched_at = clock_timestamp()
    where singleton and switched_at = 'infinity'::timestamptz;
   commit;
   ```

4. 켠 뒤 새 주문 하나의 번호가 20자리이고 앞 12자리가 주문 생성 시각(한국 시간 날짜·시·분)과 같은지 확인한다. 주간 변경 기록도 이 주에 적는다.

기본을 '적용 시각 + N시간 예약'이 아니라 '꺼짐 + 앱 배포 확인 뒤 켬'으로 한 이유: 예약 방식은 앱 배포가 기한 안에 성공하지 못하면(실패·재실행 대기·멈춤) 배포 전 앱이 20자리를 만나 어드민 조회·선물 화면이 깨지고, 그것을 막으려면 사람이 기한 안에 운영 DB를 고쳐야 한다. 꺼짐 기본은 아무도 손대지 않으면 종전 동작을 유지하고, 켜는 일도 운영 DB 변경의 유일한 정상 경로인 파이프라인 migration으로 한다. 앱이 시작할 때 DB 스위치를 켜는 방식은 운영 도메인에 붙기 전 배포 URL의 콜드 스타트에서 먼저 켜질 수 있고, `deploy-vercel` 뒤에 켜는 단계를 두는 방식은 앱 배포 job에 운영 DB 자격을 주고 이 기능만의 단계를 파이프라인에 남긴다. 대가는 켜는 PR이 하나 더 필요하다는 것이다.

긴급 대응(사람 게이트 — 운영 DB 직접 변경이라 승인 필요): 파이프라인을 쓸 수 없으면 1·2를 확인한 뒤 Supabase SQL 편집기에서 `update private.commerce_number_time_switch set switched_at = <앱 배포를 확인한 뒤의 시각, 보통 now()> where singleton and switched_at = 'infinity'::timestamptz;`로 켤 수 있다. 과거 시각은 넣지 않는다 — 그 사이 꺼진 상태로 16자리를 받은 주문이 '전환 시각 이후 주문은 20자리'라는 기록과 어긋난다(번호 자체는 바뀌지 않는다). 켠 뒤 새 20자리 발급을 멈춰야 하면 `update private.commerce_number_time_switch set switched_at = 'infinity'::timestamptz where singleton;`으로 끈다. 이미 발급한 20자리 번호는 그대로 남으므로 운영 앱은 계속 두 형식을 읽어야 한다.

로컬·격리 스택에서 바로 확인하려면 그 DB에서만 `update private.commerce_number_time_switch set switched_at = now() where singleton;`을 실행한다.

전환을 켠 뒤에는 이 변경 전 버전의 앱으로 롤백하지 않는다. 옛 앱은 20자리 번호가 든 주문을 일부 화면에서 읽지 못한다. 그래도 롤백해야 하면 먼저 전환을 끄고, 이미 20자리를 받은 주문은 옛 앱에서 일부 화면이 읽지 못한다는 것을 감수한다. 한 번 발급한 번호를 없애거나 다시 부여하는 DB 롤백은 하지 않는다.

## 무통장 입금코드

입금자명 끝에 붙이는 입금코드는 주문번호에서 만든 숫자 6자리다(10/14 회의 D7). 앞 1자리는 주문일의 10일 주기 자리(`(주문일 - 2000-01-01) mod 10`), 뒤 5자리는 그날 주문 일련번호의 끝 5자리다(예: `2026102710000001` → `600001`, `20261027091510000001` → `600001`). 주문번호의 두 형식 모두 앞 8자리가 주문일, 끝 5자리가 일련번호 끝이라 규칙이 같고, 전환하는 날도 카운터를 이어 쓰므로 두 형식의 코드가 겹치지 않는다. 입금 대기는 최대 48시간(24시간 + 1회 연장)이라 동시에 열린 주문의 주문일은 연속한 3일 안이고, 연속한 10일의 주기 자리는 서로 다르다. 따라서 하루 주문이 10만 건을 넘지 않는 한 입금 대기 주문 사이 코드가 겹치지 않는다. 한글 4자 이름과 붙여도 은행 입금자명 14바이트(EUC-KR) 안에 든다. DB `private.bank_transfer_deposit_code`와 앱 `bankTransferDepositCode`가 같은 규칙이고, 함수 이름과 호출 형태(`(uuid)`)는 바꾸지 않았다.

안내된 코드는 바꾸지 않는다. 이 규칙으로 바꾼 시각(migration `20261027140200` 적용 시각, `private.bank_transfer_deposit_code_switch`) 전에 만든 주문은 그때 안내받은 옛 코드(UUID 앞 8자리)가 입금코드다. 그 시각은 DB만 알므로 이미 만든 주문의 코드를 보여주는 화면은 DB가 준 코드를 쓴다 — 고객 주문서는 `get_my_bank_transfer_deposit_code(주문 id)`(본인의 무통장 주문만), 미입금 콘솔은 조회 결과의 `deposit_code`.

파이프라인은 DB를 먼저, 앱을 몇 분 뒤 배포하므로 그 사이 옛 앱의 주문서는 옛 코드를 안내한다. 그래서 입금코드 규칙 전환 시각부터 2시간 안에 만든 주문은 입금 제안과 미입금 검색이 옛 코드(UUID 앞 8자리)도 함께 받는다(`private.bank_transfer_switch_grace_code`). 그 뒤에 만든 주문은 공식 코드만 받는다.

입금 제안은 입금자명에 든 코드가 입금 대기 주문 한 건에만 맞을 때만 코드로 제안한다. 오래 남은 입금 대기 주문(결제 확인 필요 등)과 코드가 겹치면 제안하지 않고 운영자가 고른다. 미입금 검색은 6자리 입금코드를 정확히 일치로만 찾고, 주문번호 부분 일치는 8~20자리 숫자일 때만 쓴다. 검증: `supabase/tests/bank_transfer_order_number_code.sql`, `supabase/tests/order_number_time.sql`, `lib/payments/bank-transfer.test.ts`.

## 적용 순서와 검증

DB migration 3개(`readable_order_numbers`, `smartstore_delivery_list_export`, `commerce_number_readers`)를 순서대로 적용한 뒤 앱을 배포한다. 번호 부여 migration은 주문·품목·배송 테이블을 잠그고 새 번호 열만 채운다. 기존 업무·갱신시각 트리거의 활성 상태를 저장하고 같은 트랜잭션에서 정확히 복원해, 번호 부여가 결제·재고·알림·수정시각을 바꾸지 않도록 한다. 실패하면 번호와 트리거 상태를 함께 롤백한다. 주문 시각 형식 migration(`20261112150000_order_number_time`)은 기존 행을 고치지 않고 발급 함수·형식 제약·번호를 읽는 함수만 바꾸며, 같은 배포의 앱이 두 형식을 모두 읽는다. 전환은 꺼진 채 배포되고 위 '전환 켜는 순서'로 켠다.

운영 DB 적용과 배포는 별도 승인 범위다. 적용 전 격리 DB에서 기존 업무 데이터와 트리거 상태 보존, 한국 시간 자정 경계, 번호 중복·변조 방지, 검색, 숫자 상품주문번호 회신의 멱등성, 권한을 확인한다. 검증 파일은 다음과 같다.

- `supabase/tests/readable_order_numbers.sql`
- `supabase/tests/order_number_time.sql` (전환 전후 형식·짝·자정·하루 상한·입금코드·검색·회신·테스트 배송완료)
- `supabase/tests/readable_order_numbers_concurrency.py` (격리 DB 또는 CI만 허용)
- `supabase/tests/smartstore_shipment_workbook.sql`
- `lib/commerce-number.test.ts`, `lib/commerce-number.readers.test.ts`, `lib/admin/staging-test-tools.test.ts`
- `lib/admin/smartstore-delivery-list*.test.ts`, `lib/admin/smartstore-shipment-workbook.server.test.ts`

정확한 JSON 키를 검사하는 배송지·환불 송금·클레임 비용·합포장·선물·문의 만족도 조회는 기존 RPC 응답을 유지하고 새 앱만 `*_numbered` 조회를 사용한다. 합포장 버전 값과 변경 영수증은 기존 계약을 유지한다. 따라서 DB 적용 직후의 기존 앱과 앱 롤백에서도 UUID 연결·기존 조회를 유지한다(주문 시각 형식 전환 뒤의 앱 롤백은 위 '주문 시각 형식' 절을 따른다). 한 번 외부에 표시한 번호를 없애거나 다시 부여하는 DB 롤백은 수행하지 않는다.
