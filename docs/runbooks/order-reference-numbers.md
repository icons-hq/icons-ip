# 주문·상품주문·배송 번호

화면과 스마트스토어 양식 엑셀은 DB에 한 번 발급해 저장한 16자리 번호를 사용한다.

| 종류 | 저장 열 | 형식 예시 |
| --- | --- | --- |
| 주문번호 | `orders.order_number` | `2026102110000001` |
| 상품주문번호 | `order_items.product_order_number` | `2026102120000001` |
| 배송건번호·배송비 묶음번호 | `order_shipments.shipment_number` | `2026102130000001` |

앞 8자리는 원 주문 생성일의 한국 시간 날짜다. 다음 1자리는 주문 1·상품주문 2·배송 3이며, 뒤 7자리는 날짜·종류별 일련번호다. 서로 다른 종류의 번호가 같아져 잘못 연결되는 일을 막는다. 같은 시각의 동시 주문도 DB 카운터의 원자적 증가와 각 열의 UNIQUE 제약으로 구별한다. 하루·종류별 9,999,999건을 초과하면 잘린 번호를 만들지 않고 실패한다.

기존 주문은 생성일·UUID 순서로 번호를 부여한다. 이 순서는 이전에 발급되지 않았던 표시 번호를 결정하는 기준이며 과거 영수증을 재작성하지 않는다. 새 주문·품목·배송 건은 INSERT 트리거에서 발급하고, 발급 후 번호 변경과 임의 번호 지정은 거절한다. 화면 순서·엑셀 행 번호·UUID 절삭이나 해시로 번호를 계산하지 않는다.

UUID 기본키, 외래키, URL, 서버 액션·결제 시도·PG 주문번호와 멱등 키는 기존 값을 사용한다. 주문·상품주문·배송 검색은 새 번호와 기존 UUID를 지원한다. 일반 운송장 입력의 기존 8자리 조회는 종전처럼 여러 건이 겹치면 거절한다. 스마트스토어 회신의 새 상품주문번호는 전체 16자리가 일치하는 품목만 찾고, 알 수 없는 품목이 하나라도 있으면 발송 전에 파일 전체를 거절한다. 김포·서원 전용 창고 양식의 기존 식별 계약은 이 변경으로 바꾸지 않는다.

16자리 번호는 Excel의 숫자 정밀도 한도를 넘으므로 XLSX·CSV와 화면에서 문자열로 처리한다. 숫자 셀로 바뀐 상품주문번호와 송장번호는 재업로드에서 거절한다. 주문 당시 기본가·옵션가 분리 기록이 없는 항목에 현재 상품가를 대신 넣지 않는다.

## 적용 순서와 검증

DB migration 3개(`readable_order_numbers`, `smartstore_delivery_list_export`, `commerce_number_readers`)를 순서대로 적용한 뒤 앱을 배포한다. 번호 부여 migration은 주문·품목·배송 테이블을 잠그고 새 번호 열만 채운다. 기존 업무·갱신시각 트리거의 활성 상태를 저장하고 같은 트랜잭션에서 정확히 복원해, 번호 부여가 결제·재고·알림·수정시각을 바꾸지 않도록 한다. 실패하면 번호와 트리거 상태를 함께 롤백한다.

운영 DB 적용과 배포는 별도 승인 범위다. 적용 전 격리 DB에서 기존 업무 데이터와 트리거 상태 보존, 한국 시간 자정 경계, 번호 중복·변조 방지, 검색, 숫자 상품주문번호 회신의 멱등성, 권한을 확인한다. 검증 파일은 다음과 같다.

- `supabase/tests/readable_order_numbers.sql`
- `supabase/tests/readable_order_numbers_concurrency.py` (격리 DB 또는 CI만 허용)
- `supabase/tests/smartstore_shipment_workbook.sql`
- `lib/admin/smartstore-delivery-list*.test.ts`, `lib/admin/smartstore-shipment-workbook.server.test.ts`

정확한 JSON 키를 검사하는 배송지·환불 송금·클레임 비용·합포장·선물·문의 만족도 조회는 기존 RPC 응답을 유지하고 새 앱만 `*_numbered` 조회를 사용한다. 합포장 버전 값과 변경 영수증은 기존 계약을 유지한다. 따라서 DB 적용 직후의 기존 앱과 앱 롤백에서도 UUID 연결·기존 조회를 유지한다. 한 번 외부에 표시한 번호를 없애거나 다시 부여하는 DB 롤백은 수행하지 않는다.
