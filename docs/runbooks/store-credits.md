# 주문 할인용 적립금 운영

영업 피드백 [#488](https://github.com/icons-hq/icons-ip/issues/488)·[#489](https://github.com/icons-hq/icons-ip/issues/489)의 별도 원장이다. 무료 코인·카드·카드팩·기존 쿠폰 발급 원장과 교환하거나 금액을 공유하지 않는다. 유상 충전·현금 출금·타인 양도 기능은 없다.

## 정책 설정과 활성화

관리자는 `/admin/settings/store-credits`에서 적립 방식·값·주문당 적립 상한·보유 상한·유효기간·1회 사용 하한/상한·만료 후 복원 유효기간·환불 회수 방식과 정책 승인 근거를 저장한다. 직원(staff)은 정책이나 적립금을 조정할 수 없다. 앱과 DB 모두 현재의 활성 admin 역할을 다시 확인한다.

초기 정책은 **비활성**, 수치·회수 방식은 **미설정**이다. 빈 값을 0원이나 무제한으로 해석하지 않는다. 모든 필수 값과 근거가 있어야 활성화할 수 있다. 입력한 명시적 0원 상한은 해당 지급/사용을 허용하지 않는 실제 상한이고, 무제한을 뜻하지 않는다. 유효기간은 양의 일수이며 복원 유효기간은 0일도 명시할 수 있다. 정률 값의 입력 단위는 0.01%다.

비활성화는 신규 지급·신규 주문 사용을 닫는다. 과거 주문의 사용 선점·결제 확정·복원·만료 이력을 지우지 않으며, 활성 정책 아래 주문 당시 약속한 거래확정 적립은 그 주문의 정책 스냅샷을 따른다. 활성화 전에 만든 주문에는 이후 정책을 소급해 적립하지 않는다.

## 단건 지급·정정과 조회

고객 상세에서 `/admin/customers/[userId]/store-credits`로 이동한다. 잔액의 사용 가능·주문 사용 대기·회수 예정 금액과 전체 원장 건수/페이지를 확인한 후 조정한다.

- 지급은 금액·정확한 만료 일시(KST)·고객에게 표시할 사유가 필요하다. 만료 일시는 저장 시점의 정책 유효기간 안이어야 한다.
- 차감 정정은 사용 가능한 금액 안에서만 할 수 있다. 이미 주문에 선점한 금액이나 만료 금액은 차감하지 않는다.
- 금액과 사유가 같은 요청의 재시도는 같은 운영 요청 키를 사용한다. 성공 이후의 새 조정은 새 요청 키를 사용한다. 동일 키로 값을 바꾸면 충돌로 거절한다.
- 다른 작업으로 잔액이 바뀌면 저장을 거절하고 입력을 보존한다. 최신 이력을 다시 확인한 뒤 재입력한다. 고객에게 보일 사유에 내부 개인정보나 결제사 비밀을 넣지 않는다.

고객은 `/my/store-credits`에서 본인 잔액과 모든 이력을 30건씩 조회한다. 조회 실패는 0원으로 표시하지 않는다. 개별 지급과 정정의 사유·시각, 주문 선점·사용 확정·복원, 만료와 원적립 회수를 구별한다. 정책 비활성 시에도 기존 이력은 유지한다.

## 주문 금액과 결제 경계

기간 할인가로 품목 소계를 정한 뒤 대상 쿠폰 1장, 적립금 순서로 계산한다. 배송비 산정은 기존 기간 할인 후·쿠폰/적립금 사용 전 소계를 유지한다. 적립금은 쿠폰 이후 **굿즈 잔여 금액** 안에서만 사용하며, 배송비에는 사용할 수 없다. 기존 최소 유상 결제액 1,000원을 유지한다. 사용 요청이 현재 잔액·정책·금액 경계를 넘으면 조용히 줄이지 않고 주문 생성을 거절한다.

`orders.discount_total`은 쿠폰 할인, `orders.store_credit_total`은 적립금 사용 스냅샷이다. `orders.total = 품목 소계 + 배송비 - 쿠폰 할인 - 적립금 사용`이고, 결제 attempt·최종 payment·주문 조회와 엑셀은 이 금액을 따른다. 적립금의 사용 단위는 1원이다.

서비스 전용 `place_order_with_store_credits`가 사용자·checkout key·요청 금액을 멱등 보존하고 기존 주문 생성 RPC를 호출한다. 주문 core는 쿠폰 평가 이후, 총액 저장·무통장 결제 attempt 생성 이전에 `private.reserve_order_store_credits`를 호출한다. 예약판매 등 후속 core 교체도 이 순서를 보존해야 한다. 주문 시점의 옵션/가격/배송/쿠폰 재검증을 건너뛰는 별도 주문 작성 경로는 없다.

앱 주문서는 기대한 보유 쿠폰 번호를 받는 6인자 오버로드를 사용한다. 고객별 잠금 안에서 현재 선택과 기대값을 비교하므로 다른 탭의 선택 변경·해제가 있으면 적립금 예약 전에 중단한다. 이미 만들어진 주문의 재시도는 최초 쿠폰 사용 기록을 비교하고 기존 5인자 경로의 주소·결제수단·적립금 금액 검사로 이어진다. 5인자 경로는 기존 신뢰된 호출자와의 호환을 위해 유지하며, 두 경로 모두 service role 전용이다.

## 선점·확정·실패·환불

사용은 만료가 빠른 출처부터 선점한다. `pending`의 사용 대기 금액은 다른 주문에서 사용할 수 없다. 검증된 결제 finalizer가 주문을 `paid`로 바꿀 때 사용을 확정하며, 중복 callback은 원장을 다시 차감하지 않는다.

`unknown`·`needs_review` 등 결제 결과 불명 상태는 사용 선점을 유지한다. 결제 attempt의 `declined`만으로 아직 결제 가능한 주문을 임의 취소하지 않는다. 기존 무결제 취소·checkout 만료 또는 검증된 전액 취소/환불 finalizer가 **주문을 `canceled`로 종결할 때** 사용분을 한 번 복원한다. 결제사 취소 증거·기존 클레임 승인·필요한 출고지 회수 확인을 우회하지 않는다.

복원할 출처의 원 유효기간이 남아 있으면 그 기한을 유지한다. 원 유효기간이 지났으면 주문에 고정한 복원 유효기간을 적용한다. 명시적 0일은 복원 시에도 만료 상태다. 복원은 별도 lot로 남기며 원적립 출처를 유지한다. 정책 변경이나 재시도로 기존 기한을 연장하지 않는다.

## 거래확정 적립과 원적립 회수

거래확정(`done`)에서 주문의 할인 후 굿즈 금액(`total - shipping_fee`)을 기준으로 적립한다. 배송비·쿠폰 할인·사용한 적립금은 기준에 포함하지 않는다. 기준 금액이 0원이면 적립하지 않는다. 주문 당시 정책의 정률/정액과 상한을 적용하고 출처 주문당 한 번만 적립한다. 보유 상한 때문에 지급되지 않은 금액을 이후 소급 발급하지 않는다.

거래확정 뒤 하자 반품 등으로 주문이 전액 환불되면 그 주문의 원적립과 이를 복원한 출처를 함께 추적한다. 남은 금액은 회수하고 이미 사용·선점·상계한 금액은 회수 예정으로 남긴다. 지원하는 회수 방식은 관리자가 명시적으로 선택한 **이후 적립·복원 금액에서 상계**다. 해당 원적립을 쓴 다른 주문이 나중에 취소되면 아직 남은 회수 예정액부터 줄이고, 후속 적립으로 이미 상계한 부분만 실제 잔액으로 돌려준다. 고객에게 현금을 청구하거나 결제사 전액 환불액을 줄이지 않는다.

## 만료·잠금·감사

매분 `expire-store-credits` 작업이 만료 대상을 처리한다. 고객/관리자 조회와 지급·사용·복원 경계도 만료를 재확인하므로 cron 지연 때문에 만료 금액을 쓸 수 없다. 원장 행을 삭제하지 않고 만료 변동을 추가한다.

주문 처리의 잠금 순서는 기존 주문 잠금 이후 정책 공유 잠금·사용자 적립금 계정·출처 lot다. 계정 이후 다른 주문을 잠그지 않는다. 원적립 주문·사용자 UUID의 private 이력은 삭제 cascade FK를 두지 않으며, 주문으로의 역방향 FK 잠금도 발생시키지 않는다. 공개 원장은 본인 RLS 읽기만 허용하고 변경 RPC와 private 내부 테이블 직접 쓰기는 봉인한다. 정책·단건 조정은 운영 요청 원장과 `audit_log`, 주문 전이는 주문/출처별 적립금 원장을 남긴다.

## 검증

- `supabase/tests/store_credit_ledger.sql`: 정책 미설정·ACL·역할 변경·중복 지급·잔액 충돌·만료·정확한 전체 페이지 수.
- `supabase/tests/store_credit_checkout.sql`: 쿠폰 병용·배송비 제외·최소 유상금액·주문 재시도·검증된 결제 확정·전액 환불·만료 복원·무통장 안내·거래확정 적립.
- `supabase/tests/store_credit_earned_refund.sql`: 원적립을 이미 쓴 주문의 환불·후속 적립 상계·원사용 주문 환불·PG 환불액 불변.
- `supabase/tests/store_credit_concurrency.sh`: 중복 지급·동시 주문 사용·만료와 취소 복원 경합. `SUPABASE_DB_CONTAINER`로 작업 전용 DB를 명시해야 하며 기본 로컬 스택을 선택하지 않는다.

정책 설정·실제 운영 수치/증빙·운영자 인수와 production 활성화는 구현/합성 검증 통과와 별도로 확인한다.
