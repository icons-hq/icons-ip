# 지연 주문 고객 안내

영업 피드백 #494, US55~US57. 2026-09-11 승인된 채널은 앱 알림과 주문 이메일이다. 구현·합성 자료 검증의 승인은 production 활성화나 실제 고객 발송 승인이 아니다.

## 운영 동선

1. **발주·발송 → 발송 지연**에서 배송 건을 선택하고 **선택 주문 N건 고객 지연 안내**를 누른다. 일반 배송 건은 발주확인 후 3일 경과, 예약 배송 건은 현재 약속일의 KST 날짜 경과를 기준으로 한다.
2. 고객용 제목·내용을 직접 입력한다. 기존 내부 지연 사유는 자동 복사하지 않는다. 발송 예정일은 **확인 중**이 기본이다. 확정된 날짜를 안내할 때만 날짜를 입력한다. 이 입력은 주문의 예약 일정이나 내부 메모를 변경하지 않는다.
3. **대상·고객 문구 미리보기**에서 주문번호, 실제 구매자, 구매자 이메일, 안내 대상 배송 건, 최종 문구를 확인한다. 같은 주문의 배송 건 여러 개는 한 안내로 묶는다. 같은 구매자의 주문 여러 개에는 주문별로 앱 알림 1건과 이메일 1건을 요청한다. 배송지 수취인에게 임의로 보내지 않는다.
4. 이메일 준비 상태가 정상일 때 **앱 알림·이메일 발송 요청**을 누른다. 미리보기는 1시간 유효하다. 그 사이 구매자·이메일·내부 지연 메모·배송 건·주문 상태가 달라지거나 고객에게 확인한 날짜가 지나면 새 미리보기가 필요하다. 한 대상이 달라도 최초 요청 전체를 거절해 일부 앱 알림만 먼저 발행하지 않는다.
5. **안내 결과 새로고침**으로 주문별 두 채널 결과를 확인한다. 페이지를 떠난 뒤에는 지연 탭의 **고객 지연 안내 이력·결과**에서 최근 30개 안내·미리보기를 다시 연다. 지연 주문이 목록에서 사라져도 이력은 남는다.
6. 재시도 가능 표시가 있는 경우 **실패한 이메일만 재시도**한다. 이미 발행한 앱 알림과 공급자가 접수한 이메일은 재발송하지 않는다. 미리보기 저장 응답이 유실되면 **같은 미리보기 접수 확인**을 사용한다.

예약 재고 미할당·퀵·방문수령 배송 건도 지연 안내 대상으로 선택할 수 있다. 기존 출고지시 내보내기 적격성은 유지하므로 고객 안내 선택만으로 출고가 가능해지지 않는다. 일부 출고 주문은 선택한 미발송 배송 건만 안내에 표시한다. 결제 대기·발송 완료·취소·처리 중인 클레임은 대상이 아니다.

## 결과 읽기

| 표시 | 뜻과 다음 행동 |
|---|---|
| 미요청 | 저장된 미리보기다. 고객에게 전달하지 않았다. |
| 앱 알림 발송 | 주문 구매자의 알림함에 DB 트랜잭션으로 발행했다. |
| 이메일 발송 대기 / 처리 중 | 내구성 있는 작업 대기열에 있으며 완료가 아니다. |
| 공급자 접수 | 공급자가 요청을 접수했다. 수신함 도착 확인은 아니다. |
| 발송 / 수신 서버 전달 | 기존 서명 검증 웹훅이 확인한 단계다. 고객의 읽음 확인이 아니다. |
| 실패 · 재시도 가능 | 설정 미완료 또는 일시적인 공급자 거절이다. 같은 요청 키로 실패 이메일만 다시 처리한다. |
| 결과 불명 | 접수 후 연결이 끊겼을 수 있다. 같은 요청 키를 이용한 자동 복구 외에 새 메시지를 보내지 않는다. 안전 창 만료나 대상 변경이면 운영 검토로 멈춘다. |
| 발송 제외 | 구매자 이메일 누락·잘못된 형식, 발송 전 대상 변경, 공급자 제외 처리다. 이미 보낸 앱 알림은 회수하지 않는다. |

기존 dispatcher는 영구 거절 응답도 needs_review로 보존한다. 화면에는 결과 불명과 자동 처리 중단 안내가 표시되며, 공급자에서 원인을 확인하기 전 새 메시지나 새 멱등 키로 우회하지 않는다.

확정 예정일은 KST 기준으로 발송 시점에도 지나지 않아야 한다. 진행 중인 클레임·배송 전이·수신 이메일 변경이 발견되면 내용을 수정해 재전송하지 않는다. 공급자 접수 이력이 이미 있으면 접수 결과를 보존한다. 이미 시도한 요청의 대상이 변하면 결과 불명으로 보존하고, 시도 전이면 발송 제외한다.

## 활성화와 설정

- `private.order_delay_notice_delivery_control.enabled`는 기본 `false`다. 일반 Data API 사용자·staff·service role의 직접 조회/변경과 공개 활성화 RPC는 없다. 별도 승인된 운영 변경으로만 활성화한다.
- 주문 지연 안내는 이 전용 gate를 사용한다. `private.email_dispatch_control`의 Auth Hook·탈퇴 알림 전환 gate와 5개 readiness는 변경하지 않는다. 지연 안내 활성화를 위해 해당 readiness를 사실과 다르게 바꾸지 않는다.
- 기존 `emailDispatcherFromEnvironment()`의 service role, `EMAIL_DISPATCH_HMAC_SECRET` 설정 검사와 Resend provider를 재사용한다. `RESEND_API_KEY`·`RESEND_FROM`·`RESEND_REPLY_TO`·`RESEND_API_ENDPOINT`가 모두 비어 있으면 기존 앱의 `EMAIL_PROVIDER_API_KEY`·`EMAIL_FROM`·`EMAIL_REPLY_TO`를 그대로 사용한다. 기존 endpoint는 미설정 또는 `https://api.resend.com/emails`여야 한다. 전용 설정을 하나라도 입력했다면 `RESEND_API_KEY`·`RESEND_FROM` 두 값이 모두 필요하며 기존 계정과 섞지 않는다. webhook 수신과 서명 검증은 기존 `/api/webhooks/resend` 경로를 따른다. 환경 미구성 또는 전용 gate가 꺼져 있으면 화면에서 이유를 표시하고 두 채널 최초 요청을 막는다.
- 작업 cron은 `GET /api/cron/order-delay-notices`, 기존 `CRON_SECRET` 인증, 매분, 최대 25건 claim·5건 병렬 발송이다. 요청에는 수신자·문구를 받지 않으며 응답은 집계만 반환한다. 일부 실패·결과 불명·저장 실패는 HTTP 503으로 관측한다.
- Preview·CI에는 실 provider key와 고객 자료를 넣지 않는다. 검증은 합성 주문·계정과 `RESEND_API_ENDPOINT`의 로컬 fake HTTP provider만 사용한다. gate 변경도 격리된 테스트 DB에서만 한다.
- 실제 활성화 전 승인된 발신자·provider/webhook 설정, 보존·접근·파기 운영 절차, HMAC 키 유지 정책을 확인한다. HMAC 값의 임의 회전은 기존 source/recipient/provider digest와 멱등 fence를 끊으므로 기존 dispatcher의 키 회전 제한을 그대로 따른다.

## 저장·멱등·재시도 계약

`private.order_delay_notices`가 전용 고객 문구·예정일·행위자·요청 UUID를, `private.order_delay_notice_targets`가 주문당 실제 구매자·이메일·배송 건·읽은 버전·채널 결과·작업 lease를 고정한다. 고객은 기존 본인 `notifications`만 읽는다. staff도 전용 RPC로만 미리보기·결과를 읽고 요청한다. 사용자 입력 수신 주소로 대상을 바꾸는 경로는 없다.

최초 요청은 앱 알림 발행·이메일 작업 등록·감사를 한 트랜잭션에서 확정한다. 같은 미리보기 UUID의 요청 재실행은 기존 영수증을 반환한다. 이메일 source는 대상 UUID이고 기존 HMAC digest, intent/fence, `email/<intent UUID>` 공급자 멱등키를 계속 사용한다. 공급자 접수 기록의 응답이 유실되면 기존 정확한 claim 복구 RPC가 저장된 접수를 보존한다. 접수 전 timeout은 같은 공급자 키로만 재처리한다.

기존 공급자 멱등 유효기간은 최초 시도부터 24시간이며 만료 5분 전에는 새로운 호출을 멈춘다. 작업 lease는 10분이다. 동시 cron은 `SKIP LOCKED`로 다른 작업을 선택하며 오래된 worker의 claim token으로 결과를 덮어쓸 수 없다. 작업 시도 100회 상한에 도달하면 결과 불명·운영 검토로 멈춘다. 실패 재시도는 기존 키와 고정된 내용을 유지하고 발송된 채널을 초기화하지 않는다.

고객 문구와 이메일 복사본은 민원·안내 사실 확인에 필요한 주문 운영 기록으로 private에 보존한다. 감사 로그에는 대상 ID, 건수, 채널, 결과 코드만 남기며 원문 이메일·고객 문구·내부 지연 사유를 복제하지 않는다. **정확한 TTL이나 자동 파기 승인은 이 변경이 새로 정하지 않는다.** 기존 [트랜잭션 이메일](../transactional-email.md)의 승인된 cutoff·개인정보 보존 절차를 따른다. 일반 Auth 이메일 파기 함수는 주문 지연 안내와 탈퇴 안내를 제외해 운영 기록이나 재발송 방지 fence를 먼저 없애지 않는다. 주문 운영 기록을 실제 파기할 때는 안내 본문·수신자 snapshot·앱 알림·intent/fence의 연계 수명도 함께 검토해야 한다.

신규 필드는 주문 고객 안내 전용으로 상품 편집 초안·상품 공개 상세·상품 엑셀과 연결하지 않는다. 고객 공개 소비자는 본인 앱 알림과 해당 주문 이메일이다.

## 검증

- `supabase/tests/order_delay_notices.sql`: 주문당 수신자·내부 메모 분리, 요청 replay, 권한, lease, failed only retry, 변경된 이메일과 부적격 주문 거절.
- `supabase/tests/order_delay_notice_recovery.sql`: 전용 gate 격리, 공급자 접수·응답 유실, 수신자 변경 후 제외/불명, 24시간 만료와 재시도 제한.
- `supabase/tests/order_delay_notices_concurrency.sh`: 격리된 테스트 DB에서 동시 요청·동시 worker·오래된 claim 결과 거절.
- `app/admin/order-delay-actions.test.ts`, `lib/email/order-delay-jobs.server.test.ts`, cron route 및 배송 콘솔 테스트: 권한·불완전 응답·설정 미완료·로컬 fake provider 계약·이메일 재시도·기존 출고 선택 보존.
