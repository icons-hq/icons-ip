# 매니저 권한 전환과 이메일 초대

정본 결정은 [ADR-0019](../adr/0019-store-manager-capabilities.md), 업무별 권한은 `lib/admin/access.ts`와 `private.operator_role_capabilities()`를 따른다. 운영 배포·DB 적용·최초 역할 활성화는 명시적으로 승인된 범위에서 수행한다.

## 최초 전환

1. 앱과 `20261013040906` 이후 권한·lifecycle·초대 migration을 같은 배포 범위로 준비한다. migration 자체는 전역 역할 설정을 활성화하지 않는다.
2. 기존 관리자가 판매자 정보 → 매니저 관리에서 모든 기존 운영자를 확인한다. migration 시점의 운영자 명단만 전환 전 호환 권한을 유지하며 이후 raw `staff/admin`을 추가해도 자동 권한은 생기지 않는다.
3. 이용 중인 기존 관리자 한 명을 통합 매니저로 **명시적으로 선택**한다. 나머지 모든 운영자는 역할 또는 권한 회수를 지정한다. 설정하는 본인은 통합 매니저 또는 계정 주매니저로 남겨야 하며 정지 계정은 회수한다.
4. 확인 후 역할 적용을 실행하고 목록·본인 역할·각 역할의 접근 범위를 다시 읽는다. 명시적으로 지정한 역할은 전역 활성화 전에도 즉시 제한되며, 활성화 후 역할 없는 계정의 어드민 접근은 차단된다.

활성화와 역할 변경은 전체 권한 버전, 대상 역할 버전, 요청 ID를 검사한다. 다른 관리자가 먼저 저장했으면 최신 목록을 확인하며, 통신 결과가 불명확하면 화면의 **같은 요청으로 결과 확인**을 사용한다. 불명확한 요청을 새 ID로 복제하지 않는다.

## 역할 변경·회수·승계

- 통합 매니저와 계정 주매니저만 다른 매니저를 관리한다. 본인과 통합 매니저의 역할은 일반 변경·회수 대상이 아니다.
- 계정 주매니저는 다른 주매니저를 직접 회수할 수 없다. 업무 범위에 맞는 다른 역할로 변경한 다음 회수한다.
- 통합 매니저만 이용 중인 다른 계정 주매니저에게 승계한다. 한 트랜잭션에서 기존 소유자는 주매니저, 대상자는 통합 매니저가 된다. 통합 매니저는 정확히 한 명이며, 승계 전 정지·일반회원 전환·탈퇴는 차단된다.
- 담당업무는 표시용이다. 대표는 통합 매니저에 고정되며 다른 업무 표시는 접근 권한을 추가하지 않는다.
- 회수 후 기존 로그인 세션도 다음 서버 요청부터 제한된다. 이미 승인·완료된 외부 결제 처리를 반영하는 수신 경로는 기존 요청·실행자·공급자 증거에 결속된 완료 작업만 허용한다.

## 이메일 초대

초대 생성 → 이메일 발송 접수/전달 → 수락은 각각 별도 상태다. 한 번에 1~10명을 초대하며 통합 매니저를 제외한 매니저와 유효한 수락 대기 초대를 합해 최대 1,000명이다. 초대는 생성 후 7일 동안 유효하다.

이메일 발송에는 기존 `EMAIL_DISPATCH_HMAC_SECRET`, Resend 공급자 설정, 이메일 발송 제어를 사용한다. 이 기능이 공급자나 전역 발송 제어를 자동으로 활성화하지 않는다. 설정 누락·발송 비활성·불확실한 공급자 결과도 초대 등록 성공과 구분해 화면에 표시한다.

- **발송 재시도:** 동일 초대와 기존 outbox를 이용한다. 공급자 접수·전달은 기존 멱등 dispatcher의 상태를 따른다.
- **재초대:** 기존과 같은 이메일을 다시 입력하고 새 초대 ID·링크를 발급한다. 이전 링크는 무효가 된다. 수락 완료된 초대는 재초대하지 않고 현재 매니저 권한을 관리한다.
- **초대 취소:** 아직 수락하지 않은 초대를 막는다. 이미 보낸 이메일은 회수하지 않는다.
- **초대자 권한 회수:** 초대자가 매니저 관리 권한을 잃으면 그 사람이 만든 수락 대기 초대가 취소된다. 발송 준비와 실제 outbox claim에서도 현재 권한·초대 상태·만료를 검사한다. 이미 받은 공급자 처리 결과는 일치하는 claim에만 완료 기록한다.

수신자는 초대받은 주소와 일치하는 **인증된 Auth 이메일**로 로그인한다. 수정 가능한 `profiles.email`로 소유권을 판단하지 않는다. 수락은 동일 계정에 한 번만 역할을 적용하며, 이미 수락한 링크를 재사용해도 이후 회수한 권한을 복구하지 않는다.

## 비밀값과 기록

초대 토큰은 서버에서 HMAC으로 만들며 DB에는 SHA-256 해시만 저장한다. 원본 토큰은 이메일의 `/manager-invitation#token=…` fragment에만 넣고 관리자 화면·outbox·감사 로그에 노출하지 않는다. 수락 화면은 즉시 fragment를 제거하고 로그인·가입 복귀에는 고정 경로만 쓴다. 같은 탭의 sessionStorage로 로그인 사이에 전달하고 성공 시 삭제한다. 브라우저가 저장을 막거나 새 탭으로 이동한 경우 이메일 링크를 다시 연다.

HMAC 키가 바뀌어 기존 미발송 초대의 해시와 토큰이 일치하지 않으면 자동으로 다른 링크를 보내지 않는다. 화면의 재초대를 통해 새 링크를 만든다. 이미 보낸 링크는 저장된 해시를 기준으로 원래 만료일까지 검증한다. 개인정보 원문은 private 초대 원장에만 보관하며 목록에는 이메일을 가려 표시한다.

## 검증

운영 수신자에게 시험 메일을 보내지 않는다. 격리 DB에서 `operator_manager_lifecycle.sql`, `operator_email_invitations.sql`, 권한 coverage 테스트를 실행하고 fake provider로 생성·접수·실패·중복·비활성 상태를 확인한다. 대표 지정, 역할별 메뉴/직접 URL/RPC 차단, 권한 회수 후 기존 세션, 초대 취소·만료·재초대·인증 이메일 불일치, 수락 경쟁과 인원 제한을 각각 검증한다.

초대 동시성 검증은 `SUPABASE_DB_CONTAINER=<격리 컨테이너> OPERATOR_INVITATION_TEST_SCOPE=isolated-local bash supabase/tests/operator_email_invitation_concurrency.sh`로 실행한다. CI의 scope 값은 `ci`다. 스크립트는 원본 DB를 덤프해 별도 DB로 복제하고, cron 작업을 제외한 복제본에서만 역할 fixture를 구성한 뒤 종료 시 제거한다. Python 테스트를 기존 `postgres` DB에 직접 실행하지 않는다.
