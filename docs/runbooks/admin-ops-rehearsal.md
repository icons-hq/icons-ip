# 운영 콘솔 S1~S5 리허설

정본: [ADR-0014](../adr/0014-admin-console-redesign.md), [스펙 #437](https://github.com/icons-hq/icons-ip/issues/437), [리허설 #434](https://github.com/icons-hq/icons-ip/issues/434). 환경·계정·배포 경계는 [staging.md](staging.md)를 따른다.

**오픈 게이트는 실제 운영팀의 스테이징 수행 결과다.** 자동 테스트, SQL 시드 검증, 에이전트 브라우저 연습은 기술 검증으로 기록한다. 이를 운영팀 리허설 통과로 대체하지 않는다. 2026-09-08 현재 실제 운영팀 수행 기록은 없으며, hosted 고정 URL도 배포 대기다.

## 합격 기준과 담당

## 시작 전 기록

1. 실행 종류를 **운영팀 리허설** 또는 **에이전트 기술 연습**으로 선택한다. 운영팀 수행 전 워크플로를 익히는 연습은 본 측정과 분리한다.
2. 환경 URL, 앱 commit SHA, migration 최신 버전, 일시·시간대, 참여자 역할, 브라우저·화면 크기를 기록한다. 로컬 `3300/55421/55432`는 임시 기술 검증 환경이고 hosted staging 완료 증거가 아니다.
3. production·shared preview가 아닌 승인된 격리 staging인지 확인한다. 기존 연습 DB를 reset하거나 일반 `supabase/seed.sql`로 덮어쓰지 않는다. 신규 결제 gate와 실제 메일 발송은 닫힌 상태를 유지한다.
4. `supabase/seeds/admin-ops-staging.sql`은 고정 demo 상품 20종·옵션, 주문 120건·배송 건, 문의 10건의 **누락 행만** 채운다. 새 DB의 첫 100주문은 `paid`이며 나머지 20건은 상태 예시다. 기존 120건의 상태·금액·답변·재고·배송 정보는 그대로 보존한다.
5. 실제 창고·택배사에 어떤 연습 파일도 보내지 않는다. 합성 주문에는 실제 PG 승인 증거가 없으므로 결제 취소 성공의 근거로 쓰지 않는다. 실제 WMS 양식 검증은 #429/#177의 제공 자료에 따로 결속한다.

### 재현 파일 만들기

상품 목록의 **엑셀 등록·수정 → 양식 내려받기**에서 현재 XLSX를 받는다. 다음 명령은 로컬 파일만 만들며 DB에 연결하지 않는다. Node 프로젝트 의존성 설치가 선행돼야 한다.

```sh
node scripts/admin-rehearsal-workbooks.mjs \
  --run ops-20260908-s1 \
  --ip demo-maple-placeholder \
  --origin gimpo \
  --template /absolute/path/icons-goods-template.xlsx \
  --out /absolute/path/rehearsal-s1

node scripts/admin-rehearsal-orders.mjs \
  --run ops-20260908-s3 \
  --origin gimpo \
  --out /absolute/path/rehearsal-s3
```

첫 명령은 30상품·60옵션의 `goods-draft.xlsx`, 마지막 상품의 재고 두 칸을 잘못 넣은 `goods-draft-errors.xlsx`, 공개 검증용 `goods-publish.xlsx`, `goods-images.zip`을 만든다. 대표 이미지는 코드로 만든 96px 합성 색상표이며 권리 확보된 판매 에셋으로 취급하지 않는다. 고시·연락처도 연습 표식의 가상 값이다. 원본 템플릿의 열 이름으로 입력하므로 실행 시점 양식과 맞지 않으면 중단한다. 바이너리는 Git에 넣지 않고 이 스크립트와 현재 다운로드 양식으로 재생성한다.

두 번째 명령은 `orders-100.sql`과 `orders-manifest.json`을 만든다. 제품 소유자/환경 담당자가 SQL을 검토한 뒤, `staging.md`의 검증된 격리 연결에서 `app.staging_seed_enabled=admin-ops-v1` 세션으로 실행한다. 같은 `run`은 기존 주문·옵션·배송비·상태·고객 수정값을 보존한다. 다음 리허설에 새 `paid` 100건이 필요하면 기존 상태를 초기화하지 말고 새 `run` 이름을 사용한다. 검색어는 manifest의 `query`다. 이 고객은 비밀번호 없는 합성 계정이고 운영자 계정과 분리된다.

로컬 기술 검증용 실행 예시는 연결 포트를 명시한다. 다른 환경에는 이 로컬 포트를 그대로 복사하지 않는다.

```sh
PGHOST=127.0.0.1 PGPORT=55433 PGUSER=postgres PGDATABASE=postgres \
  PSQL_BIN=/absolute/path/psql node supabase/tests/admin_ops_rehearsal.mjs
```

비밀번호는 환경 담당자의 비밀 저장소/연결 환경에서 제공한다. 명령 예시나 출력에 넣지 않는다. 이 검증은 전체 트랜잭션을 rollback하며 100주문·100배송 건, 재실행 시 금액·상태·정책 스냅샷·프로필 보존을 검사한다.

## 공통 측정 방법

- 로그인·테스트 파일 준비·측정 대상 조회는 준비 단계에 기록한다. 시나리오의 시작 상태를 캡처한 뒤 초시계를 켜고, 첫 업무 동작부터 마지막 성공 상태 확인까지 잰다.
- 포인터 클릭과 동일 기능의 키보드 활성화는 각각 1회로 센다. 파일 선택 창의 선택·열기, 확인 대화상자도 포함한다. 스크롤·문자 입력은 클릭 수에서 제외하지만 소요 시간에는 포함한다. 키보드로 버튼을 눌렀다는 이유로 0회로 줄이지 않는다.
- 서버 검증·이미지 대기·실패 행 수정·재시도 시간은 측정 시간에 포함한다. 외부 택배사의 실제 운송 대기 대신 준비된 합성 운송장 파일을 사용했다면 그 사실을 기록한다.
- 관찰자는 클릭마다 번호·버튼·결과를 적는다. 실행자에게 다음 버튼을 알려줬거나 개발자가 SQL/코드로 중간 상태를 바꿨다면 도움 내용을 기록하고 독립 수행 성공으로 표시하지 않는다.
- 실패 후 결과를 지우지 않는다. 원래 측정은 실패로 남기고 수정 후 새 회차를 작성한다. 화면 녹화는 비밀번호 입력을 시작하기 전에 멈추거나 로그인 후부터 시작한다.

## S1 — 상품 30종 초안·검수·공개

시작 상태: 상품 목록, 선택 0건. 비보관 IP와 사용 중인 출고지, 현재 양식으로 만든 30상품·60옵션 및 이미지 ZIP이 준비돼 있다. 공개 표면까지 검증할 IP는 공개 상태여야 한다.

1. **엑셀 등록·수정**을 열고 `goods-draft-errors.xlsx`와 ZIP을 올려 **파일 검증**한다.
2. 미리보기에서 신규 29상품과 오류 1상품/2행, 원래 행 번호와 재고 오류를 확인한다. 확인 전에는 상품이 저장되지 않는지 확인한다.
3. 검증한 상품을 적용한다. 이미지 검증 대기를 포함해 29상품·58옵션 성공을 확인한다. 오류 상품은 저장되지 않아야 한다.
4. **실패 행 내려받기**로 받은 파일에서 오류 재고 두 칸만 `10`으로 고친다. 그 2행 파일과 원래 ZIP만 다시 올려 남은 1상품·2옵션을 등록한다. 성공한 29상품을 다시 등록하지 않는다.
5. 목록에서 run 상품코드로 검색해 30상품이 모두 초안인지 확인한다. 옵션의 이름·판매가·재고, 대표 이미지, 고시정보, 출고지를 검수한다.
6. 현재 검색 결과를 **엑셀 내보내기**로 내려받는다. 파일을 그대로 올려 **변경 없음 30상품**을 확인한다. 이 단계는 값 보존 확인이며 추가 상품을 만들면 실패다.
7. 내보낸 파일의 게시 상태만 모두 `공개`로 바꿔 다시 검증·적용한다. 실제 저장된 이미지 URL을 유지한다. 공개 전환 경고와 필수 정보 검증을 확인한다. 준비된 `goods-publish.xlsx`를 사용했다면 이미지 재검증 시간도 포함한다.
8. 목록의 공개 30상품, 각 상품 옵션 2개, 대표 상품의 공개 상세를 확인하고 시간을 멈춘다. **30분 이하**, 중복 생성 0, 실패 행 재시도 성공이 모두 필요하다.

기록: 시작/종료 시각, 29+1/30 상품 수, 58+2/60 옵션 수, 최초 실패 행, 재업로드 행 수, 변경 없음 결과, 공개 확인 링크, 총 시간. 서버 500행 처리 벤치마크는 이 사람 측정 시간을 대체하지 않는다.

## S2 — IP 이미지 실패와 입력 복구

시작 상태: 새 IP 폼. 실행자가 제목·식별자·소개·분류·정렬 관련 값을 입력하고 관찰자가 입력값 표를 작성한다.

1. 지원하지 않는 확장자 또는 제한을 넘는 연습 이미지를 선택해 업로드 실패를 만든다. 오류가 보이는 상태에서 다른 입력이 그대로인지 대조한다.
2. 서버 검증 오류도 한 번 만든다. 오류 필드 외 입력이 보존되고 서버 오류가 복구 배너보다 우선하는지 확인한다.
3. 안전한 텍스트를 더 입력하고 자동 저장 표시를 확인한다. 새로고침한 뒤 **저장되지 않은 입력 복구**를 눌러 내용을 복구한다. 이미지 파일 자체를 복구했다고 기록하지 않는다.
4. 유효한 이미지로 바꾸고 저장한다. 성공 후 같은 폼을 다시 열어 오래된 복구 제안이 남지 않는지 확인한다.

판정: 실패 직전과 직후의 의도한 입력값 차이 **0건**. 복구하지 않기로 선택한 값, 보안상 저장 대상이 아닌 파일/연락처 등은 값 보존 결과와 분리한다. 다른 계정이나 다른 IP의 저장 내용이 나오면 즉시 실패로 기록한다.

## S3 — 주문 100건 출고

시작 상태: manifest 검색어로 조회한 새 `paid` 주문 100건, 선택 0건. 담당자는 해당 run과 출고지를 확인한다. 합성 운송장 입력 파일을 준비할 담당자와 실제 WMS 양식 미확인 여부도 기록한다.

1. 100건을 선택해 **발주확인**을 일괄 처리한다. 대상·성공·실패 수를 기록한다. 페이지마다 반복 선택해야 했다면 그 클릭도 모두 센다.
2. 성공한 주문의 선택이 유지된 발송 대기 화면에서 출고지시 파일을 내려받는다. 검색 조건도 유지돼야 한다. 상품코드·옵션코드·배송 건 번호·받는 사람·출고지와 총 행 수를 확인한다. 실제 창고에는 보내지 않는다.
3. 내부 운송장 양식의 배송 건 번호에 합성 택배사/운송장을 매핑해 업로드한다. 모든 행이 성공하고 메일 대기열 경고가 없으면 같은 검색 조건의 배송중 화면으로 이동하며 등록 건수를 표시한다. 실패·경고가 있으면 남아 있는 결과에서 원인과 행을 확인한다. 실제 WMS 회신 파일을 사용하지 않았다면 “합성 회신”으로 기록한다.
4. 해당 배송 건 100건을 배송완료로 처리한다. 주문의 배송 상태와 배송 건 상태를 함께 확인한다. 출고지가 여러 개라면 일부 배송만 완료된 주문이 전체 완료로 표시되지 않는지도 별도 확인한다.
5. 클릭 집계를 닫는다. **발주확인부터 배송완료까지 10회 이하**, 처리 대상 누락/중복 0이 기준이다. 11회 이상이면 기능이 작동해도 이 시나리오는 실패다.

기록: 준비 조회 조건, 100주문/배송 건 수, 출고지별 파일명·행 수, 업로드 결과, 클릭 이벤트별 목록, 총 클릭·시간, 최종 상태. 실제 WMS 원본 대조 완료 여부와 hosted 미배포는 별도 미완료 항목으로 남긴다. 현재 사용자가 제공한 WMS 원본을 대조 중이며, 아래 S3 기술 연습에서는 그 파일을 사용하지 않았다.

## S4 — 문의 화면에서 이력 확인·답변

시작 상태: 답변하지 않은 demo 문의 1건. 연결 주문·고객이 정확한 레코드인지 미리 대조한다.

1. 문의 상세를 열고 연결 주문 요약·결제·배송 건·클레임 이력을 같은 화면 안에서 확인한다. 다른 주문이나 첫 목록 행으로 대체되면 실패다.
2. 내부 메모를 남기고 고객에게 노출되지 않는지 확인한다. 담당자를 배정하거나 재배정하고 답변 초안을 작성한다.
3. 문의 화면을 떠나지 않고 이력에 근거한 답변을 저장한다. 작성자 표시명·담당자·답변 상태와 고객 화면의 공개 답변을 확인한다.
4. 문의 화면을 이탈한 횟수, 불필요하게 새로 연 페이지 수, 잘못 연결된 식별자 수를 기록한다. **화면 이동 0**, 정확한 연결과 답변 저장이 기준이다.

합성 시드의 실제 PG 승인 원장·클레임은 비어 있을 수 있다. “이력 없음” 표시를 확인한 결과와 실제 원장이 있는 주문을 확인한 결과를 구분한다. 비어 있는 자료를 실결제/클레임 검증 완료로 쓰지 않는다. 필요한 비어 있지 않은 이력은 승인된 테스트 결제·클레임 시나리오로 준비하고, production 데이터를 복제하지 않는다.

## S5 — 설정을 배포 없이 변경

시작 상태: admin 계정의 설정 화면, staff 계정의 읽기 화면. 현재 배포 SHA와 배송비·무료 기준·택배사·CS 연락처 원래 값을 기록한다.

1. admin이 출고지 기본 배송비와 무료 배송 기준을 연습값으로 바꾼다. 화면 재조회와 감사 이력에서 저장자·변경값을 확인한다.
2. 해당 출고지 기본 택배사와 운영 연락처를 연습값으로 바꾼다. 존재하는 택배사만 사용하고 실제 업무 연락처로 오인될 값은 넣지 않는다.
3. 공개 상품 배송 안내·장바구니/결제 견적·법정 배송 안내·CS 표시를 확인한다. 변경 전에 만든 주문의 금액과 배송 정책 스냅샷은 그대로여야 한다.
4. staff가 설정을 읽을 수 있고 admin 전용 저장은 수행할 수 없는지 확인한다. 브라우저 UI 숨김만으로 권한 검증을 끝내지 않는다.
5. 앱 SHA가 바뀌지 않았고 배포 작업이 없었음을 확인한다. 측정 후 원래 설정으로 복구하고 복구 이력도 남긴다.

판정: 지정한 설정 4종 반영, 새 견적에 적용, 기존 주문 무변경, admin/staff 경계 유지, **배포 0회**.
