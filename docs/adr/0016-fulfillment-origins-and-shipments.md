# 출고지와 배송 건 — 굿즈별 출고지, 주문은 출고지별 배송 건으로 갈라지고 배송비는 배송 건마다 붙는다

- Status: accepted (2026-09-07)
- 관련: [ADR-0014](./0014-admin-console-redesign.md), [ADR-0007](./0007-bank-transfer-payments.md)

## 맥락

실물 굿즈는 두 곳에서 나간다. 김포 창고는 WMS와 한진택배 계약으로 운영되고, 남양주(서원)는 별도 회사라 출고지시를 엑셀로 받는다. 두 곳의 택배사·출고 방식·배송비가 다른데 코드에는 출고지 개념이 없고(`shipping_carriers` 시드 한진 1개, 배송비는 TS 상수+SQL 사본 3곳), 주문은 운송장 하나만 가진다. 2026-09-07 운영 리뷰는 출고지별 택배사·배송비·무료 배송 기준 설정을 요구했고, 사방넷·ERP 연동은 비용과 가치 문제로 후순위로 미뤘다.

## 결정

- **출고지**(`fulfillment_origins`)를 도입한다. 출고지는 기본 택배사, **배송 정책**(기본 배송비·무료 배송 기준·추가 요금 조건), 반품 주소, 출고 마감, 출고지시 내보내기 양식을 가진다. 초기 행은 김포와 남양주다.
- 굿즈마다 출고지를 하나 지정한다(필수, 기본값 김포).
- 서로 다른 출고지의 굿즈가 한 장바구니에 섞이는 것을 **허용**한다. 주문 하나는 출고지별 **배송 건**(shipment) N개로 갈라지고, 운송장과 배송비는 배송 건마다 붙는다. 배송비 판정은 배송 건의 할인 전 소계 기준으로 그 출고지의 배송 정책을 적용한다(기존 "할인 전 소계" 규칙 유지).
- 주문 상태 사다리의 `shipping`·`delivered`는 배송 건의 상태에서 파생한다. 일부만 발송·도착한 주문은 `shipping`이고, 모든 배송 건이 도착해야 `delivered`다. 배송 건별 `delivered_at`은 각각 보존하며, 기존 주문 단위 클레임이 읽는 `orders.delivered_at`은 **모두 배송 완료됐을 때의 가장 늦은 도착 시각**이다. 하나라도 미완료면 주문의 도착 시각은 null이다.
- 굿즈마다 **배송비 유형**을 둔다 — 출고지 정책 따름(배송 건 안에서 묶어 1회), 무료배송(합산 제외), 개별 배송비(그 굿즈만 따로 1회). 착불은 지원하지 않고 도서산간 추가요금은 #177 회신 전까지 보류한다.
- 사방넷·ERP·WMS API 연동은 이 결정의 범위 밖이다. 출고지시 내보내기 양식을 출고지 속성으로 두어 서원의 엑셀 양식과 WMS용 CSV가 같은 구조에 들어오게 한다.

## 검토한 대안

- **혼합 결제 차단** — 구현은 단순하지만 고객이 두 번 결제해야 하고, 굿즈가 어디서 나가는지 고객이 알 이유가 없다. 기각.
- **주문당 배송비 한 번** — 한 출고지가 상대 출고지의 배송비를 떠안고 정산이 불명확해진다. 네이버 스마트스토어의 판매자별 묶음배송 관행과도 어긋난다. 기각.

## 결과

- `orders.shipping_carrier`·운송장은 배송 건으로 이동한다. 운송장 일괄 등록의 키는 주문번호에서 배송 건으로 바뀌며, 발송 콘솔은 출고지별로 묶어 보여준다.
- `lib/shipping.ts`와 `place_order`·무통장·쿠폰 SQL의 배송비 상수는 출고지 설정을 읽는 함수 하나로 수렴한다.
- 무료 배송 기준을 출고지별로 두면 장바구니의 "얼마 더 담으면 무료배송" 안내도 출고지별로 갈라진다. 카트 UI가 이를 그룹으로 표시해야 한다.

## 현재 클레임 지원 범위와 한계 (2026-09-08)

- 클레임은 계속 **주문 단위**다. 출고지별 배송 건을 만들었다고 품목별/배송 건별 부분 취소·반품·환불을 지원하는 것은 아니다. 취소·반품 환불은 결제금액 전액(최초 배송비 포함)이고, 교환은 결제와 원주문 스냅샷을 유지한다.
- 반품·교환 접수는 주문이 `delivered` 또는 `done`일 때만 허용한다. 먼저 받은 배송 건만 독립적으로 반품·교환하는 접수는 없다. 기존 기한 함수는 주문의 도착 시각을 기준으로 일반 사유 7일·하자 사유 3개월을 비교하고, 승인 시에는 신청 시각으로 다시 확인한다. 이는 현재 구현 범위를 기록한 것이며 배송 건별 권리 판단이 구현됐다는 뜻이 아니다.
- 취소 접수는 기존과 같이 `shipping`·`delivered`·`done`에도 열려 있다. `cancel` 승인에는 회수·입고 단계가 없고, `return`·`exchange`만 `collecting` → `collected`를 거친다. 따라서 배송 중인 혼합 주문의 전액 취소가 출고지별 물리 회수를 검증한다고 볼 수 없다. 이 기존 한계는 배송 건 도입으로 해결되지 않았다.
- 교환 재출고는 주문의 모든 품목 수량을 대상으로 같은 굿즈 안의 옵션을 선택한다. 선택을 생략한 품목은 마지막 출고 옵션을 다시 보내며, 회수 옵션 복원과 재출고 옵션 차감을 원자적으로 처리한다. **클레임 하나의 재출고 택배사·운송장은 한 쌍**이므로 여러 출고지에서 각각 재출고하는 배송 건/부분 교환 흐름은 없다. 옵션 가격 차액의 추가 결제·부분 환급도 하지 않는다.
- `fulfillment_origins.return_address`는 운영자가 관리할 수 있지만 클레임 DTO나 배송 스냅샷에 복사하거나 반품 접수 시 자동 선택하지 않는다. 공개 반품 안내처럼 신청 확인 때 운영자가 반송 주소·방법을 개별 안내하는 범위다. 혼합 주문에 단일 반품 주소를 자동 지정하거나 출고지별 회수 주소를 자동 안내하는 기능은 아직 없다.

구현 근거는 [`order_claims_domain`](../../supabase/migrations/20260818120000_order_claims_domain.sql), [`option_stock_recovery_reshipment`](../../supabase/migrations/20260908034215_option_stock_recovery_reshipment.sql), [`order_shipments_contract`](../../supabase/migrations/20260908040020_order_shipments_contract.sql)다. 부분 클레임·출고지별 회수/재출고 모델 또는 접수 가능 상태를 바꾸려면 별도 계약과 검증이 필요하다.
