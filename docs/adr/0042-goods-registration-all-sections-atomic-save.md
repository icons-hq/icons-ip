# 상품 등록은 나머지 설정까지 한 트랜잭션에 저장하고, 새 상품도 저장 후 공개한다

- Status: accepted (2026-11-12) — 사용자 결정(원장 재작업 묶음 10·11, 아래 인용). main 머지와 운영 배포는 별도 승인.
- 관련: 10/27 회의 D6②(KC·예약판매 원자 저장, `admin_save_good_workspace`), [ADR-0036](./0036-goods-kc-self-declaration.md)(KC 자가 신고), [ADR-0037](./0037-goods-type-from-category.md)(유형 = 카테고리 연결값), [ADR-0040](./0040-instant-discount-period-ledger.md)(즉시할인 기간)

## 맥락

10/27 회의에서 MD는 "저장하기를 눌렀을 때 이 뒤에 KC 인증이나 이런 게 나오는데 … 상품 등록 단에서 그게 보여야"라고 했다(1027T-024). D6②가 KC·예약판매만 첫 저장에 넣었고, 나머지 18개 운영 항목은 저장 전에는 이름만 보여 저장한 뒤 다시 펼쳐 입력해야 했다. 9/1 회의의 "상품 하나 등록하는데 10번 클릭"(0901-008)에 대해서는 신규 상품이 저장한 뒤 판매 준비 카드에서 공개하는 2단계였다(#637 측정 17클릭).

사용자 결정 원문:

- 1027T-024(묶음 10): "저장 전 전부 입력 (Recommended)" — 원래=업계. 상태를 바꾸는 항목(재고 조정·옵션 사용·복사·보관)만 저장 뒤, 나머지는 첫 저장 때 한 번에(원자 저장 확대, 저장 RPC 재정의·계약 재등록). 크기 L, 돈·배송비·재고.
- 0901-008(묶음 11): 빈 화면에서 공개까지 10클릭 이내(E2E로 셈, 신규 등록에도 '저장 후 공개').

판단 위임 원칙(11/12)으로 오케스트레이터가 정한 것: '나머지' = 판매 방식·기간 할인·추가 구성·사은품·A/S·사이즈·복수구매 할인·착불·수량별 배송비·묶음그룹·정기배송·수령 방식·제작·목록 색상칩·매입단가, 관리자 전용 활성화는 서버가 권한을 다시 검사, 신규 '저장 후 공개'는 같은 요청에서 저장을 끝낸 뒤 공개를 시도하고 거절되면 저장은 남기고 이유를 보인다.

## 결정

1. **섹션 RPC를 새로 쓰지 않고 기존 저장 RPC를 같은 트랜잭션에서 그대로 부른다.** `admin_save_good_workspace`가 기본 저장·KC·예약판매·기타 인증 다음에 `private.save_goods_workspace_extra_sections`를 부르고, 이 함수가 섹션마다 저장된 상품의 독립 패널이 쓰는 RPC(`admin_set_goods_option_sale_mode`·`admin_save_goods_variant_purchase_cost`·`admin_save_goods_price_period`·`admin_save_goods_additional`·`admin_save_goods_benefit_content`·`admin_save_goods_after_sales_content`·`admin_save_goods_size_chart`·`admin_save_goods_listing_colors`·`admin_save_good_transaction_terms`·`admin_assign_shipping_charge_group`·`admin_save_goods_subscription_policy`·`admin_save_goods_fulfillment`·`admin_save_goods_production`)를 부른다. 권한(매입단가는 platform.manage+admin)·검증·서로 함께 쓸 수 없는 조합의 거절·감사 기록은 각 RPC가 지금처럼 한다. 판매 방식(랜덤 전환)은 섹션 순서의 맨 뒤에 저장해, 기존 전환 검사가 같은 요청의 정기배송·기간 할인을 모두 본다. 하나라도 실패하면 기본 입력까지 되돌리고, 실패는 `goods_workspace_section_failed:<섹션>:<원래 오류>`로 섹션을 담아 화면이 그 칸에 안내한다.
2. **새 상품의 첫 저장에서만 받는다.** 새 상품이라 기대 버전은 같은 트랜잭션의 지금 저장값이고, 섹션 작업 ID는 섹션마다 새로 만든다. 같은 등록 요청의 재시도는 래퍼 영수증이 저장 결과를 돌려주므로 섹션 RPC에 다시 들어가지 않는다. 저장된 상품의 섹션은 지금처럼 같은 자리의 독립 패널이 자기 버전(CAS)으로 따로 저장한다 — 래퍼는 `previous_id`가 있는 요청의 나머지 섹션을 거절한다.
3. **저장 후 공개는 저장을 끝낸 뒤의 별도 시도다.** `good.publish=true`(새 상품만)이면 기본 저장 체인은 초안으로 저장하고, 모든 섹션을 저장한 뒤 같은 요청에서 `admin_set_good_published`(기존 판정·KC·출고지 가드 그대로)를 시도한다. 공개가 거절되면 그 시도만(하위 트랜잭션) 되돌려 저장은 남기고, 거절 이유를 영수증 `publish`에 싣는다. 화면은 성공으로 알리지 않고 '저장했지만 공개하지 않았습니다'와 이유를 보이며, 공개는 판매 준비에서 이어서 한다.
4. **화면은 저장된 상품과 같은 자리·같은 부품이다.** 등록 화면의 나머지 설정은 저장된 상품의 '이어서 설정'과 같은 묶음·같은 순서·같은 id에 '상품과 함께 저장'으로 놓이고, 입력 부품은 독립 패널과 같은 것을 쓴다(값만 폼 키 밖 provider에 둔다). 저장 뒤에만 하는 일은 재고 조정·옵션 사용·복사·보관이다.

## 결과

- 등록 화면에서 저장 한 번으로 상품을 완성할 수 있고, 필수 입력과 KC를 채우면 저장 후 공개로 공개까지 한 번에 끝난다(측정: `scripts/goods-register-click-count.mjs`).
- 트레이드오프: 공개 거절은 '부분 성공'(저장은 됨, 공개는 안 됨)이다. 저장 전체를 되돌리는 대신 저장을 남기는 쪽을 골랐다 — 입력을 잃지 않고, 공개 조건은 판매 준비에서 그대로 다시 판정된다. 섹션 저장의 실패는 반대로 전체를 되돌린다(돈·배송비·재고 설정이 반만 들어간 상품을 만들지 않는다).
- 섹션 RPC를 재정의하지 않으므로 그 함수들의 운영자 계약 지문은 그대로다. 래퍼만 앵커 치환으로 고치고 같은 migration 끝에서 계약을 다시 적는다.
- 섹션 RPC가 바뀌면(인자·검증) 래퍼의 호출부도 함께 바꿔야 한다. `supabase/tests/goods_workspace_atomic_save.sql`의 T15b 절이 13개 섹션의 함께 저장·롤백·권한 재검사·영수증·공개 거절을 고정한다.
