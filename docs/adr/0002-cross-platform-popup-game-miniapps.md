# 온라인 팝업 게임요소를 첫파티 webview 미니앱으로 구현하고 웹·Expo 동일 경험을 구조로 보장한다

> 2026-08-13 superseded: #66과 #115를 현재 제품 범위에서 제거했다. 이 문서는 당시 검토한 전달 계층의 역사 기록이며 현행 구현 지시나 active acceptance criteria가 아니다. 웹 참여형 게임의 현재 경계는 루트 PRD·ARCHITECTURE와 ADR-0003·0004를 따른다.

온라인 팝업의 게임요소(마블 룰렛 등 참여형 게임·래플 추첨)를 **자기완결 웹 번들 = 게임, 호스트가 띄운다**는 첫파티 미니앱 아키텍처로 구현한다. 웹은 게임을 라우트로 직접 렌더하고, 추후 Expo 네이티브 앱은 같은 원격 URL을 `react-native-webview`로 로드한다. **하나의 번들, 두 호스트**여서 "웹·앱 동일 경험"이 규율이 아니라 구조로 보장된다. 게임 결과는 항상 서버 RPC가 결정하고 게임은 그 결과를 재생하는 **렌더러**이며, 호스트↔게임은 세션 주입과 네이티브 편의만 노출하는 **얇은 브리지** 하나로 연결한다.

이 결정은 [online-popup 4부작](../online-popup/02-prd.md)이 이미 스코핑한 게임·래플·무료 리워드 규제 설계 **위에** 얹는 전달·렌더링 계층 결정이다. 유료 가챠([0001](./0001-paid-digital-gacha.md)) vs 무료 리워드 피벗([03-roadmap §0](../online-popup/03-roadmap.md))의 상위 BM 결정은 **본 ADR 범위 밖**이다 — 어느 쪽이든 게임 결과는 서버가 정하고(`pull_gacha` 또는 `draw_raffle`/`grant_cards`) 게임은 렌더러라, 본 아키텍처는 BM 중립적으로 성립한다.

## Considered Options

- **네이티브 2번 빌드** — 웹은 React, Expo는 Skia/Reanimated로 게임을 각각 구현. 최상의 네이티브 감이지만 "동일 경험"이 규율에 의존하고, 게임 추가마다 앱 릴리스가 필요하며, 코스메틱 물리를 두 런타임에서 결정론적으로 이중 유지해야 한다(부동소수점·타임스텝 지옥). "다수·상시 추가"와 정면충돌.
- **토스급 풀 미니앱 플랫폼** — 샌드박스 런타임·외부 SDK·권한 API·원격 배포·심사 파이프라인. 외부 개발사가 게임을 올릴 때 정당화되지만, 게임을 **자체 제작**하는 현 단계에선 순수 과설계다([AGENTS.md](../../AGENTS.md) 과설계 금지, YAGNI).
- **첫파티 webview 미니앱 (채택)** — 게임 = 원격 URL 웹 번들. 웹은 라우트로, Expo는 webview로 같은 URL. 새 게임 = 웹 배포만 → 웹·앱 동시 반영, 앱 심사 없이. 첫파티 전용이라 신뢰 경계가 자기 자신이므로 샌드박스가 불필요하다.

## Consequences

- **결정론 이점**: 웹·Expo 둘 다 webview에서 **동일한 WASM/JS 번들**(box2d-wasm 등)을 실행하므로 물리 연출이 두 호스트에서 일치한다. 네이티브 재구현이었다면 감수했을 크로스런타임 물리 불일치를 임베딩 선택이 제거한다.
- **마블 룰렛의 두 역할 정합** (본 repo가 `둘 다`로 확정):
  - **참여형 게임** — 무과금 플레이, 보상은 `grant_cards`(무상 카드/도장/포인트). per-user, 공정성이 크리티컬하지 않으므로 **코스메틱 연출**로 충분(서버가 결과, 물리는 장식). commit-reveal 불필요.
  - **래플 추첨 시각화** — `draw_raffle`의 **commit-reveal 검증가능 결과**를 마블 연출로 표시. 정원 제한·당첨자 정가 결제(구매권). 선정은 검증가능, 연출은 코스메틱 — **선정과 연출은 다른 층**이다.
- **경품 경계 유지**: 무료 리워드 모델(01-report §5.1 규제 가드) 그대로. 참여형 게임 보상은 무상 카드/포인트, 래플 실물 굿즈는 당첨자 정가 결제. 카드에 닿는 유상 경로를 코드상 만들지 않는다.
- **실시간 회피**: 래플은 async 마감→commit-reveal을 유지한다([04-dev-spec §5](../online-popup/04-dev-spec.md)). "라이브 발표"는 예약 시각에 **검증된 결과를 공개·재생하는 연출**이지 실시간 물리 추첨이 아니다 → 기존 트래픽·동시성 설계를 깨지 않는다.
- **Apple App Store 4.7(2025.11 강화)**: webview로 동적 로드되는 HTML5/JS 미니게임이 전면 심사 대상이 됐다(WebKit 강제·연령 장치·네이티브 API 노출 제한·소프트웨어 색인). 게임을 **첫파티·앱 경험의 일부**로 프레이밍(미니앱 마켓이 아님)해 리스크를 낮추고, 원격 URL은 **첫파티 오리진 허용리스트**로만 로드한다. 앱 출시 시점에 재점검한다.
- **브리지 신뢰 경계**: 세션 주입은 호스트→webview 단방향 주입 경계를 신뢰하고, 게임은 서버 RPC(RLS 하)만 호출한다. 게임 코드에 결과·경품 결정 권한을 두지 않는다.
- **웹 우선, 앱은 계약으로 대비**: 게임은 V1에 **웹으로 먼저** 만들되 처음부터 브리지 계약(세션·서버 RPC·자기완결 번들) 뒤에서 구현한다. 그러면 Expo webview 임베딩(V2/V3)이 재작성 없이 얹힌다.
- **되돌리기 비용**: 모든 게임이 이 브리지 계약과 렌더러 규율에 묶이므로 사후 변경 비용이 크다 — 그래서 이 ADR로 기록한다.
