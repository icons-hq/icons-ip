# 자동 발주확인 — 매일 정한 시각에 그때까지 결제된 주문을 시스템이 발주확인한다

- Status: accepted (2026-10-27) — 사용자 확정 D1·D11, PR #608 merge
- 보완: [ADR-0017](./0017-order-claim-intake-and-origin-collections.md)의 직접 취소 경계("발주확인 전까지")는 그대로 두고, 발주확인을 일으키는 주체에 시스템을 더한다
- 관련: 2026-10-14 실사용 QA 회의 A1·S23·A15, [ADR-0018](./0018-staff-initiated-order-cancellation.md), [클레임 런북](../runbooks/order-claim-intake.md)

## 맥락

`paid → confirmed`는 운영자가 누르는 `admin_update_order_status`뿐이었다. 회의에서 "발주확인을 사람이 누르는 건 하루에 주문 10개씩 받겠다는 얘기"라는 지적이 나왔다. 발주확인을 하지 않은 주문은 발송지연 시계(`confirmed_at + 3일`)에도 잡히지 않는다.

발주확인은 고객 직접 취소를 닫는다(ADR-0017). 결제 직후 바로 확인하면 직접 취소와 발주확인 전 변심 취소 자동 승인이 사라지고 모든 취소가 문의·운영자 전액 취소로 몰린다. 운영 DB에는 사람이 처리 연습 중인 가주문이 있어, 기존 주문을 자동으로 바꾸는 기능은 켠 뒤 결제된 주문에만 적용해야 한다.

## 결정

- **실행 시각:** 매일 운영자가 정한 KST 시각(기본 16:30)에 그때까지 결제가 끝난 신규주문을 일괄 발주확인한다. 그 시각 뒤 결제는 다음 날 처리한다. 마감 전까지 고객 직접 취소는 열려 있다. 출고지별 `fulfillment_origins.cutoff`는 이번 결정에서 쓰지 않는다.
- **설정:** `private.auto_order_confirmation_settings`(켜짐, 실행 시각, 켠 시각 `enabled_at`, 수정자·시각, revision). 발주(주문)확인/발송관리 화면 상단에서 `sales.manage` 운영자가 바로 켜고 끄고 시각을 바꾼다(`admin_save_auto_order_confirmation`, 운영자 권한 레지스트리 등록, operation ID 재전송·revision 충돌·감사 `admin.auto_order_confirmation.settings`). 끌 때는 이어 가던 실행도 닫는다. 켤 때마다 `enabled_at`을 새로 잡는다. migration은 켜진 상태(16:30, `enabled_at = 적용 시각`)로 시작한다.
- **대상:** `paid` 주문 중 `enabled_at ≤ 결제완료 시각 ≤ 그날 마감`. 결제완료 시각은 주문이 처음 `paid`가 된 DB 시각을 `private.order_paid_marks`에 남긴 값이다(결제사 승인 시각이 아니다). 이 migration 이전에 `paid`가 된 주문은 기록이 없어 대상이 아니므로 운영 가주문은 사람이 처리한다. 화면의 결제일(결제사 승인·입금확인 증거)과 몇 초 다를 수 있다.
- **실행:** pg_cron 매분 틱(`auto-order-confirmation`)이 KST 오늘의 마감이 지났고 오늘 실행이 끝나지 않았으면 실행한다. 날짜별 실행 행 하나(`private.auto_order_confirmation_runs`)가 멱등 경계이며 컷오프·켠 시각·처리/제외 건수를 남긴다. 한 틱은 결제 시각 순으로 최대 200건을 골라 처리하고, 남으면 다음 틱이 같은 실행을 이어 간다. KST 자정을 넘긴 미완료 실행도 다음 틱이 저장된 마감·켠 시각으로 먼저 이어 처리해 닫는다. 한 실행 안에서 판정한 주문은 다시 보지 않는다(`private.auto_order_confirmation_outcomes`는 주문별 결과·사유를 남기는 로그이며 주문 FK를 두지 않는다 — FK 검사가 다른 트랜잭션의 주문 잠금을 기다리면 묶음 전체가 실패하기 때문이다). 실행을 닫을 때마다(완료·설정 변경·끄기) `system.order.auto_confirmation_run` 감사에 `closedBy`를 남긴다. 놓친 날은 다음 실행의 대상(이전 결제분 포함)으로 처리된다. 오늘 아직 돌지 않았으면 바꾼 시각에 돌고, 이미 돈 날은 시각을 바꿔도 다시 돌지 않는다. 켠 시각이 오늘 마감 뒤면 오늘은 돌지 않는다.
- **제외(신규주문에 남김, 사유 기록):** 진행 중인 취소·반품·교환 요청 또는 취소 원장이 있는 주문(`cancellation_in_progress` — 수동 발주확인도 거절하는 조건), 예약 품목 중 실재고 할당 전 품목이 있는 주문(`preorder_unallocated` — 출고할 수 없는데 고객 직접 취소만 일찍 닫히는 것을 막는다. 할당 뒤 다음 실행이 확인한다). 잠금 대기 3초 초과·교착(`locked`)과 예기치 못한 오류(`failed`)는 그 주문의 예외 블록만 되돌려 그 실행에서 건너뛰고, 같은 묶음의 나머지 주문은 그대로 확정·커밋된다. 다음 날 실행이 다시 본다. 제외 판정은 잠그기 전에 먼저 보고, 잠근 뒤 다시 보아 제외되면 블록을 되돌려 잡았던 잠금을 바로 놓는다. 선물 주문은 받는 분이 주소를 입력하고 수락한 뒤에만 주문·결제가 생기므로(`place_my_gift`) "선물 수령 대기 중인 결제완료 주문"은 현재 상태 모델에 없다.
- **전이:** 수동 발주확인과 자동 발주확인은 같은 내부 함수 `private.confirm_paid_order`로 전이한다. 취소 진행 재검사, `confirmed_at`(발송지연 시계 시작), 고객 직접 취소 종료, 감사 `admin.order.status_updated`({from, to})가 두 경로에서 같다. 자동 경로는 `actor_id = null`과 `trigger='auto_order_confirmation'`·실행일·컷오프를 감사에 더하고, 실행이 끝나면 `system.order.auto_confirmation_run`을 남긴다. 기존 판독기(타임라인·직접 취소 판정·배송지 변경)는 같은 감사 형식을 그대로 읽는다.
- **경합:** 여러 주문은 저장소 공통 규칙대로 주문 id 오름차순으로 잠그고(결제 시각은 묶음을 고르는 기준일 뿐이다), 한 주문 안에서는 고객 직접 취소·수동 발주확인과 같은 주문 → 배송 건 순서를 쓴다. 잠금 대기 한도(3초)는 주문별 블록 안에서만 적용한다. 고객 취소가 먼저 잠그면 자동 실행은 기다렸다가 취소 진행으로 제외하고, 자동 실행이 먼저 잠그면 고객 취소는 기다렸다가 `not_cancelable`을 받는다. 수동 발주확인과 겹치면 한 번만 전이한다. 배송 건을 쥔 트랜잭션·여러 주문을 id 순으로 잠그는 트랜잭션과 겹쳐도 교착 없이 끝난다(`supabase/tests/auto_order_confirmation_concurrency.sh`).
- **일괄 수동 발주확인(100건)** 은 그대로 쓴다. 자동 발주확인을 꺼도 수동 경로는 바뀌지 않는다.

## 자동 구매확정 소급 (D11)

자동 구매확정은 운영자가 켜는 정책이고, 지금까지는 배송완료 당시 정책이 꺼져 있었던 주문에 기한을 만들지 않았다. 2026-10-27 결정(네이버 관행, 배송완료 + 설정 일수)에 따라, 정책을 켜면(또는 켜진 채 저장하면) 기한이 없는 배송완료 주문 — 꺼져 있던 기간과 구매확정 도입 이전의 배송완료 — 에 `배송완료 시각 + 현재 기간`을 저장한다. 이미 기한을 받은 주문은 그때 기간을 유지하고, 보류·클레임·실물 배송 검사는 그대로다. 정책 저장과 배송완료 순간의 정책 읽기는 직렬화한다. 운영 정책 스위치는 migration으로 켜지 않는다 — 켜는 것은 사람이 한다(운영 가주문 30건이 즉시 대상이 될 수 있다).

## 스테이징 테스트 배송완료 (A15)

> 2026-11-11 보완(1014-083): 사용자 결정 "운영 전체 주문 허용"(원장 재작업 결정 묶음 3, 10/14 회의 요청 "아니면 지금 구매하고 배송 완료로 바꿀 수 있어요" / "어차피 테스트하면서 강제로도 해야 되니까")에 따라 화면의 도구는 환경 판별 없는 **강제 배송완료**(`admin_force_order_delivery_preview`·`admin_force_order_delivered`, `20261112130100`)로 바뀌었다. 발주확인 이후 주문의 남은 배송 건을 배송완료로 옮기고 합포장은 묶음 전체를 함께 옮긴다. 택배는 운송장 없이, 택배 외 방식(퀵·직접배송·화물배송·방문수령·배송없음)은 실제 인계·일회 수령 확인값 대신 `shipment_delivery_operations`의 `forced_delivered` 증거(사유·처리자)로 옮기며, 배송 방식 가드(`guard_shipment_delivery_method`)는 이 증거만 예외로 받는다. 택배 발송 메일은 생기지 않지만, 주문이 배송완료가 되면 기존 주문 상태 트리거가 고객 앱 알림 "배송이 완료됐어요"를 만든다(일부만 남아 배송중이 되면 "배송이 시작됐어요"). 구매확정 기한·자동 구매확정·리뷰는 정상 배송완료와 같다. 안전장치는 환경 허용 행 대신 배송 처리 권한(`sales.manage`), 사유 필수(500자), 대상 미리보기 확인창(배송 방법·출고지시 전달 여부·합포장 동반 주문·막는 사유)과 확인 체크, 출고지시를 전달한 발송 전 택배 건이 있으면 창고 출고 확인 체크 추가, operation ID 재전송, 감사(`admin.order.forced_delivered` — 사유·처리한 배송 건·방법, 합포장으로 함께 옮긴 주문에도 같은 사유)다. **예외**: 디지털 파일(구매자가 내려받을 때만 제공 시작 — 청약철회가 제한되는 시점이라 강제로 만들지 않고, 섞인 주문은 나머지만 옮긴다), 예약 재고 미할당·주문제작 미완료(실물이 없어 재고 불변식상 막는다 — 오케스트레이터 결정), 진행 중인 취소·반품·교환, 발주확인 전 주문. 아래 스테이징 전용 함수·허용 행은 남아 있지만 화면은 더 이상 부르지 않는다.

구매확정·리뷰 시험을 위해 스테이징에서만 발주확인 이후 택배 주문을 운송장 없이 배송완료로 기록한다(`admin_mark_staging_test_delivered`). 준비 → 배송완료로 바로 옮겨 발송 메일 대기열을 만들지 않는다. 합포장 소속 배송 건은 운영 배송완료와 같이 `lock_shipment_pack_scope`로 묶음 전체를 잠가 함께 옮긴다. DB에는 자신이 운영인지 알려 주는 기존 표식이 없어서, 검증된 스테이징 세션(`app.staging_seed_enabled`)에서만 실행되는 시드가 넣는 허용 행(`private.staging_test_tools`)이 없으면 거절한다(운영은 이 시드를 실행하지 않는다). 운영 프로젝트 ref가 담긴 토큰도 거절하고, 서버도 운영 배포·운영 Supabase·운영 도메인이면 화면과 액션을 닫는다.

## 결과와 검증 경계

- 운영 DB에 배포되는 순간 자동 발주확인이 켜지지만 대상은 배포 뒤 결제된 주문뿐이다. 첫 실행은 배포 시각 뒤 처음 오는 16:30(KST)이다. 끄려면 발주 화면에서 바로 끈다.
- 화면 결제일과 자동 대상 판정 시각은 다른 원장이다. 결제사 승인 직후 DB 확정이 마감을 넘기면 다음 날 처리된다.
- CI·로컬 DB에서도 매분 틱이 돈다. 스모크는 실행 날짜를 미래로 고정하고 트랜잭션 안에서만 주문을 만들며, 경합 시험은 cron이 없는 복제 DB에서 돈다. 커밋된 결제완료 주문을 남기는 다른 스크립트가 KST 16:30 마감과 같은 분에 돌면 그 주문이 자동 발주확인될 수 있다.
- 법정 청약철회는 여전히 앱 상태와 별개다(ADR-0017 §직접 신청과 청약철회 의사표시).

검증: `supabase/tests/auto_order_confirmation.sql`(경계·제외·멱등·묶음·자정 이월·시각 변경·끄기·다시 켜기·주문별 오류 격리·권한·감사·수동 경로), `auto_order_confirmation_concurrency.sh`(고객 취소·수동 발주확인 경합, 잠금 대기 초과, id 순 잠금 교착 방지), `purchase_confirmation.sql`(소급), `staging_test_delivery.sql`(운영 형태 거절·메일 미생성·합포장 함께 처리), `forced_order_delivery.sql`(허용 행 없는 운영 형태에서 권한·사유·확인창 미리보기(출고지시 전달 여부)·막는 사유·재전송·감사·합포장 동반·택배 외 강제 증거·디지털 제외·고객 앱 알림, 가드가 강제 증거 없는 택배 외 배송완료를 여전히 거절).
