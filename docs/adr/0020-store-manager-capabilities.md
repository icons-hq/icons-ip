# 매니저 권한은 현재 DB의 업무 능력으로 판정한다

- Status: accepted (2026-10-13), 보완 (2026-11-11 — 물류출고관리의 출고 전용 능력), 보완 (2026-11-12 — 상담 중 고객 구매이력·문의 자동 안내 저장·운영자별 처리 이력, ERP 품목 반입은 상품 관리 능력)
- 관련: [ADR-0014](./0014-admin-console-redesign.md), [ARCHITECTURE](../ARCHITECTURE.md)

판매자센터는 통합 매니저·계정 주매니저·계정 부매니저·인플루언서·대행사·물류출고관리의 6역할을 사용한다. 기존 `profiles.role`의 `user/staff/admin`과 담당업무 표시는 이 권한을 대신하지 않는다. 메뉴, 화면 로더, 서버 액션, 직접 RPC, 테이블·Storage 정책은 같은 업무 능력을 기준으로 제한하며, JWT에 저장된 과거 권한을 최종 판단에 사용하지 않는다.

기존 함수의 시그니처와 의존 관계를 유지하면서 능력 검사를 추가한다. 전체 함수를 private 스키마로 옮기고 일괄 wrapper를 만드는 대안은 문자열 기반 SQL 호출과 저장 의존성이 서로 다른 함수를 가리킬 수 있고, 함수 속성·기존 내부 호출을 재현하는 범위가 커서 채택하지 않는다. 공개 읽기·고객 본인 접근과 직원 접근이 섞인 함수는 직원 분기만 제한한다.

전환 전 호환 권한은 migration 시점의 기존 운영자 ID 명단에만 적용한다. 명시적으로 지정한 매니저 역할은 전환 완료 전에도 즉시 적용하며, 새로 만든 raw staff/admin 계정은 자동 호환 대상이 아니다. 최초 활성화는 통합 매니저를 명시적으로 선택하고 기존 운영자 전원에게 역할 또는 회수를 지정한 뒤 한 트랜잭션으로 처리한다. 현재 관리자 중 대표를 자동으로 정하지 않는다.

업무 변경은 계정 제재 잠금과 현재 권한을 함께 확인하여 역할 회수와 직렬화한다. 외부 PG 처리를 시작하는 권한과 이미 완료된 처리를 DB에 반영하는 권한은 구분한다. 유효한 작업·실행자 결속과 공급자 증거가 있는 완료 반영을 권한 회수만으로 막아 실결제와 주문 상태가 달라지게 하지 않는다.

초대는 기존 이메일 발송 경로를 사용한다. 네이버의 문자 운송 방식과 달리 이메일 주소의 소유를 확인한 계정으로 수락하며, 생성·발송 결과·수락을 구분한다. 초대의 7일 유효기간과 역할 변경·회수·승계는 별도 원장 및 멱등 요청으로 검증한다. 운영 환경의 활성화와 통합 매니저 지정은 배포 절차의 명시적 작업이다.

## 보완 (2026-11-11): 물류출고관리의 출고 전용 능력

처음 결정은 판매자센터 권한표처럼 물류출고관리에 홈과 상품 공지사항만 주고, 물류 담당자가 발송을 처리하려면 계정 주매니저로 초대하게 했다. 10/14 운영 회의에서 "배송은 배송에서 봐야 된다고"(메인 49:32), "물류에서 그걸 바로 보고"(50:15)라는 요청이 나왔고, 2026-11-11 사용자는 "물류 전용 출고 권한 (Recommended)" — 출고지시 내려받기·송장 회신·발송·배송완료, 환불·고객 관리 제외 — 를 골랐다(원장 1014-084). 주매니저 초대는 환불·정산·매니저 관리까지 넘기게 되어 택하지 않았다.

물류출고관리는 기존 상품 공지사항 관리에 더해 출고 전용 능력 `sales.dispatch`를 받는다. 이 능력은 발주(주문)확인/발송관리와 배송현황 관리 화면, 출고지시 내려받기와 전달 표시, 운송장 회신 반입, 발송(발송 대기→배송중)과 배송완료, 발송 안내 메일 대기열 등록, 회신 대조용 출고지 설정 읽기, 그리고 퀵·방문수령·직접배송·화물·직접전달의 실제 인계·수령 기록과 그 기록에 필요한 인계 정보 읽기만 연다. '발송·배송완료'를 택배로 좁히지 않는다. 물류 계정은 주문 상세 없이 발송·배송현황 목록의 팝업으로 인계·수령을 기록한다. 발주확인(주문 상태 변경)·배송 방식 변경(고객 요청·배송비 동의)·취소·환불·반품·교환, 주문 상세·고객 이력·회원, 상품, 목록 엑셀, 합포장·고객 지연 안내·자동 발주확인 설정은 지금처럼 `sales.manage` 등 기존 능력에 남는다.

같은 웨이브에서 새로 생긴 출고 업무도 `sales.dispatch`로 연다(통합 migration `20261112200000`): 발송처리 화면의 행 운송장 입력·[배송 방법]·[택배 외 발송처리](S36-072·S36-X04, `private.dispatch_console_capability()`), ICONS 표준 양식 바코드 공백 경고, 출고지시 전 재고 차이 경고. 발송처리 화면의 방법 적용은 그 출고지에서 운영 조건이 켜진 방법만 고르고, 고객이 고른 방법과 다르면 사유를 남기며 배송비·결제 금액은 바꾸지 않는다. 고객 요청·배송비 동의 근거를 받는 주문 상세의 방식 변경과 운영 강제 배송완료(운송장 근거 없이 철회 기간을 연다)는 `sales.manage`에 남긴다. 재고 차이 경고는 주문 조회(`sales.read`)에서 출고(`sales.dispatch`)로 옮겨, 그 경고를 그리는 발송 화면을 열 수 없는 인플루언서(`sales.read`만 보유)는 더 부르지 못한다.

`sales.manage`는 `sales.dispatch`를 포함한다. 이 함의는 DB의 `private.has_operator_capability`와 앱의 `hasAdminCapability`가 같은 표로 판정하고, 통합 매니저·계정 주매니저·전환 전 운영자의 능력 목록에는 적지 않는다. 그래서 다른 역할의 권한은 넓어지지도 좁아지지도 않고, DB를 먼저 올리는 배포 동안 옛 앱이 낯선 능력 이름 때문에 운영자 권한 응답 전체를 거절하는 일도 없다. 통합·주매니저 목록에 `sales.dispatch`를 직접 적는 방법은 그 배포 사이에 모든 운영자의 어드민 접근을 끊을 수 있어서, 새 역할을 만드는 방법은 물류 역할이 둘이 되어 택하지 않았다.

열람 범위는 2026-11-11 사용자 결정 "수령인 정보만"을 따른다. 주문 조회 권한(`sales.read`)이 없는 출고 전용 운영자는 주문·결제·고객 원본 표를 직접 읽지 못하고, 발송·배송현황 목록 응답에서 구매자 닉네임·주문 총액·결제수단·선결제 배송비가 비어 온다. 구매자(닉네임·이메일)로 찾거나 결제수단·결제일로 거르거나 금액으로 정렬하는 조건은 DB가 무시해 그 값을 간접으로도 알아내지 못한다. ICONS 표준 출고지시 파일은 구매자·결제·금액 칸을 모든 줄에서 비운다 — 줄의 구매자·결제·품목 금액은 DB가, 배송 건의 선결제 배송비는 앱이 비운다. 착불은 2026-11-12 사용자 결정 "착불 금액은 보이게 (Recommended)"에 따라 비우지 않는다: 착불 배송비(배송 건별)·합포장 착불 합계·착불 수납 정보(수납 주체·수납 방법·고객 안내·착불 환급 문의)는 창고가 수령인에게 받을 금액과 방법이라 출고 전용 운영자에게도 보이고(파일의 배송 운영 안내 시트, 본 시트의 배송비 형태 '착불', 발송·배송현황 화면의 배송 건 행), 선결제 여부와 금액은 계속 비운다(통합 migration `20261112200100`이 합포장 요약의 착불 합계 비움을 되돌렸고, `20261112200400`이 화면용 착불 요약 `admin_shipment_collect_summaries`(sales.dispatch, 읽기 전용)를 더했다 — 결정이 파일에만 한정되지 않는다는 오케스트레이터 판단). 착불을 비우면 착불 건이 배송 운영 안내에서 빠져 택배사가 받을 금액을 창고가 모를 수 있었다. 인계 정보 읽기의 배송비·방식 정책·방식 변경 근거도 주지 않는다. 창고 고유 양식(김포 21열·서원 송장양식)은 창고가 쓰는 형식이라 이번 결정 범위에 두지 않았다. 주문 조회 권한이 있는 통합·주매니저의 목록·파일은 그대로다. 출고 RPC의 능력 검사와 비움은 다른 트랙과 같은 함수를 고칠 수 있어 앵커 치환으로 바꾸고 같은 migration에서 운영자 계약 지문을 다시 적는다.

## 보완 (2026-11-12): 상담 중 고객 구매이력·문의 자동 안내 저장·운영자별 처리 이력

처음 역할표는 판매자센터 권한표처럼 상담(`cs.manage`)과 주문 조회(`sales.read`)를 나눴다. 그래서 계정 부매니저·대행사는 상담 화면을 열어도 고객이 무엇을 샀는지 보지 못했고(10/14 운영 회의 "얘가 뭘 샀는지 알아야 돼. 얘랑 상담을 해야 돼. 안 그러면 여기에서 다 뒤져야 돼."), 문의 자동 안내는 매니저 권한 전환 전 호환 단계에서 admin만 저장했다. 2026-11-11 사용자는 구매이력에 "전부 다 아무나 볼 수 있게", 자동 안내 저장에 "아무나 가능하게"를 골랐고, 2026-11-12 해석 확인에 "이대로 (Recommended)"로 답했다(원장 1014-103·TKT-019·TKT-099).

상담 화면을 여는 모든 운영자 역할(통합·주·부매니저·인플루언서·대행사, 전환 전 기존 운영자)은 상담 중 고객의 전체 구매이력 — 주문번호·상태·결제 금액·대표 상품·품목 수·주문 시각 — 을 본다. 이 열람은 `admin_inquiry_purchase_history`가 문의 번호로만 열어 그 문의를 쓴 고객의 주문만 돌려주고, 열람마다 감사 기록(`admin.inquiry.purchase_history_viewed` — 문의·고객·운영자·보여 준 주문 목록·연결 주문)을 남긴다. 상담 화면은 새 메시지마다 다시 그려지므로, 같은 운영자가 같은 문의·같은 페이지에서 10분 안에 똑같은 목록(보여 준 주문과 연결 주문이 모두 같음)을 다시 그릴 때만 기록을 겹쳐 남기지 않는다. 그사이 새 주문 등으로 보여 준 내용이 바뀌면 새 열람으로 남긴다. 배송지·연락처·결제수단·클레임과 주문 상세 화면은 지금처럼 주문 조회·처리 권한에 남고, 고객 번호로 주문을 읽는 고객 관리 경로(`admin_operator_customer_history`)도 `sales.read`를 그대로 요구한다. 부매니저·대행사의 능력 목록에 `sales.read`를 더하는 방법은 주문 목록·주문 상세·배송지까지 열려 택하지 않았다. 대행사는 외부 인력일 수 있어 개인정보 처리위탁 범위 확인은 운영 측 할 일로 남는다.

문의 자동 안내는 그 탭을 여는 운영자(`store.manage`)가 켜고 끄고 문구를 저장한다. 같은 저장 함수의 사업자·CS 연락처·무통장 계좌는 지금처럼 `seller.manage`(호환 단계 admin)다. 저장 감사(`admin.store_settings.updated`, 변경 전후)는 그대로다.

같은 날 사용자는 담당자 처리 히스토리(원장 1014-105)로 "운영자별 처리 이력"을 골랐다. 운영자별 집계·처리 목록은 운영자 활동 기록이라 매니저 관리 권한(`operators.manage` — 통합·주매니저, 호환 단계 admin)으로만 열고 열람마다 감사한다(`admin.operator.inquiry_history_viewed`). 좁히지 않으려고 문의 하나의 처리 이력(담당 지정·변경·답변·완료 — 누가·언제)은 그 문의를 여는 운영자(`cs.manage`) 누구나 본다. 둘 다 이미 남는 감사 기록(답변·완료·담당 변경)을 원본으로 쓰며 새 기록 표를 두지 않는다. 7일 무응답 자동 종결은 실행자가 없어 운영자 완료로 세지 않는다.

## 보완 (2026-11-12): ERP 품목 반입은 상품 관리 능력

처음 결정은 ERP 품목 화면을 다른 플랫폼 설정처럼 `platform.manage`(통합·주매니저)에만 열었다. 10/27 회의에서 MD가 "ERP 품목 이렇게 복사 붙여넣기 하는 데"를 직접 쓰겠다고 했고(1027T-016), 2026-11-11 사용자는 "미연결 안내+MD 권한"을 골랐다. 부매니저(MD)는 `platform.manage`가 없어 화면을 열 수 없었다.

ERP 품목 화면 읽기(목록·ERP 분류 목록·옵션 ERP 품명 제안 검색)·붙여넣기 반입·ERP 분류 연결은 상품 관리 능력 `catalog.manage`로 연다(migration `20261113040000`). RPC 6개(`admin_import_erp_items`·`admin_search_erp_items`·`admin_list_erp_items`·`admin_list_erp_categories`·`admin_set_erp_category_mapping`·`admin_set_erp_category_mappings`)의 능력 검사와 표 읽기 정책 3개(`erp_items`·`erp_category_mappings`·`catalog_category_erp_mappings`)를 같은 능력으로 바꾸고 운영자 계약 지문을 다시 적었다. 반입한 값을 같은 ERP 코드의 상품 옵션(연결 상품)에 반영하는 미리보기·확정 RPC(`admin_preview_erp_linked_goods`·`admin_commit_erp_linked_goods`, migration `20261113040100`)도 상품 편집과 같은 `catalog.manage`다. 확정은 기존 상품 저장 RPC와 옵션 ERP 식별자 저장 함수를 그대로 불러 가격·바코드 규칙과 감사 기록이 상품 편집과 같다.

`catalog.manage`를 가진 인플루언서·대행사에게도 열리지만, 그 역할은 이미 상품 화면에서 판매가·옵션·바코드를 직접 고칠 수 있어 권한이 넓어지지 않는다. 반입 품목 삭제(`admin_delete_erp_items`)는 요청 범위 밖이고 지운 품목이 옵션 제안에서 사라지므로 `platform.manage`에 남겼다(화면은 삭제 칸을 그 능력이 있을 때만 그린다). ERP 전용 능력을 새로 만드는 방법은 DB를 먼저 올리는 배포 사이에 옛 앱이 낯선 능력 이름 때문에 권한 응답 전체를 거절하고 역할 목록을 바꿔야 해서 택하지 않았다.
