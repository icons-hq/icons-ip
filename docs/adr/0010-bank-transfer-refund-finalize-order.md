# 무통장 환불은 운영자 증빙으로 finalize하고, 송금 전 비종결 상태를 거쳐 종결한다

무통장 입금([ADR-0007](./0007-bank-transfer-payments.md)) 주문의 클레임 환불에는 PG 왕복이 없어서, 재고 복원·카드팩 회수(finalize)와 실제 계좌 송금의 순서·증빙·상태를 정해야 한다. 결정의 본질은 하나다 — **송금 완료는 finalize의 선행 조건이 아니고, finalize는 환불의 종결이 아니다.** (초안을 PR #290 리뷰로 개정: 유형별 순서, 증빙·수단의 DB 강제, 비종결 상태, 원문 계좌 열람 seam.)

- **finalize의 증빙은 운영자의 취소 확정 기록이다.** 송금 완료를 선행으로 요구하는 대안은 기존 원장 규율(완료 기록이 클레임 종결을 선행 요구)과 교착한다.
- **순서는 클레임 유형을 따른다.** 출고 전 **취소**는 finalize → 환불 filed → 송금 → completed. 출고 후 **반품**은 durable claim이 finalize의 선행 요건이므로 수거 완료 → 환불 filed(durable claim 생성) → finalize → 송금 → completed. "finalize가 항상 먼저"라고 읽으면 반품 경로가 실행 불가가 된다.
- **송금 전 무통장 환불은 비종결이다.** finalize 시점에 환불을 done/refunded 같은 종결 신호로 쓰면, "환불 완료" 라벨과 계정 삭제의 미결 환불 차단이 송금 전에 풀린다. 송금 대기 **비종결 상태를 신설**하고, 송금 증빙 기록이 이를 종결로 전환한다. 미송금 큐는 이 상태가 정의한다(완료 시각 공백은 보조 신호).
- **완료 기록은 비어 있지 않은 불변 송금 증빙(처리자·시각·근거)을 DB 경계에서 요구한다.** 앱 검증만으로는 게이트가 아니다 — 지금은 근거 메모 없이도 완료 기록이 가능하다.
- **수단 불변식.** 무통장 결제에 연결된 환불의 수단은 계좌 송금뿐이다 — DB가 강제하고, UI는 주문 결제 수단에서 파생해 고정한다(결제사 취소 기본값을 무통장 주문에서 고를 수 없어야 한다).
- **송금 목적지 열람 seam이 선행 요건이다.** 원문 환불계좌의 마스킹·격리 원칙은 유지하되, 송금 실행자가 원문을 받을 감사되는(열람자·시각 기록) 좁은 권한의 서버측 열람 경로를 함께 만든다. 이것 없이는 수동 송금 절차 자체가 실행 불가능하다.

## Considered Options

- **송금 완료를 finalize 선행 조건으로 요구** — 재고 복원 전 돈이 먼저 나가는 창을 없애지만, 완료 기록이 클레임 종결을 선행 요구하는 기존 원장 규율과 교착하고, 규율 재설계는 Korpay·legacy Toss 경로까지 흔든다. 폐기.
- **운영자 취소 확정 기록을 finalize 증빙으로 인정 (채택)** — 입금 확인(어드민 액션이 증빙을 기록하고 DB 멱등 finalizer를 호출)과 거울 대칭이다. 초안의 "완료 시각 공백 큐만으로 관리"는 종결 신호 오염(리뷰 지적: finalize가 환불 done·"환불 완료" 라벨·계정 삭제 차단 해제를 즉시 만든다)이 확인되어 비종결 상태 신설로 보강했다.

## Consequences

- finalize 함수 마이그레이션(#280): 무통장 결제를 운영자 증빙 등가물로 인정하고, 무통장 환불을 종결 상태로 쓰지 않는 상태 모델을 함께 도입한다. TS에서 가짜 증빙을 주입하는 우회는 게이트 우회라 금지.
- 완료 기록의 송금 증빙을 DB가 강제(#280)하고 UI가 필수로 받는다(#281). 수단 불변식도 DB와 UI 양쪽에 둔다(#280·#281).
- ADR-0007의 "클레임 접수 시 환불계좌 수집 필수"가 선행 조건이다(현재 미구현) — 접수 시 필수화 + 어드민 사후 기입·정정 + 감사되는 원문 열람 seam(#279).
- 미송금 큐(비종결 상태 기반)가 운영 절차에 추가된다. 뱅크다류 연동이 송금 확인을 보조할 수 있지만 기록 주체는 여전히 운영자다.
