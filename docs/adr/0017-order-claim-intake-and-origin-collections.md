# 주문 전체 클레임 — 직접 신청 시점을 제한하고 출고지별 회수를 확인한다

- Status: accepted (2026-09-09)
- Supersedes: [ADR-0016의 2026-09-08 클레임 지원 범위](./0016-fulfillment-origins-and-shipments.md#현재-클레임-지원-범위와-한계-2026-09-08)
- 관련: [정본 #437](https://github.com/icons-hq/icons-ip/issues/437), [#453](https://github.com/icons-hq/icons-ip/issues/453), [PR #407의 혼합 출고지 리뷰](https://github.com/icons-hq/icons-ip/pull/407#discussion_r3946457427)
- 보완: 발주확인 뒤 첫 발송 전의 운영자 처리 경로는 [ADR-0018](./0018-staff-initiated-order-cancellation.md)(운영자 전액 취소)을 따른다. 이 문서의 직접 신청 경계는 바뀌지 않는다.
- 보완: 발주확인은 운영자 외에 매일 정한 시각의 자동 발주확인으로도 일어난다([ADR-0025](./0025-auto-order-confirmation.md)). 고객 직접 취소는 그 실행 전까지 열린다. 이 문서의 직접 신청 경계는 바뀌지 않는다.
- 보완: 회수 주소는 승인 때 상품이 고른 반품/교환지(없으면 출고지 반품 주소)로 고정하고, 한 배송 건 안에서 반품지가 갈리면 회수 묶음(배송 건 × 반품지)으로 나눠 묶음마다 입고를 확인한다(2026-11-12, 아래 '상품별 반품/교환지와 회수 묶음'). 아래 결정의 "출고지별 반송 주소·각 출고지의 입고"는 배송 건 안의 반품지별 묶음까지 포함해 읽는다.
- 보완: 교환 재출고는 배송 건(출고지)마다 기록하고, 하자·오배송 교환은 사유·근거 사진을 남기면 회수 확인 없이 재출고할 수 있다([ADR-0041](./0041-claim-reshipments-per-origin.md), 2026-11-12). 아래 결정의 "필요한 회수가 하나라도 미완료면 … 교환 재출고를 종결하지 않는다"는 교환에서 배송 건 단위로 읽고, 모든 배송 건이 재출고돼야 교환을 종결한다.

## 후속 적용

2026-10-16 승인된 [배송 중 반품·교환 접수](../research/smartstore-admin/in-transit-claims.md)는 아래 9월 결정 중 직접 접수 시점을 확장한다. 주문 전체 배정과 실제 발송 근거를 확인하고, 전액 처리·전체 회수 확인·기존 기한·금융 원장의 경계는 유지한다. 아래 내용은 당시 결정 이력이며 현재 절차는 [클레임 런북](../runbooks/order-claim-intake.md)을 따른다.

2026-11-11 사용자가 직접 반품·교환 시점을 "배송 중부터"로 다시 확정했다(원장 TKT-156·TKT-157, 묶음 9 "배송 중부터 확정" — 현행 유지, 코드 변경 없음). 9/9 결정의 "전체 품목 배송완료 뒤"와 "일부 수령 주문 거절"은 이 확정으로 대체됐다. 업계(스마트스토어는 배송중·배송완료 상태에서 반품·교환 접수)와 같은 방향이다. 상태 되돌림으로 발송 이력을 지우지 않는 규칙, 누락·일부·초과 배정 수량 거절은 그대로다(`supabase/tests/order_claim_origin_policy.sql`).

## 맥락

혼합 출고지 주문은 허용하지만 부분 취소·부분 환불은 범위 밖이다. 기존 주문 전체 취소는 배송 후에도 접수됐고, 승인 뒤 물리 회수를 확인하지 않고 환급·재고 복원으로 진행할 수 있었다. 일부 배송만 도착한 주문의 회수 주소와 수량을 단일 주문 상태로 표현할 수도 없었다. 사용자는 주문 전체 처리를 유지하면서 회수를 보완하는 A안을 선택하고, 직접 취소는 발주확인 전까지, 직접 반품 신청은 모든 굿즈의 실제 배송 완료 뒤에만 허용하도록 결정했다.

## 결정

- 혼합 출고지 결제와 **주문 전체** 클레임을 유지한다. 출고지·품목별 부분 환불이나 가격 차액 정산을 새로 도입하지 않는다. 취소·반품의 환급액은 기존 주문 결제금액 전액(최초 배송비 포함), 교환은 기존 결제를 유지한다. 수거비 부담·환급액 산식·법정 기한은 이 결정으로 변경하지 않는다.
- 주문 상세의 직접 취소는 발주확인 전인 `pending`·`paid` 주문에만 연다. 현재 상태를 과거 상태로 되돌렸다는 이유로 발주확인·발송 이력을 없었던 것으로 취급하지 않는다. 발주확인 후부터 전체 배송 완료 전까지는 직접 취소·반품·교환 신청을 열지 않는다.
- (2026-10-16 승인·2026-11-11 사용자 확정으로 대체 — 현재는 실제 발송된 배송 중부터 주문 전체로 접수한다. TKT-156·157) 직접 반품·교환은 `delivered`·`done` 표시뿐 아니라 주문 **전체 품목 수량의 실제 배송 완료**를 확인한다. 다른 배송 건이 미완료이거나 취소되어 일부 품목만 도착한 주문을 전체 수령으로 간주하지 않는다. 접수 가능 여부를 읽는 RPC는 상태·배송 사실을 보여주며, 작성 RPC가 권한·활성 클레임·기한과 사실을 다시 검증한다.
- 교환품 재출고는 원 배송의 완료 이력과 구별한다. 재출고된 교환품의 배송완료를 직원이 근거와 함께 확인하기 전에는 새 반품·교환 신청을 열지 않는다. 확인자·근거·기록 시각은 보존하며 원주문 배송 시각이나 기존 신청 기한을 자동으로 바꾸지 않는다. 교환 후 기한 예외는 CS에서 거래 사실을 검토한다.
- 반품·교환 접수의 회수 대상은 주문 전체다. 출고지별 반송 주소와 대상 품목·수량을 해당 클레임의 회수 근거로 보존하고, 각 출고지의 입고를 구별한다. 필요한 회수가 하나라도 미완료면 환급·재고 복원·교환 재출고를 종결하지 않는다. 화면 표시나 provider 취소 응답을 물리 회수 증거로 대신하지 않는다.
- 기존 주문·배송·가격·옵션·금융 원장은 덮어쓰지 않는다. 이미 진행 중인 과거 클레임에는 없는 회수 증거를 만들어 넣지 않는다. 전환 시 처리 가능 여부는 실제 단계와 provider 진행 사실을 검토하고, 금융 결과가 불명확한 건은 중복 취소 없이 기존 재정합 경계를 따른다.

## 비용 안내와 운영 확인액 (#491, 2026-09-10)

상품의 `claim_return_allowed`·`claim_exchange_allowed`·제한 사유·반품비·교환비는 고객 안내용 nullable 정책이다. 값이 없으면 확인되지 않은 상태로 표시하고, 0원은 확인된 무료 비용으로 구별한다. `order_cancellation_requests`의 `operational_fee_*` 필드는 CS가 실제로 확인한 비용 유형·금액·메모·근거·확인자·시각을 별도 감사 RPC로 기록한다. 이 기록은 고객에게 추가 청구하지 않고 환불액에서 차감하지 않으며, 클레임 접수·단계 전이·회수·재고·결제를 자동으로 바꾸지 않는다. 기존 주문 전체 환급과 출고지별 회수 계약은 그대로 유지한다.

## 상품별 반품/교환지와 회수 묶음 (S36-040·S36-044·QNA-031, 2026-11-12)

사용자 결정(2026-11-11 묶음 9): "상품별 반품/교환지(주소록 선택, 비우면 출고지 반품 주소, 접수 때 회수 주소 상품 우선) + 상세에 교환·반품 가능/제한 표시(접수는 막지 않음) + 승인 뒤 고객 반품 진행 칸에 배송 묶음별 회수 주소."

- **반품/교환지 주소록**(`public.return_addresses` — 이름·주소·연락처)을 둔다. 등록·수정·삭제는 출고지 설정과 같은 권한(platform.manage, 감사 기록)이고, 상품 운영자(catalog.read)는 읽기만 한다. 상품이 고른 주소는 지울 수 없다. 상품은 반품/교환지(`goods.return_address_id`)를 고르고, 비우면 그 출고지의 반품 주소를 쓴다. 출고지 반품 주소는 그대로 기본값으로 남는다.
- **회수 주소 스냅샷**은 지금과 같은 시점(승인 때 `private.prepare_claim_collections`)에 상품 우선으로 잡는다. 스냅샷은 출고지 → 상품 → 주소록 순 공유 잠금 아래에서 만들어, 같은 순서로 잠그는 상품 저장과 직렬화된다. 이후 주소록·상품 반품지를 바꿔도 이미 승인한 회수 주소는 바뀌지 않는다.
- **회수 묶음 = 배송 건 × 반품지**(`public.order_claim_collection_bundles`). 한 배송 건 안에서 상품별 반품지가 갈리면 반품지마다 묶음을 나누고 회수 확인(실제 입고일·근거)은 묶음마다 받는다. 하위 호환을 위해 배송 건 행(`order_claim_collections`, 키 = 클레임 × 배송 건)을 그대로 두고, 그 배송 건의 모든 묶음이 입고된 때 배송 건 행을 회수 완료로 적는다(입고일 = 묶음 가운데 가장 늦은 날). 그래서 회수 완료 판정·회수 생략(배송 건 단위 결정)·배송 건 재출고·교환품 제작·회수 정보 정정은 키를 바꾸지 않는다. 묶음이 하나인 배송 건은 예전 배송 건 키 RPC로 확인할 수 있고, 둘 이상이면 묶음 키 RPC(`admin_record_order_claim_collection_bundle`)로 확인한다. 이 기능 전의 회수 행은 묶음 하나로 옮겼다.
- 재고 대조 흐름은 회수한 품목이 그 품목의 묶음 입고 시각에 돌아온 것으로 센다. 고객 철회는 묶음 하나라도 입고되면 막힌다(회수가 시작된 것).
- **고객 회수 주소**: 승인 뒤(묶음이 생긴 뒤) 고객 회수 문서가 배송 묶음마다 회수 주소(반품지 이름·주소·연락처, 출고지 기본은 주소만)와 품목을 싣는다. 선물 주문은 받는 분에게만 보이고(보낸 분은 문서를 받지 않는다), 회수 생략 배송 건은 고객에게 주소 대신 반송이 필요 없다고 말한다.
- **교환·반품 가능/제한 표시**: 상품 상세는 상품의 반품·교환 조건에서 파생해 "교환·반품 가능" 또는 "교환·반품 제한(사유)"를 보이고, 하자·오배송은 제한할 수 없다는 문장을 함께 둔다(전자상거래법 제17조 제3항). 고지일 뿐 접수를 막지 않는다(업계 — 불가 사유 고지 뒤 사후 거부).
- 하지 않은 것: 회수 정보 정정 계획(회수 방법·택배사·송장)은 배송 건 단위 그대로다 — 반품지가 갈린 배송 건의 묶음별 수거 송장은 자동 회수 접수(T13b, QNA-032)가 묶음 키로 다룬다. 교환품 제작 시작 판정도 배송 건 단위 그대로다(품목의 묶음이 먼저 와도 배송 건 전체 입고 뒤 시작 — 보수적 방향).

## 직접 신청과 청약철회 의사표시

직접 신청 조건은 앱의 처리 경계이며 법정 권리를 소멸시키는 약관이 아니다. 발주확인 후 또는 일부 수령 상태의 청약철회 의사는 1:1 문의·공개된 고객지원 통로에서 받는다. 운영자는 원문, 접수 시각, 주문과 배송 건별 사실을 보존해 검토한다. 문의가 클레임·환급 원장을 자동 생성하지는 않으며, 운영자가 닫힌 주문 API를 우회하거나 배송 중 즉시 환급하는 새 권한을 만들지 않는다. 법정 기한과 앱의 주문 단위 기한이 맞지 않는 사례는 고객에게 전체 배송을 기다린 뒤 다시 신청하라고만 돌려보내지 않고 담당자에게 넘긴다.

전자상거래법은 공급 시점 등을 기준으로 청약철회 기간과 예외를 정한다. 발주확인이라는 앱 상태는 그 자체로 법정 예외가 아니며, 법정 규정에 어긋나는 불리한 약정의 효력도 제한된다. 따라서 이 결정은 앱 접수와 CS 검토를 분리한다. 구체적인 권리 판단은 거래 사실과 법령에 따르며 새 환급 기한·반송비 예외를 이 ADR에서 정하지 않는다. [제17조](https://www.law.go.kr/LSW//lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0017&lsiSeq=282793&urlMode=lsScJoRltInfoR), [제35조](https://www.law.go.kr/LSW//lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0035&lsiSeq=282793&urlMode=lsScJoRltInfoR) (확인: 2026-09-09, 시행 2026-07-21)

## 결과와 검증 경계

배송 건별 부분 클레임을 구현하는 대안은 할인·배송비 배분 및 부분 환급 원장이 필요해 현재 범위를 넘는다. 혼합 결제를 막는 대안은 기존 허용 결정을 뒤집는다. 선택한 계약은 두 대안의 구현을 완료했다는 뜻이 아니며, 일부 도착 때의 CS 검토와 두 출고지의 회수 운영 부담을 남긴다. 교환 재출고 운송장은 기존 클레임당 한 쌍이고, 출고지별 별도 재출고 배송 건을 도입한 결정도 아니다. (2026-11-12 [ADR-0041](./0041-claim-reshipments-per-origin.md)이 재출고 기록을 배송 건(출고지)마다로 바꿨다. 별도 출고지시 배송 건을 만드는 것은 여전히 아니다.)

이 ADR의 accepted는 정책 승인을 뜻한다. 앱·SQL 우회 경로, 출고와 접수 경합, 한 출고지의 회수 미완료, 중복 환급·재고 복원, 과거 진행 중 클레임, 공개 안내를 검증한 증거와 배포 승인은 별개다. 공개 문서의 공지·시행일과 기존 동의 이력의 한계는 [운영 런북](../runbooks/order-claim-intake.md)에 기록한다.
