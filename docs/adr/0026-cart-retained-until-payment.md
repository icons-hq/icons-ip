# 장바구니는 주문 생성이 아니라 결제 확정이 비운다

- Status: accepted (2026-10-27)
- 관련: [공통 주문 구조](0021-goods-transaction-sources.md), [무통장 입금](0007-bank-transfer-payments.md), 10/14 실사용 QA 회의 D2·D3(S12·S8), migration `20261027120000_cart_retained_until_payment`

지금까지는 주문을 만드는 트랜잭션이 장바구니 줄과 장바구니 쿠폰 선택을 지웠다. 그래서 결제창을 닫거나 결제가 실패·만료되면 결제하지 않았는데도 장바구니가 비어 있었고, 고객은 같은 굿즈를 다시 담거나 '취소하고 다시 주문하기'를 거쳐야 했다. LINE FRIENDS SQUARE와 네이버 스마트스토어는 결제가 끝날 때까지 장바구니를 그대로 두고, 무통장 입금은 접수를 주문 완료(입금대기)로 본다. ICONS도 이 관행을 따른다. 바로구매는 담기와 같은 카트 계약으로 담은 뒤 장바구니로 이동하고, 주문은 장바구니 전체로 만든다(D2 — 선택 주문 체크박스는 두지 않는다).

카드 장바구니 주문은 생성할 때 장바구니와 쿠폰 선택을 지우지 않고, 그 주문에 들어간 줄을 보류(`private.cart_order_holds`)로 기록한다. 결제 finalizer가 주문을 paid로 바꾸는 바로 그 트랜잭션의 `orders` AFTER 트리거가 기록된 수량만큼 장바구니에서 뺀다. 주문 뒤 수량을 늘렸으면 차액만 남고, 같거나 작으면 줄을 지우고, 이미 없으면 무시한다. 그 주문이 쓴 쿠폰이 장바구니에 선택돼 있으면 선택도 지운다. 장바구니 정리는 결제 확정을 되돌리지 않는다 — 어떤 이유로든 줄을 바꾸지 못하면 그 줄을 그대로 두고(`kept`) 결과를 보류에 남긴다. 트리거 이름을 다른 결제 후속 트리거(적립금·쿠폰·등급)보다 먼저 실행되게 골라 finalizer의 잠금 순서를 주문 → 시도 → account-action → profiles → 장바구니 → 적립금·쿠폰으로 고정했다. 무통장 주문은 종전처럼 접수 시 장바구니에서 뺀다. 선물·정기배송 회차는 장바구니를 읽지 않으므로 보류가 없고, 결제 확정도 장바구니를 건드리지 않는다. 운영의 기존 결제 대기 주문(보류 없음)도 그대로다.

결제 전 주문은 여전히 재고·쿠폰·적립금·회원 구매 한도·첫구매 혜택을 잡는다. 장바구니가 남은 채로 다시 주문하면 이 점유가 겹치거나 견적이 '쿠폰 사용됨'·'구매 한도 초과'로 막힐 수 있다. 그래서 같은 계정이 장바구니로 새 주문을 만들면, 계정 잠금 뒤·장바구니 잠금 전에 이전 미결제 카드 장바구니 주문을 만료 sweep과 같은 닫기 경로(`cancel_order`, 결제 중 접수된 취소 요청이면 `finalize_order_cancellation_with_provider_evidence`)로 닫아 점유를 먼저 돌려준다. prepared 결제 시도는 TTL과 무관하게 canceled로 바꾸므로, 결제창에서 늦게 돌아온 콜백은 claim이 terminal로 거절하고 승인 API를 부르지 않는다(토스 인증은 승인 없이 만료된다). 고객이 장바구니·주문서로 돌아오면 화면이 견적 전에 같은 닫기를 요청한다(`release_unpaid_cart_orders`). 화면을 보기만 하는 경로(서버 렌더·prefetch)에는 두지 않고 클라이언트 마운트에서만 부른다. 닫기는 계정 advisory만 쥔 채 대상 주문 행을 모두 먼저 잠그고, 그 뒤에 account-action·profiles·장바구니를 잡는다. claim·prepare·finalize가 주문 → account-action → profiles 순서로 잠그므로, actor 잠금을 이전 주문 행보다 먼저 잡거나 취소(등급 재계산의 profiles 잠금)를 account-action보다 먼저 하면 같은 계정의 승인 처리와 교착한다. 장바구니 변경 RPC(담기·수량·병합)도 사용자 advisory → account-action → profiles → 'cart:' 순서로 잠가(20261020085341) 다른 탭의 장바구니 변경과 주문 생성이 서로 앞 잠금에서 기다린다(2세션 경합 스모크 `cart_retained_concurrency.py`, 정적 단언 `assert_every_cart_lock_follows_account_action`). 다른 탭에서 결제창을 연 채 장바구니로 돌아오면(상품 상세 [구매하기]도 담은 뒤 장바구니로 이동하므로 같다) 그 결제는 승인되지 않고 끝난다 — 돈이 움직이지 않는 안전한 실패를 막다른 길보다 택했다.

이전 주문의 결제를 지금 승인 확인 중(confirming, 유효한 claim)이면 새 주문을 `checkout_payment_in_progress`로 막는다. 허용하면 이전 주문의 승인과 새 주문의 결제가 같은 장바구니를 두 번 청구할 수 있고, 확인 창은 승인 API 시한(최대 수십 초, claim 리스 10분) 안에 끝나기 때문이다. 결과를 자동으로 확정할 수 없는 이전 주문(unknown·needs_review·결제 원장 존재·환불 진행)은 막지도 닫지도 않는다. 웹훅·재정합이 자동으로 돌지 않으므로 막으면 고객이 기한 없이 주문하지 못한다. 대신 새 주문을 만들 때 그 주문의 보류를 장바구니에서 떼어 내(`detached`), 나중에 승인으로 확정돼도 새 장바구니를 건드리지 않게 한다. 이 경우의 중복 결제 가능성은 기존 '확인 중'·운영자 검토 절차가 다룬다.

'결제 준비하기' 단계는 없앤다(S8). 결제 화면이 열리면 서버가 로그인·주문 소유권·금액·재고를 다시 확인하고 결제 시도를 준비해 위젯을 띄운다. 결제 시도는 주문당 하나이고 유효 시간이 10분이므로, 시간이 지나거나 승인이 거절된 주문은 같은 주문으로 다시 결제하지 않는다. 장바구니가 그대로 있으므로 '다시 결제하기'로 주문서에 보내고, 주문서의 [결제하기] 한 번이 이전 주문을 닫고 새 주문·새 시도를 만든다. 생성 시 장바구니를 비웠던 이전 주문만 기존 '취소하고 다시 담기' 흐름을 쓰고, 장바구니가 남은 주문은 서버 복원 액션이 다시 담지 않는다(중복 재담기 금지).

결제 전 주문이 잡은 재고는 그 주문이 닫힐 때까지 돌아오지 않으므로, 재고가 적은 굿즈는 결제 대기 중에 같은 옵션을 장바구니에 더 담을 수 없다. 장바구니·주문서로 돌아오면 닫기가 먼저 돌아 해소된다.

앱의 두 장바구니 주문 진입점(legacy `place_order_with_cart_snapshot`, 거래 런타임 `place_cart_goods_transaction`)이 같은 규칙을 쓴다. "주문 = 장바구니 전체" 스냅샷 계약은 유지하며, 다른 탭의 중복 주문은 이전 미결제 주문 닫기로 정리된다. 직접 호출하는 신뢰 경로(`place_order*`)는 생성 시 소비를 유지한다.
