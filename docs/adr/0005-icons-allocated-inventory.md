# 판매 재고는 WMS에서 격리한 ICONS 할당 물량으로 한다

2026-09-08: **WMS 물량을 ICONS 판매용으로 격리한다는 운영 계약은 유지한다.** 아래는 굿즈 단위 재고를 사용하던 당시 결정의 기록이다. 저장·선점 단위와 운영자 입력 대상은 [ADR-0015](./0015-goods-variants.md)가 대체한다. 현재 재고 진실원은 `goods_variants.stock_qty`이며, `goods.stock_qty`는 보관 옵션을 포함한 전체 옵션 합계 캐시다. 운영자는 옵션 재고를 조정하고, 굿즈 캐시를 WMS 수량으로 직접 덮어쓰지 않는다. 캐시 갱신·대조 규칙은 ADR-0015에 기록한다.

모회사는 이미 물류 스택(김포 창고 · 한진택배 · WMS)을 보유하고 있어 같은 굿즈의 실재고가 WMS에도 존재한다. 그런데 ICONS의 `place_order`는 `goods.stock_qty`를 행 잠금으로 원자적 선점하며([`p1_commerce.sql`](../../supabase/migrations/20260617090002_p1_commerce.sql)), 이 락은 **ICONS 안에서만** 유효하다 — WMS는 이 선점을 모른다. 첫 실판매에서는 WMS 실재고 중 일부를 **ICONS 판매용으로 격리**하고, 그 물량에 한해 `goods.stock_qty`를 단일 진실원으로 삼는다. 격리된 물량은 다른 판매 채널이 건드리지 않는다는 것이 이 결정의 전제이자 운영 계약이다.

## Considered Options

- **공유 재고 + 실시간 동기화** — WMS 실재고를 여러 채널이 공유하고 ICONS는 이를 미러링한다. 채널이 늘어도 재고가 한 곳에서 관리되는 정공법이다. 그러나 웹훅이나 폴링 동기화 인프라가 필요하고, 그 스펙은 WMS 연동 표면(API 여부)에 종속돼 첫 판매 일정 밖에 있다. 동기화가 없거나 지연되면 결제 완료 후에 재고 부족이 발견된다 — 실물 커머스에서 가장 비싼 실패다. 폐기(후속 전환 대상).
- **WMS를 진실원으로 두고 ICONS는 판매만** — 주문 시점에 WMS에 재고를 조회·차감한다. 초과판매는 원천 차단되지만 외부 호출이 주문 트랜잭션 경로에 들어와 `place_order`의 원자성이 깨지고, WMS 장애가 곧 판매 중단이 된다. 폐기.
- **ICONS 할당 재고 (채택)** — 물리적/논리적 격리로 **동기화 문제 자체를 없앤다**. 코드 변경이 0이고 기존 원자적 선점이 그대로 정확해진다. 대가: 격리 물량을 운영자가 수동으로 정하고 입력해야 하며, 채널 간 재고 이동이 운영 작업이 된다. SKU 3종 소프트런칭에서는 이 부담이 동기화 인프라 구축 비용보다 훨씬 작다.

## Consequences

- **`goods.stock_qty`의 의미가 좁아진다.** 전체 실재고가 아니라 **ICONS에 할당된 물량**을 가리킨다. [`CONTEXT.md`](../../CONTEXT.md)에 "할당 재고"로 정의했다. 이 구분을 놓치면 어드민 재고 조정이 WMS 숫자를 반영하려 들면서 초과판매를 만든다.
- **초과판매 방지의 책임이 코드에서 운영으로 이동한다.** ICONS의 원자적 선점은 여전히 정확하지만, 그 정확성은 "격리가 지켜진다"는 운영 계약 위에 서 있다. 계약이 깨지면 코드는 막지 못한다.
- **판매 개시의 선행 조건이 하나 늘어난다** — 할당 물량 확정과 `stock_qty` 입력이 필요하다([first-sale-readiness §3.3 F3](../first-sale-readiness.md)).
- **되돌리기 비용**: 채널이 늘어 공유 재고로 전환하려면 WMS 연동·동기화·충돌 해소를 한 번에 지어야 하고, 그 사이 두 모델이 공존하는 기간의 정합성 처리가 따로 필요하다 — 그래서 기록한다. 전환은 WMS 연동 표면과 실제 다채널 수요가 확인될 때 별도 이슈와 ADR로 결정하며, 폐기된 범용 팝업 에픽에 종속하지 않는다.

## 2026-11-12 보완 — 재고 파일 대조(동기화 아님)

2026-10-07 회의 요청("재고가 일치가 해야 아무래도 클레임 같은 거나 이런 것도 줄기 때문에")과 11/11 사용자 결정("재고 파일 반입·대조")에 따라, **할당 재고 모델과 동기화 기각은 그대로 두고** 수동 반입 경로를 더한다. ERP·WMS API 연동은 여전히 하지 않는다(비용·계약 뒤 별도 ADR).

- 운영자가 올리는 파일 수량은 **그 시각 창고에 있던 ICONS 몫 실물**이다. 위 Consequences의 위험("어드민 재고 조정이 WMS 숫자를 반영하려 들면서 초과판매")을 피하려고 파일 수량을 그대로 넣지 않는다. 사이트 재고는 주문 때, 창고 실물은 출고 때 줄므로 `맞춘 뒤 재고수량 = max(파일 − 출고 대기 − 파일 기준 시각 뒤 출고, 0)`으로 계산한다. 주문 접수·출고는 이 차이를 바꾸지 않아 미리보기 뒤 주문이 들어와도 그대로 반영할 수 있다.
- 반영은 미리보기 → 확인 → 상품·옵션 행 잠금 아래 한 번에(모두 아니면 아무것도) 하고, 멱등·옵션별 감사 기록을 남긴다. 못 찾은 행·중복 행·다른 출고지 상품은 반영하지 않는다.
- 파일 수량이 출고 대기보다 적으면(부족) 재고수량을 0으로 두고 경고한다 — 이미 받은 주문의 처리는 운영 판단(ADR-0018)이다. 출고지시 전 경고는 최근 파일 기준으로 같은 부족·차이를 보인다.
- 운영 절차와 한계는 [재고 파일 대조·안전재고 요약 메일 운영](../runbooks/stock-reconcile-safety-digest.md)에 둔다.
