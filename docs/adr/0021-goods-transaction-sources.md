# 주문 계산은 공유하고 선택 원본·배송 당사자·자동결제를 분리한다

- Status: accepted (2026-10-14)
- 관련: [공통 주문 계약](../research/smartstore-admin/goods-transaction-module-proposal.md), [선물](../research/smartstore-admin/gift-orders-transaction-proposal.md), [정기배송](../research/smartstore-admin/subscription-transaction-proposal.md)

일반 장바구니, 선물, 정기배송 회차는 같은 굿즈의 가격·할인·운임·재고·혜택을 사용한다. 각 경로에 별도 금액 산식을 만들거나 고객의 장바구니를 임시로 교체하는 대신, DB의 공통 확정 견적과 주문 생성을 재사용하고 소유권을 검증한 선택 원본만 달리한다. 주문 생성은 관련 상태를 잠근 뒤 다시 계산하며, 고객이 확인한 조건이 달라지면 새 견적을 요구한다. 이 구조는 원본별 정책을 공통 함수에 무제한 추가하지 않으면서 재고·쿠폰·적립금과 전체 취소/환불 계약을 공유한다.

계산 버전 2는 기간 할인 후 소계에서 복수구매 할인, 쿠폰, 적립금을 순서대로 차감하고 선불 운임을 더한 온라인 금액을 확정한다. 착불 운임은 별도 외부 수납 의무로 보존한다. 과거 주문의 금액과 배분은 현재 정책으로 재계산하지 않으며, 기존 필드의 뜻을 바꾸지 않고 새 버전과 불변 품목·운임 배분을 추가한다. 같은 주문 생성 키는 견적 개인정보가 정리된 뒤에도 원래 영수증으로 복구한다.

선물은 수령인이 수락하고 주소를 입력한 뒤 구매자가 결제한다. 금융 원장은 구매자가 소유하고, 수령인 주소는 별도 private 배송 원장이 소유한다. 주소를 기존 공개 주문에 저장하고 화면에서만 숨기는 대안은 직접 REST 조회·서버 응답·출고·알림에서 노출을 일관되게 막기 어려워 사용하지 않는다. 운영 조회는 배송 소유자를 통해 실제 주소를 읽고, 고객 DTO와 알림은 구매자와 수령인 각각의 공개 범위를 적용한다. 환불은 구매자 결제수단으로 처리하며 실제 클레임 요청자는 별도 보존한다.

정기배송은 회차마다 공통 주문을 생성하고 별도 `RecurringBilling` 인터페이스로 카드 등록·청구·조회·폐기를 수행한다. 기존 주문서형 토스와 provider 이름이 같아도 가맹점·키 종류는 같다고 가정하지 않는다. 결제 시도에는 불변 연동 종류·프로필·MID·환경·최초 쓰기 키 버전을 결속하고, 이후 조회·환불·정산도 이 식별자로 선택한다. 주소·카드 암호문을 정리해도 금융 결제 시도가 남아 있는 동안 비밀이 아닌 연결 정보와 원환불 멱등 정보는 보존한다. 계정 정보 삭제가 일반 결제 키를 선택하는 우회 경로가 되어서는 안 된다.

외부 결과가 불명확한 회차는 원래 주문·결제 시도로 조회하며 새로 청구하지 않는다. 해지는 미래 회차를 중지하고, 이미 시작한 결제의 확정·환급 복구는 유지한다. 금액·착불 조건·주기·배송지가 바뀌면 새 조건에 대한 고객 동의를 받는다. 부분취소·부분반품은 확정 제외 범위를 유지한다.

이 결정은 구현 구조와 거래 계약을 정한다. 실제 빌링 계약·키 준비, 외부 거래 실행, 배포와 공개 스위치 활성화는 별도 운영 절차다.
