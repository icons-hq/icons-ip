# 공개 상품 주소는 상품 자동코드로 연다 — 내부 id는 그대로 두고 옛 주소는 새 주소로 옮긴다

- Status: accepted (2026-11-24) — 사용자 결정(아래 인용). main 머지와 운영 배포는 별도 승인.
- 보완: [ADR-0038](./0038-system-product-number.md)(`goods.id`를 '상품 URL'이라 부르고 공개 주소·외래키로 둔 결정 — 공개 주소의 뜻만 바뀐다), [ADR-0048](./0048-auto-generated-code-labels.md)(상품 자동코드·'직접 바꾸기' — 코드가 고객 화면 주소 끝에도 쓰인다)
- 관련: [ADR-0039](./0039-ip-internal-id-and-draft-delete.md)(IP의 내부 ID와 공개 URL 분리 — 같은 모양의 선례), [ADR-0024](./0024-adult-verification-kcp.md)(19금 상품 가림)

## 맥락

MD-0051(신사업팀 김미주 대리, 2026-11-23): "상품 URL > 상품 코드로 불러오기, 영문 표기 틀림." 기대 동작은 "상품 코드에 맞게 주소가 생성됨"이다.

공개 상품 주소는 `goods.id`였다. 새 상품의 `goods.id`는 상품명을 로마자로 바꾼 값(`private.goods_slug_from_name`, 예: `/shop/hongsilkweseuteu-akeuril-hyudaepon-kiring`)이라 실제 영문 표기와 맞지 않고, MD가 고칠 수도 없었다(최초 공개 뒤 잠김). 한편 `goods.id`는 PK이자 주문·장바구니·찜·리뷰·Q&A·재고·쿠폰·전시 구성이 가리키는 외래키라 값을 바꾸면 기록 전체를 옮겨야 한다.

사용자 결정 원문(2026-11-24, 선택지): "전 상품 코드 주소 (권장) — 49개 기존 상품 포함 모두 /shop/hsq-0059처럼 상품 자동코드로 열리게 하고, 옛 주소로 들어오면 새 주소로 자동 이동. 내부 식별자는 그대로라 주문·재고 영향 없음".

## 결정

1. **공개 상세 주소는 `/shop/<상품 자동코드 소문자>`다.** 상품 자동코드(`goods.code`, 저장 시 대문자)는 이미 NOT NULL·UNIQUE라 새 열 없이 쓴다. 주소 조립은 `lib/goods-display.ts`의 `goodPublicSegment`·`goodDetailHref` 한 곳이다. 코드가 주소로 쓸 수 없는 모양(공백·한글·기호, `/shop/new`·`/shop/best`와 같은 값)이면 그 상품은 내부 id 주소에 머문다 — 퍼센트 인코딩·대소문자 변환이 어긋나 열리지 않는 주소를 만들지 않는다.
2. **`goods.id`는 바꾸지 않는다.** PK·외래키·주문 스냅샷·재고·리뷰·Q&A·찜·장바구니·쓰기 액션은 모두 내부 id로 읽고 쓴다. 새 상품의 내부 id 생성도 그대로다.
3. **상세 라우트가 끝 값을 푼다.** `/shop/[goodId]`는 끝 값을 `public.resolve_public_goods_address`로 풀어 내부 id와 정식 끝 값을 얻는다. 코드(대소문자·앞뒤 공백 무시)가 내부 id보다 먼저다. 끝 값이 정식과 다르면(옛 내부 id 주소, 대문자 코드) 쿼리를 그대로 둔 채 정식 주소로 영구 이동(`permanentRedirect`)한다. 다만 그 방문자가 볼 수 없는 상품(19금 gate가 닫힌 방문자 등)은 옮기지 않고 404다. 정적 경로(`/shop/new`·`/shop/best`)가 동적 라우트보다 먼저라 겹치지 않는다. Next 16 동적 라우트는 루트 loading이 먼저 흘러 이동이 응답 상태(308)가 아니라 본문(meta refresh·RSC digest)으로 나갈 수 있다 — 제목 생성(`generateMetadata`)에서도 같은 이동을 해, 제목 생성이 본문보다 먼저 끝나는 요청(수집기 등)에서는 응답 상태로 나갈 수 있게 했다(응답 상태 실측은 배포 뒤 확인).
4. **해석 RPC는 좁다.** `resolve_public_goods_address(p_value)`는 security definer·stable·빈 search_path이고 anon·authenticated만 실행한다. 공개 상품(게시·미보관·부모 IP 게시·미보관, 판매 제한 없음 또는 19금 판매 표면이 켜진 19금)의 id·상품 자동코드만 돌려준다. 이름·이미지·가격은 돌려주지 않는다. 인증 전 방문자는 19금 상품 행을 RLS로 읽지 못하므로(20261118160000) 정의자 읽기가 필요했고, 19금 상품의 코드는 노출돼도 된다(사용자 결정 범위). 호출자를 보지 않아 쇼핑 화면 공개 조회 캐시의 public 등급이다.
5. **링크는 코드 주소로 만든다.** 굿즈 뷰모델(`Good.code`)을 싣는 공개 표면(목록·홈·검색·컬렉션·카테고리 전시(전시 투영 `private.category_display_public_good`에 코드를 더했다)·상세 선반·위시·장바구니·최근 본·캠페인·쇼핑스토리·사이트맵·구조화 데이터·Open Graph·재입고 메일·마케팅 링크)은 코드 주소를 바로 쓴다. 화면 주소에서 굿즈 대상을 읽는 매장 분석·회원 활동 기록은 서버가 코드를 내부 id로 바꿔 기록한다(집계·리포트·마케팅 링크 대조가 내부 id 기준). 운영자가 저장한 `/shop/<내부 id>` 홈 전시 링크는 읽어 둔 공개 굿즈로 코드 주소로 바꿔 그린다. 내부 id만 아는 곳(DB가 만드는 알림 링크, 주문서·바로구매 복귀, 어드민 문의·리뷰 화면의 상품 링크)은 옛 주소로 두고 상세가 옮긴다 — 저장된 링크는 코드가 바뀌어도 끊기지 않는다.
6. **어드민 'URL' 칸은 고객 화면 주소를 보인다.** 상품 등록·수정의 예전 '상품 URL' 칸(내부 id 입력, "한 번 공개한 URL은 변경할 수 없습니다")은 읽기 전용 **고객 화면 주소**(`iconsip.com/shop/<코드 소문자>`, 새 상품은 예상 코드)로 바뀌고, 내부 id는 숨은 값으로 지금 그대로 보내 저장 계약을 지킨다. 상품 자동코드를 '직접 바꾸기'로 바꾸면 주소도 바뀐다는 안내를 붙인다. 전시 상품 선택기의 'URL로 추가'는 코드 주소를 받아 상품 URL로 바꿔 고른다.

## 검토한 대안

- **`goods.id`를 코드로 바꾼다.** 주소와 식별자가 하나가 되지만 모든 외래키·주문 스냅샷·감사 기록·저장된 전시 구성을 옮겨야 하고, '직접 바꾸기'로 코드가 바뀔 때마다 같은 일이 생긴다. 사용자 결정("내부 식별자는 그대로")과도 어긋난다. 기각.
- **새 상품만 코드 주소, 기존 상품은 옛 주소.** 주소 규칙이 둘이 되고 49개 기존 상품의 로마자 주소가 남는다. 사용자가 "49개 기존 상품 포함 모두"를 골랐다. 기각.
- **별도 공개 slug 열(IP처럼 `public_slug` + 별칭 표).** 코드와 따로 바꿀 수 있는 주소가 생기지만 MD가 관리할 칸이 하나 더 늘고, 요청은 "상품 코드에 맞게"였다. 상품 자동코드가 이미 고유하고 사람이 읽는 값이다. 기각.
- **코드 변경 이력(별칭 표)으로 옛 코드 주소도 옮긴다.** 직접 바꾸기는 드물고(창고 품번·잘못 들어간 값 수정), 옛 코드를 다른 상품이 새 코드로 쓰면 충돌 규칙이 필요하다. 이번에는 안내로 대신하고 필요해지면 별칭 표를 더한다.
- **미들웨어(proxy)에서 리디렉션한다.** 실제 308 상태를 주지만 모든 `/shop/*` 요청에 DB 조회가 붙는다. 상세 라우트 안에서 푸는 쪽을 골랐다.

## 결과

- 기존 상품도 배포 즉시 코드 주소로 열린다(데이터 이전 없음). 상품 자동코드를 처음 들일 때(2026-09-08) `upper(id)`로 채워진 뒤 그대로인 상품은 주소도 그대로다.
- 이미 공유된 옛 주소(카카오·메일·검색 색인)는 코드 주소로 옮겨진다. 사이트맵·구조화 데이터·Open Graph는 코드 주소만 싣는다.
- 상품 자동코드를 직접 바꾸면 바꾸기 전 코드 주소로는 상품이 열리지 않는다(옛 내부 id 주소는 계속 옮겨진다). 어드민 칸 안내가 이 점을 알린다.
- 어드민 여러 화면이 `goods.id`를 아직 '상품 URL'이라 부른다(목록 열·검색 대상·엑셀). 값은 이제 고객 주소가 아니라 처음 저장할 때 정한 영문 값이다 — 이름 정리는 별도 후속이다.
- 남은 경계: 한 상품의 내부 id가 다른 공개 상품의 코드 소문자와 같으면 그 끝 값은 코드 쪽 상품으로 열린다(코드 우선). 내부 id는 상품명 로마자, 자동코드는 `접두-번호`라 실제로 겹칠 가능성은 낮다.
- 검증: `supabase/tests/goods_public_read_visibility.sql` §5(권한·반환 열·공개 범위·19금 판매 표면), 상세 라우트·주소 헬퍼·사이트맵·선택기 Vitest.
