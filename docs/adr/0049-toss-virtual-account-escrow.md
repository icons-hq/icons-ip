# 무통장 입금은 토스 가상계좌(에스크로 선택)로 받는다 — 입금 대기는 결제 시도의 새 상태다

- Status: accepted (2026-11-23) — 적대적 리뷰 반영. 운영 스위치 꺼진 채 배포하고, 라이브 키 전환과 함께 켠다(runbook).
- 대체: [ADR-0013](./0013-toss-default-pg-pivot.md)과 `docs/ARCHITECTURE.md` §9의 "토스 가상계좌는 에스크로 계약이 없어 발급 즉시 취소한다"는 가드. 카드·간편결제 흐름과 판단 규율(조회 재검증·DB 멱등 finalizer·MID 대조)은 그대로다.
- 유지: [ADR-0007](./0007-bank-transfer-payments.md) 자체 법인계좌 무통장 입금은 닫힌 채 둔다(설정 계좌 없음). 이 ADR은 그 기능을 지우지 않는다.
- 관련: 토스 공식문서(MCP 2026-11-23 실조회) — 가상계좌 결제창 연동 `/guides/v2/payment-window/integration-virtual-account`, 가상계좌 총정리 `/resources/glossary/virtual-account`, 웹훅 `/guides/v2/webhook`·`/reference/using-api/webhook-events`, 결제 취소 `/guides/v2/cancel-payment`, 에스크로 `/guides/v2/escrow`·`/reference/additional#에스크로`, 배포 체크리스트 `/guides/v2/deploy-checklist`, 기관 코드 `/codes/org-codes`.

## 맥락

2026-11-23 사용자 결정(원문): 토스 라이브 키 전환과 함께 "무통장 입금도 같이 계약 됐었다고 하던데 이것도 확인해서 도와줘" → 선택 "토스 가상계좌", 순서 "가상계좌까지 끝나고 함께"(라이브 키 전환은 가상계좌 오픈과 한 번에).

- ICONS 상점 MID `iconsi0xvd`의 계약 결제수단에 가상계좌·계좌이체가 **에스크로 사용**으로 들어 있다(2026-10-12 상점관리자 실측). 자체 법인계좌 무통장은 환불 종결·입금 대조·구매안전서비스가 갖춰지지 않아 닫혀 있다.
- 토스 문서: 가상계좌는 승인 API 200이 곧 **계좌 발급**(`WAITING_FOR_DEPOSIT`)이고 입금 시 `DONE`이다. `PAYMENT_STATUS_CHANGED`는 모든 결제수단에 간다(`DEPOSIT_CALLBACK`을 함께 등록하면 가상계좌 변경이 두 번 온다). **입금 기한 만료에는 웹훅이 없고** 상태가 `WAITING_FOR_DEPOSIT`로 남는다. 일부 은행은 입금 통보(`DONE`) 뒤 취소 통보(`WAITING_FOR_DEPOSIT`)를 보낸다. 입금 전 취소는 계좌 반납(전액만, 환불 계좌 불필요), 입금 뒤 취소는 `refundReceiveAccount`(은행 코드·계좌번호·예금주)가 필수이고 부분 취소는 입금 전 불가다.
- 주문서형에서 가상계좌 입금 기한은 상점관리자 설정이 정한다(SDK에 `validHours`가 없다). 그래서 기한의 진실원은 결제 응답 `virtualAccount.dueDate`다.
- 배송이 필요한 상품의 현금성 결제(가상계좌·계좌이체)는 에스크로 적용 대상이다. 주문서형은 계좌이체·가상계좌에 에스크로 체크박스를 자동으로 띄운다(구매자 선택). 에스크로 결제는 발송 시 배송 등록 → 전 상품 배송완료 후 구매확정(3영업일 자동확정) 흐름이고, 구매확정 전에는 부분 취소가 불가하다. 2026-10 에스크로 API(`/v2/escrows`·`/v2/deliveries`)와 `escrow.changed`·`delivery.changed` 웹훅이 나왔다.

## 결정

1. **방식.** 무통장 입금은 토스 주문서형 결제 UI `ICONS`의 가상계좌로 받는다. 굿즈 주문(`purpose='order'`)만이다. 티켓·정기결제는 지금 가드(발급 즉시 반납) 그대로다. 주문의 `payment_method`는 `card`(=PG 온라인 결제) 그대로 두고, 가상계좌 여부는 결제 시도 상태·결제사 증거로 판정한다 — `order_payment_method` 열거에 값을 더하면 주문 생성·장바구니 보류·통계 함수 수십 곳이 갈라진다(조사 결과).
2. **켜는 법(사람·운영 스위치).** Production 서버 env `TOSS_VIRTUAL_ACCOUNT_ENABLED=true`일 때만 **새 발급**(승인 콜백의 `WAITING_FOR_DEPOSIT`)을 입금 대기로 받는다. 꺼져 있으면 새 발급은 지금 가드(발급 즉시 반납)라 결제 어드민 설정 실수로 가상계좌가 노출돼도 판매가 성립하지 않는다. 스위치는 새 발급만 막는다 — 이미 입금 대기인 주문의 입금·만료·반납은 결제 UI 바인딩이 있는 한 재정합으로 계속 닫힌다(drain). 결제 UI 바인딩이 없는 배포·티켓은 스위치와 무관하게 지금 가드다. 켜려면 결제 UI 바인딩(`TOSS_WIDGET_VARIANT_KEY`)이 있어야 하고 법정 문서 개정이 시행 중이어야 한다(빌드 가드). 결제 UI `ICONS`에 가상계좌를 노출하는 것은 사람이 결제 어드민에서 한다.
3. **입금 대기는 결제 시도의 새 상태 `awaiting_deposit`다.** 기존 상태로는 성립하지 않는다 — `prepared`는 장바구니 대체·만료 정리가 TTL 없이 닫고 재정합이 잡지 못한다, `confirming`은 리스가 입금 웹훅을 503으로 밀어낸다, `unknown`은 시스템 장애 집계에 섞이고 만료되지 않는다.
   - 진입: 승인 200(또는 재확인·재정합 조회)이 이 주문·이 상점·이 결제의 `WAITING_FOR_DEPOSIT`이고 입금 기한이 지금 뒤 **72시간 이내**면, 전용 finalizer가 시도 상태를 `awaiting_deposit`으로 바꾸고 주문·시도의 `expires_at`을 입금 기한으로 늘리며 가상계좌(은행 코드·계좌번호·기한·에스크로 선택·결제 UI가 받은 환불 계좌)를 private 표에 남긴다. 기한이 범위 밖이면 계좌를 반납하고 실패로 닫는다(재고를 무기한 잡지 않는다).
   - DB가 입금 대기를 거부하면(취소 요청 진행 중·계정당 열린 입금 대기 2건 초과·기한 범위 밖·주문 상태 불일치) 시도를 `needs_review`로 두고 앱이 **같은 요청에서** 계좌를 반납한다(멱등키 `release-va:{attemptId}`) — 발급된 계좌가 열린 채 남지 않게 한다. 반납은 취소 응답·조회가 `CANCELED`이거나 계좌가 만료(`expired`)됐을 때만 `declined`로 닫는다. 그 밖(반납이 거절됐는데 조회도 입금 전)은 `unknown`으로 남겨 자동 재확인이 다시 본다 — 그래서 결제 없이 닫힌 시도에 입금이 들어오는 일이 없다.
   - 입금: 웹훅·자동 재확인이 조회한 `DONE`(가상계좌)을 기존 승인 finalizer로 `approved` 확정한다. 이후 경로(결제완료·주문 확인 메일·발주확인)는 카드와 같다.
   - 만료: 웹훅이 없으므로 자동 재확인 cron이 입금 기한이 지난 `awaiting_deposit`을 조회한다(기한 무관하게 6시간마다도 한 번 — 웹훅 누락 대비). 토스가 계좌를 만료(`expired`)시켰으면 반납 호출 없이, 아니면 기한 + 30분 유예(늦은 입금 통보 재전송) 뒤 반납하고 `declined`로 닫는다 → 만료 정리(`expire_stale_checkouts`)가 주문을 취소하고 재고·쿠폰·적립금을 되돌린다. 조회가 실패하면 상태를 바꾸지 않는다(입금이 들어왔을 수 있다). 기한 + 2시간이 지나도 닫히지 않으면 시스템 상태의 미종결 결제로 보인다.
   - 조회 힌트: 주문서형 시크릿 키가 쓸 수 있다고 명시된 조회는 paymentKey 조회라, 본문에 결제 키가 없는 웹훅(`DEPOSIT_CALLBACK`)·자동 재확인은 저장한 결제 키를 힌트로 조회한다.
   - 정리 함수는 `awaiting_deposit` 주문을 건드리지 않는다: 만료 정리·장바구니 대체·취소 가드·미해결 결제 집계 목록에 상태를 더한다. 하나라도 빠지면 입금이 들어올 수 있는 주문의 재고가 풀리므로 SQL 스모크로 고정한다.
   - 입금 전 고객 취소: 주문 취소 요청 → 오케스트레이터가 계좌를 반납하고 `canceled`로 닫아 기존 취소 확정 경로를 탄다.
4. **입금 오류 되돌림.** (2026-11-24 개정 — 아래 보강이 정본이다.) 이미 `approved`인 가상계좌 결제에 `WAITING_FOR_DEPOSIT` 웹훅이 오면 원장을 되돌리지 않고, 결제사 직접 취소 감지(잔액이 그대로라 되돌림을 '이상 없음'으로 읽는다)보다 **먼저** 원장 결제 키로 조회해 되돌림이면 주문 출고 보류(사유 `deposit_reversed`)를 건다 → 발주확인·출고에서 빠진다. 해결(재입금 확인 → 보류 해제, 기한까지 재입금 없음 → 계좌 반납 뒤 주문 자동 취소)은 시스템이 한다. 토스 공식 문서 가상계좌 총정리(`/resources/glossary/virtual-account`, 2026-11-23 MCP 재조회)가 같은 경고(일부 은행, 특히 신한은 입금 통보 뒤 1~2초에서 최대 2분 이상 지나 취소 통보)와 함께 안내하는 **"2분 지연통보"**(입금 뒤 2분간 취소 통보가 없을 때만 상점에 입금 통보)는 발생을 줄이는 보조 수단이다(사람 — 신청 경로는 문서에 없어 토스 고객센터 1544-7772·영업 담당자에게 문의). 2분이 넘게 늦은 취소 통보는 막지 못하므로 신청 여부와 관계없이 시스템 처리가 필요하다. 창고에 넘어가기 전에 잡히도록 자동 발주확인은 가상계좌 주문을 마지막 입금 확인 1시간 뒤부터 확정한다([ADR-0025](./0025-auto-order-confirmation.md) 2026-11-24 보강). API 버전 1.4 이하 상점은 되돌림이 `CANCELED`로 와 결제사 직접 취소 보류로 잡힌다(지금 버전 2024-06-01).
5. **입금 뒤 환불.** 결제 원장이 가상계좌면 취소 API에 환불 계좌를 싣는다. 환불 계좌는 **결제 UI가 받은 구매자 환불 계좌**다 — 결제 어드민 '가상계좌 환불 정보 입력: 사용함'을 켜면 승인 응답의 `virtualAccount.refundReceiveAccount`(토스 은행 코드, 결제창 뒤 30분만 조회)에 실리고, 입금 대기 확정 때 private 표에 남겨 180일 뒤 지운다. 2026-11-23 보강(아래)부터는 구매자가 반품·취소 신청 화면이나 주문 상세에서 입력한 클레임 환급 계좌를 먼저 쓴다. 쓸 환불 계좌가 없으면 결제사를 부르지 않고 `needs_review`(`provider_refund_account_required`)로 남긴다 — 구매자가 주문 상세에서 계좌를 입력하면 취소는 시스템이 다시 환불하고, 반품은 운영자가 '상태 다시 확인'으로 환불한다. 구매자가 입력하지 않으면 운영자가 계좌를 받아 토스 상점관리자에서 환불하고 '상태 다시 확인'을 누르면 원장 조회가 전액 취소를 확인해 닫힌다. 멱등키는 계좌별로 가른다(`refund:{attemptId}:va-{계좌 해시}`) — 틀린 계좌로 거절된 첫 응답이 고친 계좌의 요청에 15일간 재생되지 않게 한다. 결제사가 계좌를 거절하면 `provider_refund_account_invalid`, 은행 환불이 실패(`refundStatus` FAILED)하면 `provider_refund_failed`로 환불 완료로 닫지 않는다. 부분 취소·부분 반품은 가상계좌에 열지 않는다(지금 SQL 차단 유지) — 주문 전체 취소·반품만(2026-11-25 보강이 에스크로가 아님이 확인된 입금 결제에 연다 — 아래). 입금 전 고객 취소는 환불이 아니라 반납이다(재정합 반납 힌트, 같은 `release-va` 키).
6. **에스크로.** 결제 요청에 `escrowProducts`를 싣지 않는다 — 토스가 주문 하나를 상품 하나로 만든다(에스크로 가이드). 구매자가 에스크로를 고른 결제(선택을 모르면 조회로 확인)는 입금 승인 뒤 주문 단위 배송 등록 작업이 생긴다(`private.toss_escrow_deliveries`):
   - **배송 등록**: 실물 배송 건(취소·디지털·배송 없음 제외)이 **전부** 발송됐을 때(택배는 운송장과 함께 배송중·배송완료, 퀵·방문수령·직접배송·화물은 배송완료) 한 번 등록한다 — 택배가 있으면 가장 늦게 발송된 택배의 운송장(SHIPMENT), 없으면 직접 전달(DIRECT). 실물이 없는 주문은 승인 즉시 DIRECT다. 15분 cron(`/api/cron/toss-escrow`)이 결제 조회로 `escrowKey`를 찾고 거래 조회의 `products[].id`로 `POST /v2/deliveries`(멱등키 `escrow-delivery:{orderId}:{revision}`)한다. 등록 뒤 운송장 정정은 `POST /v2/deliveries/{id}`(택배 → 택배만). 자동으로 못 하는 것(택배사 코드 없음·송장 형식 거절·에스크로 API 권한 없음·배송 방법이 바뀌는 정정)은 운영자 확인으로 남기고 토스 상점관리자에서 등록한다.
   - **키(2026-11-23 보강)**: 에스크로 거래 조회·배송 등록·수정·취소 요청 수락은 부가서비스 API라 결제 위젯 시크릿 키(gsk)로 부를 수 없다 — 토스 공식 문서 'API 키'(`/reference/using-api/api-keys`)는 gsk를 코어 API(결제 승인·결제 취소·paymentKey로 결제 조회·거래 조회·정산 조회)로 한정하고 부가서비스 API는 API 개별 연동 시크릿 키(sk)로 부르라고 한다. 처음 구현은 gsk로 불러 거래 조회가 4xx로 거절되면 작업이 운영자 확인으로 굳었다. 그래서 서버 env `TOSS_ESCROW_SECRET_KEY`(MID `iconsi0xvd`의 API 개별 연동 sk, 결제 키와 같은 모드, production 전용 — 빌드 가드·readback `Toss escrow key configured`)를 따로 받아 에스크로 API에만 쓰고, 결제 조회는 그대로 gsk다. 키가 없으면 작업자는 작업을 고르지 않고(대기 그대로) 처리할 작업이 있으면 실패(`toss_escrow_key_missing`)로 시스템 상태에 알린다. 키 거절(401·403·UNAUTHORIZED_KEY 등)은 운영자 확인이 아니라 다시 시도이고, 예전 키 거절로 굳은 작업은 migration `20261125105000`이 대기열로 돌린다.
   - **거래 상태**: 같은 cron이 1시간마다 `GET /v2/escrows/{id}`로 거래 상태를 읽어 남긴다(확정·취소되면 멈춘다). `escrow.changed` 웹훅은 등록하지 않는다(조회로 충분하고 등록·파서·서명 검증이 늘지 않는다). 구매자 취소 신청(`CANCEL_REQUESTED`)은 주문 출고 보류(사유 `escrow_cancel_requested`)로 운영 할 일에 보이고, 운영자 전액 취소가 이 거래에서는 결제 취소 대신 **에스크로 취소 수락 API**(환불 계좌는 구매자가 신청 때 등록한 계좌)를 부른다. 가상계좌·계좌이체 모두다(2026-11-23 보강 — 처음 구현은 가상계좌만 이 분기를 탔다). 신청 중에는 배송을 등록하지 않는다.
7. **웹훅.** 등록 이벤트는 `PAYMENT_STATUS_CHANGED`(기존)과 `DEPOSIT_CALLBACK`(가상계좌 입금 통보, 사람 등록)이다. 웹훅 가이드는 `PAYMENT_STATUS_CHANGED`가 모든 결제수단에 쓰인다고, 웹훅 이벤트 문서는 대상을 카드·계좌이체·휴대폰·상품권으로 적어 두 문서가 엇갈리고, 배포 체크리스트는 `DEPOSIT_CALLBACK` 등록을 요구한다 — 둘 다 등록해 같은 변경이 두 번 와도 재정합은 멱등이다. `DEPOSIT_CALLBACK` 본문(`eventType`·`paymentKey` 없는 `{createdAt, secret, status, transactionKey, orderId}`)은 orderId·status만 읽고 `secret`은 저장·대조하지 않는다. 소문자·점 이름의 부가 API 이벤트(`escrow.changed` 등)는 200으로 받고 처리하지 않는다. 어떤 웹훅 본문도 확정 근거가 아니다.
8. **고객 화면·알림.** 승인 콜백이 `awaiting_deposit`이면 주문 완료 화면이 입금 안내(은행·계좌번호·입금 금액·입금 기한)를 보이고, 주문 상세·목록은 '입금 대기'로 보인다. 발급 즉시 입금 안내 메일·앱 알림을 보내고, 입금 확인 뒤에는 기존 주문 확인 메일이 간다. 계좌번호는 결제사가 주문마다 발급한 수납 계좌라 구매자 개인정보가 아니지만 주문 본인·운영자에게만 보인다.
9. **법정 고지.** 이용약관 제11조(지급방법)에 가상계좌·구매안전서비스, 개인정보처리방침 처리위탁 토스페이먼츠 행에 가상계좌·에스크로·현금영수증, 배송·반품 정책에 입금 기한을 더한다. 공개 이후 개정이라 7일 사전 공지 뒤 시행한다(개정 예약 모듈, 빌드 가드). 사이트 하단에 구매안전서비스 가입 사실을 토스 공식 에스크로 인증 마크와 함께 표시한다(아래 보강).

## 결과

- 결제 확정 규율은 그대로다: 승인·입금·만료·반납 모두 조회 API 재검증 + DB 멱등 finalizer로만 닫힌다.
- 입금 대기 주문은 입금 기한까지 재고·쿠폰·적립금을 점유한다. 기한 상한 72시간은 결제 어드민 설정(24시간 권장) 실수를 막는 방어선이다.
- 사람 몫: 결제 UI `ICONS`에 가상계좌 노출(테스트 → 라이브)과 '가상계좌 환불 정보 입력: 사용함', 입금 기한 24시간 설정, 2분 지연통보 신청, 에스크로 사용 설정 확인, `DEPOSIT_CALLBACK` 웹훅 등록, 개발자센터 API 버전 확인, env 스위치, 법정 문서 공지일 확정.
- 남는 한계(후속): 가상계좌 결제의 부분 취소·부분 반품 없음(2026-11-25 보강으로 에스크로가 아닌 입금 결제는 열렸다 — 에스크로 결제만 남는다), 에스크로 구매자 취소 신청의 거절 경로 없음(토스 API에도 없다 — 수락 또는 확정 요청 재발송), 반품의 환불 계좌 재시도는 운영자 버튼(시스템 actor는 취소만 — 아래 보강), 티켓·선물도 같은 결제 UI를 써서 가상계좌가 보인다(티켓 판매 gate는 닫혀 있다 — 열기 전 가상계좌 없는 결제 UI 분리), 매출·ERP·통계는 가상계좌를 결제수단 '카드(PG)'로 집계한다(증거에서 파생하는 후속).

## 보강 (2026-11-23) — 계좌이체 함께 열기, 법정 고지 즉시 시행

운영 책임자가 2026-11-23에 라이브 키 전환과 함께 가상계좌와 **계좌이체**를 당일 열기로 결정했다. 실사용 회원이 없다는 이유로 약관 제3조·방침 제13조의 7일 사전 공지를 생략한다(위반 위험을 알고 정했다).

- **계좌이체.** ICONS MID `iconsi0xvd`에 계좌이체가 에스크로 사용으로 계약돼 있다(2026-11-23 상점관리자 실측, 환불 가능 기간 180일). 같은 운영 스위치(`TOSS_VIRTUAL_ACCOUNT_ENABLED`) + 결제 UI 바인딩 + 굿즈 주문이면 `DONE` 계좌이체를 `approved`로 받는다(스위치가 꺼졌거나 티켓이면 지금처럼 승인 직후 전액 취소). 환불은 취소 API가 출금 계좌로 돌려준다(환불 계좌 불필요). 에스크로를 고른 계좌이체는 선택 기록이 없으므로 승인 증거의 결제수단(`계좌이체`)으로 배송 등록 작업 대상에 넣고, 작업자가 결제 조회의 `useEscrow`로 확인해 아니면 건너뛴다(`20261125090300_toss_transfer_escrow.sql`). 계좌이체 주문의 에스크로 등록 상태는 같은 날 후속 보강(아래)부터 주문 패널·주문 상세에 보인다. 에스크로는 구매확정 전 부분 취소를 거절하므로(에스크로 가이드), 계좌이체는 작업자가 결제 조회로 에스크로가 아님을 확인하기 전까지 가상계좌와 같이 부분 취소·부분 반품·반품배송비 차감(결제사 부분 취소)을 받지 않는다(`private.toss_transfer_confirmed_non_escrow`, migration `20261125105000`).
- **법정 고지.** 개정 날짜 파일(`lib/legal/virtual-account-terms-revision.json`)은 공지일 = 시행일 = 2026-11-23이고 `noticeWaiver`에 결정을 남긴다. 빌드 가드는 이 기록이 있을 때만 7일보다 짧은 공지를 받는다(시행일이 공지일보다 앞설 수는 없다). 문안에 계좌이체(지급 방법·에스크로·출금 계좌 환급·위탁 업무)를 더했다. **2026-11-25 갱신:** 운영 책임자 결정으로 오픈 전 법정 문서를 개정 이력 없이 그날 작성한 최초 판 하나로 접었다. 가상계좌·계좌이체·구매안전서비스 고지는 최초 판(2026-11-25 시행) 본문에 있고, 날짜 파일·빌드 가드의 '개정 시행 전 스위치 거절' 조건·푸터 표시의 날짜 조건은 없앴다(구매안전서비스 표시는 늘 보인다).
- **개정 순서.** 가상계좌 개정이 부분 반품(11-27)·알림톡(11-30) 개정보다 먼저 시행되므로 "가상계좌 시행일은 앞선 개정 뒤" 규칙을 없애고, 법정 문서가 예약 개정을 **시행일 순서로** 얹는다(이전 판이 직전 시행 본문을 담는다). 세 개정의 앵커는 서로 겹치지 않는다.

## 보강 (2026-11-23 후속) — 환불 계좌 재입력·은행 환불 감시·계좌이체 에스크로 표시·인증 마크

라이브 전환 뒤 드문 예외를 사람 손에서 시스템으로 옮긴다(`20261125110000_virtual_account_refund_followups.sql`, `20261125110100_toss_transfer_escrow_admin_view.sql`).

- **환급 계좌는 클레임 환급 계좌가 먼저다.** 결정 5의 '클레임 환불 계좌는 가상계좌 주문을 받지 않는 기존 차단'을 입금된 토스 가상계좌 주문에 연다. 새 저장소를 만들지 않고 `private.claim_refund_accounts`를 쓴다 — 법정 문서가 이미 '반품·취소 신청 화면에서 입력한 환급 계좌'(배송·반품 정책 7)와 그 보관 규칙(처리방침 제1조 '취소·반품 환급 계좌', 환급 완료 30일 뒤 원문 파기)을 말하고 있어 문안·보관 규칙을 바꾸지 않는다. 결제 UI 계좌(`payment_attempt_virtual_accounts.refund_*`, 발급 180일 뒤 파기)는 그대로 두고 둘째 후보로 쓴다.
  - 고르는 순서: 이 취소·반품 요청에서 구매자가 입력한 계좌(은행 이름 → 토스 은행 코드, `lib/payments/virtual-account-refund-account.ts`)가 있으면 그것만, 없으면 결제 UI 계좌. 입력한 계좌를 그대로 보낼 수 없으면(목록 밖 은행 이름, 숫자 6~20자리 밖) 결제 UI 계좌로 넘어가지 않고 계좌 없음으로 멈춘다 — 구매자가 바꾸려던 계좌가 아닌 곳으로 송금하지 않는다.
  - 그대로 보낼 수 있는 계좌인지는 DB 판정 하나(`private.virtual_account_refund_account_usable` — 토스 은행 목록의 이름 그대로, 하이픈을 뺀 숫자 6~20자리, 예금주 1~50자)가 정한다. 주문 상세 계좌 저장·반품·취소 신청(`request_order_claim_for_parties`)이 이 판정으로 막고, 계좌 후보 응답은 `usable`로 주며 앱은 그 값을 따른다. 재시도 시작도 같은 판정을 써서 쓸 수 없는 계좌면 `account_invalid`로 돌려주고(환불을 다시 부르지 않는다) 구매자 화면은 '바꿔야 하는 계좌'(`unusable`)로 알린다. 운영자 접수·유형 전환 경로의 계좌는 막지 않고 이 알림으로 잡는다. 은행 이름 별칭은 받지 않는다(앱의 이름 → 코드 변환도 목록 이름 그대로). 계좌가 바뀌면 멱등키도 바뀐다(`refund:{attemptId}:va-{계좌 해시}` 그대로).
  - 계좌 후보 조회가 실패하면 계좌 없음과 구분해 결제사를 부르지 않고 '결제사 응답 없음'(`provider_unavailable`, 운영자 [상태 다시 확인])으로 남긴다.
  - 가상계좌 주문은 등록된 계좌를 바꿀 수 있다(결제사가 거절한 계좌를 고친다). 요청이 접수 단계이거나 계좌 때문에 결제확인필요로 멈췄을 때만이다 — 결제사 환불이 진행 중(`processing`)이거나, 다른 사유의 결제확인필요(결과 불명 등 — 결제사가 이미 앞 계좌로 환불했을 수 있다)이거나, 환불이 끝났거나 계좌 송금으로 접수됐으면 막는다. 회사 계좌 무통장 주문은 지금처럼 한 번만 받는다.
  - 재시도: 계좌를 저장하면 취소는 서버가 `service_begin_virtual_account_refund_retry`로 결제확인필요(`provider_refund_account_required`·`provider_refund_account_invalid`) → 처리 중으로 되돌리고 같은 요청에서 오케스트레이터를 다시 부른다(시스템 actor). **반품은 시스템 actor로 환불하지 않는다** — DB가 시스템 actor를 취소에만 허용하는 규칙(`assert_order_cancellation_reconciliation_allowed`·`mark_order_cancellation_needs_review`·완료 함수)을 넓히지 않고, 계좌 입력 때 운영 알림(요청)을 올려 운영자가 '환불 완료 확정'·'상태 다시 확인'으로 그 계좌에 환불한다.
- **은행 환불 감시.** 가상계좌 결제가 환불되면(결제 원장 `paid` → `refunded`·`canceled` 트리거) `private.virtual_account_refund_watches`가 열린다. 자동 재확인 cron(`/api/cron/payment-reconciliation`)이 회차당 3건을 원장 결제 키로 조회해 `virtualAccount.refundStatus`가 `COMPLETED`면 닫고, `FAILED`·`PARTIAL_FAILED`·결제사 기록 불일치·7일 넘게 송금 확인 전이면 실패로 올린다 — 운영 알림(주문, 운영 알림 요약 메일의 '시스템 장애'에 함께 센다)·감사 기록·시스템 상태의 '환불 송금 확인 필요'(할 일 건수에 더한다). 실패 건도 6시간마다 다시 조회해 운영자가 토스 상점관리자에서 재환불하면 저절로 닫히고, 결제사 밖에서 끝냈으면 운영자가 사유와 함께 '처리 완료'로 닫는다(`admin_resolve_virtual_account_refund_watch`). 조회는 환불 뒤 30일까지이고, 조회가 멈춰도(자동 재확인 정지·결제 키 누락) 7일 지난 송금 확인 전 감시는 시스템 상태·확인 목록·주문 화면에 확인 필요(지연)로 오르고 운영자가 같은 '처리 완료'로 닫을 수 있다. paymentKey 조회는 코어 API라 결제 위젯 키(gsk)로 부른다(에스크로 부가서비스 키가 아니다).
- **계좌이체 에스크로 표시.** 운영자 읽기 RPC `admin_order_transfer_escrow`(sales.read)가 가상계좌 원장이 없는 시도의 에스크로 작업을 돌려주고, 주문 패널·주문 상세가 적용 여부(작업자 확인 전에는 '확인 중')·배송 정보 등록·거래 상태·직접 등록 필요를 보인다.
- **에스크로 인증 마크.** 토스 공식 용어 문서 '에스크로'(`/resources/glossary/escrow`)가 "에스크로를 사용하는 상점은 홈페이지 하단에 에스크로 가입 인증 마크가 필요"하다고 하고 다운로드(`static.tosspayments.com/docs/glossary/escrow-auth-mark.zip`)를 준다. 그 안의 `img_mark01(2x).png`를 바꾸지 않고 `public/brand/toss-escrow-mark.png`로 쓴다(sha256 `323d0b91…222faa3c`, 시험이 고정). 그림은 원본의 위아래 투명 여백 가운데 띠에만 있어 화면은 CSS로 여백만 가린다. 기존 문구와 '서비스 가입 사실 확인' 링크는 그대로다.
- **남는 한계:** 반품의 계좌 재시도는 운영자 버튼이다. 은행 송금 실패 뒤 재환불은 토스 상점관리자에서 사람이 한다(취소 API로 다시 보낼 수 없다 — 결제는 이미 취소 상태다). `refundStatus` 열거(NONE·PENDING·FAILED·PARTIAL_FAILED·COMPLETED)는 지난 PR의 문서 조회 기록을 따르며, 2026-11-23 MCP 재조회에서는 예시의 `NONE`만 다시 확인했다 — 모르는 값은 송금 확인 전으로 보고 7일 지연 규칙이 잡는다. 에스크로 결제의 취소 요청 수락 뒤 `refundStatus`가 갱신되는지 문서에 없던 한계는 아래 2026-11-24 보강이 시스템으로 닫는다.

## 보강 (2026-11-24) — 에스크로 구매자 취소 환불은 7일 뒤 시스템이 닫는다

에스크로 결제의 취소 요청 수락(`POST /v2/escrows/{id}/cancel`)은 구매자가 취소 요청 때 토스에 등록한 계좌로 토스가 환불하고(상점에 노출되지 않는다), 그 뒤 결제 조회의 `virtualAccount.refundStatus`가 갱신되는지는 공식 문서(부가 API·에스크로 가이드, 2026-11-24 조회)에 없다. 갱신되지 않으면 `NONE`으로 남아 은행 환불 감시가 7일 뒤 지연으로 잘못 오르고 운영자가 상점관리자를 확인해 '처리 완료'로 닫아야 했다. 토스 답을 기다리지 않고, 어느 쪽이든 맞게 동작하는 규칙을 둔다(`20261125130000_virtual_account_refund_escrow_autoclose.sql`).

- 자동 재확인 cron이 송금 상태가 `NONE`(또는 값 없음)인 에스크로 결제(`useEscrow: true`)를 만나면 거래 조회 `GET /v2/escrows/{escrowKey}`(부가서비스 API라 에스크로 키 `TOSS_ESCROW_SECRET_KEY`)로 구매자 취소 수락(`status` CANCELED · `cancelType` CUSTOMER · `targetId` = 이 결제 키)인지 확인해 함께 넘긴다(`service_record_virtual_account_refund_watch`의 넷째 인자).
- 그 확인이 있고, 가상계좌 원장이 에스크로가 아니라고 기록하지 않았고(`use_escrow is distinct from false` — DB도 근거를 본다), 송금 상태가 여전히 `NONE`인 채 환불 뒤 7일이 지나면 DB가 감시를 완료로 닫는다(`completed_via = 'escrow_buyer_cancel'`, 감사 `system.order.virtual_account_refund_escrow_settled`, 운영 알림·시스템 상태 건수 없음). 이미 지연으로 오른 감시도 확인이 오면 닫는다. 주문 패널·주문 상세는 '토스 에스크로 환불로 닫힘'으로 보인다.
- 지금 판정을 그대로 두는 경우: 토스가 송금을 추적하면(`PENDING` → `COMPLETED`·`FAILED`) 이 규칙은 쓰이지 않는다. 7일 안에는 닫지 않으므로 뒤늦게 온 `FAILED`도 지금처럼 실패로 오른다. 확인이 없으면(결제 취소로 함께 끝난 `TARGET_CANCELED`, 에스크로가 아닌 결제, 에스크로 키 없음·거절) 7일 지연으로 올린다. 송금 실패·기록 불일치로 오른 감시는 닫지 않는다. 거래를 확인하지 못하면(에스크로 키 없음·전송 실패·5xx·4xx·형식 오류) 확인 없음으로 넘겨 지금 판정을 따르고, 지연으로 오른 감시도 6시간마다 다시 보므로 뒤 회차에 확인되면 닫는다 — 결제 조회 결과를 미루지 않아 자동 재확인 회차가 실패로 남지 않는다. 확인 실패는 cron 응답 `escrowLookupFailed`와 서버 로그로 남는다.
- 다음 조회는 환불 뒤 7일 경계를 넘기지 않게 잡는다 — 송금 확인 전 감시가 7일을 넘겨 시스템 상태에 '지연'으로 보이는 시간이 자동 재확인 한 회차(10분) 안이다. 구매자 취소가 확인된 `NONE` 감시는 하루 간격으로 본다.
- **포기하는 것:** 토스가 `NONE`으로 둔 채 그 환불의 은행 송금이 실패하면 우리 쪽에서는 알 수 없다. 에스크로는 대금을 토스가 보관하고 환불 계좌도 구매자가 토스에 직접 등록하므로 그 송금 실패는 토스와 구매자 사이에서 처리되는 구조이고, 운영자의 '처리 완료' 확인도 상점관리자를 보는 것 외에 더할 정보가 없었다. 고객이 환불을 받지 못했다고 하면 운영자가 상점관리자에서 환불 내역을 확인한다(주문 화면 안내).

## 보강 (2026-11-24) — 입금 오류 되돌림을 시스템이 끝까지 처리한다

2026-11-24 사용자 판단: "주문이 1만 건이면 운영자가 하나하나 확인하는 건 물리적으로 불가능하니 자동화해야 한다." 12/2 홍실 2차 예약판매 오픈을 앞두고 무통장 선호 고객이 많아 가상계좌 주문이 몰릴 수 있고 운영자는 1~2명이다. 되돌림 여부·재입금·기한 만료는 모두 토스 결제 조회로 판정할 수 있어 사람 판단이 필요 없다(`20261125160000_toss_virtual_account_deposit_reversal_auto.sql`).

- **근거(토스 MCP 2026-11-24 재조회).** 웹훅 이벤트(`/reference/using-api/webhook-events` DEPOSIT_CALLBACK): 송금 한도 초과·네트워크 이슈 등으로 입금 오류가 나면 `DONE` → `WAITING_FOR_DEPOSIT`이고 "구매자에게 다시 입금하도록 안내해야 합니다". 릴리즈 노트: "같은 주문의 … `DONE` → `WAITING_FOR_DEPOSIT`으로 변경되어 돌아올 때 다시 입금되어야 해요". 가상계좌 웹훅 블로그(`/blog/virtual-account-webhook`)의 상태도도 입금 오류가 같은 `WAITING_FOR_DEPOSIT`(입금 완료·기한 만료·입금 전 취소로 이어지는 상태)으로 돌아간다고 그린다. 입금 전 취소는 계좌 반납(환불 계좌 없음, 전액만 — 결제 취소 가이드 Case 1). **문서에 없는 것:** 되돌림 뒤 같은 계좌번호로 재입금이 되는지(문서는 '같은 주문 재입금'만 말한다), 입금 기한이 유지되는지, 반납(입금 전 취소) 뒤 `virtualAccount.refundStatus` 값. 그래서 계좌·기한은 매번 결제 조회의 `virtualAccount.dueDate`·`expired`를 진실원으로 쓰고(되돌림 기록에 조회값을 다시 적는다), 반납은 조회가 `CANCELED`(잔액 0, 환불 송금 흔적 없음)나 `expired`를 확인할 때만 '입금 없음' 증거로 받는다. 개발자센터 테스트 결제내역의 '입금처리·취소'로 재현할 수 있다고 문서가 말하지만 이 작업에서는 재현하지 않았다 — 운영에서 첫 사례가 생기면 조회값으로 위 가정을 확인한다.
- **원장 모델: `approved` + 출고 보류 그대로.** 가상계좌 총정리는 "입금 전 상태로 되돌려야 해요"라고 쓰지만, 그 요구(물품 제공 중지·재입금 대기)는 출고 보류와 재입금 안내로 충족한다. 원장을 입금 대기로 되돌리면 결제완료 뒤 일어난 일(주문 `paid` 전이 트리거·확인 메일·적립·발주 대기열·에스크로 작업·ERP 읽기)을 역전해야 해 위험이 더 크다. 해결만 자동화한다.
- **되돌림 기록** `private.virtual_account_deposit_reversals`(결제 시도당 한 행): `awaiting_redeposit`(시스템 처리 중) → `closed`(재입금 `redeposited` · 반납 `released` · 다른 경로 주문 취소 `order_canceled` · 운영자 해제 `operator_released`) 또는 `review`(운영자 확인 필요 — 재입금은 계속 자동으로 잡는다). 재입금 뒤 다시 되돌아가면 새 보류와 함께 기록을 다시 열고 번호를 올린다(고객 안내는 되돌림마다 한 번).
- **감지.** 웹훅 `WAITING_FOR_DEPOSIT` → 원장 결제 키 조회 → `service_flag_goods_deposit_reversal`이 보류 + 기록(조회한 기한) + 고객 앱 알림(`order_deposit_reversed`)을 같은 트랜잭션에서 남기고 앱이 재입금 안내 메일(`order_deposit_reversal`, 되돌림마다 한 통 — 메일은 웹훅 응답 뒤에 보낸다)을 보낸다. 고객 주문 상세에 계좌·금액·기한과 함께 재입금 안내가 보인다(재입금을 기다리는 동안만 — 결제사 기록 불일치·환불 흔적으로 확인 필요가 되면 계좌를 다시 약속하지 않는다). 감지 때 입금 기한이 이미 지났으면(기한이 지난 입금은 실패한다 — 코어 API `dueDate`) 재입금을 안내하지 않고 앱 알림이 곧 자동 취소된다고 말한다. 재입금으로 닫힌 뒤 조회가 다시 입금 전이면 결제사 거래 키가 같거나 없어도(대체 근거) 되돌림 번호를 섞은 근거로 새 보류를 건다 — 놓치면 결제 없이 출고된다. 재입금 확인·반납 닫기는 조회할 때 본 되돌림 번호를 함께 넘기고 DB가 잠금 아래에서 대조한다 — 웹훅과 자동 재확인이 겹쳐 앞선 되돌림을 본 늦은 판정이 그 사이 새로 열린 되돌림을 닫지 못한다(`stale`).
- **재입금.** 열린 되돌림이 있는 결제의 그 밖의 웹훅(`DONE`·`CANCELED` 등)은 결제사 직접 취소 감지가 아니라 되돌림 처리로 간다. 조회가 `DONE`(잔액 = 총액)이면 `service_resolve_deposit_reversal_redeposited`가 보류를 풀고(release_kind `deposit_confirmed`, 사유 없음) 고객 앱 알림을 남긴다. 웹훅을 놓쳐도 자동 재확인이 입금 기한 전에는 1시간마다 조회한다.
- **기한 만료.** 자동 재확인 cron(`/api/cron/payment-reconciliation`)의 단계가 `service_claim_deposit_reversal_checks`로 회차당 3건을 고른다(다음 조회는 기한 + 30분과 1시간 뒤 중 이른 쪽, 최소 10분, 10분 리스). 기한 + 30분(입금 대기 만료와 같은 유예)이 지나도 입금 전이면 계좌를 반납(`release-va:{attemptId}`)하고 다시 조회해 반납·만료를 확인한 뒤 `service_close_deposit_reversal`이 '입금 없음' 증거를 남기고 기존 취소 확정(`cancel_order_with_provider_evidence`)으로 주문을 닫는다 — 재고·쿠폰·적립금·뽑기권 복원. 취소 확정(`finalize_order_cancellation_with_provider_evidence`)은 증거가 있는 결제에 환불 행을 만들지 않고 결제 원장을 `refunded`가 아니라 `canceled`로 닫으며, 가상계좌 환불 송금 감시 트리거도 그 결제를 건너뛴다. 고객에게 자동 취소 메일·앱 알림이 간다. 웹훅은 반납하지 않고 다음 조회도 미루지 않는다(10초 응답 예산, 서명 없는 웹훅이 반복해서 와도 기한 뒤 반납이 밀리지 않게) — 재입금·반납 확인만 웹훅에서 닫고 나머지는 자동 재확인이 한다.
- **취소 요청과의 합류.** 되돌림이 열린 결제의 고객·운영자 취소 요청(발송된 주문의 반품 포함)은 오케스트레이터가 결제사 환불 전에 같은 반납을 먼저 한다(기다리지 않음). DB가 잠금 아래에서 반납·만료 증거를 남기면 오케스트레이터는 결제사 환불을 다시 부르지 않고 결제 금액만큼 취소된 것으로 완료를 부른다 — 만료된 계좌는 반납 호출 없이 입금 전 상태로 남아 환불 조회가 '입금 전'으로 멈추기 때문이다(근거는 방금 한 결제사 조회다). 취소 확정은 증거가 있는 결제에서 승인 경로가 먼저 남긴 환불 의도 행(`requested`·`failed`)을 지우고 환불 행 없이 닫는다 — 지우지 않으면 완료 함수가 '결제사 취소 필요'로 거부한다(환불 계좌 불필요, 구매자 알림은 기존 '결제가 완료되지 않은 주문이라 결제 취소 없이 주문을 취소했습니다'). 반품배송비 차감(부분 환불)을 물으면 '부분 취소 불가'로 돌려 전액으로 돌린다. 반납을 확인하지 못하면 결제확인필요 `provider_deposit_reversed`로 남고, 자동 재확인이 반납을 확인하면 취소는 `service_begin_deposit_reversal_cancellation`으로 처리 중으로 되돌려 시스템 actor가 마저 닫는다(반품은 DB가 시스템 actor를 허용하지 않아 운영자의 환불 단계가 닫는다). 그 요청 때문에 자동 재확인은 30분 간격으로 물러나고, 반납 확인 뒤 2시간이 지나도 요청이 닫히지 않거나 접수 단계·교환이면 확인 필요(`cancellation_pending`)로 넘긴다. 결제사 취소에 환불 송금 흔적이 있으면(돈이 들어왔다 나감) 확인 필요로 올리되 취소 요청은 보통의 환불 수렴(전액 취소 조회 → 환불 기록)으로 닫는다. 어댑터의 환불도 원장 승인·결제사 입금 전 결제를 환불하지 않고 같은 코드로 멈추고, 되돌림 기록이 없던 결제(웹훅 누락·운영자가 보류를 푼 뒤)면 그 자리에서 기록을 열어 자동 재확인이 이어 받는다.
- **운영자 몫(예외만).** 이미 발송된 주문(`order_shipped` — 시스템은 발송된 주문을 취소하지 않는다), 결제사 기록 불일치(`payment_mismatch` — 반납을 확인한 결제에 입금이 보이는 경우 포함), 입금 기한 + 2시간이 지나도 조회 실패(`lookup_failed` — 조회가 회복되면 자동 처리로 돌아온다), 환불 송금 흔적이 있는 결제사 취소(`provider_refunded`), 운영자 승인을 기다리는 취소·반품 요청(`cancellation_pending`), 취소 확정 실패(`close_failed`). 이 건들은 운영 알림(주문, 운영 알림 요약 메일의 '시스템 장애'에 함께 센다)·감사 기록·시스템 상태 '입금 취소 결제 확인 필요'(할 일 건수에 더한다)에 오르고, 주문 상세의 출고 보류 안내가 사유별 다음 일을 말한다. 기한 + 2시간이 지나도 열린 자동 처리도 같은 건수로 센다(자동 재확인이 멈춘 신호). 운영자가 사유를 적고 보류를 풀면 기록이 닫힌다(시스템이 손을 뗀다).
- **결제사 직접 취소 감지와의 경계.** 열린 되돌림 결제의 상태 변경은 직접 취소 판정을 미룬다(`in_flight` — 되돌림이 닫히면 sweep이 다시 보고, 주문이 취소되면 대상이 아니다). 우리 반납의 `CANCELED` 웹훅을 직접 취소 보류로 오탐하지 않는다.
- **함께 고친 것.** 결제 시도 게이트웨이(`createAttemptAwarePaymentGateway`)가 `releaseVirtualAccount`를 전달하지 않아, 결정 3의 'DB가 입금 대기를 거부하면 같은 요청에서 계좌를 반납' 경로가 운영에서 조용히 빠지고 있었다(입금 대기 진입 거부 시도는 `needs_review`로 남아 재정합이 닫는다). 일반 결제에 한해 전달한다.
- **남는 한계.** 알림톡 재입금·자동 취소 안내 없음(새 템플릿은 카카오 심사 대상이고 알림톡 스위치가 꺼져 있다 — 후속), 반납 뒤 `refundStatus` 값과 되돌림 뒤 기한 유지는 문서 미확인이라 조회값만 믿는다(위), 웹훅 두 종류(`PAYMENT_STATUS_CHANGED`·`DEPOSIT_CALLBACK`)가 모두 끝내 실패하면 되돌림 자체를 모른다(재전송 3일 19시간 — 승인 뒤 되돌림을 따로 다시 조회하지는 않는다), 운영 화면의 '입금 취소 결제 확인 필요'는 건수와 주문 관리 출고 보류 목록으로 이어질 뿐 전용 목록이 없다.

## 보강 (2026-11-25) — 환불 계좌 요청 알림·운영자 대신 입력·에스크로 아닌 가상계좌의 부분 취소

오픈 직전 실운영 시나리오 전수 조사(VAC-041·VAC-042·SHP-129·VAC-046·VAC-047·CLM-118)가 두 빈틈을 남겼다. 환불이 환급 계좌 때문에 멈춰도 구매자가 모른 채 주문 상세를 다시 열기 전까지 환불이 멈췄고(청약철회 환급 기한 3영업일), 운영자가 전화로 받은 계좌를 넣을 곳이 없었다. 그리고 가상계좌로 산 출고지 혼합 주문은 한쪽 발송 뒤 다른 쪽이 품절이면 미발송 몫을 시스템 안에서 환불할 길이 없었고(전액 취소는 발송 뒤 막히고 부분 취소·부분 반품은 가상계좌를 막았다), 단순 변심 반품배송비도 차감하지 못했다(`20261125210000_virtual_account_refund_account_notice.sql`, `20261125212000_virtual_account_partial_cancel.sql`).

- **근거(토스 공식 문서 결제 취소 `/guides/v2/cancel-payment`, 2026-11-25 확인).** 입금 뒤 가상계좌 취소는 `refundReceiveAccount`(은행 코드·계좌번호·예금주) 필수, 입금 전은 반납(부분 취소 불가), "가상계좌 입금 이후에는 부분 취소가 가능합니다"(`cancelAmount`). 에스크로는 구매확정 전 부분 취소 불가(결정 6·에스크로 가이드). 2026-11-24 샌드박스에서 입금된 가상계좌 1,000원 부분 취소 뒤 잔액 1,200원 취소가 `refundReceiveAccount`와 함께 성공했다(`PARTIAL_CANCELED`). 운영 결제 UI `ICONS`는 '가상계좌 환불 정보 입력: 사용함', 입금 기한 1일(Chrome 실측).
- **계좌 요청 알림.** 취소·반품 요청이 `provider_refund_account_required`·`provider_refund_account_invalid`로 결제확인필요가 되는 전이(주문 전체는 `mark_order_cancellation_needs_review`, 부분 반품은 부분 환불 원장의 상태 동기화)에서 DB 트리거가 같은 트랜잭션에 구매자(주문자) 앱 알림을 남긴다(`claim_updated`, 링크 주문 상세, dedupe `claim:refund_account_{required|invalid}:{요청}` — 같은 요청·같은 사유는 한 번). 메일(`order_refund_account`, 같은 dedupe 단위)은 그 전이를 만든 오케스트레이터가 바로 보내되, 보낼지는 서비스 함수(`service_virtual_account_refund_account_notice`)가 지금 상태로 다시 판정한다(그 사이 계좌가 입력돼 환불이 다시 진행됐으면 보내지 않는다). 선물 주문은 받는 분·보낸 분 흐름이 따로라 알리지 않는다. 고객 주문 취소 화면도 입금된 가상계좌 주문이면 반품 신청과 같은 환급 계좌 칸(같은 부품 `RefundAccountFieldset`, 같은 DB 판정 `private.virtual_account_refund_account_usable`)을 보이고, 계좌를 넣으면 클레임 접수 라우트(취소 유형)로 같은 접수 함수가 받는다.
- **운영자 대신 입력.** `admin_set_order_claim_refund_account`(sales.manage — 환불 처리·[상태 다시 확인]과 같은 권한)는 구매자 입력과 같은 판정(`private.order_claim_refund_account_blocker` → 가상계좌 판정, `usable`)과 같은 저장소(`private.claim_refund_accounts` — 법정 문서의 '취소·반품 환급 계좌', 환급 완료 30일 뒤 원문 파기)를 쓴다. 사유(2~200자)를 받고 감사 기록 `admin.order.claim_refund_account_entered`(누가·언제·사유, 계좌 원문 없음 — 같은 요청 대조용 해시만)를 남기며, 서버가 개인정보 접속기록(정정, 대상 클레임)을 남긴다. 같은 작업 번호는 같은 결과(다른 내용이면 충돌). 저장 뒤 동작은 기존 재시도 규칙 그대로다 — 취소는 서버가 `service_begin_virtual_account_refund_retry`로 시스템 재시도, 반품은 운영자 [환불 완료 확정]·[상태 다시 확인]. 주문 처리 패널의 가상계좌 칸과 클레임 상세의 요청 내용에 계좌 사유로 멈춘 요청일 때만 보인다.
- **에스크로 아닌 가상계좌의 부분 취소.** 판정 하나 `private.toss_virtual_account_partial_cancel_ready(시도)`가 참일 때만 막는 판정 세 곳(부분 취소 `order_partial_cancellation_blockers`, 부분 반품 `order_partial_return_order_blocker`, 반품배송비 차감 `return_fee_deduction_plan`)과 부분 반품 환급 계좌 입력 차단이 가상계좌를 연다: 가상계좌 원장의 에스크로 선택이 false(발급 때 결제 조회 `useEscrow:false`)이거나 작업자가 결제 조회로 에스크로가 아님을 확인했고(작업 skipped·거래 키 없음 — 계좌이체의 `toss_transfer_confirmed_non_escrow`와 같은 근거), 그 밖의 에스크로 작업이 없고, 입금 오류 되돌림이 열려 있지 않을 때. 선택을 모르는 결제·에스크로 결제·입금 전은 지금처럼 막는다. 게이트웨이 부분 취소는 결제 조회의 `useEscrow`가 false일 때만 진행하고(그 밖은 '부분 취소 불가'로 돈을 움직이지 않는다 — 차감은 전액 환불로 돌리고 재고 부족 부분 취소는 진행하지 않음), 전액 환불과 같은 계좌 고르기(이 요청의 구매자·운영자 입력 계좌 → 결제 UI 계좌)로 `refundReceiveAccount`를 싣는다. 멱등키는 단계(차감 `deduction`·남은 잔액 `remainder`·부분 취소 원장 `partial`)별 키에 계좌 접미(`:va-{계좌 해시}`)를 붙인다. 계좌가 없거나 결제사가 거절하면 결제사를 부르지 않거나(없음) 돈이 움직이지 않은 채 결제확인필요로 멈추고, 부분 반품이면 위 알림이 간다. 재고 부족 부분 취소는 구매자가 계좌를 넣을 요청이 없어 결제 UI 계좌만 쓰고, 없으면 운영자가 고객에게 받아 토스 상점관리자에서 그 금액만 부분 환불한 뒤 [결제사 잔액 조회해 해소]로 반영한다(판단이 갈리는 곳은 환불하지 않고 운영자 확인으로).
- **은행 환불 감시.** 가상계좌 부분 환불(토스 부분 취소 원장 completed, 환불액 > 0)도 감시를 연다. 앞 환불의 감시가 끝났으면(completed·resolved) 새 환불로 다시 열고(전액 환불 트리거도 같다), 송금 확인 전·실패 감시는 그대로 둔다. 작업자에게 결제사에 남아야 할 잔액(`expectedBalance` — 결제 원장이 아직 paid면 결제 금액 − 적용된 토스 부분 취소 합계, 아니면 0)을 함께 주고, 조회 판정은 0이면 `CANCELED`·잔액 0, 0보다 크면 `PARTIAL_CANCELED`·그 잔액이어야 송금 상태를 읽는다(아니면 기록 불일치로 운영자 확인).
- **남는 한계.** 에스크로 결제의 부분 취소는 여전히 없다(토스가 구매확정 전 부분 취소를 받지 않는다 — 전액 취소·반품만). 입금된 가상계좌에 대해 토스가 `isPartialCancelable`을 true로 싣는지는 이 작업에서 실측하지 않았다 — false면 게이트웨이가 '부분 취소 불가'로 돈을 움직이지 않는다(차감은 전액 환불, 재고 부족 부분 취소는 진행하지 않음). 한 결제에 환불이 여러 번 있을 때 `virtualAccount.refundStatus`가 마지막 환불만 말하는지는 문서에 없다 — 앞 환불 송금이 실패했는데 뒤 환불이 COMPLETED면 감시가 닫힐 수 있어, 실패로 오른 감시는 새 환불로 다시 열지 않는다(운영자가 닫는다). 재고 부족 부분 취소에서 결제 UI 계좌가 없으면 구매자 알림 없이 운영자 몫이다. 선물 주문의 계좌 대신 입력은 없다(지금처럼 상점관리자 환불 뒤 [상태 다시 확인]).
