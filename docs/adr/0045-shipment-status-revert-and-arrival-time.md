# 배송 상태 오처리 정정과 택배사 배송완료 일시

- Status: accepted (2026-11-19) — 실운영 전 3차 수정 트랙 C(운영 시나리오 원장 #14). main 머지와 운영 배포는 별도 승인.
- 관련: [ADR-0033](./0033-shipment-extra-trackings-auto-delivery.md)(추가 운송장·택배 추적 자동 배송완료), [ADR-0025](./0025-auto-order-confirmation.md)(강제 배송완료), [ADR-0035](./0035-review-confirms-purchase.md)(리뷰 = 구매확정), [택배 추적 자동 배송완료 런북](../runbooks/delivery-tracking.md), [출고지시와 운송장 회신 런북](../runbooks/warehouse-export.md) "발송·배송완료 오처리 정정" 절

## 맥락

2026-11-18 운영 시나리오 전수 조사(원장 #14)에서 배송 상태 쪽 빈틈 셋이 나왔다.

- **SHP-048**: 배송 건 전이는 발송 대기 → 배송 중 → 배송완료 전진만 있었다. 엉뚱한 배송 건을 발송·배송완료 처리하면 되돌릴 RPC·화면이 없어 DB를 직접 고쳐야 했다. 잘못 누른 배송완료는 청약철회 기간·자동 구매확정 기한을 시작시키고, 잘못 누른 발송은 고객에게 발송 메일·앱 알림을 보내며 그 운송장번호를 붙잡는다(#679 이후 다른 주문은 같은 번호를 등록할 수 없다).
- **SHP-050·SHP-086**: 청약철회 기산점 `delivered_at`은 실제 도착이 아니라 운영자가 [선택 배송완료]를 누른 시각(`clock_timestamp()`)이었다. 일찍 누르면 법정 7일이 앞당겨지고(고객 불이익), 늦게 누르면 구매확정·정산이 늦어진다. 원장 action은 "택배사 도착일을 기준으로 하는 운영 규칙(처리 지연은 고객 유리)".
- **SHP-046·CLM-028·SHP-051**: 택배 추적 자동 배송완료는 꺼져 있고(서비스 계약 전), 켜기 전 사람 게이트 하나가 "자동 판정 오류 정정 정책 — 지금은 되돌리는 화면이 없다"였다. 배송완료 누락은 무기한 반품 창구가 된다.

## 결정

1. **한 단계 되돌리기 RPC 두 개.** `admin_revert_shipment_delivery`(배송완료 → 배송 중, 배송완료 일시 비움)와 `admin_revert_shipment_dispatch`(배송 중 → 발송 대기, 대표·추가 운송장·발송 시각 비움). 합포장은 묶음 전체(`lock_shipment_pack_scope`, 주문 id → 배송 건 id 잠금 — 운영 배송완료·자동 배송완료·반품 접수·자동 구매확정과 같은 순서). 사유 5~500자, 작업 ID 재전송(`operator_lifecycle_replay`), 화면이 본 값 대조(배송완료 일시 / 대표 운송장, 다르면 PT409 `shipment_revert_changed`), 감사 `admin.shipment.delivery_reverted`·`admin.shipment.dispatch_reverted`(합포장으로 함께 옮긴 주문에도), 배송 건별 직전 값 원장 `private.shipment_status_reverts`.
2. **권한은 판매 관리(`sales.manage`).** 정정은 출고 담당(`sales.dispatch`, 물류 계정)보다 넓은 권한이다 — 실물·고객 연락을 판단해야 하고, 강제 배송완료(ADR-0025)와 같은 권한이다.
3. **되돌리지 않는 경우(안전한 쪽).** 주문이 거래확정(`done`)·구매확정 행 확정·리뷰 있음(리뷰 = 구매확정, ADR-0035) — 적립금·정산이 이미 움직였다. 취소·반품·교환 요청이 진행 중이거나 끝난 주문(거절·철회만 허용) — 수거·환불·재출고가 그 배송 기록을 근거로 움직였다. 재고 부족 부분 취소 진행 중. 택배 외 배송(퀵·직접배송·화물배송·방문수령·배송없음) — 인계·일회 수령 확인 증거 원장(`shipment_delivery_operations`·`shipment_receipt_confirmations`)과 방식 가드가 전진만 전제하므로 정정이 필요하면 개발 담당이 처리한다. 발송 되돌리기는 주문이 배송 중일 때만, 발송 안내 메일을 보내는 중(임대 중)이면 잠시 뒤에.
4. **구매확정 기한 행은 지운다.** 포착 트리거(`capture_purchase_confirmation_policy`)는 배송완료 전이 때 `on conflict do nothing`으로 정책·기한을 고정하므로, 남겨 두면 다시 배송완료해도 잘못 누른 시각의 기한이 그대로 남는다. 무효화 칸을 더하고 트리거를 고치는 대신 행을 지우고, 다음 배송완료 때 그 일시와 그때 정책으로 새로 잡힌다. 지운 행(정책·기한·보류·연장·요청 시각)은 원장과 감사에 남는다. 보류·연장 사용은 새 행에서 초기화된다 — 되돌린 동안 주문은 배송 중이라 구매확정 자체가 열리지 않고, 실제 도착 뒤 기한이 새로 시작하는 것이 고객에게 불리하지 않다.
5. **주문 상태.** 배송완료 되돌리기는 배송 건 트리거(`refresh_order_fulfillment`)가 주문을 배송 중으로 다시 계산한다(`orders.delivered_at`도 비워져 청약철회 기한이 열린 상태로 돌아간다). 발송 되돌리기로 주문의 배송 건이 모두 발송 대기가 되면 그 트리거는 상태를 그대로 두므로(`derive_order_shipment_status`) 함수가 발주확인(`confirmed`)으로 되돌린다. 주문 상태 역전이를 막는 트리거는 없고(사다리 가드는 `admin_update_order_status` RPC 안에만 있다), 진행 중 클레임·부분 취소 가드(`guard_order_transition_during_cancellation`)는 위 3이 미리 막는다.
6. **고객 안내.** 고객 앱 알림("배송이 완료됐어요"/"배송이 시작됐어요")은 dedupe 키로 한 번만 가므로, 되돌린 단계의 알림을 받은편지함에서 지워 다시 처리할 때 다시 가게 한다. 이미 본 알림과 발송 안내 메일은 회수할 수 없어 확인창·결과 문구가 고객 연락을 안내한다. 아직 보내지 않은 발송 메일 작업은 지우고(다시 발송하면 올바른 운송장으로 새로 쌓인다), 보낸 작업은 남긴다 — 메일 원장의 dedupe(`order_shipped:주문:배송 건`)가 같은 배송 건 메일을 다시 보내지 않으므로, 결과 문구가 올바른 운송장을 직접 안내하라고 알린다.
7. **택배사 배송완료 일시.** [선택 배송완료]는 새 RPC `admin_complete_shipments_at(uuid[], timestamptz, text)`를 쓴다. 기존 `admin_complete_shipments(uuid[])`는 그대로 두고(처리 시각) 새 함수가 트랜잭션 로컬 값 `icons.shipment_delivered_at`으로 일시를 넘긴 뒤 부르며, 안쪽 전이 함수의 `clock_timestamp()` 한 줄만 앵커 치환으로 `private.shipment_operator_delivered_at(shipped_at)`로 바꾼다(다른 트랙의 같은 함수 수정과 충돌하지 않게). 범위:
   - 하한은 배송 건의 발송 등록 시각(`shipped_at`) — 택배 추적 자동 배송완료가 도착 시각을 발송 등록 시각 밑으로 내리지 않는 것과 같다. 금 출고·토 도착·월 회신처럼 회신이 늦게 등록된 건은 회신 등록 시각 이후로 넣게 되는데, 실제보다 늦은 기산이라 고객에게 불리하지 않다. 하한에 걸린 배송 건만 실패하고 함께 고른 다른 건은 처리된다.
   - 상한은 지금. 운영자 PC 시계 차이 10분까지는 지금으로 맞춘다.
   - **7일보다 이른 일시는 사유가 필요하다**(5~500자, 감사 `admin.shipment.arrival_recorded`). 법정 기산점은 실제 수령일(전자상거래법 제17조)이라 늦게 처리한 건을 실제 일시로 소급하는 것이 맞지만, 7일(단순 변심 청약철회 기간)보다 이르면 처리 순간 고객의 철회 기간이 이미 끝나 있으므로 근거를 남기게 한다. 브리프의 예시(발송 후 60일)보다 좁게 잡았다 — 60일을 사유 없이 허용하면 철회 기간 전체를 조용히 지울 수 있어 "처리 지연은 고객 유리" 원칙에 맞지 않는다.
   - 화면 입력의 처음 값(확인창을 연 시각)을 그대로 두면 일시를 보내지 않고 처리 시각으로 기록한다.
8. **강제 배송완료에는 일시 입력을 열지 않는다.** 강제 배송완료는 운송장·인계 근거 없이 철회 기간을 여는 예외 도구(시험 주문 등)라, 근거 없이 소급하는 길을 더 만들지 않는다. 처리 시각 그대로가 고객에게 유리하다.
9. **택배 추적 자동 배송완료는 되돌린 배송 건을 같은 발송 동안 다시 완료하지 않는다.** 같은 운송장의 "배달완료" 이벤트가 남아 있어 다음 회차가 되돌리기를 곧바로 덮어쓰기 때문이다(`service_complete_tracked_deliveries` 후보·재확인 두 곳 앵커 치환 — 원장의 배송완료 되돌리기 시각이 발송 등록 시각 이후이면 제외). 사람이 실제 도착을 확인해 일시를 넣어 처리한다. 발송을 되돌려 새 운송장으로 다시 발송하면 새 발송 시각부터 다시 자동 대상이다. 자동 배송 기록(`shipment_auto_deliveries`)은 청약철회 근거라 지우지 않고, 배송현황의 "자동 확인 · 택배 추적" 표시는 배송완료 일시가 그 기록과 같을 때만 나오므로 사람이 다시 처리하면 "수동 처리"로 보인다.

## 결과

- 오처리는 DB 직접 수정 없이 화면에서 감사와 함께 정정한다. 되돌린 번호는 올바른 배송 건에 다시 등록된다.
- 청약철회·구매확정 기산이 택배사 배송완료 일시를 따른다. 늦게 처리할수록 기간이 뒤로 밀리지 않고(정산 지연 해소), 일찍 누르는 실수는 되돌리기로 고친다.
- 택배 추적 자동 배송완료를 켜기 전 사람 게이트의 "오판 정정 도구"가 생겼다. 언제 되돌릴지(고객 미수령 신고 기준·연락 절차)는 운영 승인으로 남는다.
- 남은 한계: 택배 외 배송 정정 도구 없음, 이미 나간 메일·본 알림은 회수 불가, 발송 메일은 같은 배송 건에 다시 보내지 않음, 배송완료 누락 점검(SHP-051·CLM-028)은 배송중 탭의 "N일째 배송 중" 표시와 운영 루틴에 맡긴다.

## 검토한 대안

- **구매확정 행에 무효 표시를 두고 포착 트리거가 덮어쓰게 하기**: 트리거와 정책 행의 의미가 바뀌어 다른 경로(구매자·관리자 확정, 소급 백필)까지 살펴야 한다. 행 삭제 + 원장 보존이 변경 면적이 작다.
- **기존 `admin_complete_shipments`에 인자 더하기**: 시그니처가 바뀌면 옛 앱·시험이 깨진다. 새 함수 + 트랜잭션 로컬 값으로 옛 경로를 그대로 둔다.
- **배송완료 되돌리기를 발송 대기까지 한 번에**: 운송장과 메일·알림 처리가 섞인다. 단계마다 되돌려 확인창이 각 단계의 결과를 정확히 말하게 했다.
