# 상품 유형 층을 없애고 대표 카테고리만 남긴다

- Status: accepted (2026-11-18) — 사용자 결정(아래 인용). main 머지와 운영 배포는 별도 승인.
- 대체: [ADR-0037](./0037-goods-type-from-category.md)(상품 유형은 대표 카테고리에서 파생한다) 전부.
- 관련: [ADR-0036](./0036-goods-kc-self-declaration.md)(KC 자가 신고), [ADR-0043](./0043-xsquare-figma-storefront.md)(X SQUARE 스토어), [카테고리 운영 절차](../runbooks/storefront-categories.md), [KC 검토 절차](../runbooks/goods-kc-review.md)

## 맥락

ADR-0037로 상품 유형(피규어·인형·키링·아크릴·문구·쿠션·파우치·세트·기타)은 대표 카테고리(없으면 가까운 상위)에 연결한 값이 됐고, 연결이 없으면 공개할 수 없었다. 2026-11-18 운영 데이터 정리 뒤 사용 중인 카테고리 358개 가운데 7개만 연결돼 있었다(그나마 시연 상품 분포로 채운 초기값이라 '캘린더 = 피규어' 같은 잘못된 값이 섞여 있었다). MD가 `문구 > 카드/편지지 > 봉투`를 대표 카테고리로 고른 상품을 등록하다 "연결된 상품 유형 없음"을 보고 이유를 물었다.

상품 유형을 읽는 곳을 코드와 운영 DB에서 확인했다.

- **KC**: `private.goods_kc_context`에 유형이 들어 있어 값이 바뀌면 검토가 미검토로 돌아간다. 하지만 유형으로 KC 제도를 고르지는 않는다([KC 검토 절차](../runbooks/goods-kc-review.md): "상품 유형이나 카테고리만 보고 적용 제도를 자동 판정하지 않는다").
- **고시 템플릿**: 유형 이름으로 프리셋을 검색해 제안만 한다.
- **고객 화면**: 목록의 '타입' 필터, 검색 부제·검색어 일치, 주문서 줄의 작은 라벨.
- **공개 조건**: 연결이 없으면 공개를 막았다. 이번 문제의 직접 원인이다.

즉 유형이 실제로 결정하는 것은 고객 필터 칩 정도인데, 그 축을 유지하려고 카테고리마다 유형을 따로 지정해야 했다. 스마트스토어처럼 카테고리 자체로 상품 종류를 나타내면 같은 정보를 한 번만 관리한다.

사용자 결정 원문(2026-11-18): 선택지 "안 1. 공개 조건만 풀기 / 안 2. 상품 유형 층 제거" 가운데 "안 2로 진행".

## 결정

1. **공개 조건은 "대표 카테고리가 있다"이다.** 유형 조건은 없다. 대표 카테고리 없이 공개하면 `goods_category_required`로 거절한다(`private.set_good_published`, 저장과 함께 공개·엑셀 공개 포함).
2. **상품 유형을 파생·판정하지 않는다.** 초안 유형 맞춤 트리거(`goods_category_type_derive`), 카테고리 연결·상위 변경 때 하위 초안을 맞추던 트리거(`catalog_categories_good_type_refresh`), 파생 함수(`private.goods_category_type`·`goods_category_type_majority`)를 없앤다. 등록 화면 원자 저장의 유형 대조(PT409 `goods_type_category_changed`)도 없앤다.
3. **공개 중인 상품도 다른 대표 카테고리로 옮길 수 있다.** 비우는 것만 `goods_published_category_clear`로 막는다(공개 조건을 지키려고). 카테고리 이동은 KC 재검토 대상이 아니다 — KC 가드 열 목록에서 ADR-0037이 더한 `category_id`를 뺐다.
4. **판매 준비 사유는 `category_missing` 하나다.** 초안은 공개를 막고, 공개 중이면 검토 사유로 알린다. `type_missing`·`type_category_mismatch`·`type_no_category`는 없앤다.
5. **화면에서 상품 유형을 없앤다.** 상품 등록·수정·그룹 공통정보·카테고리 관리(연결 칸·이름 추천·트리 표기·분류 CSV 열·기존 유형 이관 메모)·판매 준비·상품 엑셀·어드민 가이드. 고시 템플릿 제안은 대표 카테고리 이름(리프에서 위로)으로 찾는다.
6. **고객 '타입' 필터는 예약판매(PRE-ORDER)만 남긴다.** 상품 종류는 `/shop`의 카테고리 필터와 카테고리 전시 화면의 하위 분류 탭이 맡는다. 옛 `?type=키링` 링크는 오류 없이 무시한다. 검색의 굿즈 부제는 `IP · 대표 카테고리 이름`이고 검색어도 대표 카테고리 이름과 맞춘다(고객 카테고리 기능이 꺼져 있거나 보관된 카테고리면 쓰지 않는다). 주문서 줄의 유형 라벨은 값이 비면 그리지 않는다.
7. **저장 칸은 다음 PR에서 지운다(확장·축소 순서).** `goods.type`, `order_items.good_type_snapshot`, `catalog_categories.good_type`, `goods_type_category_migrations`와 `admin_set_category_type_migration`, `admin_upsert_category`의 `target_good_type` 인자는 이번 변경에서 남긴다. 배포 순간에는 DB가 먼저 바뀌고 앱이 몇 분 뒤 바뀌는데, 그 사이 이전 앱이 이 칸들을 읽고 쓰기 때문이다. 그때까지
   - `goods.type`은 새 상품에서 `''`이고, 운영 화면·엑셀은 기존 상품의 저장된 값을 그대로 다시 보낸다(값이 바뀌면 KC 지문이 바뀌어 검토가 미검토로 돌아가므로). 값 목록(`goods_type_check`)은 남기되 공개 여부와 묶지 않는다.
   - KC 지문(`goods_kc_context`)은 그대로 둔다. 값이 바뀌지 않으니 영향이 없고, 지문 형식을 바꾸면 기존 KC 검토가 모두 무효가 된다.
   - `catalog_categories.good_type`·`goods_type_category_migrations`는 어디에서도 읽지 않는다. 앱은 `target_good_type`에 항상 `null`(= 그대로)을 보낸다.
   - 상품 목록의 판매 준비 필터는 옛 사유 값(`type_missing` 등 3종)을 이전 앱 호환으로 받되 아무 상품도 걸리지 않는다.
   - 칸을 지울 때 KC 지문에서 `type`을 빼면 `private.goods_kc_review_current`가 저장된 맥락(`goods_kc_reviews.context_snapshot->'good'`, `type` 포함)과 현재 맥락을 그대로 비교하므로 모든 기존 검토가 현재가 아닌 상태가 된다. 그 migration은 저장된 검토 맥락의 `{good,type}`도 같은 트랜잭션에서 함께 지워야 한다(검토 이력 이벤트의 스냅샷은 이력이라 그대로 둔다).

## 검토한 대안

- **공개 조건만 풀기(안 1).** 연결이 없으면 '기타'로 보고 공개를 허용한다. 공개는 풀리지만 고객 '타입' 필터에 대부분의 상품이 '기타'로 쌓이고, 결국 카테고리마다 유형을 연결하는 일이 남는다. 사용자가 고르지 않았다.
- **카테고리 연결값만 채우기.** 코드는 그대로 두고 MD가 카테고리마다 유형을 지정한다. 당장은 빠르지만 같은 정보를 두 번 관리하는 구조와 새 카테고리마다 지정해야 하는 일이 남는다.
- **이번 PR에서 칸까지 지우기.** `goods.type`을 지우면 SQL 시험 250여 개 파일의 굿즈 삽입문과 주문 스냅샷을 읽는 130여 개 파일, 주문 생성 함수(돈 경로)를 함께 고쳐야 하고, 배포 사이 이전 앱이 지운 칸을 읽다 실패한다. 동작을 먼저 바꾸고 칸은 후속 PR에서 지운다.
- **KC 지문에서 유형을 빼기.** 지문 형식이 바뀌어 기존 KC 검토가 모두 무효가 된다. 값이 더 이상 바뀌지 않으므로 칸을 지울 때 함께 정리한다.
- **카테고리 전시 화면에 하위 카테고리 필터를 새로 더하기.** 그 화면에는 이미 하위 분류 탭이 있어 더하지 않았다.

## 결과

- MD가 상품을 공개하려면 대표 카테고리(마지막 단계) 하나만 고르면 된다. 카테고리 관리에서 유형을 연결하는 일이 사라졌다.
- 공개 중인 상품의 대표 카테고리를 바꿔도 KC 재검토가 생기지 않는다.
- 고객 목록 필터에서 9종 유형 칩이 사라지고, 검색 부제가 카테고리 이름으로 바뀐다.
- 판매 준비에 `category_missing`이 새로 생겼다. 배포 사이 몇 분 동안 이전 앱 판은 모르는 사유를 '준비 상태 확인 필요'로 보이고(fail-closed), 새 오류 코드(`goods_category_required`·`goods_published_category_clear`)는 일반 저장 실패 문구로 보인다.
- 정리 단계(2026-11-18, `20261118162500_goods_type_layer_cleanup.sql`, 운영 배포 뒤): `catalog_categories.good_type`, 기존 유형 이관 메모(`goods_type_category_migrations`·`admin_set_category_type_migration`·운영자 계약 행), 필터의 옛 사유 3종을 지웠다. 카테고리 저장 RPC의 `target_good_type` 인자는 기본값이 null이라 시그니처를 바꾸지 않고 받기만 하고 무시한다(앱은 더 보내지 않는다).
- 칸 삭제 1단계(2026-11-19, `20261118173000_goods_type_columns_unused.sql`): 상품·주문 저장(상품 저장·복제·그룹 상품 만들기·주문 생성·랜덤 배정·거래 계산)이 `goods.type`·`order_items.good_type_snapshot`을 쓰지 않는다(새 행은 기본값 `''`). KC 맥락·가드에서 `type`을 뺐다. 저장된 KC 검토 기록은 고치지 않고 현재 여부를 비교할 때 옛 `type` 키를 뺀다(결정 7의 "기록에서 지운다" 대신 — 검토 기록을 바꾸지 않는 쪽을 골랐다). 앱은 두 칸을 읽거나 보내지 않고, 배포 사이에 오는 옛 `type` 키(그룹 공통정보 읽기·선물 주문 응답)는 값을 읽지 않고 받아 둔다. 상품 저장 RPC의 `target_type` 인자는 시그니처를 유지한 채 무시한다.
- 칸 삭제 2단계(1단계 운영 배포 뒤, `20261118175000_goods_type_columns_drop.sql`): 읽는 쪽(카테고리 진열·고객 주문 품목·선물 주문·어드민 주문 상세·스마트스토어 출고·탈퇴 법정 기록)에서 유형을 걷고 `goods.type`(+ `goods_type_check`)·`order_items.good_type_snapshot`을 지웠다. 카테고리 진열의 '타입' 묶음은 예약판매 하나만 남고 `types` 조건도 '예약판매'만 받는다. 그룹 공통정보 공통 칸·상품 임시저장 허용 칸에서 `type`을 뺐고(저장된 임시저장 값에서도 지웠다), 앱의 옛 `type` 키 허용도 걷었다.
- 남긴 것: 상품 저장 RPC의 `target_type` 인자(시그니처 유지, 무시), KC 검토 기록과 탈퇴 법정 기록에 이미 남은 옛 `type`·`goodType` 키(이력이라 고치지 않고, KC 현재 여부 비교가 `type`을 뺀다), 상품 엑셀의 빈 '상품 유형' 열(내려받은 옛 파일의 열 순서 호환).
