# 리뷰 등록이 구매확정을 겸한다 — 새로 등록되는 리뷰는 구매확정된 주문에만 남는다

- Status: accepted (2026-11-12) — 사용자 결정 1014-079(원장 재작업 묶음 20·21)
- 보완: [구매확정 계약](../research/smartstore-admin/purchase-confirmation.md)과 [ADR-0025](./0025-auto-order-confirmation.md)의 자동 구매확정 소급(D11)은 그대로 두고, 구매확정을 일으키는 길에 리뷰 등록을 더한다
- 관련: 2026-10-14 실사용 QA 회의 47:35, [리뷰 유형 계약](../research/smartstore-admin/review-types-plan-20261016.md)

## 맥락

회의 발언 "리뷰를 남긴 구매 확정이 되는 편이죠"는 "리뷰를 남기면 구매확정"과 "구매확정 뒤에 리뷰" 두 뜻으로 읽혔다. 사용자 결정 원문은 "리뷰 쓰며 함께 확정으로 진행하되 구매확정만 누를 수 있어야 하며, 일정 기간이 지나면 자동으로 확정되는것도 켜놔야함"이고, 자동 확정 기간은 "8일 (Recommended)"을 골랐다.

그전까지 리뷰는 배송완료(`delivered`) 이상이면 쓸 수 있었고, 구매확정은 주문 상세 [구매확정]과 기본 꺼짐의 자동 정책으로 따로 돌았다. 구매확정은 주문 당시 정책의 적립금 지급과 이력·감사를 남기는 돈 경로라, 리뷰 쪽에서 따로 확정 로직을 만들면 지급과 잠금 순서가 두 갈래가 된다.

## 결정

- **새로 등록되는 리뷰는 구매확정된 주문에만 남는다.** 미확정(`delivered`) 주문에 리뷰를 등록하면 같은 트랜잭션에서 구매확정한다(`create_good_review_v3`). 리뷰 저장이 어떤 이유로든 실패하면 확정도 되돌아간다. 이 결정 전에 쓴 미확정 주문의 리뷰와, 확정 뒤 반품·취소된 주문의 리뷰는 예외다(거래확정 상태가 아닐 수 있다).
- **확정은 [구매확정] 버튼과 같은 길이다.** `private.change_purchase_confirmation`(구매자 직접 확정)을 그대로 불러 `done` 전이·적립금 지급 trigger·확정 이력·감사가 버튼과 같다. 이력 메모 "리뷰 등록과 함께 확정"으로 버튼 확정과 구분한다. 같은 리뷰를 다시 보내면 `review_already_exists`로 끝나고 확정·적립은 늘지 않는다.
- **고지와 확인:** 등록 전에 [구매확정] 패널과 같은 안내(주문 당시 정책의 적립금 지급, 확정 뒤에도 반품·교환은 별도 자격과 기한)와 확인 체크를 보인다. DB도 확인(`p_acknowledged`) 없이는 확정하지 않는다. 이미 확정된 주문은 확인 없이 리뷰만 저장한다.
- **확정할 수 없으면 리뷰도 막는다.** 진행 중인 취소·반품·교환, 운영자 보류, 배송 미완료 품목, 계정 제한, 결제 원장 불일치처럼 구매확정이 거절되는 주문은 같은 이유로 리뷰도 막고 고객에게 이유를 보인다. 막을지는 기존 `purchase_confirmation_eligible` + 보류 하나로만 정하고, `private.purchase_confirmation_block_reason`은 막힌 이유만 고른다.
- **리뷰 없이 [구매확정]만 누르는 길과 자동 구매확정의 확정 조건은 그대로다.** `confirm_my_purchase`는 바꾸지 않고, `settle_delivered_orders`는 잠그는 방식만 바꾼다(아래 자동 작업 항목). 자동 구매확정 정책 값도 migration이 켜지 않는다 — 배포 뒤 운영자가 '구매확정 정책'에서 배송완료 후 8일(구매자 연장 없음)로 켠다.
- **확인 없는 기존 작성 함수는 미확정 주문을 거절한다.** `create_good_review_v2`(와 이를 부르는 `create_good_review`)는 미확정 주문에 `review_purchase_confirmation_required`를 낸다. 기간·중복·결제 원본 같은 다른 자격 오류가 먼저 나오도록 저장 직전에 검사한다.
- **과거 기록은 바꾸지 않는다.** 이 결정 전에 쓴 미확정 주문의 리뷰는 소급 확정하지 않는다. 리뷰 수정·삭제는 확정하지 않는다.
- **잠금 순서:** 행위자 잠금 → 계정 작업 잠금 → 프로필(`NO KEY UPDATE`) → 주문 → 확정 행. 결제·선물(행위자 → 계정 작업 → 프로필)·운영자 고객 RPC(`lock_operator_subjects`: 계정 작업 → 프로필)와 같은 순서다. 구매자 구매확정 세션 검사(`purchase_confirmation_identity`)가 프로필 → 계정 작업 순서였을 때는 운영자 고객 RPC 약 50개(고객 메모·적립금 조정·정지 등)와 같은 고객에서 교착했다(리뷰 시험 3000회 경합 중 18건). 그래서 이 함수가 프로필보다 계정 작업 잠금을 먼저 잡게 고쳤고, 같은 함수를 쓰는 [구매확정] 버튼도 함께 이 순서가 됐다. 리뷰 등록은 확정이 필요한 배송완료 주문에서만 이 검사를 지나고, 이미 확정된 주문은 v2로 바로 넘겨 프로필을 `NO KEY UPDATE`로 잡지 않는다. v2의 잠금은 그 뒤에 이미 쥔 잠금을 다시 잡을 뿐이다. 자동 작업은 아래처럼 기다리지 않고 잡는다.
- **읽기:** `my_review_targets_v3`가 v2 행에 확정 필요 여부·막힌 이유·보류 사유(운영자가 고객용으로 적은 문구)를 붙이고, 확정할 수 없는 미확정 주문은 작성 불가로 둔다. v2 읽기는 이전 앱이 계속 읽도록 그대로 둔다.
- **자동 구매확정 작업은 남을 기다리며 잠그지 않는다(오케스트레이터 판단 ④).** 자동 확정을 운영에서 켜면 매일 KST 03:00 작업이 결제 확정·선물·리뷰·[구매확정] 경로와 같은 고객을 잠근다. 이전 작업은 후보 조회 안에서 고객마다 계정 작업 잠금을 기다려 잡아 배치 끝까지 쥐었고, 결제·선물 경로(행위자 → 계정 작업 → 프로필, 선물은 두 고객을 id 순서로)와 순서가 엇갈려 교착 시 결제 쪽이 희생될 수 있었다. 이제 후보는 잠그지 않고 고르며(`private.purchase_confirmation_candidate` — 계정 차단만 잠그지 않고 읽는 eligible 쌍둥이), 주문마다 하위 트랜잭션에서 행위자 → 계정 작업 → 프로필 → 주문 → 확정 행을 기다리지 않고(try-lock·SKIP LOCKED) 잡고 원래 eligible로 다시 판정한다. 확정 뒤 trigger(적립금 등)의 대기는 `lock_timeout` 100ms(교착 검사 1초보다 짧다)로 묶어 그 주문만 되돌린다. 건너뛴 주문은 기한·자격이 그대로라 다음 실행이 확정한다 — 누락 없이 지연만 생긴다. 확정 조건·이력·적립금은 바꾸지 않는다(`20261113003100`).

## 결과와 검증 경계

- DB가 먼저 배포되는 짧은 틈에 이전 앱으로 미확정 주문에 리뷰를 등록하면 일반 실패 문구가 보인다. 새 앱이 올라가면 확정 안내 화면으로 바뀐다.
- 자동 구매확정을 켜면 이미 배송완료된 주문도 배송완료일 + 8일로 기한을 받고 다음 자동 처리에서 확정된다(D11, 11/12 읽기 전용 확인 당시 운영 배송완료 30건). 자동 확정 뒤의 리뷰는 확인 없이 저장된다.
- 확정 뒤에도 반품·교환 자격은 배송일·사유별 기존 계약을 따른다. 구매확정 자체로 권리를 소멸시키지 않는다.
- 자동 작업과 겹친 주문은 그날 확정되지 않고 다음 실행(다음 날)에 확정될 수 있다. 확정이 늦어지는 쪽은 고객에게 불리하지 않다.
- 검증: `purchase_confirmation.sql`(리뷰 등록 확정·확인 없음/다른 세션 거절·클레임/보류 거절·실패 시 확정 되돌림·중복 등록·자동 확정 상호작용·버튼 경로·소급 없음·ACL·자동 작업 잠금 계약과 후보 쌍둥이 본문 대조), `purchase_confirmation_concurrency.py`(리뷰·버튼·자동 작업 동시, 같은 리뷰 6번 동시, 리뷰·반품 접수 동시 — 확정·적립 중복 0, 미확정 주문의 리뷰 0; 결제·선물·리뷰·[구매확정]·적립금 잠금을 쥔 채 자동 작업 실행 — 0.2초 안에 쥔 고객만 건너뛰고 쥔 쪽은 모두 무사, 이전 작업은 같은 상황에서 38초 기다림; 실제 결제 확정·선물 잠금 뒤 결제 확정·리뷰 등록과 자동 작업 3회 동시 — 교착 0·결제 승인·확정 누락 0; 운영자 쪽이 계정 작업 잠금을 쥐고 프로필을 기다리는 사이 리뷰 등록(미확정·확정 주문)·[구매확정] — 모두 커밋, 이전 순서는 같은 시험에서 교착; 실제 `admin_add_customer_note`와 리뷰 등록·[구매확정] 40쌍 동시 — 교착 0), `goods_reviews.sql`(기존 작성 함수의 미확정 거절), 앱 테스트(쓰기 화면·목록·서버 액션·문구 계약).
