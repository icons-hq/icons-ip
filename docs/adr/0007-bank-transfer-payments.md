# 무통장 입금은 자체 법인계좌 + 계좌수집 서비스로 받는다

회사 기존 판매 채널에서 무통장 입금 고객 비중이 크다는 사업 현실이 확인됐고, 오픈 게이트에 무통장 결제가 포함됐다(2026-08-14 스마트스토어 어드민 카피 그릴링, [docs/research/naver-smartstore/](../research/naver-smartstore/README.md)). 문제는 경로다: 현재 유일한 신규 결제 provider인 코페이(Korpay)의 연동 표면은 **카드 인증결제 하나뿐**이다 — 인증결제 가이드 v1.2.2가 `payMethod`를 "card 고정"으로 명시하고, 코페이가 "주기적으로 업데이트한다"고 안내한 공식 Notion 가이드 허브에도 인증결제 가이드 단 한 건만 존재하며(2026-08-14 실측), 우리 어댑터(`lib/payments/korpay-gateway.server.ts`)도 `payMethod === 'CARD'`를 검증한다. PG 가상계좌라는 표준 경로가 이 계약에는 없다.

무통장 주문은 **회사 법인계좌로 직접 입금받고, 입금 확인을 거쳐 서버 finalizer로 확정한다.** 입금 내역 대조는 수동 콘솔로 시작하고, 뱅크다류 계좌수집 서비스 연동은 매칭 *제안* 자동화로 병행 도입한다. 오픈 게이트는 수동 대조 콘솔까지다 — 외부 계약(뱅크다)이 오픈을 막지 않는다.

## Considered Options

- **코페이 가상계좌** — 주문별 고유 계좌·입금 웹훅·입금자명 문제 원천 차단으로 기술적으로 최선이지만, 위 근거로 현 계약·연동에서 **불가 판정**. 별도 계약 문의도 사용자가 배제했다(제한업종 가맹 특성상 기대가 낮고, 오픈 일정을 외부 회신에 묶는다). 폐기.
- **무통장용 별도 PG 추가** — 가상계좌만을 위해 두 번째 PG 계약·어댑터·원장 분기를 들이는 것은 provider-neutral seam을 만든 직후에 복잡도를 되돌리는 일이다. 폐기.
- **자체 법인계좌 + 수동 확인, 계좌수집 서비스로 보강 (채택)** — 입금자명 매칭이라는 고전적 리스크를 안는 대신, 계약 의존 없이 즉시 구현 가능하고 회사가 이미 원하던 실시간 입금 가시성(뱅크다류)과 한 방향이다. 매칭 리스크는 입금자명=주문번호 규칙 + 금액 대조 + 미매칭 큐로 관리한다.

## Consequences

- **"callback은 진실원이 아니다" 원칙은 유지된다.** PG 왕복이 없을 뿐, 입금 확인은 어드민 액션이 증빙(확인자·근거·시각, 연동 후엔 뱅크다 레코드)을 기록하고 DB 멱등 finalizer(`provider = 'bank_transfer'`로 기존 `payment_attempts`/`payments` 원장 통일)를 호출하는 구조다. 뱅크다 연동 후에도 자동은 매칭 *제안*까지 — 자동 확정 전환은 안정화 후 별도 결정.
- **운영 부담이 생긴다.** 수동 대조·미아 입금 반환·기한 연장 판단이 사람 일이 된다(CS 운영 가이드 S4·S5). 뱅크다 연동이 이를 줄이지만 없애지는 않는다.
- **재고 선점 창이 길어진다.** 무통장 주문은 24시간 선점(카드 15분) — 한정 드롭 굿즈는 `allow_bank_transfer=false`로 무통장을 차단해 잠김을 막는다. 티켓은 무통장 미지원(회차 임박과 충돌).
- **환불이 비대칭이 된다.** 무통장 환불은 PG 경로가 없어 계좌 송금뿐 — 클레임 접수 시 환불계좌 수집이 필수가 되고, `refunds` 원장에 수단 구분(`pg_cancel`/`bank_transfer`)이 생긴다.
- 코페이가 가상계좌를 지원하게 되면 provider seam 위에서 `bank_transfer`를 가상계좌 provider로 대체할 수 있다 — 원장 구조는 그대로 쓴다.
