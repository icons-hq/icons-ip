# 운영자가 시작하는 배송 전 전액 취소

- Status: accepted (2026-10-13, PR #557 merge·운영 배포)
- 보완: [ADR-0017](./0017-order-claim-intake-and-origin-collections.md)의 직접 신청 경계는 그대로 두고, 운영자 처리 경로 하나를 더한다
- 관련: 2026-10-12 토스 결제 출시 준비 점검 OPS-8·OPS-5·REF-1, [클레임 런북](../runbooks/order-claim-intake.md)

## 맥락

고객 직접 취소는 발주확인 전 `pending`·`paid` 주문에만 열린다(ADR-0017). 그 뒤부터 첫 발송 전까지 생기는 일을 시스템 안에서 끝낼 경로가 없었다.

- 발주확인 뒤 창고 재고가 모자라 출고할 수 없다(품절·출고 불가).
- 발주확인 뒤 고객이 1:1 문의로 취소를 요청했고 창고가 출고를 멈췄다.
- 토스 심사 창(테스트 키) 동안 생긴 무과금 `paid` 주문을 라이브 키로 바꾸기 전에 정리해야 한다. 키를 바꾼 뒤에는 테스트 결제를 조회·취소할 수 없다.

어드민에는 상태를 `confirmed`·`shipping`·`delivered`로만 미는 RPC가 있었고, 클레임은 구매자만 만들 수 있었다. 런북은 "임의 클레임 생성"과 "service-role 직접 환급"을 금지했다. 그래서 운영자는 토스 상점관리자에서 직접 취소하는 수밖에 없었고, 그러면 주문·재고·쿠폰·적립금·카드팩이 실제와 어긋난다.

## 결정

- staff는 사유와 함께 **모든 배송 건이 아직 발송 전인** 주문의 전액 취소를 시작할 수 있다. 감사 RPC `admin_start_order_cancellation(order, reason_code, note, warehouse_stop_confirmed)` 하나로만 연다. 화면은 주문 통합검색(`/admin/sales/orders`)에서 주문을 선택하면 열리는 주문 패널이고, 양식은 아래 결제 조건과 같은 조건(실패가 아닌 결제가 모두 토스 결제완료)일 때만 그린다.
- 허용 조건(DB가 주문·배송 건 잠금 아래에서 판정):
  - 주문 `paid` 또는 `confirmed`, 주문 발송·배송완료·거래확정 시각 없음
  - 모든 배송 건이 `ready`·`canceled`이고 발송·배송완료 시각 없음
  - 진행 중인 취소·반품·교환 요청과 미해결 결제 시도(`prepared`·`confirming`·`unknown`·`needs_review`)가 없음
  - 결제가 토스 결제 1건 이상이고 모두 `paid`(paymentKey 있음). Korpay(취소 API 없음)와 무통장(계좌 송금 종결 미구현 #279·#280·#281)은 열면 결제확인필요에 갇히므로 거절한다
  - 출고지시 파일이 나간 배송 건(`exported_at`)이 있으면 "창고에 출고 중단을 확인했다"는 명시 확인
- 사유 코드는 `out_of_stock`(품절·출고 불가), `customer_request`(고객 요청 — CS 접수), `test_payment_cleanup`(테스트 결제 정리), `other`(기타 — 메모 필수)다. 사유·메모·운영자·창고 확인 여부를 요청 행(`origin='staff'`, `staff_reason_code`, `staff_note`, `initiated_by`, `warehouse_stop_confirmed`)과 감사 로그(`admin.order.staff_cancellation_started`)에 남긴다. `requested_by`는 계속 구매자다 — 알림·RLS·기존 대조가 그 값을 본다. 운영 사유·처리자는 구매자 컬럼 grant 밖이다.
- 만들어진 요청은 고객 취소와 같은 원장 구조(`order_cancellation_requests` + `order_cancellation_claims` + 결제별 `refunds`)로 바로 `processing`이 되고, 서버가 같은 오케스트레이터 → 토스 전액 취소 → fresh 조회 검증 → `complete_order_cancellation_request` → finalizer로 닫는다. 재고·쿠폰·적립금 복원과 미개봉 카드팩 회수는 finalizer 한 곳에서 정확히 한 번 일어난다. 실패·모호 결과는 결제확인필요로 남고 운영자가 같은 경로로 재시도한다.
- 발주확인·출고지시 이후를 막던 판정(`private.order_cancel_eligible`)은 **staff 발원 활성 요청이 있는 주문에 한해서만** 발송 전 조건으로 열린다. 고객 직접 신청과 고객 화면의 신청 가능 판정은 바뀌지 않는다.
- 구매자에게는 사유별 문구로 취소 사실을 알리고, 결제사 취소가 확인되면 "결제 취소가 완료됐어요"를 따로 보낸다.

## 결과

- 심사 창 테스트 결제 주문은 **라이브 키로 바꾸기 전에**, 테스트 키가 살아 있을 때 이 경로(사유 `test_payment_cleanup`)로 정리한다. 키 교체 뒤에는 같은 주문을 조회·취소할 수 없어 결제확인필요에 남는다.
- 클레임 런북의 "임의 클레임 생성 금지"는 SQL·service-role로 요청·환급 원장을 만드는 우회를 금지한다는 뜻으로 유지한다. 이 RPC는 staff 세션·감사·잠금·결제사 검증을 모두 거치는 승인된 처리 경로라 그 금지에 해당하지 않는다. 문의를 받았다는 사실만으로 이 경로를 자동 실행하지는 않는다 — 운영자가 배송 건별 사실과 창고 중단을 확인한 뒤 누른다.
- 발송된 배송 건이 하나라도 있으면 이 경로는 닫힌다. 일부 발송·배송 사고(분실·수취거부 반송)의 회수·환불 경로는 이 결정의 범위 밖이며 #453의 상태별 허용표와 함께 다룬다.
- 사유 구분(`reason_type`)의 구매자 값(`change_of_mind`·`defect`)은 청약철회 기한·반송비 부담을 가른다. 운영자 요청을 그중 하나로 적으면 운영 화면·필터·통계가 운영자 전액 취소를 구매자 단순 변심으로 센다. 그래서 운영자 요청은 `reason_type = 'staff'`(운영자 전액 취소)로 남기고 실제 사유는 `staff_reason_code`에 둔다. 두 값은 제약으로 묶인다(`origin = 'staff'` ⇔ `reason_type = 'staff'`). 구매자 신청은 계속 구매자 값 두 개만 받는다. 클레임 목록·상세·주문 패널·통계·목록 엑셀은 "운영자 전액 취소 · 품절·출고 불가"처럼 운영 사유를 적고, 클레임 목록 사유 필터는 운영자 전액 취소 전체와 운영 사유 하나로 거른다(20261013110300, 2026-10-12 브라우저 QA QA-4).

## 검증 경계

`supabase/tests/staff_order_cancellation.sql`이 권한(staff 세션 전용)·허용 조건·창고 확인·감사·알림·고객 정책 불변·완료/재시도의 정확히 한 번 복원을 고정한다. 실제 토스 테스트 키로 취소 왕복을 확인한 증거는 이 ADR이 아니라 런북의 심사 트랙 기록에 남긴다.
