# 반품 자동 회수 접수와 반품입고 파일 반영 — 승인 밖 지연 큐, 계약 전에는 DB 스위치로 닫아 둔다

- Status: accepted (2026-11-12) — 사용자 결정 2026-11-11(원장 재작업 결정 묶음 8 "반품 자동 회수 접수"·"반품입고 파일 반영", QNA-032·QNA-034), 원장 재작업 웨이브 2 T13b
- 바꾸는 기록: [판매·정산 후속 범위 분류](../research/smartstore-admin/sales-remaining-scope.md)와 [출고지시·회신 런북](../runbooks/warehouse-export.md)의 2026-10-15 "운송장 발급·회수 접수 자동화 제외" 가운데 **회수 접수**(운송장 발급 자동화 제외는 그대로)
- 관련: [ADR-0017](./0017-order-claim-intake-and-origin-collections.md)(출고지별 회수·환급 기한), [ADR-0033](./0033-shipment-extra-trackings-auto-delivery.md)(택배 추적 seam), [ADR-0041](./0041-claim-reshipments-per-origin.md)(회수 생략), [반품 회수 런북](../runbooks/return-pickup-intake.md)

## 맥락

- 반품·교환을 승인하면 고객이 안내받은 반품지로 직접(착불) 보낸다. 상품 상세는 "착불로 보내주세요"라고 안내하고, 운영자는 창고 회신을 보고 회수 묶음(배송 건 × 반품지, T14a)마다 실제 입고일·근거를 손으로 적는다(T11b). 업계(스마트스토어·카페24)는 반품 승인 때 택배사 반품 회수(방문 수거)를 자동 접수하고, 창고 입고 파일로 입고를 일괄 반영한다.
- 택배사 반품 회수 계약·API·회수 운임(우체국·한진)과 개인정보 처리위탁(택배사에 고객 주소·연락처를 넘김)·처리방침 고지는 사람 게이트다. 서원 반품입고 파일 양식·주기도 아직 없다.
- 회수 확인(입고)은 환급 기한(반환받은 날부터 3영업일)·재고 복원의 기산점이라 틀린 주문에 기록되면 돈·재고가 틀린다.

## 결정

1. **스위치(DB 강제, 기본 꺼짐).** `private.return_pickup_settings` 한 행에 두 스위치를 둔다 — 자동 회수 접수(`pickup_enabled` + 서비스 이름·근거·켠 시각, 자동 재시도 상한·간격)와 반품입고 파일 반영(`intake_enabled` + 근거·켠 시각, 열 이름 대응표 `intake_columns`). 게이트가 달라 따로 켠다. 출고지마다 회수 계약을 따로 켠다(`private.return_pickup_origins` — 그 출고지의 회수 계약 택배사). 바꿀 때마다 리비전·감사(`system.return_pickup.settings_changed`)가 남고 행은 지우지 못한다. 앱 env만으로는 켜지지 않는다. 꺼져 있으면 큐를 만들지 않고, 택배사를 부르지 않고, 회수 묶음 읽기(운영 상세·일괄·고객 회수 주소)에 키를 더하지 않는다 — 화면·동작이 지금과 같다(SQL·vitest로 고정).
2. **자동 회수 접수는 승인 트랜잭션 밖의 지연 큐다(오케스트레이터 판단 ④).** 승인(`prepare_claim_collections`)은 바꾸지 않는다. 5분마다 크론(`/api/cron/return-pickups`)이 `service_return_pickup_work`로 할 일을 받는다: DB가 새 회수 묶음을 큐(`private.claim_return_pickups`, 묶음 하나에 한 행)에 넣고 → 필요 없어진 접수를 닫거나 취소로 돌리고 → 기한이 된 접수·취소를 10분 임대(lease)해 넘긴다. 앱은 어댑터로 택배사에 접수·취소하고 결과를 `service_record_return_pickup_results`로 남긴다. 접수 실패가 승인을 되돌리지 않는다.
   - **대상:** 스위치·출고지 계약을 켠 **뒤** 승인된 수거중 회수 묶음만. 켜기 전 승인분은 고객이 이미 보냈을 수 있어 넣지 않는다. 회수 생략(ADR-0041, 결정 표 `private.claim_collection_waived`) 배송 건, 고객이 이미 보냈다고 기록된 배송 건(회수 정보 정정의 구매자 발송, 판매자 접수의 회수 방법), 운영자가 회수 정보 정정으로 수거 방법을 따로 기록한 배송 건은 넣지 않는다.
   - **멱등·재시도:** 묶음마다 고정된 멱등 키(`icons-return-<묶음 id>`)를 택배사에 함께 보낸다 — 재시도·응답 유실 뒤 다시 보내도 수거가 두 번 잡히지 않는 것이 어댑터 계약이다. 실패는 상한(기본 5회)까지 간격을 늘려(기본 30분 × 2ⁿ, 최대 24시간) 다시 시도하고, '자동 수거 실패'로 세어 반품·교환 목록 위와 상세에 보인다. 운영자는 상세의 "회수 다시 접수"로 바로 다시 큐에 넣는다(`admin_retry_claim_return_pickup`, sales.manage, 감사). 임대가 바뀐(다른 회차가 다시 잡은) 결과는 받지 않는다.
   - **취소:** 요청이 철회·거절·종결되거나 회수 생략·고객 직접 발송으로 회수가 필요 없어지면, 한 번도 보내지 않은 접수는 그냥 닫고, 접수됐거나 접수됐을 수 있는 것은 멱등 키·회수 송장으로 취소를 요청한다(취소 실패도 '자동 수거 실패'로 센다). 묶음이 입고되면 접수는 끝난다(`collected`).
   - **기록:** 접수되면 회수 송장을 저장하고 클레임 회수 이력(`private.claim_collection_events`, 처리자 없음 — 지금 회수 문서 이력 모양 그대로)·감사(`system.order.claim_return_pickup_requested`)에 남기고 고객에게 알린다("방문 회수가 접수됐어요"). 취소도 이력·감사에 남긴다. 감사·이력·크론 응답에는 고객 이름·연락처·주소를 싣지 않는다.
   - **개인정보:** 택배사에는 회수지 최소 필드(받는 분 이름·연락처·우편번호·주소)와 반품지(받는 곳), 품목 이름·수량, 원래 출고 운송장만 보낸다. 회수지는 클레임 연락처 정정과 같은 순서로 고른다: 회수 주소 정정(암호문 — 앱 서버가 클레임 연락처 키로 열고 주소 HMAC을 대조한다) → 판매자 접수 회수 주소 → 주문 배송지. 연 주소는 저장하지 않는다.
   - **어댑터 seam:** `lib/fulfillment/pickup/*`. 서비스 이름이 DB(`provider`)와 서버 env(`RETURN_PICKUP_PROVIDER`)에서 같아야 쓰인다. 지금 등록된 것은 격리 시험·QA용 가짜 어댑터뿐이다(운영 배포에서는 만들지 않는다). 우체국·한진 반품 회수 어댑터는 계약·API 문서 전이라 인터페이스와 TODO 경계만 두고 응답 파싱을 추측해 구현하지 않는다. 키·주소는 서버 env(`RETURN_PICKUP_API_KEY`·`RETURN_PICKUP_API_URL`)만 쓴다. 택배 추적 seam(ADR-0033)과는 계약이 달라 별도 스위치다 — 회수 송장의 택배 추적은 이번 범위가 아니다(입고 확인은 아래 파일 반영과 회수 확인이 한다).
   - **고객 안내(스위치에 묶음):** 굿즈의 출고지에 회수 계약이 켜져 있으면 상품 상세의 "착불로 보내주세요"를 방문 회수 안내로 바꾸고(`get_good_return_pickup`), 진행 중 반품·교환이 방문 회수면 주문 상세의 수거중 안내도 바꾼다(`get_my_order_return_pickup`). 고객 회수 정보의 회수 묶음에 회수 송장이 보인다(접수된 묶음에만 `pickup` 키).
3. **반품입고 파일 반영은 열 이름 대응표로 받는다(오케스트레이터 판단).** 서원 양식이 없으므로 화면 코드는 양식을 모르고, DB 설정의 대응표(회수 송장·주문번호·연락처·입고일 네 칸의 머리글 별칭)로 읽는다. 다른 열(이름·주소 등)은 읽지 않고 서버로 보내지 않는다. 파일은 운송장 회신 업로드와 같은 경계(비밀번호 XLSX 풀기·크기·압축 한도·수식 거절, CSV·TSV 엑셀 저장 글자)로 읽는다.
   - **매칭(④ 엉뚱한 주문을 입고 처리하지 않게):** 회수 송장이 자동 접수 회수 송장이나 회수 정보 정정의 수거 송장과 같으면 그 회수 묶음, 아니면 주문번호와 연락처 끝 8자리가 함께 맞는 주문의 회수 묶음. 주문번호만으로는 맞추지 않는다. 아직 입고되지 않은 묶음이 정확히 하나일 때만 맞추고(반품지가 갈린 배송 건은 상세에서), 회수 생략 배송 건은 파일로 확정하지 않으며(T11b 일괄 계획과 같다), 한 파일의 같은 묶음 두 줄은 뒤 줄이 중복이다. 입고일은 오늘(KST) 이하·주문일 이상.
   - **미리보기 → 확정:** "등록 전 확인"은 아무것도 바꾸지 않는다(`admin_preview_claim_return_intake`). 확인창을 거쳐 확정하면 같은 파일(SHA-256이 같아야 함)을 다시 읽어 미리보기의 묶음과 함께 보내고, DB가 다시 맞춰 같은 묶음일 때만 T11b·T14a 회수 확인 경로(`private.record_order_claim_collection_bundle`)로 기록한다 — 실제 입고일 = 파일의 입고일, 근거 = "반품입고 회신 파일 SHA-256 <해시> · N행", 처리자 = 운영자. 미리보기 뒤 바뀐 줄은 기록하지 않는다. 줄마다 따로 기록해 한 줄의 실패가 다른 줄을 막지 않고, 주문 순서로 처리해 다른 회수 확인과 같은 잠금 순서를 지킨다. 같은 확정 번호의 재전송은 저장된 결과를 돌려준다(`private.claim_return_intake_imports`, 감사 `admin.order.claim_return_intake_confirmed`).

## 택하지 않은 대안

- **승인 트랜잭션 안에서 택배사 호출:** 택배사 지연·실패가 승인을 막거나 되돌린다. 외부 호출은 트랜잭션 밖이 업계 관례다.
- **승인 때 큐 행을 만드는 트리거:** 승인 경로(여러 트랙이 재정의하는 함수)에 새 실패 지점을 더한다. 크론이 묶음을 찾아 넣는 쪽이 승인을 건드리지 않는다.
- **회수 정정 계획(`claim_collection_plans`)에 자동 접수 송장 쓰기:** 계획은 배송 건 단위(송장 한 칸)라 반품지가 갈린 배송 건의 묶음별 송장을 담지 못하고, 운영자 정정 리비전 계약과 섞인다. 자동 접수는 묶음 단위 큐에 두고, 이력만 같은 회수 이력 표에 남긴다.
- **스위치를 켜면 이미 승인된 수거중 요청까지 접수:** 고객이 이미 착불로 보냈을 수 있어 수거가 헛걸음하거나 이중 반송이 생긴다.
- **반품입고 파일을 주문번호만으로 맞추기:** 번호 오기 하나로 다른 고객의 반품이 입고 처리돼 환급 기한·재고가 틀린다. 연락처를 함께 맞춘다.
- **서원 양식을 추측해 고정 열로 구현:** 양식이 오면 코드가 바뀌어야 하고, 추측이 틀리면 엉뚱한 칸을 입고일로 읽는다. 대응표는 값만 바꾼다.
