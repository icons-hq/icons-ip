## 기존 기능과의 차이

- [현재 카테고리 관리](../../../components/admin/screens/CategoryScreen.tsx)는 최대4단계의 코드·이름·부모·순서·보관/복원과 대표/추가 말단 분류를 관리한다. [카테고리 타입](../../../lib/admin/category.ts)에는 전시 상품목록이나 상단 콘텐츠가 없다. 이 상품분류의 이름·계층은 분류/ERP 용도다. 전시만을 위한 이름·부모·순서를 바꾸는 독립 전시트리가 별도로 필요하다.
- [공개 상품목록](../../../lib/shop-catalog.ts)의 `category` 조건은 현재 상품의 **대표 `categoryId`와 조상**으로 필터링한다. 추가 카테고리까지 현재 공개 필터가 사용한다고 가정하지 않는다. [상품 선택기](../../../supabase/migrations/20261020085237_shopping_story_goods_picker.sql)는 대표·추가 분류를 조회하므로 두 동작을 혼동하지 않는다.
- [공개 메뉴](../../../lib/store-navigation.ts)는 고정 메뉴의 이름·노출·순서다. [홈 구성](../../../components/screens/Home.tsx)은 홈 본문을 소유한다. 어느 쪽도 분류별 상품목록의 배너·영상·추천상품을 대신하지 않는다.
- [용어집](../../../CONTEXT.md)의 카테고리는 굿즈 분류이자 ERP 분류 매핑 대상이다. 전시를 위해 `goods.category_id`, `goods_additional_categories`, ERP 매핑, 속성 정의/상품값, 고시·KC 값을 바꾸지 않는다.

## 독립 전시트리와 기존 데이터 이관

전시 전용 `private.category_display_nodes`가 이름·부모·순서·보관 상태를 소유한다. 초기 이관은 기존 모든 `catalog_categories`의 UUID·이름·부모·순서·보관 상태·시각을 그대로 복사한다. 동률 순서의 기존 `code` 기준은 이관용 정렬 키로 고정해 유효 순서도 유지한다. 이후 상품분류를 만들거나 이름·계층·순서를 바꾸어도 전시 노드를 자동으로 추가하거나 변경하지 않는다.

`private.category_display_compositions.category_id`는 같은 UUID의 전시 노드를 참조하도록 FK만 전환한다. 기존 composition/source/goods 행, 배너·영상·추천 데이터, revision·updated_at, `/shop?displayCategory=` 주소를 그대로 유지한다. 원본 상품분류 연결은 기존 `category_display_sources.source_category_id`의 상품분류 FK를 유지하며 관리자 DTO도 `categories`(전시트리)와 `sourceCategories`(상품분류)를 구분한다. 기존 `/shop?category=`, 굿즈 대표/추가 분류, ERP 매핑, 속성·고시·KC·가격·재고·홈 전시는 변경하지 않는다.

신규 전시분류는 원본에서 확인한 20자 이름, 최대3단계, 최상위19개·같은 상위 아래15개 한도를 사용한다. 기존 4단계와20자를 넘는 이름은 이관 과정에서 자르거나 삭제하지 않는다. 기존 긴 이름을 그대로 저장할 수 있고, 다른 이름으로 바꾸면20자 한도를 적용한다. 부모 변경은 하위 전체를 포함해3단계 이내에서 가능하다. 순환·없는 부모·보관된 상위·한도 초과는 서버에서 거절한다.

생성·이름/부모/순서 변경·보관/복원을 전시 화면에서 처리한다. 순서는 같은 부모 아래 위/아래 이동이며 부모 변경은 선택 상자에서 한다. 물리 삭제 대신 보관하며 그 노드와 하위 공개 전시를 숨기고 상품 연결·상단 콘텐츠를 보존한다. 상위 복원은 별도로 보관한 자손을 임의로 복원하지 않는다. 보관된 노드도 관리 목록과 저장 설정을 읽을 수 있다.

전시트리 저장은 `store.manage`, 최신 계정/프로필 검사, 작업 UUID 영수증, 기존 상품분류 트리 잠금, 전시트리 전체 revision CAS로 확정한다. 트리 revision과 전시별 콘텐츠 revision은 분리한다. 이름/부모/보관 변경은 콘텐츠 revision·이미지 claim·상품 연결을 건드리지 않는다. 같은 요청 재시도는 원 결과를 반환하고 다른 payload의 UUID 재사용은 거절한다. 충돌과 응답 유실에는 입력을 유지하고 최신 조회 또는 동일 요청 확인을 제공한다.

상품 ID 변경·실제 삭제의 기존 FK 후속 처리는 유지한다. 전시 원장이 상품 카테고리나 ERP 값을 역으로 쓰지 않는다. UI에 **“전시 목록만 바뀌며 상품의 카테고리·ERP 정보는 바뀌지 않습니다.”**를 표시한다. 상품분류 자체는 원래 `catalog.manage` 화면에서 관리한다.

## 상품 연결과 공개 목적지

1. **분류 연결:** 활성 카테고리를 최대10개 고른다. 선택한 분류의 하위 전체에서 대표 또는 추가 분류가 일치하는 상품을 중복 제거한다. 이관된 전시에는 기존 상품분류를 초기값으로 유지한다. 새 전시는 상품분류를 명시적으로 고르며 전시 UUID를 상품분류로 취급하지 않는다. 추가 분류 포함은 새 전시 목록의 명시적 계약이며 기존 `/shop?category=` 필터의 의미를 변경하지 않는다.
2. **개별 상품 연결:** 최대1,000개를 명시적으로 고르고 순서를 저장한다. 상품코드/이름 검색, 연결 해제, 위/아래 이동을 제공한다. 이 한도는 ICONS 편집·요청 크기 한도이며 원본 상한이 아니다. 분류 연결의 자동 결과에는 1,000개 절단을 적용하지 않는다.
3. 연결 방식별 저장 목록을 보존하고 활성 방식만 공개 조회에 사용한다. 방식 전환은 최종 적용 전까지 초안이다. 비활성 방식의 목록을 합치거나 전환만으로 상품분류를 수정하지 않는다.
4. 신규 목적지는 기존 페이지의 **`/shop?displayCategory=<display UUID>`**를 사용한다. 기존 전시 UUID와 주소는 유지한다. [현재 `app/shop/page.tsx`](../../../app/shop/page.tsx)가 서버에서 파라미터를 읽고 별도 전시 조회 결과를 기존 `Shop` 렌더에 전달한다. 실제 경로 생성은 `lib/routes.ts` 계열의 한 helper로 모은다. 설치된 Next의 `searchParams` 서버 페이지 규약을 유지한다.
5. `displayCategory`는 정확히 한 개만 허용한다. 기존 `category`와 동시에 받은 경우 잘못된 조건을 안내하고 임의로 전체 목록으로 넓히지 않는다. IP·유형·가격·정렬 조건은 전시 목록 **안에서** 적용한다. 전시 카테고리 변경은 이 추가 필터와 더보기 상태를 초기화한다. 필터 해제는 현재 전시 카테고리를 유지하고, 별도 `전체 상품` 링크만 `/shop`으로 이동한다.
6. 공개 GNB의 고정8개 메뉴는 유지한다. `/shop`의 카테고리 탐색 영역에 전시 가능한 카테고리 목적지를 별도로 연결하고 독립 전시트리의 현재 이름·계층·순서를 사용한다. 구성 없는 카테고리의 기존 `category` 필터와 기존 마케팅 링크는 그대로 둔다. `displayCategory` 주소는 기존 category 마케팅 링크의 목적지를 조용히 바꾸지 않는다.
7. 전시가 꺼졌거나 전시분류/조상이 보관됐거나 기존 고객 카테고리 전역 게이트가 꺼진 주소는 일반적인 이용 불가 상태를 반환한다. 임의 UUID·비공개 설정값·비공개 상품 존재를 노출하지 않는다. 유효한 전시에서 공개 가능한 본문 상품이0개이면 메뉴에서는 숨기고 직접 주소에는 빈 목록과 전체 상품 이동을 제공한다. 추가 필터 때문에0개인 경우에는 필터 초기화를 제공한다.

수동 추천순은 저장 순서→상품ID, 분류 연결 추천순은 현재 공개 상품목록의 `display_order`→기존 ID 비교 규칙을 유지한다. 최신순·가격순도 기존 목록과 같은 의미로 제공하며, 서버와 TypeScript의 숫자 포함 ID 정렬 차이를 검증한다. 신규 매출/인기도 산식을 붙이지 않는다.

## 페이지 조회와 기존 상품 모델 재사용

- 관리 상품 선택은 [쇼핑스토리의 서버 조회](../../../lib/admin/shopping-stories.server.ts)·[선택기](../../../components/admin/ShoppingStoryGoodsPicker.tsx)의 상품명/코드·분류·상태·20개 페이지를 재사용할 우선 후보로 삼는다. 홈 선택기의 배열 `slice`만 붙여 전체 결과라고 하지 않는다. 검색을 바꿔도 다른 페이지의 선택 ID를 유지하며, 저장 직전에 전체 선택 ID를 서버에서 재검사한다.
- 공개는 **한 번에20개와 다음 조회 정보**를 반환하고 현재 VIEW MORE 동작을 유지한다. 연결상품 집합→현재 공개 게이트→추가 필터→안정 정렬→페이지를 한 조회 계약으로 묶는다. `total`은 공개 가능한 전시 전체, `filteredTotal`은 IP·유형·가격 조건을 적용한 전체다. facet과 가격 상한은 기존 Shop처럼 추가 필터 적용 전 전시 전체를 기준으로 유지한다. 중간 페이지의20개를 전체로 집계하지 않는다.
- [현재 `getCatalogSnapshot`](../../../lib/catalog.ts)의 goods 읽기는 페이지 반복이 없는 단일 질의다. 이를 신규 목록의 전수 조회 근거로 사용하지 않는다. [선택 상품 조회](../../../lib/catalog.ts)의 `getCatalogGoodsByIds`는 공개/IP 게이트·옵션 가격/재고와 완전한 ID 페이지 읽기를 제공하지만 입력1,000개 한도가 있으므로 큰 분류 결과를 한 번에 전달하지 않는다.
- 신규 공개 읽기는 DB에서 페이지 대상·전체 건수를 결정하고 필요한 상품만 같은 공개 카드 projection으로 조립한다. 한 RPC의 같은 조회 스냅샷에서 카드 원자료·전체 건수·facet·조회시각을 반환해, ID 페이지 뒤 별도 질의로 가격/공개 상태를 읽는 사이에 결과가 달라지는 문제를 피한다. 서버는 이 자료를 공유 mapper로 정규화한다. 가격은 기존 `resolve_goods_variant_price`와 공개 카드의 옵션 가격범위, 재고는 기존 supply 계산과 일치시킨다. 관리자 상품 조회 RPC를 익명에게 열거나 기본 상품 가격만으로 다른 정렬을 만들지 않는다. 기존 공개 projection을 공유하기 위해 필요한 작은 추출은 가능하나 상품/주문 가격 계약은 바꾸지 않는다.
- 조회 도중 공개 상태·가격·재고가 변할 수 있다. 각 요청은 그 시점의 공개 조건을 재검사하며, 여러 요청에 걸친 과거 전체 스냅샷을 보장한다고 표현하지 않는다. 불투명한 조회 토큰에 조건·정렬·전시 revision을 결속하고 revision이 바뀌면 처음부터 갱신한다. DB revision 자체를 별도 공개 필드로 보내지 않는다. 같은 상품ID의 중복 append를 제거한다. 페이지 읽기 실패는0건/완료로 처리하지 않고 기존 결과와 재시도 동작을 유지한다.
- 검증에는1,001개 이상 자동 연결, 수동1,000개 경계·1,001개 거절, 동일 정렬값, 말단/상위·추가 분류 중복, 마지막/0건 페이지, 가격/공개상태 변경과 낮은 PostgREST 응답 상한을 포함한다. 특히 한 RPC의 후보 ID가 모두 도착했는지와 공개 카드 전량 수신을 별도로 검산한다.

## 노출·권한·저장

**공개:** 기존 고객 카테고리 전역 활성 조건과 독립 전시분류/조상의 비보관을 통과한 뒤 해당 전시 enabled를 검사한다. 기존 전역 게이트를 임의로 켜거나 별도 우회하지 않는다. 상품분류 연결의 후보 집합은 원래 상품분류 활성 조건을 유지하지만 수동 전시는 상품분류 이름/보관에 종속되지 않는다. 상품/IP의 공개·비보관·판매제한없음 조건은 모든 본문·추천·영상에서 동일하게 적용한다. 품절 및 판매 시작 전/종료 후 공개 탐색은 기존 계약대로 유지하고 구매 가능 여부는 기존 상품/결제 규칙에 맡긴다. 알 수 없는 분류를 전체 목록으로 바꾸거나 비공개 상품 ID·선택 사유·revision·운영자 정보를 공개 projection에 넣지 않는다.

**권한:** 관리 화면·읽기·미리보기·저장에 현재 `store.manage`를 사용한다. [기존 매니저 규칙](../../../lib/admin/access.ts)의 최신 프로필·원장으로 검사하고, 전시 편집을 위해 `catalog.manage`나 `platform.manage`를 새로 부여하지 않는다. 상품 선택 전용 읽기는 `store.manage`가 볼 수 있는 기존 편성용 최소 필드만 사용한다. 상품 기본 정보/분류/ERP 변경은 원래 권한·화면에 남긴다.

**저장:** 카테고리당 전체 전시 설정·관계·이미지 claim을 단일 트랜잭션으로 저장한다. `expectedRevision`과 작업 UUID·정규화한 요청를 받고 최초0→1, 이후 CAS를 적용한다. 기존 운영자 잠금→작업 키→카테고리 트리→정렬한 상품 행→전시 행 순서를 따른다. 실제 상품 편집기 rename과 물리 DELETE FK 경합을 독립 clone에서 검증했다. 없는 전시 행의 동시 최초 저장도 하나만 성공해야 한다. 업무 충돌은 기존 합의대로 `PT409`로 반환하고 현재 입력을 보존한다. 전시 이름/부모 변경과 콘텐츠 저장은 같은 트리 잠금 순서를 사용하고 서로의 revision을 덮어쓰지 않는다.

같은 actor·작업 UUID·같은 요청은 같은 결과1개를 반환하며 다른 내용의 UUID 재사용은 거절한다. 현재 권한 검사는 영수증 재생보다 먼저 한다. 결과가 불명확하면 최초 요청·UUID를 고정해 결과 확인/같은 요청만 재시도하고, null을 미실행 증거로 삼지 않는다. 성공 응답과 readback의 revision·순서·이미지 연결을 대조한 뒤 초안을 지운다. 실패·충돌·로그인 변경 때 저장본이 빈 기본값으로 대체되지 않게 한다.

새 원장은 private schema·RLS·직접 DML 봉인을 사용한다. public RPC는 생성 직후 `public, anon, authenticated, service_role` 모두의 execute를 회수하고 관리자 RPC는 authenticated, 공개 최소 조회만 anon/authenticated에 필요한 grant를 준다. operator RPC 계약 등록과 권한 철회·서비스 롤 거부 검증을 포함한다. [Supabase 공식 Data API 지침](https://supabase.com/docs/guides/api/securing-your-api)의 grant와 RLS를 별도로 적용한다.

초기 조회는 현재 조건을 매번 읽어 장기 캐시가 비공개 전시를 되살리지 않게 한다. 저장 후 관련 관리자 경로·`/shop`을 갱신한다. 전시분류 보관·고객분류 전역 비활성화는 저장값을 보존하면서 공개만 막고, 복원 시에도 전시의 enabled 값을 임의 변경하지 않는다. 영구삭제는 연결 관계가 있는 동안 거절하는 쪽을 권고한다.

실제 앱 QA 뒤에는 공통 셸과 겹치던 본문 제목만 제거하고 설명을 유지했다. 해당 파일 ESLint와 관련18개 테스트는 통과했으며, 이 작은 표시 변경의 최신 source 화면 확인은 다음 브라우저 인계 때 수행한다. 기존 기능 QA의 source SHA와 이 변경은 결과 manifest에서 구분한다.

## 구현 Module과 검증 기준

`category-display` Module의 Interface는 전시/상품분류 목록 조회, 트리 변경, 관리 설정 조회, 상품 후보 페이지 조회, 전체 설정 저장, 공개 전시 페이지 조회다. 저장 검증·권한·CAS·claim·공개 후보·중복 제거·페이지 검산은 Module의 Implementation에 둔다. 관리 미리보기와 공개 페이지는 같은 공개 모델을 사용하며 미리보기용 가짜 상품목록을 별도로 만들지 않는다. 홈 배너/상품카드/영상의 순수 렌더·정규화는 실제로 공유하고, 홈 편성의 수명과 카테고리 편성 수명은 합치지 않는다.

기존 상품 연결·상단 콘텐츠 원장·저장/공개 조회, Shop 연결/탐색, 관리 편집기와 상단 콘텐츠를 구현했다. 아래 실제 앱 근거는 기존 부착 방식의 검증이며 새 독립 전시트리의 실제 앱 증거로 합산하지 않는다. ARCHITECTURE에 계약을 반영했고, census 완료 판단은 named DB 적용과 실제 앱 QA 결과를 별도로 따른다. 현재 로컬 검증을 운영 배포 증거로 인용하지 않는다. 실제 앱 근거는 검증 결과 (`output/category-display-qa-20261014/actual-app/result.json`)에 보존했다. 공개 PC/390px, 수동21개 선택 후 공개22개 페이지, 분류/수동 전환, 배너별 currentSrc, 수동 영상 재생/해제, 충돌/응답 손실의 동일 작업 재시도를 통과했다. 검증 후 전용 카테고리와 Storage 객체3개를 제거하고 원래 영상 빈 상태와 카테고리 활성값·근거를 복원했다.

- 기존 상품 대표/추가 분류·ERP 매핑·속성·고시·가격/재고, 카테고리 원행, 홈 큐레이션이 전시 저장 전후 그대로인지 DB 지문으로 확인한다.
- 격리 DB에서 최초 저장 경합·CAS·동일/다른 UUID payload·권한 철회·카테고리 보관/이동·이미지 claim 소비·영상 해제/교체·참조상품 ID 변경과 삭제를 검증한다. 공유/운영 DB는 reset하지 않는다.
- 실제 Chrome PC/390px에서 분류/개별상품 모드 저장·전환 보존·21번째 이상 선택·다른 페이지 선택 유지·순서·새로고침·공개 URL·필터/뒤로가기·더보기·빈 목록을 확인한다. 원본 토글이 OFF인 기능의 결과를 원본 실측이라고 표시하지 않는다.
- 배너의 PC/모바일 실제 `currentSrc`, 링크 없음, 새 이미지 claim, 영상 수동재생/실패·교체/해제, 추천0/1/12개·비공개/품절과 본문 중복을 확인한다. 두 탭 충돌·오프라인 결과불명·같은 요청 복구·Escape/포커스·미저장 이동 경고도 확인한다.

**독립 전시트리는 전체 운영 UI 이식에 포함된 필수 구현이다.** 전시 전용 영상 업로드는 확인하지 않은 별도 자산 수명까지 확대하므로 이 변경에서 추가하지 않는다. 이 제안의 배너1개·수동1,000개·분류10개·추천 후보100개 등의 자체 한도는 원본을 더 확인하면 변경할 수 있다.
