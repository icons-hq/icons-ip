# 전역 적립금 지급관리·지급내역 설계

migration 파일 경로는 [배포 매핑](../../../supabase/manifests/admin-rollout-migration-map.json)을 반영했다. 아래 과거 검증·적용 기록은 당시 원본 DRAFT 기준이며 이번 운영 배포의 성공을 뜻하지 않는다.

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

조사: 2026-10-12. 원본 확인에 따라 전역 지급관리·전체 원장·대상 반입·원자 일괄 지급·감사 엑셀을 구현했다. 격리 DB 및 UI 검증 결과는 아래에 구분하며 운영 지급·운영 정책 활성화·배포를 의미하지 않는다. 사용자 운영 데이터는 복사하지 않았다.

## 원본과 대응할 화면

[스토어 대응 조사](store-parity.md)의 `store/200–215` 캡처를 기준으로 확인했다. 201b는 지급관리 목록, 203b/204/205는 지급폼, 206/206b는 회원 검색, 207은 엑셀, 208b는 비구매 분기, 209/210c/211/212/213/214/215는 이력 조회다. 원본 입력·선택 단계만 조사했으며 실제 지급은 하지 않았다.

Npay 비즈월렛·충전·잔액 및 구매/비구매별 최근 30일 고정 상한은 제공자 계약이다. ICONS의 보유 상한·유효기간을 대신하지 않는다. 최근 30일 지급액은 실제 운영 지급 원장 합계를 참고값으로 보여 줄 수 있지만 새 제한을 자동으로 만들지 않는다. 알림 발송은 이 기능의 지급 저장과 별도이며, 이번 구현에서 묵시적으로 고객 메시지를 보내지 않는다.

## 현재 코드의 재사용 경계

정본: [`sales_store_credit_ledger.sql`](../../../supabase/migrations/20260910083943_sales_store_credit_ledger.sql), [`sales_store_credit_checkout.sql`](../../../supabase/migrations/20260910083947_sales_store_credit_checkout.sql), [`lib/store-credits.ts`](../../../lib/store-credits.ts), [`store-credit-actions.ts`](../../../app/admin/store-credit-actions.ts), [`StoreCreditForms.tsx`](../../../components/admin/screens/StoreCreditForms.tsx).

- 정책·지급·고객별 전체 이력은 **활성 admin 전용**이다. 신규 전역 화면을 staff에 개방하면 기존 권한이 넓어진다. 같은 admin 경계를 유지한다.
- `private.store_credit_lots`는 원발급·잔액·선점·사용·만료·회수·상계·부채를 보존한다. `issued_amount`는 구성 수량의 합과 같아야 한다. 고객·주문 FK로 원장이 연쇄 삭제되지 않도록 안정된 UUID를 기록한다.
- `public.store_credit_ledger`는 `grant`, `adjustment_credit`, `adjustment_debit`, `expire`, `reserve`, `consume`, `restore`, `earned_reversal`, `debt_offset`, `restoration_expired`를 구분한다. authenticated 직접 SELECT는 본인 행만 허용하고 운영 전역 조회는 새 admin RPC가 필요하다.
- `admin_adjust_store_credit`는 `operationId`와 actor/kind/payload 일치를 확인한 뒤 정책 활성, 정상 계정·탈퇴 쓰기 봉인, 만료 정리, 예상 사용 가능 잔액, 보유 상한과 만료 시각을 검증한다. 양수 지급은 `issue_store_credit_lot`를 사용하며 이미 사용한 환불 적립금 부채를 먼저 상계한다. **발급액과 즉시 사용 가능한 증가액이 다를 수 있다.**
- 개별 차감 정정은 가용 lot를 만료 순으로 차감한다. 특정 지급 건의 취소·되돌리기와 같지 않다. 일괄 내역에 단순 음수 지급을 연결해 `지급취소`로 표시하면 안 된다. 지급 취소 기능은 이번 양수 지급 범위에서 분리한다.
- `private.store_credit_history`는 읽을 때 만료 lot를 정리하고 원장을 추가한다. 전역 대상 프리뷰에서 고객별 이력 함수를 반복 호출하는 방식은 읽기 전용 검증이 아니다. 프리뷰는 현재 시각 이후 만료되는 가용액과 선점·부채를 계산하고, 실제 지급은 기존 만료 정리 함수를 사용한다.

## 구현한 데이터·RPC 계약

1. **작업/대상 스냅샷**: 지급 목적·사유·1인당 금액·만료 시각·actor·정책 version·정확한 입력 payload·대상 UUID와 검증 결과·생성/만료 시각을 갖는 비공개 프리뷰 원장. 최종 실행은 프리뷰 ID만 받아 서버가 저장된 내용으로 처리한다. 클라이언트가 다시 보낸 합계·가능 여부·대상 이름을 신뢰하지 않는다.
2. **대상 프리뷰**: 최대 1,000개 UUID, 중복·없는 고객·계정 상태·탈퇴 봉인·정책 비활성·만료 시각·잔액 상한을 실제 정책으로 판정한다. 기존 부채 상계를 반영해 지급액/상계액/가용 증가액을 표시한다. 지급 목적은 운영 분류만 보존하며 구매 이력에 관한 새 지급 자격을 만들지 않는다.
3. **선택과 확정**: 불가 대상은 사유를 표시하며 최종 대상에서 제외한 내용을 다시 검증한다. 운영자가 확인한 유효 대상 집합만 고정한다. 대상/금액/만료 변경 시 화면은 이전 프리뷰를 폐기하고 새로 검증한다. 저장된 이전 작업을 조회하는 경우에는 원래 고정 내용만 실행할 수 있다. 실제 실행 때 정책 version·계정 상태·잔액을 다시 확인한다.
4. **일괄 지급**: 전체 실행을 한 트랜잭션으로 처리하고 고객 UUID 오름차순으로 account lock을 잡는다. 각 대상은 배치/고객에 묶인 고정 child operation ID로 기존 `admin_adjust_store_credit` 계약을 재사용한다. 외부 PG 호출은 없다. 한 명이라도 검증 상태가 바뀌면 지급 전체를 롤백하고 재확인을 요구한다. 이미 성공한 동일 프리뷰/작업 재시도는 기존 결과를 반환한다.
5. **결과·이력**: 작업 헤더와 대상별 실제 lot/operation/ledger 연결을 남기고 권한 있는 readback으로 확정 건수·총액·가용 증가액을 확인한다. 프리뷰 제외/실행 전 충돌/실제 지급 성공을 각각 구분한다. 전체 롤백인데 일부 성공한 것처럼 집계하지 않는다.
6. **전역 검색·엑셀**: 지급 작업 목록과 원장 발생 내역을 서로 다른 조회로 제공한다. KST 기간·종류·고객/주문/작업 필터·정렬·페이지 분할은 DB에서 적용한다. 엑셀은 같은 조건·행 제한·개인정보 안내·감사를 따른다. 원장의 재지급/차감/상계 행을 원발급 합계에 중복 합산하지 않는다.

프리뷰/작업은 기존 금융 원장처럼 고객 FK 연쇄 삭제를 피하고, RLS·전체 기본 execute revoke 후 admin 게이트를 적용한다. 잠금 순서는 작업 멱등 키 → 정책 share → UUID순 고객 계정이며, 기존 주문→고객 계정 경로와 역방향 주문 잠금을 만들지 않는다. 실제 기존 수동 지급 함수를 호출할 때의 operation/account 잠금 순서도 회귀 검증한다.

## 구현·검증 순서

- 먼저 읽기 전용 전역 목록/원장 검색·공통 표·필터·엑셀을 추가한다. 기존 고객별 화면과 정책 설정은 유지한다.
- 그다음 대상 검색/파일 반입/프리뷰와 양수 일괄 지급 RPC를 하나의 흐름으로 연결한다. 기존 정책이 비활성인 환경에서는 입력 준비와 내역 열람만 제공하고 활성화나 임의 정책 입력은 하지 않는다.
- 격리 DB: admin/staff/customer/anon 경계, 만료 예정분, 부채 상계, 상한 직전, 대상 상태 변경, 중복 ID, 정책 변경, 예상잔액 충돌, 같은 batch 재생·다른 payload 충돌, 중간 실패 전부 롤백, 두 batch 동시 지급과 기존 단건 조정 경합을 검증한다.
- 앱: XLSX/CSV 1,000명 상한·중복·수식 셀/잘못된 ID·초과 파일을 검증하고, 값 변경 시 프리뷰 폐기·확정 전 예상액·실패 입력 보존·결과 재조회·권한 없는 경로를 확인한다.
- UI 검수는 사용자가 지정한 Chrome/CUA에서 실제 컴포넌트와 합성 action을 사용한다. fixture 저장은 운영 적립금 지급 증거가 아니다. 운영 정책 활성화·실제 고객 지급·배포는 실행하지 않는다.

## 구현 파일과 확인 결과

- 화면: `StoreCreditConsoleScreen`·`StoreCreditBatchForm`, `/admin/sales/store-credits` admin 전용.
- 계약: `lib/admin/store-credit-console*`, `app/admin/store-credit-console-actions.ts`, `20261020085137_admin_store_credit_batches.sql`.
- 반입: 기존 bounded ZIP/안전 셀 reader를 재사용하는 `store-credit-target-file.server.ts`, XLSX/CSV 한 열·1,000행·500KB.
- 내보내기: `/api/admin/store-credit-workbook`와 `admin_export_store_credit_console`, 동일 검색 조건·최대 10,000행·감사·마스킹·비암호화 취급 확인.
- 검증: 원자 지급 SQL의 1,000명 실행·미리보기 무변경·상계·전체 롤백·정책/잔액/시간 경합·재시도·권한·감사를 격리 DB에서 확인했다. 동일 조건 exporter·10,001행 거부·감사·낮은 권한 거부까지 최종 재실행을 통과했다.
- 남은 원본 차이: 원본의 Npay 지갑/제공자 고정 한도/예약 지급/지급취소는 현재 ICONS 원장 계약 밖이다. 일괄 지급은 즉시 양수 지급이며, 단건 차감을 특정 지급의 취소라고 표현하지 않는다.

- 실제 앱 검증: Chrome/CUA에서 격리 정책 설정 → 정확한 고객 검색 → 단건 1원 저장 → 잔액이 달라진 배치 전체 실패 → 새 1,000원 배치 성공 → 원장 2행/가용잔액 1,001원 → 같은 검색 조건 엑셀 1행을 확인했다. DB readback은 실패 작업 operation 0/감사 1, 성공 작업 operation 1/감사 1이었다. 390px 원장·입력 폼 모두 document 가로 넘침이 없었다. 증거는 로컬 `output/smartstore-reference-20261012/verification-store-credits/manifest.json`에 SHA-256으로 연결한다.
- 파일 반입 후속 검증(2026-10-14): 이전 확장 차단을 해소한 현재 Chrome의 실제 파일 선택창으로 CSV·XLSX를 반입했다. CSV의 같은 문자열 중복 제거로 2명, XLSX를 기존 선택과 합쳐 3명과 중복 제외 안내를 확인했다. 수식 셀·추가 열·닫히지 않은 따옴표·1,001행 오류는 기존 선택 3명을 보존했다. 390px에서 실제 파일 재선택·동일 파일 재반입·대상 비우기와 문서 폭/스크롤 폭 380/380을 확인했다. 파일 반입 UI 증거 (`output/store-credit-file-ui-qa-20261014/manifest.json`).
- 이 후속에서는 합성 UUID·이메일 문자열만 반입했고 대상·총액 검증이나 지급·회수는 실행하지 않았다. 기존 지급원장 4행·배치 2행·정책 1행·operation 4행·계정 3행의 전체 지문이 전후 동일했다. 입력은 비운 뒤 본인 탭과 390px 설정을 정리했으며 인증·정책을 바꾸지 않았다. 파일 reader의 500KB 등 나머지 경계는 앞선 코드 검증과 구분한다.
