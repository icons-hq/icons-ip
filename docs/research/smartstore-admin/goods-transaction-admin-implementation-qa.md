# 복수구매 할인·착불·수량 배송비의 관리자 설정 구현

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-14. **관리자 설정·공통 주문 계산·운영 SQL의 구현과 격리 검증을 마쳤다.** 소유한 로컬 앱에서 출고지 착불 계약과 상품의 복수구매 할인·수량 배송비를 실제 저장하고 PDP·장바구니·주문서·응답 유실 뒤 원 주문 복구를 확인했다. 관리자 착불 수납·정정·환급, 무통장 환불 송금 대기/완료와 정산 파일도 실제 화면에서 확인했다. 운영·Preview 배포는 하지 않았다.

## 상품 정책

- [상품 편집 패널](../../../components/admin/GoodsTransactionTermsPanel.tsx)은 복수구매 할인과 확장 배송비를 각각 저장한다. 같은 상품의 옵션 수량/정상가 합계 조건, 개당 정액/비율 할인, 한국 시간의 선택적 시작·종료, 선결제/착불/구매자 선택, 기존 운임/수량 반복/2·3구간을 제공한다.
- 초안은 불완전한 입력을 제한된 문자열로 보존한다. 활성화할 때 실제 숫자·달력·구간을 검사하고 DB의 최신 상품/정책 CAS와 착불 계약 준비 조건을 통과해야 한다. 과거 주문의 가격을 현재 정책으로 재작성하지 않는다.
- 기본 상품에 미저장 변경이 있거나 기본 저장 중이면 정책 저장을 막는다. 정책 요청 중에는 기본 상품 폼을 비활성화한다. 각 정책 저장은 다른 정책의 미저장 입력을 보존한다.
- [서버 Action](../../../app/admin/goods-transaction-terms-actions.ts)은 현재 actor와 `catalog.manage`를 확인하고 저장 영수증·fresh readback을 대조한다. 키 순서나 같은 시각의 offset은 의미상 같게 비교하지만 PostgreSQL 마이크로초 차이는 유지한다.
- 결과가 불명확하면 원문·작업 UUID를 보존해 같은 요청으로 확인한다. 충돌이나 저장 이후 새 변경은 입력과 최신 저장본을 나란히 비교한다. 다른 상품·계정·로그인 세션으로 늦게 도착한 응답은 적용하지 않는다.
- 개인정보를 포함하지 않는 상품 정책 입력은 계정·상품·로그인 세션을 결속해 브라우저에 7일 임시보관한다. 새로고침 후에도 불명확 요청의 UUID와 원문을 복원한다. 새 로그인 세션에서는 이전 입력을 복원하지 않는다.

## 출고지 착불 수납 계약

- [출고지 패널](../../../components/admin/ShippingCollectContractPanel.tsx)은 수납 주체·방법·고객 환급 문의처·안내와 계약·출고 표기·증빙·내부 분쟁 처리 근거를 관리한다. 실제 계약이나 운송사 수납을 실행하는 UI가 아니다.
- 전체 계약 조회·저장은 기존 출고지 운영 정책과 같은 `platform.manage` 및 legacy 관리자 조건을 사용한다. 일반 상품 편집자에게 계약 체결·활성화 권한을 추가하지 않는다. 상품 설정은 기존 `catalog.manage`를 유지한다.
- 연락처·계약 원문은 브라우저 저장소에 넣지 않는다. 응답이 끊긴 요청의 식별자·출고지·로그인 세션만 같은 탭에 남긴다. 서버 조회는 현재 actor의 해당 작업 영수증만 반환한다.
- 영수증이 아직 없다는 응답을 미실행으로 단정하거나 자동 재저장하지 않는다. 현재 저장값을 다시 확인한 뒤 명시적으로 새 편집을 시작할 수 있으며, 이후 저장도 현재 revision을 대조해 늦은 이전 요청이 새 정책을 덮어쓰지 못한다.
- 고객에게 표시되는 수납 안내와 계약 근거·내부 연락처를 구분한다. 상품 담당자용 안전한 준비 상태 RPC는 SQL에서 별도로 제공하며 계약 원문을 반환하지 않는다.

## 이 단계의 검증

9개 관련 테스트 파일의 111개 사례와 변경 소스 ESLint, 전체 TypeScript 검사를 통과했다. 검사 대상은 엄격한 입력·날짜/마이크로초·영수증, actor/권한 변경, 알 수 없는 write 오류, 저장 이후 다른 버전, 중복 callback, 동일 요청 복구, 세션별 복원, 한 정책 저장 시 다른 입력 보존, 계약 본문의 브라우저 저장 금지, 출고지 화면 권한 분기다.

초기 UI 구현 근거와 소스 SHA는 구현 검증 기록 (`output/goods-transaction-admin-qa-20261014/implementation-verification.json`)에 둔다. 이후 공통 거래 SQL·독립 검산·실제 경합 (`output/goods-transaction-design-20261014/ci-wrapper-proof-manifest.json`), 고객 실제 화면과 주문 복구 (`output/goods-transaction-browser-qa-20261014/result.json`)는 별도 검증 범위다. 수량 3개·정상가 30,000원·복수구매 할인 3,000원·수량 배송비 6,000원에서 선불 온라인 33,000원과 착불 온라인 27,000원/별도 6,000원을 확인했다. 같은 요청의 응답이 끊긴 뒤 새로고침·재확인해 주문 한 건과 재고 예약 한 번만 남았다. 실제 택배 수납·은행 입금·PG 결제는 수행하지 않았다.

## 관리자 후속 검증

관리자 실제 화면 기록 (`output/goods-transaction-browser-qa-20261014/admin-ui-progress-result.json`)에서 착불 6,000원의 수납·정정·재기록과 PG 정산 45건의 3개 탭·전체 파일을 확인했다. 다운로드 재조회 (`output/goods-transaction-browser-qa-20261014/export-readback-result.json`)는 실제 받은 파일의 값과 형식, 암호화 선물 목록을 별도로 대조한다.

이어 발견한 무통장 환불의 계좌 보완과 송금 단계 분리를 수정했다. 최종 실제 화면 검증 (`output/bank-transfer-refund-qa-20261014/browser-result.json`)에서 주문 취소/재고 50 복원 후 결제는 `paid`, 환불은 `awaiting_transfer`, 요청은 `processing`으로 남았다. 송금 완료 증거를 기록한 뒤에만 27,000원 결제/환불/요청을 종결했고 별도 착불 6,000원도 환급 기록으로 마쳤다. 확인 응답을 서버 저장 뒤 끊어도 새로고침·동일 요청 조회로 복구해 중복 재고 복원이 없었다. 환불계좌 원문은 감사 후 `private, no-store` POST 응답에서만 잠시 표시하며 같은 열람 요청을 재사용하면 원문 없이 409로 거절한다.

합성 자료 퇴역 (`output/goods-transaction-browser-qa-20261014/cleanup-result.json`)과 후속 계좌 경로 퇴역 (`output/bank-account-route-qa-20261014/retirement-result.json`)은 금융·감사·이전 migration과 기존 전역 설정을 보존하면서 상품/IP 비공개, 검증 계정의 권한·세션 회수와 로그인 차단을 확인한다. 전용 런타임 정리 (`output/bank-transfer-refund-qa-20261014/runtime-retirement.json`)도 마쳤다. 실제 은행 송금·PG 승인·운송사 수납을 수행한 기록은 아니다.
