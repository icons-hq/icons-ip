migration 파일 경로는 [배포 매핑](../../../supabase/manifests/admin-rollout-migration-map.json)을 반영했다. 아래 과거 검증·적용 기록은 당시 원본 DRAFT 기준이며 이번 운영 배포의 성공을 뜻하지 않는다.

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-15 현재 작업 트리와 원본 조사 기준. 운영 배포는 하지 않았다. 이 문서의 **구현 완료**는 현재 ICONS 코드에 연결된 기능을 뜻하며, 원본 메뉴 전체의 동등성이나 실제 운영 거래 완료를 뜻하지 않는다. 항목별 로컬 검증과 브라우저 제약은 아래에 구분한다.

2026-10-15 확정한 물류 운영은 남양주·김포 담당자의 창고 양식 엑셀 다운로드와 각 WMS 입력이다. 운송장 발급·회수 접수·배송추적 API와 운송사 이벤트 기반 배송완료 자동 동기화는 사용자 결정으로 제외하며 공급자 API 확인 대기로 남기지 않는다. 기존 출력·운송장 회신 등록과 실제 창고 WMS의 파일 수용은 [출고지시·회신 런북](../../runbooks/warehouse-export.md)의 서로 다른 검증 단계다.

## 근거와 검증 범위

- 원본 판매 11개·정산 8개 메뉴의 표시 컨트롤·주요 읽기 상태를 확인했다. 로컬 `output/smartstore-reference-20261012/sales/manifest.json`에는 SHA-256이 결속된 **채택 증거 333파일**이 있다. 추가 취소 5개·반품 11개·VAT 11개·교환 12개·배송현황 9개·발주/발송 11개 도움말을 독립 본문으로 확인했다. 판매자 반품/교환 접수 조건별 양식과 교환 사유/수거정보 수정 새 창도 미제출 상태로 읽었다. 초기 VAT 겹침 후보 24파일은 채택에서 제외했다.
- 모든 실제 네이버 저장·삭제·발주·발송·환불·금전 이동·가입·약관 동의·외부 메시지 전송은 미실행이다. 원본 사진은 로컬 비공개 증거이며 고객·주문·주소·정산값을 문서/테스트에 복사하지 않았다.
- 판매 조회·구매제한·적립금·배송정보 템플릿은 소유한 격리 DB에서 합성 데이터와 권한/경합/멱등 계약을 검증했다. 테스트는 트랜잭션 종료 시 ROLLBACK했다. 운영 DB 적용은 하지 않았다.
- 배송정보 템플릿의 입력·서버·액션·SSR와 관련 가이드/nav/CSS 검사, 전체 타입 검사·ESLint를 통과했다. 2026-10-13 Chrome의 소유 격리 환경에서 저장·오래된 미리보기 충돌·입력/선택 보존·두 합성 상품 적용·UI/DB 재조회·390px 모바일을 검증했다. 구매제한 복수등록도 실제 입력/제외/등록/결과 링크/해제/재조회와 동일 요청 재생을 검증했으며, 복수등록의 결정론적 UUID 해제 검증 결함을 수정했다.
- 적립금은 차단 전에 격리 로컬 실제 화면에서 정책·잔액 충돌·중복 대상·정상 지급·필터·엑셀 읽기·모바일을 검증했고 DB 원장도 대조했다. 파일 업로드 UI는 브라우저 확장의 파일 URL 권한 부족으로 미검증이며 파일 파서는 단위 검증했다.
- 원본 발송 전 주소수정·합포장·구매확정 요청/연장 등 남은 입력 폼과 VAT 사업자 유형 도움말은 미확인이다. 업무 결과가 없는 빈 목록·미가입 상태를 기능 없음으로 판단하지 않는다.

## 다음 독립 구현 후보

판매방해 고객 복수등록과 선택 해제는 구현했다. 원본 근거·부분 결과·권한·멱등성과 실제 브라우저 검증과 제한은 [복수등록 문서](purchase-restriction-batches.md)에 기록했다.

**판매자 직접 취소·반품·교환 접수**는 주문 상세에서 요청만 생성하는 단위로 구현했다. [접수 계약과 검증](seller-claim-intake-reuse.md)에 고객 합의·문의 소유자·실제 담당자·별도 고객 요청 시각·전체 수거 계획·기한·중복 잠금을 기록했다. 고객 RPC의 무결제 즉시 종결·paid 자동 승인을 호출하지 않고 승인·회수·전액 환급/재출고는 기존 경로로 넘긴다. 격리 로컬 Chrome에서 두 유형의 접수·입력 보존·상세 재조회·중복 차단·390px 저장을 검증하고 DB 멱등 재생을 대조했다. 운영 배포와 실제 거래는 수행하지 않았다. 이후 취소도 전용 합성 pending/paid 주문으로 PC·390px 접수와 재조회를 완료했다. 취소는 수거 계획 없이 requested만 생성하며 주문·결제·환불·취소 실행 원장은 바꾸지 않는다. 유형 전환은 아래 계약으로 구현했다. 원본 남은 입력 폼 조사는 후속 범위다. 반품의 “한번에 하기”는 한 상품주문의 여러 단계 통합이며 복수 주문 일괄 기능으로 보지 않는다.

## 기존 거래 단위를 바꾸기 전 필요한 설계

### 1. 상품주문 조회와 처리의 분리

주문별 조회는 기존 중복 제거 계약을 유지한다. 별도의 [상품주문 조회 RPC](../../../supabase/migrations/20261020085244_admin_order_item_console.sql)는 `order_items.id`를 고유번호로 하여 한 품목당 한 행을 반환한다. `order_shipment_items`의 품목 기본키를 통해 그 품목의 출고지·송장만 연결하고, 품목 수·중복 제외 주문 수·총 수량을 각각 반환한다. 상품명·옵션·단가·직접 입력 옵션은 주문 당시 기록이다.

`/admin/sales/orders?view=items`는 상품주문번호·주문번호·상품/옵션·구매자·수취인·전화·이메일·해당 품목 송장을 검색한다. 기존 KST 날짜 기준·결제 증거·정렬·20/50/100개 URL 계약을 공유한다. 상세의 돌아가기 링크는 품목 보기·검색·페이지를 복원한다. 상품금액은 단가×수량이며 혜택·배송비 배분 후 실결제액으로 표시하지 않는다.

취소·반품은 주문 전체·전액 처리다. 품목 선택 발주확인도 중복을 제거한 주문번호만 기존 액션에 전달하고, 같은 주문의 미선택 품목도 포함됨을 실행 전에 안내한다. 진행 중인 클레임과 결제 대기 품목은 선택에서 제외한다.

전용 엑셀은 같은 검색의 전체 품목을 500개씩 읽되 10,000행 상한을 지킨다. 전체 투영의 fingerprint가 달라지면 건수·ID가 같아도 409로 중단한다. [계약과 실검증](order-item-console.md)에 SQL·권한·대량 조회·브라우저 다운로드와 주문 전체 실행 근거를 기록했다.

### 2. 주문 전체 취소·반품 유지 — 승인된 원본 차이

2026-10-12 사용자가 부분취소·부분반품을 허용하지 않고 주문 전체 및 전액으로만 처리하도록 확정했다. 원본의 상품주문 단위 취소·반품은 이번 이식의 필수 보완 항목이 아니다. [정책 경계 문서](partial-claims-contract.md)와 기존 [ADR-0017](../../adr/0017-order-claim-intake-and-origin-collections.md)을 따른다. 교환의 일부 수량 정책은 이번 발언에서 새로 추론하지 않고 기존 주문 단위를 유지한다.

API는 수량·품목·부분 금액 추가 입력을 거부하고 고객·관리자 안내를 유지한다. 전액 환급·전체 회수·공급 복원·혜택 처리와 기존 PG 증빙 finalizer를 바꾸지 않는다.

### 3. 판매자 접수·전환·배송지 변경

현 [클레임 접수 계약](../../adr/0017-order-claim-intake-and-origin-collections.md)은 발주확인 전 취소와 전체 배송완료 후 반품/교환을 구분한다. CS 문의에 청약철회 의사표시가 남는 것과 클레임/RPC가 생성되는 것은 별개다. 이 조사에서 배송 중 문의를 판매자가 직접 정식 접수하는 전용 어드민 액션은 확인하지 못했다.

판매자 접수는 고객 요청 시각·근거·대리 접수자·대상 품목을 남겨야 한다. 단순히 소유자 검사를 제거하거나 기존 신청 가능 상태를 넓히는 것으로 끝내지 않는다. 반품↔교환 전환은 기존 claim의 금융/회수 진행 상태, 이미 발송한 교환품, 수량 점유를 검사하고 원래 유형·전환 이력을 보존한다.

발송 전 배송지 변경은 주문 상세에서 구현·검증했다. 현재 배송비를 보존하는 주문 전체 변경만 허용하고 출고지시/발송 이력·열린 클레임·지역 불가·배송비 차이를 차단한다. 오래된 출고지시 파일의 전달 확인은 버전 충돌로 거절한다. [배송지 계약과 실검증](order-address-changes.md)에 비공개 이력·두 탭 충돌·PC/390px 저장·10개 실제 경합을 기록했다. 네이버 공식 도움말의 발송 전/일부 발송 후 전체 변경 불가 조건을 확인했으며 원본 수정 팝업 자체는 여전히 미확인이다.

원본의 발주해제는 발송 의무기한 경과 후 자동 전이되는 Npay 계약이다([공식 도움말 3565](https://help.sell.smartstore.naver.com/faq/content.help?faqId=3565)). 목록의 발주확인해제는 조회 상태이며 수동 해제 버튼으로 확인한 것이 아니다. 따라서 초기 대조표의 수동 발주확인 해제 일반 기능 항목은 정정·제외했다. 2026-10-13 공식 본문과 원본 상·하단 처리 버튼을 다시 읽어 같은 결론을 확인했다. [개별 보류·해제와 선택 범위](claim-hold-contract.md)에 함께 기록했다.

### 4. 구매확정과 PG 정산

[자동 거래확정 함수](../../../supabase/migrations/20260908040010_order_shipment_transitions.sql)의 `settle_delivered_orders`는 모든 배송건의 배송완료와 8일 경과, 열린 클레임/취소 부재를 확인한다. 구매자 구매확정을 도입하면 누가 언제 어떤 배송 대상에 대해 확정했는지와 자동 확정의 근거를 따로 저장하고, 기존 공급일·하자 요청 기한을 덮어쓰지 않아야 한다.

정산은 다음 연결 중 토스 원본 기록·원결제/환불 연결·수수료·원본 지급일/지급액까지 독립 읽기 원장으로 구현했다. 나머지는 공급자 원본과 계정 계약을 확보한 뒤 연결한다.

`provider 원본 기록 → 원결제/환불 연결 → 수수료·조정·보류 → 지급 묶음과 예정/완료일 → 실제 입금 대사`

현재 모델은 원본 source/외부 ID/가져온 시각·해시, 수집 작업·페이지·거래별 정산·수수료와 고정된 대조 결과다. 두 차례 수집의 거래 집합이 일치해야 완료하며 재수집 결과를 중복 합산하지 않는다. 외부 자료가 빠진 기간은 0원 대신 미수집으로 표시하고, PG 원본과 주문 금액이 다르면 불일치로 남긴다. 지급 묶음·조정/보류·은행 실입금 근거는 별도 계약 확인 대상이다.

기존 거래확정 엑셀의 정수 금액 배분·스냅샷·감사 구조는 재사용할 수 있지만, 그 안의 결제 승인 시각이나 주문 `done_at`을 PG 정산일로 간주하지 않는다. 세무 자료의 기간 귀속·과세 구분·증빙 계약은 정산 합계를 그대로 재명명하지 말고 별도로 검증한다.


### 5. 고객 요청 철회

[철회 계약](claim-withdrawal.md)은 판매자 거절과 구분한 `withdrawn` 단계, 고객/관리자 진입점, 실제 물류·금전 차단, 동일 요청 고정·재조회와 별도 통계를 포함한다. 원본 반품거부(철회) 입력창은 조회했고 실제 원본 변경은 수행하지 않았다. 수거 후 실물 반환·금전 재정산은 별도 후속 범위다.

### 6. 반품·교환 전환

[전환 계약](claim-type-conversion.md)에 원본 사전동의·재출고 전 조건, 주문 전체·금액 보존, 접수/입고/SLA·보류 유지, 무통장 계좌·파기 경합과 고객 이력을 확정했다. OWN/FRESH SQL·권한, 17개 실제 잠금 경합, PC 반품→교환과 390px 교환→반품 실제 저장·고객 재조회가 통과했다. 네이버 원본 사진 삭제·별도 Npay 배송비 취소 규칙은 복제하지 않았다.
