# 개별 클레임 보류·해제와 원본 선택 범위

migration 파일 경로는 [배포 매핑](../../../supabase/manifests/admin-rollout-migration-map.json)을 반영했다. 아래 과거 검증·적용 기록은 당시 원본 DRAFT 기준이며 이번 운영 배포의 성공을 뜻하지 않는다.

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-13 로그인된 원본, 공식 도움말과 현재 코드를 대조했다. 실제 네이버의 저장·해제·환불은 실행하지 않았다. 복수 주문 보류 기능은 새로 만들지 않는다.

## 원본에서 확인한 단위

| 관측 | 확인한 사실 | ICONS 대응 |

원본 보류 설정의 초기 폼과 기타 사유 선택을 읽었다. 실제 보류 해제 결과, 비용 청구/차감 결과와 통합 환불 결과는 미실행이다. 취소·교환의 복수 주문 선택 범위도 이 조사로 확정하지 않았다. 미확인 항목을 곧바로 일반 기능 미구현으로 분류하지 않는다.

원본 증거는 `output/smartstore-reference-20261013/claim-hold-reference/`와 `confirmation-reversal/`에 보관한다. 목록 radio의 DOM 속성과 입력창의 텍스트·스크린샷을 함께 저장했으며 주문·고객 원문을 테스트 fixture나 공개 문서에 옮기지 않았다. 통합 처리 PNG는 창 상단이며, 하단 완료/취소 버튼을 포함한 전체 입력 계약은 함께 저장한 DOM 텍스트로 확인했다.

## 현재 보류·해제 계약

운영자는 요청 상세의 보류 설정 또는 보류 해제를 열고 최신 유형·상태를 확인한다. 보류 사유는 기존과 같이 10~200자이며 구매자 알림에 전달된다. 해제하면 저장된 보류 전 단계로 돌아가며, 환불·재출고를 자동 실행하지 않는다. 기존 처리중·결제확인필요 건의 보류와 원래 단계 복귀도 유지한다.

입력할 때 받은 계정, 요청번호, 요청 유형과 `claim_revision`을 저장 요청에 결속한다. 다른 운영 처리·고객 철회·유형 전환이 먼저 진행되면 충돌로 거절한다. 최신 상태를 다시 읽어 확인해야 하며, 유형 또는 계정이 달라졌으면 이전 입력과 확인을 초기화한다. 같은 유형의 상태 변화에서는 사유를 보존하되 확인을 다시 받는다.

한 실행의 UUID와 최초 본문을 고정한다. 응답이 사라지거나 결과가 일치하지 않으면 새 실행을 만들지 않고 같은 결과를 읽거나 같은 내용으로 재시도한다. 완료 영수증은 실행자·요청·유형·버전·보류/해제·사유를 검증한다. 다른 계정은 영수증을 읽을 수 없다.

[전용 migration](../../../supabase/migrations/20261020085300_order_claim_hold_operations.sql)은 계정/구매자 잠금 → 실행 잠금 → 주문 → 정렬된 배송 건 → 요청 순서로 검사한다. 실행 결과 조회도 같은 실행 잠금을 기다리므로 처리 중인 결과를 미저장으로 오인하지 않는다.

기존 `admin_decide_order_claim`의 본체는 내용 변경 없이 private으로 이동하고 직접 실행 권한을 봉인했다. 공개 3인자 진입점의 검토·승인·거부는 기존 본체로 위임한다. 무버전 보류·해제는 거절하며 전용 진입점만 기존 보류 전 단계, 알림, 감사 구현을 호출한다. 승인·환급·결제사 정합화·재고 복원 코드는 바꾸지 않았다.

## 검증

- DRAFT를 격리 트랜잭션에서 검증했다. 권한·다른 계정 재조회·본문 충돌·동일 요청 재생·유형/버전 충돌·종결 요청 차단과 주문·배송·금전·재고 불변을 확인했다.
- 소유 DB를 복제한 임시 DB에서 실제 잠금 경합 13개를 통과했다. 동일 실행, 다른 실행자, 본문 변경, 결과 읽기, 유형 전환/철회/검토와 보류의 양방향, 유형 전환과 해제의 양방향, 권한 회수를 포함한다.
- FRESH의 공식 legacy fixture wrapper에서 기존 전체 클레임 SQL 회귀를 통과했다. 새 철회 단계 추가로 낡은 9개 집계 기대값을 10개와 철회 단계 존재 검사로 고쳤다. 테스트 후 fixture lease·trigger를 제거했다.
- 관련 Vitest 85개, 전체 TypeScript, 수정 파일 ESLint를 통과했다. 저장 뒤 과거 상태 문구를 함께 표시하던 부분을 정리한 후 영향받은 UI·가이드 41개를 다시 통과했다.
- migration을 OWN/FRESH에 한 번씩 적용하고 저장된 전체 SQL과 파일의 SHA-256 `a48a0c94e97353ed53ee382a87a709c1092e85261a95680a563df1f89f8535e6`이 모두 일치함을 확인했다. 적용된 FRESH 기능 SQL과 OWN 권한 계약 검사도 통과했다.
- 실제 Chrome PC에서 합성 반품 보류·해제, 별도 탭에서 반품→교환 전환 후 오래된 보류 저장의 충돌, 최신 유형 재조회와 이전 사유/확인 체크 초기화를 검증했다. 전환된 두 합성 요청에는 보류 실행 기록이 없다. 초기 시도는 개발 HMR로 폼이 닫혀 폐기하고 파일 동기화가 없는 구간에 새 합성 요청으로 다시 확인했다.
- 390×844 화면에서 가로 넘침 없이 교환 보류·해제 저장과 결과를 확인했다. 모바일 크기에서는 키보드로 입력·확인·실행했으며 실기기 터치 검증으로 주장하지 않는다. 두 유형의 보류·해제 영수증은 총 4개이고, 전후 주문 상태·금액·배송 정보·재고가 동일했다.
- 응답 소실 후 같은 본문 재시도·결과 불일치·다른 계정·연속 클릭은 단위 테스트와 DB 경합으로 검증했다. 브라우저 네트워크 응답 소실을 인위적으로 만들지는 않았다. 소유 탭을 닫고 모바일 크기 설정도 해제했다.

최종 UI와 DB 증거는 `output/smartstore-reference-20261013/claim-hold/manifest.json`에 연결한다. 첫 보류 캡처는 성공 후 상태 문구를 정리하기 전 진단 자료로만 보존하고 최종 시각 증거에서 제외했다.

운영 DB·외부 PG·실제 네이버 거래는 변경하지 않았다.
