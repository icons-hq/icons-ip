# 상품 사진 선명도·블러·비네팅 — 계산 계약과 검증

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-14. [기존 사진 편집](product-photo-editor-implementation-qa.md)에 선명도·중앙 원형 블러·중앙 선형 블러·비네팅을 추가한다. 아래 값과 계산은 ICONS 자체 계약이다. 원본 보정 캡처 (`output/smartstore-reference-20261012/product-photo-tool-adjust.jpg`)에서 확인한 도구 이름·기본값0을 넘어서 네이버의 수치 범위·서버 계산·비영점 효과와 같다고 주장하지 않는다.

## 값과 합성 순서

| 값 | 허용 범위 | 의미 |
| --- | --- | --- |
| `sharpness` | 정수 -100~100 | 음수는 부드럽게, 양수는 윤곽 강화 |
| `circularBlur` | 정수 0~100 | 원본 중앙의 원 안은 선명하게 두고 바깥을 흐리게 |
| `linearBlur` | 정수 0~100 | 원본 중앙의 수평 띠 안은 선명하게 두고 바깥을 흐리게 |
| `vignette` | 정수 0~100 | 중앙을 유지하며 가장자리를 부드럽게 어둡게 |

모든 값0은 정확한 무효과다. 재설정·원본 비교·무변경 완료 판정에 네 값을 포함한다. ROI 이동·반경·각도 입력은 추가하지 않는다. 원형·선형 블러는 움직임 방향을 늘이는 motion blur가 아니다.

처리 순서는 **기존 밝기·대비·채도·색온도 → 선명도 → 원형·선형 블러 공동 합성 → 비네팅 → 모자이크 → 텍스트 → 전체 회전·반전·자르기 → 미리보기만 축소**다. 매 요청은 동일한 원본 해상도에서 다시 계산하며 이전 미리보기 픽셀을 입력으로 재사용하지 않는다. 텍스트 색은 사진 보정에 영향받지 않는다.

좌표는 EXIF 표시 방향을 반영한 원본 기준이다. 중심은 `(W/2, H/2)`, 픽셀 좌표는 중심점 `(x+0.5, y+0.5)`를 쓴다. 효과 영역은 사진과 함께 회전·반전되며 자르기로 자동 재중심화하지 않는다. 따라서90도 회전하면 선형 블러의 수평 띠도 함께 회전한다.

## 고정 계산

입력 픽셀의 색을 `P`, alpha를 `A`라 한다. 공간 평균은 `B = Σ(K × P × A) / Σ(K × A)`이며 분모가0이면 원래 값을 유지한다. 중간 합을 나누거나 반올림하지 않고 최종 RGB에서만 `Math.round` 후0~255로 제한한다. 출력 alpha는 항상 입력 alpha다. alpha0인 픽셀의 숨은 RGB도 변경하지 않으며 평균에 섞지 않는다. 투명 윤곽을 넓히는 RGBA blur와 구분한다.

`smoothstep(a,b,d)`는 `t=clamp((d-a)/(b-a),0,1)`, `t²×(3-2t)`다.

- **선명도:** 양축 커널 `[1,4,6,4,1]`의5×5 alpha 가중 평균 `B`를 구한다. `s=sharpness/100`, 출력은 `P+s×(P-B)`다. -100은 해당 평균, 0은 원본, +100은 차이를 한 번 더 더한 값이다. 음수·초과값은 Uint32에 저장하지 않고 최종 RGB에서 제한한다.
- **공통 블러:** 반경은 `R=min(32,max(1,round(min(W,H)/50)))`다. 양축의 균일한 `(2R+1)` 박스 커널을 사용한다. 사진 바깥 좌표는 가장자리 픽셀로 clamp하며 반복된 가장자리의 가중치도 보존한다.
- **원형 마스크:** `dc=hypot(x+0.5-W/2, y+0.5-H/2)/(min(W,H)/2)`, `mc=(circularBlur/100)×smoothstep(0.45,0.9,dc)`다. 거리 계산은 원본 픽셀 기준이므로 정사각형이 아닌 사진에서도 원형이다.
- **선형 마스크:** `dl=abs(y+0.5-H/2)/(H/2)`, `ml=(linearBlur/100)×smoothstep(0.25,0.75,dl)`다. 중앙25% 높이의 수평 띠는 유지되며 바깥으로 부드럽게 증가한다.
- **두 블러 합성:** 같은 `B`에 `m=1-(1-mc)×(1-ml)`, 출력은 `P+m×(B-P)`다. 두 마스크를 순서대로 다시 흐리지 않는다.
- **비네팅:** `dv=hypot((x+0.5-W/2)/(W/2),(y+0.5-H/2)/(H/2))/sqrt(2)`, 출력은 `P×(1-(vignette/100)×smoothstep(0.25,1,dv))`다. 정규 타원 거리로 사진의 비율을 반영한다.

## 메모리·취소 경계

[순환 버퍼 구현](../../../lib/admin/photo-editor-effects.ts)은 한 행 전체의 수평 합을 보관한 뒤 그 행의 출력 픽셀을 쓴다. 미래 행도 미리 읽으므로 제자리 출력이 다음 계산의 원본을 오염시키지 않는다. 선명도와 블러가 같은 scratch를 재사용하며 전체4MP RGB/Float32 복제를 추가하지 않는다.

박스 합의 최대치는 `65²×255²=274,730,625`로 UInt32 범위 안이다. 최대 가로4096px·반경32의 행 버퍼와 열 누적값은 `(65×4096×4 + 4096×4)×4 = 4,325,376byte = 4.125MiB` 이하이며 마스크는 픽셀별로 계산한다. 이는 **추가 계산용 typed array의 상한**이다. 기존 bitmap·ImageData·canvas·인코더·GPU 메모리를 포함한 브라우저 총메모리 한도가 아니다.

커널은 할당 전, 초기 행 준비 중, 가로·세로 누적과 출력 중에 작은 작업 단위로 yield한다. 세션은 각 yield에서 취소를 검사하고 약8ms의 작업 시간이 지나면 이벤트 루프에 제어를 돌려준다. 네이티브 decode·getImageData·putImageData·encode 자체의 중간 취소를 보장하지는 않는다. 취소·세션 교체 후 늦은 인코딩 결과를 버리고 순차 큐·캔버스 해제를 유지한다.

## 검증 범위

기존 세 도구의 실제 픽셀·업로드·공유 원본 보존 검증은 [기존 문서](product-photo-editor-implementation-qa.md)의 별도 결과다. 네 도구의 구현·독립2D oracle·실제 브라우저 검증 근거는 새 출력 폴더 (`output/product-photo-effects-qa-20261014`)에 분리한다.

필수 확인은 독립적인2D 가중합과 순환 버퍼의 픽셀 대조, 1×1·1×N·N×1·크기보다 큰 반경·경계 clamp, alpha0 숨은 RGB를 바꿔도 가시 결과가 같음, alpha 전수 보존, 모든0의 정확한 무효과와 scratch 미할당, 초기 준비/계산/인코딩 취소, 4MP 처리 시간·프레임 간격, 원본 해상도 결과와 축소 미리보기의 일치다. 실제 Canvas 결과·JPEG 재압축·서로 다른 브라우저의 픽셀 차이는 순수 계산 단위 검사와 구분한다.

## 실제 Chrome 검증 결과

실제 UI manifest (`output/product-photo-effects-qa-20261014/ui-manifest.json`)에 구현·검수 소스 SHA와 캡처, 원본/출력 파일, DB 재조회를 결속했다. 기존8파일232테스트와 scoped lint·타입검사가 통과했다. 이 중 독립2D·경계·취소·메모리66테스트는 별도 원본 버퍼 계산과 비교하며, 최대 추가 scratch 4,325,376바이트도 실제 typed array 할당 계측으로 확인했다.

- 원본400×400에 선명도65·원형70·선형45·비네팅50을 UI로 입력했다. 생산 함수를 import하지 않는 독립 full2D 계산과 실제 브라우저 PNG의 **640,000채널 전부가 일치**했다. 이 실제 입력은 불투명 사진이다.
- 재설정 후 PNG는 무효과 시작 PNG와 바이트까지 같았다. 선명도 슬라이더에서 왼쪽 키는0→-1로 바뀌었고, 무변경 완료는 업로드·상품 변경을 만들지 않았다. 원본 비교 중에는 원본 사진을 표시하고 완료를 막았다.
- 기존 텍스트·모자이크가 포함된360×340사진에 새 효과를 적용·업로드·저장·재열기했다. 미리보기와 저장 PNG의489,600채널은 같았다. 상품 저장 전에는 DB 전체 행이 같고 저장 후에는 대상의 `image_path`·`updated_at`만 바뀌었다. 공유 상품과 보관함 원본은 그대로였다.
- 390px 화면에서 문서390px, 모달 client/scroll358/358px로 가로 넘침이 없고 완료·취소 버튼을 확인했다.
- 2000×2000 PNG에 선명도100·원형100·선형100·비네팅99를 적용했다. 입력부터 미리보기 완료까지 **986.3ms**, 측정된58프레임의 최대 간격18.6ms였다. 단일 데스크톱 Chrome의 측정값이며 다른 기기의 성능 보장은 아니다. 최종 파일을 다시 연1280px 미리보기는 이전 미리보기와 바이트까지 같았다.
- 400만 alpha값은 전부 유지됐다. 입력은 투명40,000·부분투명120,000·불투명3,840,000픽셀이다. 이 검사는 RGB 독립 oracle과 구분한다. CPU8배 감속에서 미리보기 계산 중 및 완료 파일 생성 중 취소 후 추가 업로드 claim이 없고 DB 재조회도 정확히 같았다. CPU는1로 복원했다.

합성 상품2/IP1과 두 단계 검수에서 만든 객체7개만 제거하고 원본 사진 행·바이트를 다시 대조했다. 미저장 입력과 계측 코드·viewport·CPU 설정은 정리했고 정상 검수 탭은 닫았다. 이전 단계의 응답 없는 별도 검수 탭은 남은 도구 제약으로 기록한다. Safari/iOS와 실제 저메모리 기기, 브라우저 전체 메모리 피크는 실행하지 않았다. 원본 서비스의 내부 알고리즘과 수치 범위 일치는 주장하지 않는다.

구현 회귀는8파일232테스트를 통과했다. 별도 작성한2D 직접합 oracle과 ring 결과를 대조한66개 검사에 1픽셀·좁은 이미지·반경32·alpha1/17/64/128/254/255·숨은 RGB·합성 순서·중앙 보호·90도 관계·정수 범위·초기 준비와 중도 종료를 포함한다. typed array 생성자 계측으로0값의 scratch 미할당, 복합 선명도·블러의 버퍼2개 재사용, 최대4,325,376byte를 확인했다. 관련 ESLint·타입검사도 통과했다. 구현 소스 SHA와 검사 기록 (`output/product-photo-effects-qa-20261014/implementation-verification.json`)은 실제 브라우저 QA와 분리하며, 실제 Canvas·저장·4MP 성능은 위 실제 Chrome 결과와 UI manifest를 따른다.
