# 매니저 권한·초대·승계 대응 근거

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

확인일: 2026-10-13 KST. 로그인된 원본의 현재 계정은 **계정 주매니저**다. 원본 메뉴·권한변경·초대 입력과 공식 도움말을 읽었다. 역할 적용, 초대 전송·수락·삭제, 승계는 실행하지 않았다. 구현 전 계약 자료이며 ICONS의 권한 변경이나 운영 배포가 완료됐다는 뜻이 아니다.

증거는 `output/smartstore-reference-20261012/manager-reference/manifest.json`의 01–10이다. 기존 `store/169-manager-role-options.jpg`, 263–265도 같은 선택 구조를 보여준다. 캡처의 계정 식별·연락처는 이 문서에 옮기지 않는다.

## 변경·회수·통합 승계

| 실행자/대상 | 확인한 동작 |
| --- | --- |
| 통합 → 주/부 | 역할 변경과 권한 회수 가능. |
| 주 → 다른 주 | 역할 변경 가능, 같은 주매니저인 상태의 직접 회수는 불가. 공식 문서는 부매니저로 바꾼 뒤 회수하는 절차를 안내한다. |
| 주 → 부 | 역할 변경과 회수 가능. |
| 부/인플루언서/대행사/물류 → 매니저 | 매니저 관리 접근과 변경·회수 불가. |
| 본인/통합 매니저 행 | 현재 주매니저 로그인 화면에서 일반 역할변경 버튼이 없다. 다른 주매니저 행에는 변경만 있고 삭제는 없다. |

위 변경·회수 규칙은 [FAQ4032](https://help.sell.smartstore.naver.com/faq/content.help?faqId=4032)와 원본 증거01·10으로 대조했다. 주매니저가 다른 주매니저의 권한변경 입력을 열면 일반 5역할 모두 보인다. 인플루언서·대행사·물류를 **대상**으로 한 회수 동작과 자기 역할변경의 서버 결과는 현재 계정의 실제 행/저장으로 검증하지 않았다.

통합 매니저는 **사업자번호당1명**이며 일반 초대 대상으로 선택하지 않는다. 현 통합 매니저만 현재 스토어의 주매니저를 승계 대상으로 고른다. 대상이 다른 스토어에서 이미 통합 매니저이면 승계할 수 없다. 승계는 이전 통합 매니저가 맡은 모든 스토어의 통합 권한에 영향을 주며, 각 스토어의 기존 담당자 지정은 보존된다. 통합 매니저가 없으면 고객센터가 별도로 확인한다. [FAQ12468](https://help.sell.smartstore.naver.com/faq/content.help?faqId=12468), 증거09.

현재 계정은 통합 역할이 아니므로 승계 탭이 보이지 않는다. 실제 승계 후 이전 계정의 상세 역할·승계 확인창 제출·담당업무 자동 변경의 최종 상태는 미실행이다. ICONS의 현 단일 스토어에 이 구조를 옮길 때는 기존 `admin` 여러 명 중 누가 대표인지 코드가 임의로 선택할 수 없다.

## 담당업무·담당자·수신동의는 별도

[2026-08-07 업무별 담당자 공지](https://sell.smartstore.naver.com/#/center-notice/detail/200001142)는 담당업무를 직무별 안내 수신 분류로 정의한다. **대표**는 통합 매니저에 자동 지정되어 선택/변경할 수 없다. 직접 고르는8종은 영업·마케팅·CS·디자인콘텐츠·물류·회계·총괄·기타다. 공지 본문의 ‘정산회계’가 현 선택 UI에서는 ‘회계’로 표시된다. 총괄은 모든 업무 안내를 받고, 담당 직무가 비어 있으면 대표/총괄로 전달한다. 외부 대행사도 자신이 맡은 직무를 별도로 선택한다. 증거03·05.

직무를 바꿔도 메뉴 권한이 생기지 않는다. 스토어 ‘담당자’ 지정은 판매자 정보에서, 본인의 연락처·이메일·광고 수신동의는 본인 회원정보에서 수정한다. 정책·계약 중요 공지는 통합 매니저에게 계속 간다. 담당업무를 골랐다는 이유로 광고 수신동의까지 켜면 원본과 다른 동작이다. [업무별 담당자 공지](https://sell.smartstore.naver.com/#/center-notice/detail/200001142), 원본 매니저 목록 안내.

## ICONS 구현 경계와 대응

현재 `lib/admin/roles.ts`는 `user/staff/admin`이고, `guard.server.ts`·`action-access.server.ts`는 staff 여부와 `adminOnly`만 구분한다. `navigation.ts`도 같은 방식이다. 원본 하위4역할을 모두 `staff`로 바꾸면 판매·환불·통계 등의 권한이 과도해진다. 다음은 현재 코드와 원본을 대조한 **구현 방향**이며 네이버 내부 구현에 대한 설명이 아니다.

| ICONS 표면/계약 | 필요한 구분 |
| --- | --- |
| 관리자 셸·검색·즐겨찾기·홈 요약 | 역할별 허용 메뉴와 같은 능력 목록 사용. 제한 역할의 홈·알림·검색도 주문·금전 집계를 간접 노출하지 않아야 한다. |
| `/admin/sales/orders`·`purchase-restrictions` | 인플루언서의 예외 범위. 주문 검색 RPC를 열더라도 해당 화면의 환불/발송 등 다른 업무 호출이 따라 열리지 않도록 분리. |
| `/admin/sales/settled` | 거래확정 내역이며 원본 ‘항목별 정산 내역’과 다른 도메인. 인플루언서 정산 예외를 이 경로에 임의 대응하지 않음. |
| `/admin/catalog/announcements` | 물류출고관리의 상품공지 예외. 상품 전체 쓰기를 허용하는 근거가 아님. |
| `/admin/settings/origins`·발송/송장 | 현재 출고지 주소·배송요금과 실제 주문 발송이다. N판매자배송의 마감시각/수용량/휴무 계약이 없으므로 물류 역할에 통째로 열지 않음. |
| `/admin/settings/store` | 사업자·계좌·CS·브랜드/SNS·메뉴·문의안내가 한 화면에 섞인다. 원본의 스토어관리 허용과 판매자정보 부분 허용을 섹션·읽기/쓰기 RPC 단위로 분리해야 함. |
| `/admin/display/campaigns` | 현 메뉴 배치는 혜택/마케팅이지만 본문/상품을 가진 캠페인은 프로모션 성격도 있다. 쿠폰·지급·공지발송이 같은 허용 묶음으로 따라가지 않도록 실제 계약 기준으로 배치. |
| 문의·리뷰의 주문 링크/회원관리 | 문의 응대는 허용해도 별도 판매/회원 민감 작업까지 허용했다는 근거는 없음. 연결 endpoint/반환 데이터도 동일 경계 적용. |
| 상품속성 스키마·ERP·IP/카드/게임·검표 | 네이버 표에 정확한 대응이 없는 ICONS 추가 도메인. 기존 `adminOnly`/별도 운영 권한을 일괄 해제하지 않고 명시 능력으로 유지. |

기존 DB `is_staff()`·`is_admin()`에 기대는 RPC와 직접 테이블 RLS도 같은 능력 경계를 적용해야 한다. UI 숨김만으로 완료 처리하지 않는다. root가 추출한 DB 함수 목록은 `/tmp/icons-operator-permission-inventory.json`이며, 함수별 허용 업무·위임 대상·잠금/현재역할 재검증을 대조할 입력이다. 공개 고객 브라우징·기존 거래 무결성·금전 확정 경로는 매니저 역할 추가와 별개로 유지한다.

초대의 생성·발송 결과·수락·만료·회수와 통합 승계를 별도 상태로 검증한다. 같은 링크의 동시 수락, 회수와 쓰기의 경합, 역할 변경 뒤 기존 세션의 즉시 거절, 통합 매니저1명 불변식, 동료 주매니저의 직접 회수 차단이 구현 시 핵심 회귀다. 네이버의 실제 전송/수락/다른 역할 로그인 결과는 이번 읽기 조사로 확인하지 않았다.
