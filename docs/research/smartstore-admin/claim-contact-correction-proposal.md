## 1. 1차 범위와 남는 범위

같은 우편번호·기본주소 안에서 **이름, 전화번호, 상세주소**를 고객과 확인해 정정한다. 구매자가 물건을 보내는 회수지와 교환품을 받는 재배송지는 별도 대상이다. 주문 전체 취소·반품, 출고지별 실제 회수, 동일 상품 옵션의 주문 수량 전체 재출고 계약은 유지한다.

| 대상 | 이번 제안 | 미지원 |
| --- | --- | --- |
| 반품·교환 구매자 회수지 | 착수 전 이름·전화·상세주소 정정 | 우편번호·기본주소·지역 변경, 수거 진행 후 변경 |
| 교환 구매자 재배송지 | 재출고 전 이름·전화·상세주소 정정과 최종 재출고 주소 확인 | 우편번호·기본주소·지역 변경, 재출고 후 연락처 변경 |
| 수거 계획·실제 물류 | 기존 계획과 입고 증거 읽기 | 수거방식·택배사·송장 수정, 운송사 접수·취소·자동 추적 |
| 비용·수량 | 기존 주문 금액·배송비·운영 비용·수량 보존 | 비용 재계산·추가 청구·환불 차감·부분교환·새 물류 상태 |

우편번호·기본주소는 읽기 전용으로 보여 주고 정정 RPC의 변경 필드에도 넣지 않는다. 서버는 현재 주소에서 이 두 값을 유지하고 허용된 세 필드만 결합한다. 주소 검색이나 기본주소 직접 입력은 제공하지 않는다. 동일 지역의 정정이라는 이유로 실제 운송사의 비용·인계 결과를 보증하지 않는다.

원본 스마트스토어의 전체 주소 변경 기능을 그대로 구현하는 작업이 아니다. 전체 주소·지역 변경과 실제 물류 연동은 [판매 후속 범위](sales-remaining-scope.md)의 미지원 항목으로 남긴다.

## 3. 기존 주소와 신규 연락처 계획의 구분

| 현재 저장 위치 | 의미와 유지할 계약 |
| --- | --- |
| `orders.address` | 원주문 배송지다. [기존 주문 주소 변경](order-address-changes.md)은 발송·활성 클레임 이후 차단된다. 이번 정정에서 갱신하지 않는다. |
| `private.seller_order_claim_intakes.payload.collectionAddress` | 판매자 대리 접수 당시 구매자 회수지다. 같은 행의 `payload.collections`와 `collection_snapshot`은 당시 고객 합의와 출고지별 수거 계획이다. 원본 접수 증거를 새 주소로 덮어쓰지 않는다. |
| `order_claim_collections.return_address_snapshot` | 구매자 주소가 아니라 **출고 창고의 반송 목적지**다. 출고지·품목/수량 snapshot과 실제 입고 시각·확인자·근거를 유지한다. |
| 교환 재배송지 | 최초 구현에는 별도 최종 주소 snapshot이 없었다. 현재 [연락처 서비스](../../../lib/claim-contact/service.server.ts)와 [신규 DB 계약](../../../supabase/migrations/20261020085406_order_claim_contact_corrections.sql)은 별도 암호화 계획·최종 목적지 snapshot을 실제 재출고와 결속한다. |

정정 후 화면은 `원주문 배송지`, `접수 당시 회수지`, `현재 회수지`, `현재 교환 재배송지`, `실제 재출고에 확인한 주소`를 구분한다. 기존 [대리 접수 근거](../../../components/admin/screens/SellerClaimIntakeEvidence.tsx)의 주소를 현재 주소처럼 바꾸지 않는다.

회수지 초기값은 유효한 대리 접수 주소가 있으면 그것을 사용한다. 고객 직접 접수처럼 별도 회수지가 없으면 원주문 주소를 **참고값**으로 표시하고 고객과 현재 주소를 확인해야 한다. 교환 재배송지 초기값도 원주문 주소 참고값이며, 이전 교환의 주소를 자동으로 새 클레임에 이어받지 않는다. 유효한 이름·연락처·우편번호·기본주소를 읽을 수 없으면 정정을 열지 않고 기존 상담 경로로 넘긴다. 없는 주소를 빈 기본값으로 저장하지 않는다.

## 4. 변경 가능 단계와 차단 조건

기존 `on_hold`는 진행 단계 위에 놓이는 보류다. `held_from`이 없거나 알 수 없으면 정정 가능 단계로 추정하지 않는다. 아래 조건은 화면 표시와 실제 writer가 같은 판정을 사용하고, 잠금 획득 후 다시 검사한다.

| 대상 | 허용 단계 | 추가 차단 |
| --- | --- | --- |
| 구매자 회수지 | `return` 또는 `exchange`의 `requested`, `in_review`, 이 두 단계에서 보류된 건 | `collecting_at` 또는 실제 입고 이력 존재, 대리 접수 계획의 `customer_sent`·`seller_arranged`, 기존 수거 택배사/송장, 출고지별 수거 계획을 안전하게 해석할 수 없는 경우 |
| 교환 재배송지 | `exchange`의 `requested`, `in_review`, `collecting`, `collected`, 이 단계에서 보류된 건 | `reshipped_at`, 재출고 택배사/송장, 재출고 품목, 교환품 배송완료 증거 중 하나라도 존재 |
| 공통 | 위 조건을 모두 만족 | 주문 취소, `processing`·`needs_review`·완료·거절·철회, 취소 실행 원장 또는 환불 원장 존재, 현재 `sales.manage` 상실, 주소 정보 파기·삭제 진행 |

회수지는 어느 출고지든 실제 입고가 있으면 전체 주소 정정을 막는다. 공통 구매자 회수지를 일부 출고지에만 소급 적용하지 않는다. 재배송지 정정은 이미 존재하는 입고 시각·증거를 전혀 수정하지 않는다.

현재 DB에는 운송사 인계 여부를 독립적으로 확인하는 상태가 없다. 따라서 `collecting`인 회수 건을 송장이 비었다는 이유로 다시 열지 않는다. 재배송지도 외부 출고지시를 이미 전달하거나 실제 발송한 사실이 있으면 정정 대상으로 삼지 않는다. 운영자에게 이 사실과 고객 합의를 확인받되, 그 확인을 운송사 API가 보증한 상태로 표시하지 않는다. 실제 재출고 v2와의 결속 범위는 7절에 한정한다.

## 5. 입력·현재 주소 확인·별도 계획

- 대상은 `collection`과 `reshipment` 중 하나다. 한 요청에서 두 주소를 함께 바꾸지 않는다.
- 화면은 현재 주소와 정정할 세 필드, 원래 접수일, 현재 단계, 기존 운영 비용 기록을 보여 준다. 고객이 현재 주소와 변경 내용을 확인했다는 체크와 2~500자의 내부 합의 근거를 받는다. 내부 근거에 계좌·주민번호·불필요한 전화/주소를 반복 입력하지 않도록 안내한다.
- 이름 1~50자, 숫자로 정규화한 전화 8~15자리, 상세주소 0~200자와 제어문자 차단은 현재 주소 계약에 맞춘다. 서버가 유니코드 코드포인트 길이와 잘못된 UTF-16·제어문자를 검증한다. SQL은 초기 평문 참고주소를 같은 규칙으로 검사하며, 신규 암호문은 평문 길이를 추측하지 않고 envelope·버전·권한·CAS를 검사한다. 메모·추가 전화·수거방법 등의 미지원 키는 무시하지 않고 거절한다.
- 정정하려는 현재 주소의 digest와 `claim_revision`, 기대한 클레임 유형을 context에서 받는다. digest는 주소에 결속된 개인정보 취급 자료이며 일반 감사·알림·URL·로그에 내보내지 않는다. 고정된 필드 순서·정규화 규칙으로 서버에서 계산하고 클라이언트 계산을 신뢰하지 않는다.
- 우편번호와 기본주소는 서버가 읽은 현재 값 그대로 보존한다. 자유로운 주소 재해석·지역 정규화로 다른 장소를 같은 주소라고 허용하지 않는다. 초기 참고값을 고객이 확인한 사실과 실제 세 필드 변경은 구분한다.
- 새로운 private 현재 계획은 클레임과 대상별 주소를 보관한다. 별도 private operation 이력에 최초 기준·변경 전/후·담당자·시각·합의 근거를 보존한다. 최초 seller intake, 주문 주소와 창고 입고 snapshot은 수정하지 않는다.
- 정정은 원접수일·고객 요청 시각·사유·기한/SLA·보류 전 단계/사유/시각·결정자·기존 비용을 유지한다. `claim.updated_at`은 새 변경을 나타내며 revision을 올리지만 `requested_at`이나 비용 확인시각을 다시 쓰지 않는다.

동일한 이름·전화·상세주소를 다시 제출하면 no-op 영수증만 남긴다. claim revision, 현재 계획, 변경 이력, 감사, 고객 알림은 늘리지 않는다. 현재 주소를 읽고 확인한 사실만으로 최초 접수 주소가 새로 수정됐다고 기록하지 않는다.

## 6. 권한·CAS·요청 영수증·고객 이력

context·정정·결과 재조회마다 현재 `sales.manage`와 계정 상태를 확인한다. 다른 사용자 ID를 클라이언트에서 받아 권한·소유권을 결정하지 않는다. 신규 private 테이블은 RLS를 켜고 `public, anon, authenticated, service_role` 직접 권한을 회수하며 목적별 RPC로만 읽는다. 새 public 함수도 네 역할의 기본 execute를 먼저 봉인한다.

잠금 순서는 기존 사유 정정과 맞춰 **운영자/고객 계정 fence → operation UUID → 주문 → 정렬된 배송건 → 클레임 → 정렬된 회수행 → 현재 계획**으로 둔다. 현재 주소·claim 유형·revision을 다시 비교하고 `PT409`로 충돌을 반환한다. 일부 출고지 입고는 마지막 입고 전까지 claim 행을 갱신하지 않으므로, claim revision만 검사하지 않고 잠근 회수행의 `collected_at`·증거를 다시 읽는다.

실제 주소 변경은 claim 행도 같은 트랜잭션에서 갱신해 기존 모든 claim update의 revision 증가 규칙에 참여한다. 승인·보류·철회·사유 변경·유형 전환과 경쟁하면 두 번째 작업은 최신 상태를 확인해야 한다. 재배송 주소가 있는 교환을 반품으로 전환해도 이전 정정 이력을 삭제하지 않고, 반품 상태에서는 재배송 계획을 사용할 수 없게 한다. 다시 교환으로 전환할 때는 현재 주소 확인을 새로 요구한다.

operation UUID는 운영자, claim, 대상, 기대 유형·revision, 현재 주소 digest, 정규화한 세 필드, 합의 근거·확인값에 결속한다. 정확히 같은 요청만 저장 당시 결과를 반환하며 다른 actor나 입력 재사용은 충돌이다. 영수증에는 저장 당시 결과와 현재 상태를 혼동하지 않도록 result revision을 남긴다. 재조회 전에 현재 권한을 다시 검사한다.

응답 유실은 최초 요청·UUID·입력을 고정한 채 결과 확인 또는 동일 요청 재전송으로 처리한다. 결과 null은 최초 요청의 종결을 뜻하지 않는다. 뒤늦은 오류·권한 거절만으로 미확정 요청을 버리고 새 입력을 제출하지 않는다. 다른 계정·대상·세션의 늦은 응답은 현재 화면에 반영하지 않는다.

민감 주소 원문을 일반 초안 자동저장이나 장기 localStorage에 추가하지 않는다. 최초 전송 본문은 현재 화면 메모리에서 유지하고 이탈을 경고한다. 재접속 복구에 필요한 세션 내 최소 operation 식별자는 주소 원문과 분리하며 로그아웃·계정/세션 변경 시 제거한다. 원문을 잃은 복구는 서버 결과 확인 전용으로 두고, null을 새 저장 허가로 쓰거나 원문을 현재 값으로 추측해 재시도하지 않는다. 이 제한과 보관 위치는 개인정보 inventory에 포함한다.

일반 감사에는 claim/operation/대상, 변경 필드명과 결과 revision만 남긴다. 기대 revision과 확인된 작업의 최소 결과는 별도 operation 원장에서 추적한다. 이름·전화·주소·합의 근거·주소 digest는 넣지 않는다. 실제 변경마다 기존 `claim_updated` 앱 알림을 operation UUID로 한 번만 기록하며, 본문은 변경 사실과 주문 상세 링크만 제공한다. 알림 전달을 고객의 수신 확인이나 운송사 통지로 표현하지 않는다.

일반 고객은 현재 주문 소유자일 때만 자기 주문의 현재 주소·변경 전/후와 시각을 읽는다. 선물 수신자는 자기 수령 정보만 읽고 발신자는 변경 사실·시각·항목만 읽는다. 내부 합의 근거·운영자 원식별자·다른 주문/고객 주소는 반환하지 않는다. PII 파기 후에는 변경 사실과 파기 표시만 보여 주고 과거 주소를 원주문이나 접수 원문에서 다시 채우지 않는다. 이메일·SMS는 발송하지 않는다.

## 7. 실제 교환 재출고 v2의 주소 결속

주소 폼 저장만으로 이 기능을 완료로 보지 않는다. [연락처 서비스](../../../lib/claim-contact/service.server.ts)와 [처리 화면](../../../components/admin/ClaimContactOperations.tsx)에 현재 교환 재배송지 확인을 연결했다. v2 RPC는 주소와 실제 재출고 결과를 한 트랜잭션으로 결속한다. 기존 서버 액션의 신규 재출고 폼은 제거했다.

1. context에서 실제 유효 주소, claim revision, 주소 digest, 상태를 읽어 보여 준다. 초기 원주문 참고 주소를 쓰는 경우도 최종 확인 대상이다.
2. 운영자가 최종 주소와 실제 발송 정보를 확인하고 operation UUID, expected actor/claim revision, expected address digest, 확인값, 택배사·송장·기존 옵션 선택을 제출한다.
3. 동일한 잠금 순서에서 현재 권한·유형·주소 digest·revision, 전체 회수 완료, 주문 상태, 취소/환불 시작 여부와 기존 재출고 흔적을 다시 검사한다. 주소 정정이 먼저 성공했으면 오래된 재출고 요청은 실패한다. 재출고가 먼저 성공했으면 후행 주소 정정이 실패한다.
4. 기존 재고 복원/차감·전체 수량·현재 상품/그룹 판매옵션·단일 재출고 송장 계약을 그대로 실행하며 최종 주소와 source, 확정 revision/digest, 시각, operation을 별도 private 재출고 목적지 snapshot에 남긴다. snapshot·재고·claim 종결·기존 재출고 감사/알림·영수증은 모두 성공하거나 모두 롤백한다.
5. 같은 operation의 정확한 재시도는 기존 결과만 반환하고 재고·snapshot·감사/알림을 늘리지 않는다. 그 뒤 주소가 파기돼도 옛 요청을 신규 재출고로 실행하지 않는다.

기존 3인자·4인자 public 재출고 RPC로 **새 재출고를 확정하는 경로는 닫는다.** v2만 주소를 확인한 뒤 동일한 private 재출고 본체를 호출하게 한다. 클라이언트가 정정 계획을 만들지 않았다는 이유로 구 RPC를 허용하면 v2를 우회하므로, 신규 실행에 공통으로 적용한다. 이미 완료된 레거시 재출고의 기존 정확 재조회/멱등 결과는 유지할 수 있지만 새 주소 확인이나 snapshot을 과거 사실로 만들어 붙이지 않는다. 레거시 목적지는 `별도 주소 확인 기록 없음`으로 구분한다.

v2는 실제 발송을 등록하는 경로이며 택배 예약·출고지시 전달 API가 아니다. DB가 외부 물류 인계를 취소하거나 이미 잘못 보낸 상품을 되돌리지는 못한다. 따라서 이 제안이 운송사까지 원자적으로 묶는 기능이라고 주장하지 않는다.

삭제 경로는 `claim → order → 현재 소유자`의 관계와 별도 운영자 식별자 모두를 인벤토리해야 한다. 신규 테이블에 운영자 `ON DELETE RESTRICT`를 무심코 추가해 담당자 계정 삭제를 더 막지 않는다. 주문/claim 삭제 cascade는 구조적 보조 수단이며 기간 파기나 Auth 탈퇴 완료의 대체가 아니다. 현재 주문·claim에도 `profiles` 참조의 RESTRICT가 있으므로 이 기능만으로 전체 계정 삭제가 완성되지 않는다.

향후 개인정보 처리 seam은 대상 소유자의 세 저장소를 열거하고, 명시적 목적·보존 판정 뒤 원문을 제거하고, 세 위치와 관련 요청 사본의 잔여 0건을 재조회해야 한다. 법적 보존은 기존 allowlist의 최소 기록으로 분리한다. 주소 원문, 원문 hash/digest 또는 합의 메모를 일반 감사·secondary tombstone에 복제하지 않는다. 파기 후 영수증 재조회는 파기 사실과 저장 결과만 반환하며 삭제된 필드를 다시 입력·복원하지 않는다.

최초 대리접수 원본, 기존 주문 주소 변경 이력과 원주문 주소에는 별도의 기존 PII도 있다. 신규 세 저장소를 정리했다고 해당 기존 사본까지 파기됐다고 보고하지 않는다. 반대로 신규 정정이 이 원본을 덮어써 기존 접수·입고 근거를 지우지도 않는다. 이 원본들의 별도 보존/파기 연계는 통합 개인정보 작업의 inventory에서 함께 추적해야 한다.

**신규 세 저장소의 암호화·보존 예외·기한 차단·실제 파기 RPC와 잔여 검사 경로를 구현했다.** 현재 관리자 세션을 요구하는 수동 보존 호출 경로는 실제 서비스·암호화·PostgREST·SQL 통합으로, 연락처 저장·조회 화면은 합성 계정의 실제 브라우저로 검증했다. 운영 키·cron·탈퇴 worker는 활성화하지 않았으며 기존 주문/접수 사본 전체의 파기를 완료했다고 주장하지 않는다. 공개 개인정보처리방침의 시행일·보존 문구는 변경하지 않았다.

## 9. 구현 검증 기준

다음 항목을 단위·격리 DB·실제 잠금 경합·브라우저에서 각각 검증한다. 현재 통합 검증의 확정 결과는 아래 기록을 갱신하며, 구현만으로 전체 완료를 표시하지 않는다.

- 주소 대상 구분, 유효 초기값·파기/누락 fail-closed, 미지원 키·우편번호/기본주소 변경 거절, 이름/전화/상세주소 길이·유니코드 경계, 합의/현재 주소 확인 필수.
- requested/in_review와 보류의 허용, 회수 착수·부분 입고·알 수 없는 수거계획 차단, 재출고 흔적·금전/종결 차단, 원주문/접수원본/창고주소/입고·비용·재고 보존.
- 같은 UUID 재생·다른 입력/actor 충돌·결과 조회·no-op, null 뒤 늦은 최초 요청, 권한 회수, 두 편집 CAS, 승인·철회·보류·사유/유형 변경·부분 입고의 양방향 실제 잠금 경합.
- 재배송 정정↔v2 재출고 양방향, 오래된 주소 digest 거절, 구 3/4인자 RPC의 신규 실행 차단, 기존 완료 레거시 재조회 보존, 재고/snapshot/감사/알림 단일 확정과 롤백.
- 운영자와 고객 본인 조회, 다른 고객 차단, 내부 합의 비노출, PII 없는 감사/알림/오류/로그, 기존 XLSX 원주문 주소 유지와 새 PII 0건.
- 개인정보 inventory 전체 열거, 목적 종료/실제 교환품 배송완료/hold 경계, 원문 제거와 잔여 확인, 파기 후 조회·재생의 재생성 금지, 운영자 삭제와 소유자 삭제 경합. 기존 Phase 1과 disabled secondary 경계가 임의로 활성화되지 않음.

구현에 맞춰 클레임 런북·ARCHITECTURE·운영 가이드와 신규 개인정보 inventory를 함께 갱신했다. 운영 활성화·실제 물류 인계와 기존 개인정보 전체 삭제는 완료 범위에 포함하지 않는다.
