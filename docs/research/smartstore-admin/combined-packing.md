# 여러 주문 합포장

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-16 승인: 같은 구매자·수취인·주소·출고지의 발송 전 주문을 합포장하고 원 주문 금액과 배송비를 유지한다. 중복 배송비를 자동 환급하지 않는다. 창고 연동은 기존 XLSX/CSV이며 운송사 API를 추가하지 않는다.

## 동작

- 발송 대기/지연에서 2~100개의 택배 배송 건을 선택해 조건을 조회하고 사유·확인 항목을 입력한다. 같은 구매자, 실제 수취 주체, 전체 주소/전화, 출고지, 선물 포장, 착불 수금 조건이어야 한다. 결제완료·실물 할당과 진행 중 취소/반품/교환을 검사한다.
- 배송 건과 주문의 기존 연결, 품목 수량, 결제/환불, 선결제 배송비와 착불 금액을 유지한다. 별도 비공개 포장 테이블이 기존 배송 건을 참조하며 주소 원문을 복제하지 않는다.
- 출고지시 전달 전에는 합포장을 해제할 수 있다. 이후 해제나 구성 변경은 제공하지 않는다. 이미 전달한 창고 지시가 취소됐다고 추정하지 않는다.
- 출고 파일에는 묶음 전체를 선택한다. 창고 원본 열과 주문번호를 유지하고 별도 `배송 운영 안내`에 합포장번호·구성 건수·착불 합계·동일 송장 회신 안내를 넣는다. CSV는 원본과 안내를 ZIP으로 전달한다. 창고가 이 별도 안내를 실제 인수했는지는 외부 운영 확인이다.
- 송장 등록·정정·실제 도착 기록은 같은 묶음 전체에 원자적으로 적용한다. 각 원래 주문에 배송 알림과 이메일 대기열을 유지한다. 여러 행의 송장이 충돌하면 첫 변경 전에 파일을 차단하며, 파싱에서 거절한 행의 참조도 DB 검사에 남긴다.
- 출고 시 주소 계약과 취소/클레임을 다시 검사한다. 읽은 이후 그룹 또는 배송 상태가 바뀌면 이전 요청을 거절한다. 저장 요청은 계정/실제 세션·작업 UUID와 조회 버전에 결속하며 불명확한 결과는 같은 요청으로 확인한다. 과거 영수증 재시도 후에는 현재 상태를 다시 읽는다.

## 잠금과 권한

`shipment_pack_scope`가 묶음 전체를 해석한 뒤 모든 주문과 배송 건을 UUID 순서로 잠근다. 잠금 대기 중 구성 변경이 생기면 추가 순서 역전 잠금 없이 `shipment_pack_changed`로 종료한다. 단건·기존 주문별 변경, 두 종류의 일괄 송장 입력, 내보내기 확정·도착 처리도 같은 경로를 사용한다. 생성은 관련 계정/수취 주체와 운영자 상태를 먼저 잠근다.

새 테이블은 RLS와 ACL로 직접 접근을 봉인한다. 새 공개 함수는 `sales.manage`를 확인하고 실제 UI/서버 계정 경계를 유지한다. 내부 함수는 operator registry에 등록한다. 운영자 가드가 행 잠금을 쓰므로 PostgREST 조회 함수도 `VOLATILE`로 실행한다. 고객에게 다른 주문번호나 합포장 내부 정보를 공개하지 않는다.

## 검증 근거

- `supabase/tests/combined_packing.sql`: 원 주문 배송비 3,000/4,000원과 합계 27,000원 보존, 서로 다른 구매자/주소 차단, 생성 재시도/CAS, 일부 구성원만 내보내기 차단, 출고 전 해제와 오래된 파일 차단, 전달 후 해제 차단, 새 취소 요청/주소 변경 차단, 충돌 송장 원자 거절, 묶음 송장/도착 적용·정확한 영향 건수·직원/ACL 경계. 트랜잭션 롤백으로 실행한다.
- `combined_packing_concurrency.py`: 동일 생성 12회는 하나의 영수증, 다른 요청 8개는 1회 성공/7회 오래된 버전 거절. 반대 구성원으로 12개 동시 발송과 8개 송장 정정 후 두 배송의 최종 송장이 일치했다. 주문 합계 40,000원, 포장 2개/생성 이벤트 2개를 확인했다.
- 앱·가이드 77개 테스트와 타입 검사·ESLint 통과. 기존 `warehouse_native_tracking.sql`은 합성 스태프 1명의 현재 operator membership만 추가한 롤백 하니스에서 1,000행·원본 열/금액·출고지·중복/오류 그룹·권한 회귀를 통과했다.
- 앱 경계: 현재 상태 재조회, 불명확한 응답 보존, 잘못된 계정/선택 거절, 원본 창고 열/주문번호/금액 보존, 파싱 오류 참조 보존, 묶음 전체 알림과 영향 건수 테스트.
- 실제 Chrome: 합성 주문 두 건을 합포장하고 1440px/390px 화면과 가로 넘침을 확인했다. 출고 파일을 실제 내려받아 원본 12열+별도 안내 14열, 두 원 주문번호를 읽었다. 송장 충돌 안내를 확인한 뒤 한 행의 정상 송장으로 두 배송 건이 배송중으로 바뀌었다. DB 재조회에서 원 주문 13,000/14,000원, 배송비 3,000/4,000원, 환불 0건, 배송 이메일 대기열 2개를 확인했다.
- 초기 네이티브 확인창은 연결 오류로 완료되지 않았다. 후속에서 대상 배송 건수와 명시적 확인 체크를 가진 앱 확인창으로 연결하고 실제 PC/390px에서 도착 기록을 완료했다. `final-interaction-readback.json`의 원래 두 배송 건 모두 `delivered`이며 기존 배송비 3,000/4,000원을 유지한다. 초기 실패를 성공으로 덮어쓰지 않고 후속 완료 근거를 별도로 남겼다.

근거 파일은 `output/smartstore-full-admin-20261016/combined-packing-*`와 `local-packing-*`다. 작업 전용 격리 DB/앱의 합성 주문으로만 실행했고 운영 데이터, 실제 창고 인계, 운송사 호출, 결제/환불/은행 송금은 실행하지 않았다. 전체 어드민의 다른 기능·화면 통합 검증과 배포는 별도다.
