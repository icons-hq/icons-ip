# PG 정산 원장·대사 구현 계약

migration 파일 경로는 [배포 매핑](../../../supabase/manifests/admin-rollout-migration-map.json)을 반영했다. 아래 과거 검증·적용 기록은 당시 원본 DRAFT 기준이며 이번 운영 배포의 성공을 뜻하지 않는다.

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-13. 토스 읽기 어댑터, private 수집 원장, 일별·건별·수수료 화면과 엑셀 내보내기를 구현했다. 격리 로컬 DB의 합성 자료로 수집·대조·권한·경합과 실제 Chrome 조회·다운로드를 검증했다. 운영 PG API를 호출하거나 지급을 요청하지 않았으며 연결은 기본 OFF다.

## 확인한 정본

- 네이버 일별/건별 정산의 날짜·주문/상품주문 검색·수수료/보류·상세와 출력 입력 상태는 `output/smartstore-reference-20261012/sales/manifest.json`의 10-daily/10b/10c 계열에 있다. 원본 고객·정산 금액은 테스트에 복사하지 않는다.
- [토스 코어 API](https://docs.tosspayments.com/reference#정산-조회)는 `GET /v1/settlements`와 매출일/지급일 기준, 날짜 범위·페이지/크기를 명시한다. 기록은 결제 다음 날부터 제공되며 응답 대기 시간을 최소 60초로 안내한다. 서버 시크릿 키를 사용하고 브라우저에서 공급자 API를 직접 호출하지 않는다.
- [Settlement 객체](https://docs.tosspayments.com/reference#settlement-객체)는 MID·결제/거래/공급자 주문 키, 통화·수단·금액, 수수료 상세·공급가·VAT·지급액, 승인시각·정산매출일·정산지급일을 제공한다. 결제의 승인과 취소는 거래 키로 구분한다. 원본 숫자를 임의 정수 반올림하거나 현재 상품/수수료율로 재계산하지 않는다.
- [테스트·라이브 환경 안내](https://docs.tosspayments.com/guides/v2/get-started/environment)에 따르면 정산 기록은 라이브에서만 제공되고 테스트 API는 기록이 없는 것으로 조회된다. 이번 45행 검증 자료는 로컬 합성 원장을 거친 fixture이며 토스 테스트 API의 실제 정산 응답이 아니다. 테스트 API의 0건을 실거래의 정산금액 0으로 해석하지 않는다.
- 같은 URL의 `POST /v1/settlements`는 별도 계약을 요구하는 수동 정산 요청이다. 읽기 대사 구현에서 호출하지 않는다. 지급대행도 이 조회 기능과 별개다.
- [코페이 공식 서비스 안내](https://www.korpay.com/business)와 현재 저장소의 [코페이 런북](../../runbooks/korpay-production-rollout.md)은 상점 관리와 결제 연동 범위를 설명한다. 이번 공식 공개 문서 확인에서는 코페이 정산 자동 조회 API와 원본 내보내기 스키마를 확인하지 못했다. 타사 Korapay의 API를 코페이로 취급하지 않는다.

## 현재 코드에서 재사용할 경계

`/admin/sales/settled`와 거래확정 엑셀은 `orders.done_at`·주문/결제 대조용이며 PG 지급일이 아니다. `payments.payment_key`, `payment_attempts.provider_order_id`, `private.payment_provider_evidence.provider_transaction_id`가 공급자 정산 행과 연결할 근거다. 공급자/키/목적/대상/금액이 일치하지 않으면 미연결 또는 불일치로 남기며 주문번호 문자열만으로 다른 결제를 강제 연결하지 않는다.

기존 `sales.manage`의 민감 작업 경계를 따라 통합·계정 주매니저가 수집/확인을 관리하며, legacy 환경의 민감 실행은 기존 admin으로 제한한다. 원문 키·MID·결제 원문·자격증명 fingerprint를 로그·문서·URL에 노출하지 않는다.

## 구현한 경계와 미연결 범위

1. 공급자 조회 작업과 기간 커버리지를 별도 원장으로 보존한다. 요청 중·일부 수집·실패·완료·확인된 0건을 구분하고, 페이지 누락/중복/조회 중 변경을 감지한다. 미완료 작업이 이전 완전한 조회를 덮어쓰지 않는다.
2. 거래별 원본 금액/수수료·정산 매출일/지급일을 private 스냅샷에 남기고 입력/응답 hash·가져온 시각을 결속한다. 카드번호·전화·계좌 등 대사에 불필요한 공급자 필드는 보관/반환하지 않는다. 재수집은 별도 완료 자료로 보존하며, 서로 다른 수집 결과를 중복 합산하지 않는다. 이전 완료 자료도 다시 조회할 수 있다.
3. 일별 지급합계와 거래 상세, 결제·취소 연결, 수수료 항목과 차이를 제공한다. 취소의 부호/금액 해석이 원본에서 확정되지 않으면 추정 합산하지 않는다. 법정 세무 신고자료·매입 세금계산서는 정산 합계를 재명명하지 않는다.
4. 공급자 정산 지급일/지급액과 은행 실입금 대사를 구분한다. API 기록만으로 실제 계좌 입금 완료를 확정하지 않는다. 코페이는 공식 원본 포맷/제공 경로 확인 전까지 자동 API가 있는 것으로 표시하지 않는다.
5. 기존 결제 finalizer·환불·재고·카드팩·거래확정은 읽기만 한다. 운영 수집 활성화와 실제 계좌/PG 연결 검증은 코드 구현·합성 테스트와 별개로 기록한다.

## 토스 수집 구현 계약

`lib/settlements/toss-settlements.server.ts`는 공식 고정 origin의 GET만 호출한다. 각 작업 단계에서 한 페이지(1,000건)를 최대 65초 동안 읽고, 기본 OFF인 `TOSS_SETTLEMENT_SYNC_ENABLED=true`, 명시적 `TOSS_SETTLEMENT_MID`와 기존의 모드가 일치하는 키 쌍이 있을 때만 연결한다. live 키는 production 환경에서만 허용한다. 이 두 정산 설정은 비활성 환경의 필수 빌드 변수가 아니다. 실제 활성화·MID와 계약키 범위 확인은 별도 운영 작업이다.

사용자가 지정한 최대 31일의 날짜 범위는 시작 전일과 종료 다음 날을 함께 요청한 뒤 `soldDate` 또는 `paidOutDate`의 요청 날짜만 선택한다. 공식 문서에서 날짜 경계 포함 여부를 명시하지 않은 부분을 보완한다. 마지막 페이지 판정은 필터 전 원본 행 수를 사용하며, 페이지당 8MiB와 최대 20페이지·20,000건을 넘으면 범위를 줄이도록 중단한다. 정확히 20페이지가 가득 차면 21번째 빈 페이지까지 확인한다. 이 한도는 ICONS의 수집 단위 제한이며 공급자 API 한도로 설명하지 않는다.

금액은 JSON 숫자 원문을 문자열로 읽고 최대 정수부 18자리·소수부 8자리 안에서 정확히 보존한다. 범위 초과는 반올림하지 않고 거절한다. 합계는 십진 정수 연산으로 계산한다. 응답의 중복 JSON 키·중복 거래 키·다른 MID·요청을 벗어난 날짜·불완전 본문은 수집 완료로 처리하지 않는다. 원본 카드·계좌·연락처·고객명·취소 사유는 저장 대상으로 내보내지 않는다.

원장 구현은 두 차례 조회의 정규화 거래 집합을 대조한 뒤 완료 스냅샷을 확정한다. 페이지 해시·수집 시각·조회 기준·요청 범위와 test/live 환경을 기록한다. 공급자가 원자적 스냅샷 API를 제공한다는 뜻은 아니며, 조회 중 변경을 감지하기 위한 검증이다. 미완료·실패·재시도는 이전 완료 자료를 바꾸지 않는다. 취소 행은 원본 부호와 취소금액을 각각 보존하고, 취소 부호의 공급자 의미가 확인되기 전에는 승인·취소 값을 임의 합산해 순입금액으로 제시하지 않는다.

## 원장·권한·확정 계약

`20261020085304_pg_settlement_ledger.sql`은 `private.pg_settlement_imports`, `pg_settlement_pages`, `pg_settlement_source_keys`, `pg_settlement_records`를 만든다. 직접 DML·기본 execute를 봉인하고 허용 RPC만 권한을 갖는다. 작업 생성·claim·page finish·fail은 현재 작업자 권한과 scope, 행 버전, 120초 lease를 검사한다. 조회·수집·내보내기는 통합·계정 주매니저의 `sales.manage` 민감 권한을 요구하며 전환 전에는 기존 admin만 허용한다.

완료 시 결제 provider·결제/주문 키·목적·대상·금액과 승인/취소 증거를 함께 대조한다. 결과는 완료 시점에 고정된다. 기존 굿즈 환불 경로가 공급자 취소 거래 식별자를 남기지 않은 경우에는 미연결·기존 거래 근거 미기록으로 표시한다. 주문번호나 금액이 같다는 이유로 일치시켜서는 안 된다. 실제 티켓 환불 경로가 남긴 취소 증거는 별도로 일치 검증했다. 수집은 주문·결제·환불·재고를 수정하지 않는다.

`/admin/settlements`는 선택 기간·환경·날짜 기준과 정확히 일치하는 최근 완료 자료를 선택한다. 새 작업의 일부 수집·실패가 이전 완료 자료를 숨기지 않는다. 수집 이력에서 이전 완료 자료를 고정해 열 수 있고, 선택 자료에 검색·승인/취소·일치/미연결/불일치·통화 필터를 적용한다. 작업 응답이 불명확하면 같은 작업을 확인하며, 생성 멱등키의 계정/scope 충돌이 확인되면 전체 화면을 새로 읽어 저장된 작업과 요청 키를 복원한다.

엑셀은 완료 자료 ID를 명시해야 하며 같은 조건의 전체 거래(최대 20,000건), 일별 합계, 수수료와 조회 정보 4시트를 제공한다. 모든 금액 셀은 텍스트다. 파일 생성 뒤에도 현재 권한·자료 지문·행 수를 DB에서 확인하고 감사 기록을 만든 뒤 응답한다. 공급자 원문 식별자·MID·연락처·계좌를 브라우저나 엑셀에 싣지 않는다.

## 검증 근거

- 소유한 두 격리 DB의 migration·정확한 적용 원문·함수/권한 계약을 대조했다. SQL 회귀는 0건·정확한 소수·이중 조회·원자적 공개·완료 불변·내보내기·권한을 포함하고, 실제 연결 11개 경합은 같은 요청·페이지 중복·lease·권한 회수 등을 확인했다. DB 검증 기록 (`output/smartstore-reference-20261013/pg-settlement-db/migration-verification.json`).
- 45행 합성 fixture는 실제 주문/티켓 결제·환불 RPC가 남긴 근거를 사용한다. 일치 2건·불일치 1건·미연결 42건, 진행 중·실패와 이전 완료 자료 유지, 별도 완료 0건을 확인했다. UI 원장 readback (`output/smartstore-reference-20261013/pg-settlement-db/ui-report-readback.json`).
- Chrome에서 20/20/5행 페이지 이동, 대조 필터, 취소 상세·소수 수수료, 일별/수수료 탭, 45행·0행 실제 엑셀 다운로드, 날짜 기준과 test/live 분리, 31일 오류, 390px 필터·표 가로 이동·상세를 확인했다. 화면 검증 기록 (`output/smartstore-reference-20261013/pg-settlement-ui/manifest.json`).
- 45행 파일을 다시 열어 4시트·전 거래수·텍스트 금액을 확인했고 8영역을 렌더링해 직접 검수했다. 렌더러의 빈 문자열 표시 차이는 원본 XML과 별도 읽기 라이브러리로 확인했으며 파일을 바꾸지 않았다. 엑셀 검수 (`output/smartstore-reference-20261013/pg-settlement-ui/xlsx-visual/review.md`).

실제 PG 응답·계약키 권한·은행 입금은 위 검증에 포함되지 않는다. 활성화는 [운영 런북](../../runbooks/pg-settlement-reconciliation.md), 부가세·수취 세금계산서·환급·보류·조정은 [미확정 계약](pg-settlement-followups.md)을 따른다.
