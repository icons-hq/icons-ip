# 클레임 수취인·상품주문·상품번호 검색

migration 파일 경로는 [배포 매핑](../../../supabase/manifests/admin-rollout-migration-map.json)을 반영했다. 아래 과거 검증·적용 기록은 당시 원본 DRAFT 기준이며 이번 운영 배포의 성공을 뜻하지 않는다.

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-14 구현·격리 로컬 검증 완료. 취소·반품·교환 목록에 기존 주문 원장을 사용하는 상세조건 세 개를 추가했다. 접수·회수·재출고·환급 정책은 바꾸지 않는다.

## 원본 확인과 ICONS 검색 계약

로그인된 원본의 [취소](https://sell.smartstore.naver.com/#/naverpay/claim/cancel), [반품](https://sell.smartstore.naver.com/#/naverpay/claim/return), [교환](https://sell.smartstore.naver.com/#/naverpay/claim/exchange) 목록에서 `상세조건` 셀의 실제 select를 다시 읽었다. 상단의 공통 주문조회 select와 구분했으며, 세 목록 모두 수취인명·상품주문번호·상품번호를 제공한다. 반품 목록에서는 각 값을 선택해 입력 활성화를 확인했다. 원본 검색·주문 처리·저장은 실행하지 않았다.

| 화면·URL 값 | 읽는 기존 데이터 | 검색 의미 |
| --- | --- | --- |
| 수취인명 `recipient` | `orders.address.recipientName` | 앞뒤 공백을 제거한 입력의 대소문자 무시 문자 포함. 수취인 미기록을 구매자명으로 대신하지 않는다. |
| 상품주문번호 `item` | `order_items.id` | UUID 전체 또는 일부의 대소문자 무시 문자 포함. UUID로 변환하지 않아 잘못된 형태의 입력도 조회 오류를 만들지 않는다. |
| 상품번호 `product` | `order_items.good_id` | 등록 상품 식별값의 대소문자 무시 문자 포함. 판매자상품코드·옵션 관리코드·상품명 검색과 다르다. |

세 조건의 `%`와 `_`는 입력 문자 그대로 검색한다. 상품번호 전체를 입력해도 그 문자열을 포함하는 더 긴 번호가 있으면 함께 나온다. 이 규칙은 [기존 상품주문 검색](../../../supabase/migrations/20261020085244_admin_order_item_console.sql)의 문자 포함 방식에 맞춘 ICONS 계약이다. 네이버의 정확 일치·부분 일치 알고리즘을 확인했다는 뜻이 아니다. 원본 입력의 50자 제한과 별개로 기존 ICONS 검색어 100자 상한을 유지한다.

`전체`에도 세 대상을 포함한다. [필터 정본](../../../lib/admin/claims.ts)의 허용 목록으로 URL을 정규화하고, 검색·단계 변경 시 첫 페이지로 이동한다. 페이지·정렬·목록 수·상세에서 돌아가기·엑셀에는 같은 대상을 보존한다. [목록 안내](../../../components/admin/screens/ClaimQueueScreen.tsx)에서 상품주문번호와 상품번호의 차이, 품목으로 찾아도 주문 전체를 처리하는 경계를 설명한다.

## DB·엑셀·권한

[migration](../../../supabase/migrations/20261020085315_admin_claim_detail_search.sql)은 기존 검색 helper와 공개 목록·단계 집계 함수만 갱신한다. 수취인·품목·상품 식별자는 `EXISTS`로 검사하므로 같은 주문에서 여러 품목이 일치해도 클레임 한 건은 목록 한 행이다. 필터를 적용한 뒤 전체 건수·단계별 건수·정렬·페이지를 계산하며 결제일 근거와 철회 단계 집계를 유지한다.

[엑셀 로더](../../../lib/admin/list-export-data.server.ts)는 화면과 같은 필터의 모든 페이지를 읽고, 일치한 요청 주문의 모든 품목을 내보낸다. 검색에 일치한 품목만 남겨 부분 처리로 보이게 하지 않는다. 조건·요청 건수·엑셀 행 수는 안내 시트와 다운로드 감사에 동일하게 기록한다. 기존 10,000행 제한과 취소 목록의 배송지·운송장 제외를 유지한다.

기존 함수의 소유자를 보존하고 private helper는 공개 역할·익명·로그인 사용자·service role에서 직접 실행할 수 없게 유지했다. 목록·단계 집계·다운로드 감사는 실제 `authenticated` 역할에서 현재 `sales.manage` 권한을 검사한다. 고객 본인 주문이나 raw staff 역할만으로 허용하지 않으며 권한 철회 뒤 같은 검색·내려받기 감사도 거절한다.

## 검증

- DRAFT 독립 검토 후 복제한 임시 DB에서 신규 기능 SQL, 이전 판매 조회 회귀, operator coverage를 통과했다. 복제 시 바뀌는 타입 OID·ACL/정책 역할 배열 순서는 원본과 함수 정의·설정·소유자·권한 항목·정책 의미가 같은지 먼저 대조하고, 변경 전 clone의 검증 기준만 재결속했다. 원본 OWN/FRESH의 기존 계약 원장은 재결속하지 않았다.
- 최종 SHA-256 `e1ccaed87441edd19c07efc8200c61af55901b4645d7b88efc7b2102ae4f9a90`을 OWN/FRESH에 적용했다. 양쪽 적용 원문과 기존 함수 소유자가 일치하며 신규·이전 SQL·권한 coverage가 모두 통과했다. 로컬 security advisor에 경고·오류가 없었다.
- [기능 SQL](../../../supabase/tests/admin_claim_detail_search.sql)은 112개 합성 요청으로 수취인 누락/구매자 대체 금지, 대소문자·공백·`%`/`_`, 전체/일부 UUID, 상품명/코드와 상품번호 분리, 접두사 중복, 복수 일치 품목 중복 방지, 100건 초과 페이지, 처리 단계·사유·결제일 교집합, 현재 권한·ACL·다운로드 감사와 금전/재고 무변경을 확인한다. 브라우저용 합성 식별자도 별도 분리해 같은 DB에서 기능 SQL을 다시 실행했다.
- 관련 Vitest 5파일 75개, 전체 `tsconfig.test.json` TypeScript 검사, 변경 파일 ESLint가 통과했다. 엑셀 검증은 101건을 두 페이지에서 수집하고 같은 주문의 비일치 품목까지 포함하는 계약을 검사한다.
- 실제 Chrome에서 수취인 103건(100/3 페이지), 상품번호 104건(100/4 페이지), 상품주문번호 전체 대문자/부분 입력 각 1건을 확인했다. 상세에서 돌아온 URL은 검색 대상·입력·정렬·기간을 유지했다. 수취인과 결제일 조건을 함께 적용하면 2건, 같은 상세조건의 취소·교환은 각각 1건이다.
- 실제 XLSX 세 파일을 다시 열어 수취인 103건/105행, 상품주문 1건/3행, 상품번호 104건/106행의 순서와 주문번호·조건·감사가 DB 결과와 일치함을 확인했다. 상품주문 파일에는 검색에 일치하지 않은 같은 주문의 다른 상품도 포함됐다. 다운로드마다 감사 1건이다.
- 390×844에서 검색 선택·입력·다운로드를 조작했고 안정화 후 문서 폭·스크롤 폭이 모두 390px이었다. 처음 다운로드 이벤트 대기가 중단됐으나 UI 성공과 이미 생성된 파일을 확인해 중복 클릭 없이 보존했다. 소유 탭을 닫고 임시 뷰포트를 해제했다.

원본 컨트롤·화면·SHA-256, 적용 원문·소유자 readback, 실제 XLSX·DB 감사 대조는 `output/smartstore-reference-20261014/claim-detailed-search/`에 있다. 합성 로컬 데이터만 사용했고 운영 DB·배포·네이버 데이터·실제 결제·환불·물류·고객 안내는 변경하지 않았다.
