# 복수구매 할인·착불·수량 배송비 — 공동 주문 산식 제안

migration 파일 경로는 [배포 매핑](../../../supabase/manifests/admin-rollout-migration-map.json)을 반영했다. 아래 과거 검증·적용 기록은 당시 원본 DRAFT 기준이며 이번 운영 배포의 성공을 뜻하지 않는다.

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-14. 사용자 요청으로 세 기능의 설계·구현 포함이 확정됐으며 공통 계산·확정 견적·명시적 선택 주문 생성·착불 증빙 원장은 구현 및 격리 clone 검증을 마치고 승인된 로컬 DB에 반영했다. 정기배송 계약 보존과 PG 계정 분리도 통합 검증·독립 검토 후 승인된 세 로컬 DB에 반영했다. 실제 관리자 브라우저의 입금 확인·착불 정정·전체 취소·파일 검증을 이어가고 있다. [현재 운영 계약](../../runbooks/goods-transactions.md)에 금액·착불 증빙·환급·보존 경계를 정리했다. **기반 검증 통과는 전체 화면·운영 연결 완료 또는 운영 DB 적용을 뜻하지 않는다.** 아래 정책은 ICONS의 계약으로, 네이버의 미실측 거래 결과나 운송사 계약을 확인한 사실이 아니다. 선물·정기배송은 별도 설계와 공통 주문 계산 Interface에서 결합한다. 부분취소·부분반품 제외는 유지한다.

확정 견적 입력 selection과 저장 calculation에는 각각 직렬화 UTF-8 **2MiB** 상한을 둔다. calculation은 상품 이름·직접입력·할인/운임 근거를 포함하므로 입력보다 커진다. 1,001개의 짧은 직접입력은 실측 검증하지만, 모든 1,001개 조합을 보장하지는 않는다. 상한 초과는 주문 분할 안내로 거절하고 카트·재고·쿠폰·적립금·주문을 변경하지 않는다. 행 수 상수는 2MiB의 최소 유효 selection 행 크기에서 파생하며 PostgREST의 1,000행 페이지 크기로 카트를 자르지 않는다. 구형 주문 경로에는 이 신규 견적 크기 계약을 소급 적용하지 않는다.

카트 직접 INSERT/UPDATE/DELETE의 authenticated 권한은 회수한다. 앱의 기존 카트 RPC가 공통 actor→account-action→profile→cart 잠금을 취득하며, 클라이언트는 해당 RPC를 사용한다. 이는 기대 selection 대조와 계정 정지·탈퇴 경합을 직렬화하기 위한 계약 변경이다. 기존 회귀의 인증 사용자 fixture도 동일한 카트 RPC로 작성한다.

## 2. 권고하는 가격·운임 계약

### 복수구매 할인

상품마다 조건1개와 할인1개를 둔다. 같은 상품의 활성 옵션·직접입력 여러 줄을 합쳐 조건을 판정하고, 다른 상품은 합치지 않는다. 추가 구성으로 선택한 다른 상품도 자신의 상품 ID에 대한 조건을 따른다. 모든 신규/기존 상품은 초기 OFF이며 값은 임의로 채우지 않는다.

| 설정 | 허용 값 제안 | 의미 |
| --- | --- | --- |
| 상태 | `draft / active / disabled` | 활성 버전의 금전 조건은 수정하지 않고 새 버전 생성. OFF의 미완성 값은 보존하되 계산하지 않는다. |
| 조건 | `quantity / regular_subtotal` | 수량≥기준 또는 옵션 정상가×수량 합계≥기준. UI에 ‘옵션 정상가 합계 기준’이라고 명시한다. |
| 수량 기준 | 정수2~2,147,483,647 | 카트 줄별 수량 한도·현재 상품 구매 한도와 함께 검사. 상품 합계는 bigint로 계산한다. |
| 금액 기준 | 정수1~999,999,999,999원 | 고객 가격 노출 단위와 실제 거래 상한은 기존 provider/DB 제약도 통과해야 한다. |
| 할인 | 고정액1~2,147,483,647원 또는 정수1~100% | 구매한 각 수량에 적용. `%`는 기간 할인 후 옵션 단가에 곱하고 원 미만 버림. 고정액은 같은 단가를 넘지 않게 제한한다. |
| 기간 | 제한 없음 또는 시작·종료 둘 다 | KST 입력→명시적 timestamptz, `[start,end)`, 역전/중복 활성 기간 거절. |

적용 순서는 **옵션 정상가→기간 할인가→복수구매 할인→쿠폰1장→적립금**으로 고정한다. 복수구매 할인은 발급 쿠폰이 아니므로 `coupon_redemptions`나 쿠폰 개수에 섞지 않는다. 조건 성립 시 해당 상품의 전체 구매 수량에 적용하며 ‘기준 초과 수량만’ 또는 구매 이력 누적 할인은 만들지 않는다.

`P_i`는 기간 할인 후 단가, `q_i`는 수량이다. 조건이 충족하면 단위 할인 `d_i = min(P_i, fixed)` 또는 `min(P_i, floor(P_i × percent / 100))`, 아니면0이다. 복수구매 할인 `V_i = q_i × d_i`, 이후 상품 소계 `N_i = q_i × P_i − V_i`다.0원까지 할인된 품목은 허용하되 주문의 실제 온라인 결제액은 기존1,000원 하한을 만족해야 한다. 약속한 복수구매 할인율을 몰래 줄여 하한을 맞추지 않는다. 불가능한 장바구니는 결제 전에 이유를 표시한다.

### 수량·구간 배송비

상품별 확장 배송 조건을 별도 버전으로 두고, 값이 없거나 OFF이면 기존 `policy/free/individual` 계산 결과를 그대로 사용한다. 레거시 enum을 즉시 넓혀 구형 코드가 새 값을 기본료로 오해하게 하지 않는다. 신규 화면에서 현재 유형과 아래 확장 유형을 함께 다루는 정규화 Interface를 만든다.

| 유형 | 계산 제안 | 숫자 계약 |
| --- | --- | --- |
| 출고지 정책/무료/개별 | 현행과 동일 | 기존 비용·무료 기준·개별료 상한 유지 |
| N개마다 반복 | `ceil(Q_g / N) × baseFee` | N 정수1~2,147,483,647, baseFee 정수0~1,000,000원 |
|2구간 | Q≤N이면 기본료, Q>N이면 기본료+추가료1 | N≥1, 추가료 정수0~1,000,000원 |
|3구간 | Q≤N1 기본료, N1<Q≤N2 기본료+추가료1, Q>N2 기본료+추가료2 | 1≤N1<N2, 추가료2≥추가료1. 두 추가료를 누적하지 않는다. |

Q는 **상품별 전체 선택 수량**이다. 옵션·직접입력 줄을 쪼개도 반복료가 늘거나 줄지 않는다. 반복 횟수는 요금 계산 단위이며 실제 박스/송장/배송 건 수가 아니다. 배송 건은 기존 출고지당1개를 유지한다.3구간의 비누적 추가료는 명확한 ICONS 제안이며 원본 실제 계산으로 검증하지 않았다.

무료배송 임계값은 현행대로 **기간 할인가 소계, 복수구매·쿠폰·적립금 차감 전**을 사용한다. 수량/구간 상품에는 임의로 출고지 무료 기준을 적용하지 않는다. 따라서 할인 때문에 갑자기 무료배송을 잃거나 현재 정책 상품의 합계에서 제외된 개별 상품이 무료 기준을 채우는 일이 없다.

지역 추가료는 현재 `chargePolicyGoods/chargeFreeGoods/chargeIndividualGoods`, 임계값 면제, `per_shipment/per_good` 계약을 그대로 유지한다. 수량/구간 유형은 비용 부과 분류상 `individual`로 명시 매핑한다. 수량 반복 횟수만큼 지역비를 자동 곱하지 않는다. 계약상 박스마다 추가료가 필요하면 기존 지역 정책의 새 명시적 부과 단위와 별도 버전을 함께 설계해야 한다.

### 착불과 선결제/선택형

상품 배송 조건은 `prepaid / collect / buyer_choice`를 지원한다. 기본은 prepaid, 신규 착불은 OFF다. 선택형은 체크아웃에서 상품별로 선/착불을 명시 선택하며 초기 선택은 선결제다. 고정 착불 상품은 별도 지급액과 수납 주체를 반드시 노출한다. 착불을 상품대금 후불·무통장 결제로 해석하지 않는다.

같은 출고지의 선결제·착불 상품을 혼합 주문할 수 있다. **물리 배송 건은1개, 운임 구성요소의 결제 시점은 여러 개**다. 새 `shipping_charge_components`에 상품/유형/수량 단위·지역비·선택한 결제 시점·금액·정책 버전을 보존하고 배송 건의 `prepaid_fee`와 `collect_fee`를 합산한다.

공동 기본료와 `per_shipment` 지역비를 분리할 때에는 총 운임을 늘리지 않는다. 출고지 정책 기본료는 해당 정책 상품의 기간 할인가 소계 비중으로 상품별 정수 배분한다. 전부0원이면 수량 비중을 쓴다. 지역비는 해당 지역 정책의 부과 대상 상품만 대상으로 하며, 이미 배분된 기본료 비중→해당 상품 소계 비중→수량 비중 순으로0분모를 처리한다. `per_good` 지역비는 해당 상품에 그대로 귀속한다. 최대나머지 방식, 동률 상품 ID순으로1원 잔여를 배분한 뒤 그 상품의 선/착불 선택을 적용한다. 한 상품이 여러 품목 줄이면 같은 방식으로 품목 ID순 배분한다. 이 혼합 배분 역시 ICONS의 제안이며 원본 실거래로 확인한 정책은 아니다.

‘무료’는 선결제/착불 양쪽 운임 합계가0일 때만 쓴다. 선결제0·착불3,000원은 ‘착불3,000원’이다. 배송 시 별도 지급할 정확한 금액을 확정할 수 없거나 도입한 지역 정책이 미해결이면 주문을 막고 미확인 이유를 표시한다.

착불 활성화에는 출고지별 수납 주체·확정 요금 전달 방식·고객 영수증/분쟁/환급 담당·운송사 또는 창고의 처리 근거가 필요하다. 외부 계약 금액을3,000원 같은 예시 값으로 초기화하지 않는다. 이번 시스템은 수납 요청/증빙 원장을 만들지만 실제 운송사 수납·계좌 지급 완료를 임의로 생성하지 않는다.

## 3. 공통 주문 계산 Module

`GoodsTransactionQuote` Module이 가격·운임·혜택 계산과 기대값 대조를 숨긴다. UI·선물·정기배송이 각자 금액을 계산하지 않는다. PostgreSQL 내부의 pure calculator와 잠금/스냅샷 Adapter를 분리하고, TS는 strict DTO 검증·표시·독립 검산을 맡는다.

```text
입력: actor + 주문 목적 + 상품/옵션/수량/직접입력 정체성
      + 주소 확정 상태 + 선/착불 선택 + 보유 쿠폰 ID + 사용할 적립금
출력: 계산 버전/시각/다음 변경 시각 + 줄별 가격/복수 할인
      + 출고지별 선결제·착불 운임/지역 판정
      + 쿠폰·적립금 한도/이유 + 지금 결제액 + 별도 지급액 + 적용 조건 버전
```

| 금액 | 제안 필드와 의미 |
| --- | --- |
| 기간 할인 후 상품 소계 S | `sum(qty × order_items.unit_price)`; 기존 `unit_price` 의미 보존 |
| 복수구매 할인 V | 새 `orders.volume_discount_total`, 품목 `volume_unit_discount/volume_discount_total` 및 불변 조건 스냅샷 |
| 쿠폰 C | 기존 `orders.discount_total` 유지. 대상 조건·최소금액·할인 기준을 N=S−V로 전환하고 `terms_snapshot`에 계산 버전/대상 순액 기록 |
| 선결제 운임 H | 기존 `orders.shipping_fee`·`order_shipments.shipping_fee`를 계속 PG/무통장 결제에 포함된 운임으로 유지 |
| 착불 운임 D | 새 `orders.shipping_collect_total`·배송 건 `shipping_collect_fee`. 결제/PG 매출/적립 기준에 합치지 않음 |
| 적립금 R | 기존 `orders.store_credit_total`. 한도 `min(정책상한, 잔액, N−C, N+H−C−1000)` |
| 지금 결제액 T | **`orders.total = S − V + H − C − R`**, 최소1,000원. payment attempt/provider confirm/refund는 T만 사용 |
| 고객 부담 총액 | T+D. 화면에는 두 지급 시점과 수납 주체를 분리하고 합계임을 표시 |

쿠폰의 실제 할인은 기존처럼 `min(대상 산식 할인, max(0,N+H−1000))`다. 착불 D로 최소 PG 결제액이나 쿠폰/적립금 사용 한도를 늘리지 않는다. 대상 쿠폰이 무효·조건 미달이면 기존과 같이 주문을 거절하며 조용히 쿠폰을 빼지 않는다. 상품 전체가 복수 할인으로0원이고 선결제 운임도1,000원 미만이면 별도 무결제 주문 계약 없이 처리하지 않는다.

금액은 정수 원화로 계산한다. 곱셈/합산은 overflow가 나지 않는 numeric 또는 검증된 bigint 중간값을 사용하고, 저장 전 DB·JS 안전정수·결제수단의 실제 상한을 모두 확인한다. 입력 상한만 믿고 여러 줄 합계를 먼저 bigint로 넘치게 만들지 않는다.

미리보기와 주문 생성은 동일 계산 함수를 사용하되 주문 생성은 저장된 최신 조건을 잠금 아래 다시 읽는다. 클라이언트가 보낸 금액을 결제 기준으로 받지 않는다. 새 final quote 기대값에는 카트 정체성뿐 아니라 주소·선/착불 선택·가격/할인/운임 버전·정수 합계를 포함한다. 서버 재계산과 다르면 `transaction_quote_changed`로 새 견적을 보여주고 다시 확인받는다. 고객이 할인/착불을 확인한 상태에서 조용히 더 큰 금액으로 주문하지 않는다.

주소 미정은 `unresolved` 상태다.0원 배송비로 치환하지 않는다. 선물 수신 주소 입력 전/정기배송 회차 생성 전의 견적도 같은 Interface를 사용하되 실제 결제 가능 시점은 각 도메인의 승인 계약이 결정한다. 다른 사용자의 주소·쿠폰·적립금 권한을 계산 함수가 대리 허용하지 않는다.

## 4. 코드·DB 변경 선정과 잠금

공통 계산을 바꿀 때 다음 경로를 한 단위로 검증한다. 기존 함수명/ABI를 무조건 복제하지 않고 새 정규화 Module로 위임한다. 관련 없는 결제 provider 구현이나 재고 확정 경로는 복제하지 않는다.

| --- | --- |

| `quote_goods_sales`·`quote_goods_shipping` 및 주소별 wrappers | 공통 가격/운임 계산1회, `volumeDiscount`, 선/착불 금액, 정책 버전/시간 경계와 미확정 사유 반환. 예약 공급·구매수량·판매기간 가드 유지 |

| `goods_order_snapshot_matches` | V를 빼고 H만 더한 T를 검증. 품목 할인/운임 구성요소 합계와 `orders`/배송 건 일치도 검사. D를 PG 기대액에 합치면 안 됨 |

| 결제 prepare/claim/finalizer·무통장 안내 | 주문 T와 payment amount의 기존 일치 검사 사용. 가격/운임 조건을 결제 승인 때 현재 값으로 다시 산정하지 않음 |
| 할인·착불 감사/원장 | 새 private 버전/적용/수납 이력. UI 직접 DML 금지, 조회 DTO에 필요한 금액·상태만 노출 |

잠금 순서는 현행 사용자 advisory→카트 advisory→주문→정렬한 goods→정렬한 variants/cart·IP·예약 공급→정렬한 출고지/운임 정책→보유 쿠폰→쿠폰 정의→적립금 정책 SHARE→계정→lot 순서를 기반으로 한다. 새 복수 할인/운임 writer는 해당 부모 goods를 먼저 잠근 뒤 버전 행을 잠근다. 배송 템플릿 적용은 기존 요청 UUID→템플릿 SHARE→goods ID순→출고지 SHARE를 유지한다. 새 writer가 출고지를 잡고 goods를 역순으로 잠그지 않도록 전체 호출 그래프와 경합 테스트로 검증한다.

정기배송/선물의 별도 cycle/intent 잠금은 **재사용하는 주문 lock 안팎의 어느 위치인지 공통 계약으로 고정**한다. 계정/lot을 잠근 뒤 다른 주문을 잡는 역방향 경로를 만들지 않는다. 현재 순서를 부분적으로 바꾸는 대신 각 creator가 같은 순서를 따라야 한다. 일관된 잠금 순서가 교착 방지의 기본이라는 점은 [PostgreSQL 공식 문서](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-DEADLOCKS)와 같다.

새 public 함수는 PUBLIC/anon/authenticated/service_role 모두에서 execute를 회수하고 목적별 호출자만 허용한다. 내부 금전 함수는 private, `search_path=''`, 직접 table DML 봉인, RLS·운영 capability 재검사, operator contract registry 등록을 포함한다. Supabase의 [Data API 노출 변경](https://supabase.com/changelog)은 권한/노출을 자동으로 열어 주는 근거가 아니므로 기존 배포 방식의 노출·ACL readback도 검증한다.

## 5. 원장 배분과 전체 취소·반품

주문 생성 시 품목의 S_i/V_i/N_i를 고정하고 쿠폰은 대상 N_i에, 적립금은 쿠폰 후 N_i에 정수 최대나머지 방식으로 배분한다. 동률 ID순 규칙은 [현재 거래확정 배분](../../../lib/admin/settled-export.ts)을 재사용한다. 새 거래는 `private.order_price_allocations`에 계산 버전·품목 금액·운임 구성요소 ID를 고정한다. 과거 거래는 기존 스냅샷 계산을 유지하고 누락 데이터를 현재 정책으로 보충하지 않는다.

불변식은 `ΣV_i=V`, `ΣC_i=C`, `ΣR_i=R`, `ΣH_component=H`, `ΣD_component=D`, `Σ(N_i−C_i−R_i)+H=T`다. 기간 할인/복수 할인/쿠폰/적립금/운임은 서로 다른 필드로 보존하며 동일 금액을 두 차례 차감하지 않는다. 기존 lot별 적립금 allocation을 품목 배분 원장으로 대체하지 않는다.

| 상황 | 온라인 결제·혜택·재고 | 착불 별도 지급 |
| --- | --- | --- |
| 미결제 만료/취소 | 기존 pending 종결·공급/쿠폰/적립금 선점1회 복원 | 미수납 운임 의무만 void. 환급액을 만들지 않음 |
| 결제 후 출고 전 전체취소 | provider 증거/무통장 실제 환급 근거 후 T 전액, 기존 혜택·공급 복원 | 수납 없음이면 void, 수납 증빙이 있으면 별도 반환 검토 |
| 출고 후 전체반품 | 기존 전체 품목·회수/입고 조건을 통과한 뒤 T 전액. 현재 비용 안내/운영 비용 기록을 몰래 환불 차감으로 연결하지 않음 | 원래 D와 실제 수납 증빙·부담 주체·반환 담당을 따로 유지. PG 환급에 얹지 않음 |
| 교환 | 원래 결제·할인·운임 스냅샷 유지. 현재 재출고 계약 사용 | 새 착불 청구를 자동 재생성하지 않음. 추가 회수/재출고 비용은 승인된 별도 운영 계약 필요 |
| 중복/불확실한 외부 취소 | 기존 pending/unknown/needs_review와 멱등 finalizer 유지 | 고객의 ‘지급했다’ 신호만으로 정산 완료 처리하지 않음 |

착불 원장은 `planned → collected / void`, 필요 시 `refund_review → refunded`와 이력 이벤트로 분리한다. `collected/refunded`에는 금액·수납/반환 주체·외부 거래 참조·증빙·담당자·시각·operation UUID가 필요하다. 수납 증빙 금액이 D와 다르면 불일치 검토 상태로 두며 임의로 주문 금액을 바꾸지 않는다. 이는 사실 기록이며 계좌 이체나 운송사 취소 API를 실행했다는 뜻이 아니다. 기록 정정은 기존 행 덮어쓰기 대신 반대 이벤트+정정 근거를 남긴다.

전체 주문의 온라인 환불 완료와 외부 착불 반환 완료는 서로 다른 상태다. `orders.status='canceled'`만 보고 COD도 환급됐다고 표시하지 않는다. 수납/환급 증빙 없이 미수납으로 추정하지 않으며, 외부 비용 부담·영수증/세무 귀속은 확인한 계약을 설정으로 보존한다. 아직 확인하지 않은 택배사 규칙이나 법률 결론을 이 문서가 대신 확정하지 않는다.

토스 공식 API의 Payment는 최초 결제액·취소 가능 잔액을 구별하고, 취소 요청에 금액을 생략하면 해당 결제를 전액 취소한다. 따라서 카드로 받은 T와 운송사가 별도로 받은 D를 하나의 PG 환급액으로 다룰 근거가 없다. [토스 결제/취소 API](https://docs.tosspayments.com/reference#결제-취소). 외부 운임 반환 방식·수납 가능 계정·실제 API는 확인 전 미확인으로 둔다.

## 7. 호환성과 검증 계획

배포는 새 private 버전/원장과0원·OFF 기본값→v2 quote/creator 및 스냅샷 guard→소비자 DTO/UI/파일→관리 설정 순으로 준비한다. 모든 공개/주문 소비자가 새 필드를 이해하기 전에는 신규 정책 활성화를 막는다. 기존 주문은 `calculation_version=1`, V=0/D=0으로 읽기 호환하되 역사 행의 금액·payment·shipment를 재계산하지 않는다. 구형 caller는 신규 활성 정책 상품에 legacy 계산으로 주문을 만들지 못하도록 명시 `checkout_contract_upgrade_required`로 막고, 신규 정책 없는 주문은 기존 ABI 그대로 처리한다.

신규 상품/정책과 혼합 주문을 완전히 지원하는 것이 완료 범위다. 단순 설정 UI 저장이나 v2 견적만 통과한 상태는 완료가 아니다. 회귀 범위는 다음과 같다.

- 산식: 동일 상품 다른 옵션/직접입력 줄 합산, 다른 상품 분리, 정상가/기간가/고정/퍼센트, 기간 경계·중단·새 버전,0원/최대정수/합계 overflow·1원 잔여, 쿠폰 대상/첫구매/만료/최소금액, 적립금 lot/정책·1,000원 하한.
- 운임: Q=1/N/N+1/2N/2N+1,2·3구간 모든 경계, 같은 상품 줄 분할 불변, 혼합 무료/정책/개별/수량/구간·출고지,0원 정책 상품, 지역 per_shipment/per_good/면제/만료/주소 충돌, 선/착불/선택형 혼합과 총운임 불변.
- 경합: 할인/배송 설정 변경 vs quote/create, 동일 checkout key/다른 payload, 같은 카트 두 창·동일 쿠폰·lot·재고/예약 한도, 템플릿100건 적용 vs checkout, 출고지/택배사/지역 정책 변경 vs create, 기간 경계 대기, 전체 취소 vs 수납 증빙·교환/발송·중복 finalizer.
- 환급: 미결제/카드/무통장, 미수납 COD/실제 수납 증빙/금액 불일치/반환 검토, 전체 반품/회수 완료, 사용된 원적립의 회수, 원장/할인 스냅샷·수량/재고1회 복원, PG T를 넘는 환급 거부.
- 파일/운영: 구 v3~v7 생략 보존, 신규 시트 왕복·명시 해제·충돌/실패 재시도, 복사 OFF, 템플릿 비전파/명시 필드 적용/100건 원자성, 거래확정 정수 배분·과거 영수증 재다운로드 불변, 창고 고정 열 계약.
- 실제 브라우저: 관리자→공개 상세→카트→주소/선택→견적 변경 재확인→주문 생성/테스트 결제→내역·관리자·파일→전체 취소/반품 readback.390px·키보드·오프라인/늦은 응답·계정 변경 포함. PG/운송사 실제 LIVE 호출·운영 DB/배포는 별도 승인 경계를 유지한다.

## 8. 독립 계산 예시와 미결정 접점

예시 값은 테스트용이며 운영 기본값이 아니다. A: 정상가10,000원·기간가8,000원×3,3개 이상 각1,000원 할인. B: 정상/판매가5,000원×1. A는2개마다3,000원 선결제, B는 개별2,000원 착불, 같은 출고지의 지역비1,000원/per_shipment를 기본료6,000:2,000에 배분한다. A 대상10% 쿠폰과 적립금2,000원을 사용한다.

| 항목 | 계산 |
| --- | --- |
| S / V / N | 29,000 / 3,000 / 26,000원 |
| 기본 운임 | A6,000 + B2,000 =8,000원 |
| 지역비 배분 | A750 + B250 =1,000원 |
| H / D | 선결제6,750 / 착불2,250원 |
| 쿠폰 / 적립금 | A 순상품21,000×10%=2,100 / 2,000원 |
| T / 별도 지급 포함 | 26,000+6,750−2,100−2,000=28,650 / 30,900원 |
| 품목 적립금 배분 | A1,582 / B418원; 상품 실결제17,318+4,582=21,900원, +H6,750=T28,650원 |
| 전체 온라인 환급 | T28,650원만 PG에 요청. D2,250원의 수납/반환은 별도 증빙 상태 |

공통 설계에서 고정할 접점은 ①선물 수신 주소 확정과 결제 시점, ②정기배송 각 회차의 가격/쿠폰/적립금 동의·재고 선점 시점, ③COD 계약 주체/수납 증빙과 창고 인계 방식이다. 여기의 할인 우선순위·무료 기준·혼합 운임 배분은 공통 주문 Interface에 구현한 계약이다. 외부 계약 확인을 요구하는 항목을 코드의 기본 ON 값으로 대신하지 않는다.
