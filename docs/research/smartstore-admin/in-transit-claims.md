# 배송 중 반품·교환 접수

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-16 사용자 승인에 따라 실제 발송된 배송 중 주문의 전체 반품·교환 접수를 고객·판매자·선물 참여자 경로에 연결했다. 부분취소/부분반품, 운송사 API 자동화는 추가하지 않았다.

## 처리 경계

- 주문의 모든 품목·수량이 배송 건에 정확히 배정되어 있고 실제 발송 근거가 있어야 배송 중 접수를 허용한다. 미출고 상품이 함께 있어도 주문 전체를 대상으로 하며, 배정 누락·초과 수량과 이전 교환품의 수령 미확인은 차단한다.
- 접수 시 주문·결제 상태와 금액은 유지한다. 승인 후 출고지별 회수 기록을 만들며 모든 실물을 회수/창고 보관 확인하기 전에는 환불과 교환 재출고를 막는다. 아직 출고하지 않은 배송 건의 발송은 진행 중인 클레임이 차단한다.
- 이미 발송된 택배·퀵의 실제 도착 기록은 클레임 접수와 함께 남길 수 있다. 배송완료 기록은 반송 입고나 환급 승인을 대신하지 않는다. 자동 구매확정도 진행 중인 클레임을 건너뛴다.
- 배송 중 회송 후 교환품이 고객에게 처음 공급되는 경우, 검증된 교환품 배송완료가 주문의 최초 공급일이 된다. 원래 배송 건의 상태·도착 시각을 만들어 넣지 않는다. 기존에 공급된 주문의 배송일과 신청 기한은 연장하지 않는다. 교환품 배송완료가 원품목 배정 수량 누락을 우회하지 못하도록 별도 검사한다.
- 신청 기한·전액 환급·반송비 부담·보관 기준의 기존 계약은 유지한다. 고객 화면과 판매자 가이드·절차 고지를 함께 갱신했다. 코드 변경은 배포 전이며 운영 정책 고지·시행 일정이나 외부 운영을 완료했다는 뜻은 아니다.

## 검증

- `in_transit_claim_intake.sql`: 고객 배송 중 접수, 배송중+미출고 혼합 주문, 회수 필요 상태·금액 보존, 새 발송 차단, 부분 회수 환불 차단, 전부 회수 후 전액 환불 finalizer, 판매자 교환 접수, 회수 전 재출고 차단, 회수 후 교환과 최초 공급 기록, 클레임 중 실제 도착 기록, 배정 누락과 ACL을 검증했다. 결제 공급자는 호출하지 않았다.
- 기존 `order_claim_reshipment_delivery.sql`도 현재 구성 모드에 맞게 합성 담당자 두 명의 `primary` 권한만 추가한 격리 하네스에서 통과했다. 기존 금액·주문 배송일·품목/수량·민감한 증거 비공개·재실행·이전 교환 수령·원기한 보존을 확인했다. 저장소의 기존 테스트 본문은 변경하지 않았다.
- `in_transit_claim_concurrency.py`: 8주문에서 도착 기록 8개와 중복 접수 16개를 동시에 실행했다. 최종 실행 `741381b5`에서 주문 8건 배송완료, 요청 8개, 회수 필요 8개, 환불 생성 0개를 확인했다.
- 관련 앱 9파일 188개, 타입 검사와 대상 ESLint를 통과했다. 전체 어드민 빌드와 일괄 최종 검증은 별도 진행 중이다.
- 실제 Chrome 고객 화면에서 배송 중 반품을 접수했다. `be160000-0000-4001-8000-000000000001`의 재조회는 배송중/결제완료 유지, `requested`, 출고지 회수 필요, 환불 0개다. 판매자도 배송 중 주문 `be160000-0000-4001-8000-000000000002`를 교환으로 대리 접수했고, 담당자·고객 요청 시각·실제 접수 시각을 구분한 결과를 확인했다. 교환 요청 `ed97c8ed-3222-4778-a764-e916cbbf2525`도 배송중/결제완료 유지·환불 0개·회수 필요 상태다. PC·390px 증거는 `output/smartstore-full-admin-20261016/`에 보존한다.

교환 재출고 SQL 검사는 현재 연락처 버전 결속 함수가 호출하는 봉인된 실물 엔진을 직접 검사했다. 연락처 변경·재출고 주소 결속은 기존 contact-v2 검사와 이어지는 전체 주소 변경 작업에서 별도로 검증한다.
