# 반품·교환 유형 전환 계약과 검증

migration 파일 경로는 [배포 매핑](../../../supabase/manifests/admin-rollout-migration-map.json)을 반영했다. 아래 과거 검증·적용 기록은 당시 원본 DRAFT 기준이며 이번 운영 배포의 성공을 뜻하지 않는다.

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-13. 주문 전체 단위의 반품↔교환 전환을 구현하고 격리 OWN/FRESH DB와 실제 Chrome에서 검증했다. 운영 배포·원본 네이버 변경·PG 호출·송금은 수행하지 않았다.

## 원본 확인

[네이버 공식 반품→교환 도움말](https://help.sell.smartstore.naver.com/faq/content.help?faqId=3833)은 구매자 사전 동의와 반품완료 전 전환을 안내한다. [교환→반품 도움말](https://help.sell.smartstore.naver.com/faq/content.help?faqId=3872)은 교환품 재배송 전으로 제한한다. 원본은 별도 배송비 결제 여부와 첨부사진 삭제 규칙도 안내한다. ICONS의 운영 확인액을 결제 원장으로 취급하지 않으며 네이버 비용 결제/취소를 복제한 것으로 표시하지 않는다. 원본 전환은 제출하지 않았다. 원본 사진 삭제 규칙을 적용해 기존 요청 근거를 지우지 않는다.

## 확정한 범위

- `sales.manage` 담당자가 고객과 유형·배송비 처리에 합의한 근거를 2~500자로 남기고 명시적으로 확인한다. 취소는 대상이 아니며 부분 품목/금액 입력을 받지 않는다.
- 접수·검토·수거중·입고완료와 그 단계의 보류만 전환한다. 취소 실행 또는 환불 원장, 재출고 시각/송장/품목 원장, 처리중·결제확인필요·종결 상태는 차단한다.
- 원래 접수일·입고일·수거 수량/주소/담당자/근거, 보류의 실효 단계·사유·시각, 요청 사유, 운영 확인액을 유지한다. SLA 기산점을 새 전환 시각으로 덮어쓰지 않는다. 주문·결제·재고를 변경하지 않는다.
- 교환→반품에서 양수 무통장 주문은 유효한 환불계좌가 필요하다. 기존 미파기 계좌는 마스킹하여 확인하거나 세 항목을 모두 새로 입력한다. 계좌 원문은 기존 `private.claim_refund_accounts` 한 곳에만 저장한다. 요청 receipt에는 계좌의 SHA-256만 보관하며 공개 감사/고객 이력에 계좌나 합의문 원문을 복제하지 않는다.
- 반품→교환에서 사용하지 않는 계좌는 30일 후 파기를 예약한다. 그 전에 다시 반품으로 전환하면 현재 유효한 계좌를 확인하고 파기 예약을 해제한다. 이미 파기된 계좌는 다시 입력해야 한다. 계좌 행 잠금과 조건 재검사를 통해 파기와 재전환이 겹쳐도 빈 계좌를 유효하다고 처리하지 않는다.
- `private.order_claim_type_changes`에 원래/다음 유형, actor, 합의, 시각, 요청 버전, operation을 보존한다. 원 actor의 같은 operation·본문만 같은 receipt를 돌려준다. 권한 회수 후에는 신규 실행과 운영자 결과 조회를 차단한다.
- actor→operation→주문→배송건→claim→회수건→계좌 순서와 `claim_revision` CAS로 다른 담당자·철회·수거·환급/재출고 처리를 직렬화한다. 저장 응답이 유실되면 최초 본문을 고정하고 재조회/동일 재시도를 사용한다. 버전 충돌은 입력을 보존한 채 새 문맥과 새 동의를 요구한다.
- 관리자 화면은 저장 후 현재 유형의 상세로 이동하며 기존 유형의 링크도 현재 유형으로 연결한다. 고객 주문 상세에는 주문 소유자를 확인한 유형·시각 이력을 표시하고 내부 합의문·담당자·계좌는 반환하지 않는다.

## 실행 검증

`20261020085259_order_claim_type_conversion.sql`을 트랜잭션에서 검증한 뒤 OWN/FRESH에 각각 한 번 적용했다. 양쪽 migration ledger의 SQL SHA-256이 저장소와 일치한다. 독립 에이전트의 현재 환불/재출고/계좌 파기 잠금 검토에서도 적용 차단 사항이 없었다.

- SQL: 동의·권한·취소/종결/금전/재출고 차단, 동일 operation 재생·다른 본문/계좌 차단, CAS, 기존 접수/수거/보류/운영액 보존, 계좌 재사용·파기·재입력, 고객 소유권/필드 제한과 명시적 execute 봉인 통과.
- 실제 잠금 17개: 같은 operation, 두 actor, 다른 본문, 저장 중 조회, 검토/철회/수거/환급 접수/재출고의 양방향 경합, 계좌 파기의 양방향 경합, 역할 회수. 수락된 10개 receipt와 감사의 중복 없음, 주문 상태·금액·재고 보존을 확인했다. 테스트는 선택된 로컬 DB의 별도 복제본에서 실행하고 복제본을 정리했다.
- 앱: 신규 모델/서버 액션/클라이언트 8개 및 관련 73개 테스트, 전체 TypeScript와 대상 ESLint 통과. 최초 본문 동결, 같은 렌더의 중복 제출, 다른 주문 receipt 거절, CAS 후 입력 보존과 동의 재확인을 포함한다.
- 실제 UI: PC에서 입고완료 반품 C00110을 교환으로, 390px에서 보류 중인 무통장 교환 C00111을 계좌와 함께 반품으로 저장했다. 각각 변경·감사·인앱 알림 1개, 원래 주문 배송완료/13,000원/배송비 3,000원, 재고 100개를 유지했다. 환불·취소 실행은 0이다. C00110의 기존 회수 1건/입고시각, C00111의 원래 보류 단계/사유가 유지됐다.
- 고객 PC/390px에서 보류·유형·원래 접수시각과 전환 이력을 재조회했다. 임시 화면 크기를 해제하고 고객 검증 탭을 닫았으며 localhost의 기존 부매니저 로그인을 복원했다. 번역 확장프로그램의 HTML 속성 추가로 발생한 hydration 경고는 애플리케이션 오류와 구분했다.

증거는 `output/smartstore-reference-20261013/verification-claim-conversion/manifest.json`과 `db-readback.json`이다. 최종 PNG 4개는 직접 시각 검수했으며 하단 버튼 일부가 가려진 중간 캡처와 간격 조정 전 캡처 2개는 승인 증거에서 제외했다. CI 실행 항목을 추가했지만 원격 CI·운영 배포가 완료됐다는 의미는 아니다.
