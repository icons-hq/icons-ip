# 전체 주소 변경과 회수 방법·송장 정정

migration 파일 경로는 [배포 매핑](../../../supabase/manifests/admin-rollout-migration-map.json)을 반영했다. 아래 과거 검증·적용 기록은 당시 원본 DRAFT 기준이며 이번 운영 배포의 성공을 뜻하지 않는다.

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-16. [전체 어드민 후속](full-admin-implementation-20261016.md)의 확정 정책에 따라 기존 암호화 연락처 정정 기능을 확장했다. 운영 배포·운송사 접수는 실행하지 않았다.

## 현재 계약

- 회수 착수 전 회수지, 재출고 전 교환 수령지의 이름·전화·상세주소·우편번호·기본 주소를 고객 확인과 근거로 정정한다. 원주문 주소·최초 대리 접수·창고 반송 증거는 보존한다.
- 우편번호·기본 주소를 바꾸면 각 배송 건의 보존된 지역 요금 정책으로 이전/새 주소를 비교한다. 여러 출고지 간 증감을 상계하지 않는다. 차액, 배송 불가·수동 심사 지역, 요금 근거가 없는 주문은 위치 변경을 차단한다. 기존 이름·전화·상세주소 정정에는 새 지역 견적을 요구하지 않는다. 원주문 금액·배송비를 다시 계산하거나 청구하지 않는다.
- AES-GCM 주소 계획·이전/이후 이력, 출처와 claim revision, 현재 사용자·실제 세션·권한·계정 fence, 요청 HMAC·봉인·보존/파기는 기존 계약을 유지한다. 이전 3개 필드 요청의 HMAC 형식도 그대로 재시도할 수 있다. 새 주소 비교값은 서비스 RPC의 일시 입력이며 평문 계획·감사 기록으로 저장하지 않는다.
- 회수 방법·택배사·송장은 `claim_collection_plans`와 별도 `claim_collection_events`에 정정한다. 최초 접수 기록을 덮어쓰지 않는다. 방법은 접수 후 수거 협의/판매자 별도 수거 예정/구매자 이미 발송이며, 발송에는 현재 택배사와 송장을 요구한다. 변경 근거에 개인정보를 입력하지 않도록 안내한다.
- 계획 revision과 claim revision을 함께 검사한다. 중복 요청은 같은 결과를 반환하고, 실제 클레임 진행·회수와 같은 주문/배송/claim 잠금 순서로 직렬화한다. 시작된 수거를 미요청으로 되돌리지 못하며 실제 구매자 발송 이력을 지워 철회 제한을 우회하지 못한다. 정정만으로 실제 입고·환불·재출고 상태는 바뀌지 않는다.
- 구매자는 자기 회수 안내를 조회한다. 내부 정정 근거·감사 이력은 노출하지 않고, 선물 회수 정보는 수령인에게만 공개한다. 선물 발신자에게는 수령인의 회수 송장을 노출하지 않는다.
- 운송사 자동 접수·운송장 발급·자동 추적은 제외한다. 이 화면에 기록한 송장은 기존 창고/CS 절차로 별도 확인해야 한다.

## 검증

- 격리 로컬에 `20261020085441_claim_full_address_changes.sql`, `20261020085443_claim_collection_corrections.sql`, `20261020085444_claim_collection_carrier_labels.sql`을 적용했다. 이전 마이그레이션을 수정하지 않았다.
- `supabase/tests/claim_full_address_collection.sql`: 같은 요금 주소 저장, 원주문 보존, 차액/근거 없음 차단, 기존 연락처 정정, 중복/CAS, 수거 시작 후 주소·철회 제한, 입고/환불 미발생, 구매자·타인·선물 발신자/수령인·권한·ACL을 검사했다.
- 기존 `supabase/tests/order_claim_contact.sql`의 암호화 envelope·멱등·보존·권한·선물·최종 재출고 회귀 검사를 통과했다.
- `supabase/tests/claim_collection_concurrency.py`: 같은 요청 12개 → 이벤트 1개, 같은 버전의 서로 다른 정정 8개 → 성공 1개/충돌 7개. 최종 2개 이벤트·revision 2, 입고 기록 없음.
- 실제 Chrome 합성 주문에서 요금 근거 없음 차단 → 미처리 요청 봉인 → 합성 지역 요금 설정 후 우편번호/기본·상세주소 저장 → 암호화 이력 재조회 → 회수 방식·송장 저장 → 주소 수정 잠금 확인을 수행했다. 최초 주문 우편번호 12345를 보존하고 새 계획은 45678이며, DB의 계획·이력에 새 평문 주소가 저장되지 않았음을 확인했다.
- 실제 구매자 PC 1440px·모바일 390px에서 한진택배 송장과 변경된 회수 주소를 재조회했다. 내부 정정/합의 근거는 숨겨지고 가로 넘침은 없었다. 레지스트리 택배사 라벨을 사용하며 이전 저장 결과의 형식도 읽을 수 있다.
- 관련 앱 검사 10개 파일 293개를 통과했고, 별도 새 택배사 라벨·모델 검사와 타입/ESLint 검사도 실행했다.
- 근거는 `output/smartstore-full-admin-20261016/`의 `contact-collection-browser-readback.json`, `collection-concurrency.json`, `claim_full_address_collection.log`, `order_claim_contact.log`, `local-full-address-*`, `local-collection-*`이다. 합성 요금·주소·송장은 운영 고객이나 실제 택배를 뜻하지 않는다.

전체 어드민의 남은 합포장·비용 청구와 다른 기능은 별도 진행 중이다. 이 문서의 완료 근거를 전체 동등성 또는 운영 활성화로 확대하지 않는다.
