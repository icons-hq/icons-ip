# 공개 상품문의·리뷰 단건 답변 저장

migration 파일 경로는 [배포 매핑](../../../supabase/manifests/admin-rollout-migration-map.json)을 반영했다. 아래 과거 검증·적용 기록은 당시 원본 DRAFT 기준이며 이번 운영 배포의 성공을 뜻하지 않는다.

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-14. 공개 상품문의와 리뷰 단건 답변은 원본을 읽은 시점의 버전과 저장 요청 UUID를 함께 보낸다. DB가 권한·버전·요청을 한 트랜잭션에서 검사해 오래된 답변의 덮어쓰기와 응답 유실 뒤 중복 알림을 막는다. [초안 복구](cs-editor-drafts.md)의 최신본 비교만으로는 막지 못하던 확인→저장 사이 경합을 보완했다.

## 원본 버전

`product_questions.reply_source_revision`과 `reviews.reply_source_revision`은 bigint이며 API에서는 정밀도 손실이 없는 문자열로 전달한다. INSERT 시 0, 관련 값이 실제 달라진 UPDATE에서만 1 증가한다. 호출자가 임의로 revision을 지정해도 trigger가 계산값으로 대체한다.

| 표면 | 버전을 올리는 값 | 버전을 올리지 않는 값 |
| --- | --- | --- |
| 상품문의 | 고객 원문, 운영자 답변, 공개/비노출 | 작성·답변 시각, 작성자 메타 |
| 리뷰 | 고객 원문, 별점, 첨부 경로, 운영자 답글, 공개/비노출 | 단순 시각·감사 메타, 별도 BEST 선정 원장 |

내용을 바꿨다가 원래 값으로 돌려도 버전은 두 번 증가한다. BEST 메타의 행 잠금을 유지한 동안 답글 저장이 독립적으로 완료되는 것을 실제 세션에서 확인했다. 원문이 삭제되면 새 저장은 not-found다. 삭제 전에 확정된 동일 요청을 다시 확인하는 것은 원래 영수증만 반환하며 원문을 재생성하지 않는다.

## 저장과 재시도

`admin_save_cs_reply(operationId, actorId, surface, targetId, body, expectedRevision)`가 다음 순서로 확정한다.

1. 기존 `cs.manage` 권한 잠금과 현재 계정 일치를 검사한다.
2. 작업 UUID 잠금을 획득하고 기존 영수증의 계정·표면·대상·정규화 문구·기준 버전을 대조한다. 다른 요청에 사용된 UUID는 거절한다.
3. 대상 행을 잠그고 revision을 비교한다. **동일 문구라도 오래된 버전이면 먼저 충돌로 거절한다.**
4. 문구가 달라질 때 기존 내부 writer를 실행해 답변·감사·알림을 함께 확정하고 private 영수증을 기록한다. 현재 버전의 동일 문구는 `changed=false` 영수증만 기록하며 감사·알림·원본 버전을 바꾸지 않는다.

기존 상품문의의 답변 수정 알림 재표시와 리뷰의 최초 답글 알림 dedupe는 유지한다. 예전 `admin_answer_product_question(uuid,text)`와 `admin_reply_to_review(uuid,text)`의 본문은 보존하되 public/anon/authenticated/service_role의 직접 EXECUTE를 회수했다. 새 writer와 기존 일괄 답글의 SECURITY DEFINER owner에만 필요한 내부 실행 권한을 남겼다. 일괄 답글은 기존 timestamp/status CAS와 batch 영수증 계약을 계속 사용한다.

## 편집기와 보관

상세를 열면 새 context RPC에서 현재 원문·답변·상태·버전을 함께 읽는다. 리뷰의 별점과 첨부 경로도 같은 context를 사용한다. 읽기가 끝나기 전에는 답변 편집과 저장을 잠근다. 기존 형식의 초안은 최신 원문과 비교하고 명시적으로 확인해야 새 버전에 연결된다.

전송 전에 operation UUID·계정·대상·문구·revision을 `sessionStorage`에 고정한다. 저장소가 막혔거나 크기 한도를 넘겨 보관하지 못하면 RPC를 보내지 않는다. 충돌처럼 **최초 요청의 확정 실패**는 문구를 남기고 최신본 비교로 전환한다. 응답 유실이나 불일치 응답은 미확정 상태로 보존하며 편집·초안 버리기를 잠근다.

새로고침 후에도 명시 복구→**같은 요청으로 결과 확인**으로 이어간다. 조회 결과가 null이어도 첫 HTTP 요청이 아직 RPC에 들어오지 않았을 수 있으므로 실패로 단정하지 않는다. 같은 ID와 payload로 재시도하며, 이 복구 경로의 거절/충돌/연결 실패도 성공 영수증을 확인하기 전에는 pending을 풀지 않는다. 원문 조회가 실패해도 미확정 요청 자체는 복구해 영수증을 확인할 수 있다.

일반 초안은 24시간, 미확정 요청은 현재 계정·로그인 세션·탭 안에서 결과 확인까지 보관한다. 다른 편집기 scope의 sweep도 미확정 요청을 만료시키지 않는다. 로그아웃·계정/세션 변경과 탭 세션 종료는 기존 개인정보 정리 경계를 유지한다. 영수증으로 저장 성공을 복구한 액션도 관리자 목록과 상품 상세 캐시 갱신을 마쳐 최초 응답 유실로 갱신이 빠지는 경우를 보완한다.

## 조회 RPC의 트랜잭션 모드

권한 확인이 기존 `SELECT FOR SHARE` 잠금을 사용하므로 두 조회 RPC도 `VOLATILE` POST로 호출한다. `STABLE`로 선언하면 PostgREST는 POST도 READ ONLY로 실행한다는 [공식 계약](https://postgrest.org/en/stable/references/transactions.html)에 따라 HTTP 405/SQLSTATE 25006이 발생했다. psql의 일반 트랜잭션에서는 재현되지 않아 실제 API 검증에서 발견했다.

이미 적용된 `20261020085328_cs_single_reply_cas.sql`을 수정하지 않고 `20261020085329_cs_reply_read_transaction_mode.sql`에서 두 조회 함수의 volatility와 metadata만 보정했다. 이 보정 전후 함수 본문·owner·ACL과 무관한 기존 함수는 동일함을 확인했다.

## 검증과 적용 상태

- 본체 SHA-256: `7615b9e32c185f86ee1b8472953002c7dc21a436135b6275e0d43e0c9761ad8a`.
- 조회 보정 SHA-256: `6c8fb4418ec30af5eb039068a7e569df07880e9ed1dcbe749c3ad8d597dca73b`.
- 검토된 원문으로 disposable clone 검증 후 OWN/FRESH/59922에 적용했다. 59922는 303개 migration의 source/ledger가 일치하지만 앞선 별도 migration의 적용 순서 차이 때문에 전체 순차 실행 완료로 표시하지 않는다.
- 관련 Vitest 8개 파일·70개 테스트, 범위 ESLint, 전체 TypeScript를 통과했다. security advisor 경고와 이번 함수의 DB lint 문제는 0건이다. 전체 DB에는 기존 범위 밖 73함수·124건 진단이 남아 있다.
- SQL 기능·권한 coverage, 기존 상품문의/리뷰/일괄 답글 SQL 3종 회귀를 통과했다. 실제 두 세션 경합 19건은 서로 다른 운영자 저장, 중복 operation, stale same-body, 원문 수정·비노출·삭제, 메타만 변경, 권한 회수, 지연 원요청과 동일 재시도, BEST 독립성을 포함한다.
- 정상 부매니저 로그인으로 두 표면 context/영수증 조회 HTTP 200, 미인증 401, 물류매니저 및 다른 계정으로 묶은 요청 403을 확인했다.
- 실제 Chrome에서 상품문의의 최신 확인 뒤 다른 담당자 저장→충돌→문구 보존→명시 확인 후 저장을 확인했다. 리뷰는 작성 도중 원문·별점 변경을 반영해 충돌시키고 문구를 보존했다. 두 폼의 실패 뒤 textarea 값은 초기화되지 않았다.
- 리뷰 탭만 오프라인으로 전환해 저장 결과 미확인·입력/버리기 잠금을 확인했다. 온라인 복원→새로고침→명시 복구→같은 요청 재시도로 정상 저장했다. 임시 네트워크 설정은 복원했다.
- 합성 대상의 DB readback은 성공 영수증 5개와 대응 감사 5개, dedupe 알림 2개였다. 충돌 요청은 추가 감사/알림/영수증을 만들지 않았고, 복구한 리뷰 문구의 영수증은 정확히 1개였다. 공개 상품 상세 HTTP 200에 최종 상품문의·리뷰 답변이 모두 반영됐다.

합성 고객·주문·문의·리뷰·업무 알림은 검수 후 제거하고 성공 영수증과 감사 기록만 남겼다. 원문 삭제 후에도 정상 부매니저의 결과 조회 Server Action이 HTTP 200으로 기존 영수증을 반환하고 공개 캐시에서 검수 문구를 제거하는 것을 확인했다. 임시 브라우저 탭과 네트워크 설정은 정리했다. 새 점검 탭의 console error/warn은 0개였다.

검증 자료는 결과 디렉터리 (`output/smartstore-reference-20261014/cs-single-reply`)의 API·DB readback, 경합 로그, 단위/정적 검사와 화면 6개에 있다. 운영 환경·실제 고객 데이터 변경과 배포는 하지 않았다.
