# 쿠폰 발급 건별 조회 구현·검증

migration 파일 경로는 [배포 매핑](../../../supabase/manifests/admin-rollout-migration-map.json)을 반영했다. 아래 과거 검증·적용 기록은 당시 원본 DRAFT 기준이며 이번 운영 배포의 성공을 뜻하지 않는다.

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-14 승인된 최소 범위를 구현하고 격리 로컬 DB·실제 브라우저·다운로드 파일을 검증했다. 기존 발급 원장과 집계 산식에 건별 읽기 근거를 연결했다. 운영 DB 적용·배포는 실행하지 않았다.

## 원본 근거와 확인 한계

- 혜택 리포트 상단 (`output/smartstore-reference-20261012/store/32-benefit-report-top.jpg`)에는 혜택별 조회, 일/주/월 기간, 지급현황, 엑셀과 혜택이름을 눌러 지급 내역을 확인하는 안내가 있다.
- 하단 (`output/smartstore-reference-20261012/store/34-benefit-report-bottom.jpg`)은 조회 결과가 없는 상태다. 실제 행 클릭 이후의 발급 식별자·고객·상태 열과 파일 내용은 확인하지 못했다. 원본 manifest (`output/smartstore-reference-20261012/store/manifest.json`)의 두 캡처가 `accepted: true`이며 이번에 이미지를 다시 확인했다.
- 따라서 원본이 아래와 같은 발급 건별 화면을 제공한다고 단정하지 않는다. 지급 집계를 상세 근거와 연결한다는 원본의 목적과, 현재 ICONS의 발급수 검산 필요를 연결한 일반 기능이다. 아래 최소 열과 상태 이름은 ICONS 설계이며 원본의 열을 복제했다고 주장하지 않는다.

## 집계와 권한 기준

[기존 집계](../../../supabase/migrations/20261020085141_admin_benefit_report.sql)는 `user_coupons.issued_at`이 조회기간 안인 발급 원장을 완전히 집계한다. `cohortPaidUses`는 그 발급분 중 현재 `applied` 사용 원장과 매출 인정 주문 상태가 있는 수다. 발급일과 사용일은 다르며 결제 대기는 이 분자에 넣지 않는다.

[응답형](../../../lib/admin/benefit-report.ts)에 발급 행·전체 건수·현재 결제 사용 집계 건수·조회시각을 추가했다. [화면](../../../components/admin/screens/BenefitReportScreen.tsx)은 혜택이름의 기존 **사용 상세** 진입을 유지하고 발급수에서 **발급 상세**로 연결한다. [엑셀](../../../lib/admin/benefit-workbook.server.ts)은 발급 상세를 선택했을 때 같은 조건의 전체 발급 행을 새 시트에 추가한다. 사용하지 않은 발급분도 발급수와 사용률의 분모·분자 대조에 포함된다.

권한은 초기 migration의 단순 staff가 아니라 [현재 후속 정의](../../../supabase/migrations/20261020085215_operator_capability_guards.sql)의 `marketing.manage`를 따른다. 이 권한과 기존 화면 게이트를 새 읽기 경로에도 적용했다.

## 구현 계약

| 항목 | 범위 |
| --- | --- |
| 진입 | 혜택 리포트에서 쿠폰을 선택한 뒤 `사용 상세`·`발급 상세`로 전환한다. 기존 주소의 기본 화면은 사용 상세로 유지한다. |
| 모집단 | 같은 현재 쿠폰 검색·할인종류·대상 조건과 KST 발급일 범위, 최대366일을 사용한다. 사용일이 조회기간에 있는지는 발급 상세의 포함 조건이 아니다. |
| 표시 | 발급 ID, 쿠폰 ID, 발급일시(KST), `현재 결제 사용 집계 여부`만 반환한다. 마지막 값은 기존 `cohortPaidUses`와 같은 `exists` 판정이며 예/아니오로 표시한다. 아니오를 사용 가능·미사용·환불 완료로 바꿔 해석하지 않는다. |
| 정렬·페이지 | 발급일시 내림차순·발급 ID 오름차순으로 고정하고 50건씩 조회한다. 같은 응답에 전체 건수를 반환한다. 상세 전환과 조건 변경은 첫 페이지로 돌아가며 검색·기간·직전 비교 조건은 유지한다. |
| 조회 구현 | 기존 집계 RPC의 시그니처·산식을 유지하고 선택 쿠폰의 발급 행과 전체 건수를 반환하는 읽기 전용 RPC를 추가한다. 테이블·발급 정책은 바꾸지 않는다. `marketing.manage` 검사, PUBLIC/anon/authenticated/service_role execute 봉인 후 필요한 grant, 운영자 RPC 계약 등록을 함께 적용한다. |
| 엑셀 | 발급 상세 선택 시 같은 조건·같은 순서의 전체 발급 목록을 별도 시트로 기록한다. 10,000건을 넘으면 화면에 조건 축소 안내를 표시하고 링크를 숨긴다. 직접 API 호출도 잘린 파일 대신 `benefit_issuance_export_limit` 400 오류를 반환한다. 기존 요약·사용 상세·직전 비교와 `private, no-store`를 유지한다. |

고객 이름·연락처·회원 ID·주문 주소를 추가하지 않는다. 쿠폰 발급/회수, 대상 지정, 혜택 중복, 사용 자격 판정, 만료 정책, 적립금 성과, 전년 비교로 확장하지 않는다. 과거 시점의 사용 상태를 새로 추정하거나 저장하지 않는다.

상세의 행·전체 건수·현재 결제 사용 집계 건수는 한 읽기 응답의 같은 DB 스냅샷에서 계산한다. 별도 요청인 기존 요약과 새 상세 사이에 발급·취소가 발생할 수 있으므로 두 요청의 숫자가 언제나 원자적으로 같다고 보장하지 않는다. 이를 없애려고 발급/취소 원장을 잠그지는 않는다.

## 검증 기준

1. 발급 목록 전체 건수는 같은 쿠폰·조건의 발급수, `예` 건수는 기간 발급분의 현재 결제 사용수와 일치해야 한다. 기간 전 발급 후 기간 내 사용, 기간 내 발급 후 기간 밖 사용, 결제 대기·현재 결제 유지·복구를 구분한다.
2. KST 양끝·366일 제한·검색 특수문자·쿠폰 조건 불일치·0건·51건·1,001건·10,001건을 검증한다. 페이지와 파일이 1,000행 기본 상한에 잘리지 않아야 한다.
3. `marketing.manage` 보유·미보유·회수 후, anon·service_role 직접 실행의 권한 경계를 확인한다. 응답·파일에 추가 고객 개인정보가 없어야 한다.
4. 실제 PC/390px에서 상세 전환·페이지·조회 오류·재시도·이전 주소 호환을 확인한다. 실제 다운로드를 다시 열어 모든 발급 행·조건·개수와 DB 결과를 대조한다.

## 2026-10-14 검증 결과

- 신규 [읽기 RPC migration](../../../supabase/migrations/20261020085332_admin_benefit_issuances.sql)과 [SQL 계약 검사](../../../supabase/tests/admin_benefit_issuances.sql)는 검토 후 clone·OWN·FRESH·59922 격리 DB에서 통과했다. `marketing.manage` 역할별 허용·거부와 회수, 익명·service_role 직접 실행 거부, KST 경계·366일·특수문자·조건 불일치·정렬·페이지·1,001건·10,001건을 확인했다. 기존 집계 함수·권한·정책·migration 이력은 보존했다. 설정 완료된 OWN에서는 기존 global guard fixture를 바꾸지 않고 신규 계약과 coverage를 확인했다. 전체 guard는 다른 격리 대상에서 확인했다(DB 결과 (`output/coupon-issuance-read-detail-qa-20261014/named-targets-summary.json`)).
- 실제 Chrome의 기존 운영자 로그인에서 9장/현재 결제 사용 5장, 기간 밖 사용·결제 대기·복구·취소·결제 유지 상태를 DB와 대조했다. 51장 목록의 두 번째 페이지 1행과 검색 `%`·`_`·역슬래시, 할인종류·대상·주간·직전 비교·선택 쿠폰·발급 상세 보존을 확인했다. 조건 변경은 첫 페이지로 돌아가고 불일치는 0건으로 표시했다. 기존 `detail` 없는 주소의 사용 상세도 유지했다.
- 같은 환경에서 신규 RPC 실행 권한만 잠시 회수해 실제 오류 경계와 다시 시도를 확인한 뒤 함수 정의·소유자·ACL·등록 계약을 원상 복구했다. 0건을 오류로 대신 표시하지 않는다. PC와 390px에서 확인했으며 모바일 전환 종료 후 문서 380px/뷰포트390px로 가로 넘침 없이 표 내부 키보드 스크롤이 동작했다.
- 실제 다운로드 6개를 다시 열어 45,050셀을 검사했다. 기존 사용 상세, 발급 9·51·0·1,001·10,000행의 식별자·정렬·KST 날짜형·집계 여부·요약·일주월 추이·직전 비교·필터가 같은 조건의 authenticated DB 조회와 일치했다. 두 번째 페이지에서 내려받아도 51행 전체를 포함했다. 날짜형은 JS Date 정밀도인 밀리초까지 대조했다. 추가 고객 개인정보 열과 수식·오류 셀은 없었다(파일 대조 (`output/coupon-issuance-ui-qa-20261014/xlsx-verification.json`)).
- 10,001건에서는 안내를 표시하고, 하루 범위의 정확히 10,000건으로 줄이면 다운로드가 복구됐다. 직접 API 오류 페이지는 Chrome `ERR_BLOCKED_BY_CLIENT`로 본문을 읽지 못했으므로 실브라우저 400 응답 검증으로 기록하지 않는다. API의 400 상태·오류 코드·`private, no-store`는 자동 검사로 확인했다.
- ArtifactTool로 6개 파일을 독립적으로 가져와 오류 셀 0건을 확인하고 변경 시트 6장을 렌더링해 열·줄바꿈을 확인했다. 다만 렌더러가 `23:59:59.999`의 초를 `00`으로 표시하는 차이가 있어 날짜의 값 검증은 원본 XLSX를 읽는 openpyxl/DB 대조를 근거로 삼았다. 원본 셀은 `2026-10-01 23:59:59.999`와 날짜형 서식을 유지한다. 네이티브 Excel 화면은 검증하지 않았다.
- 관련 코드·화면·API·표면 계약 39개 검사와 범위 ESLint·타입 검사를 통과했다. 일회성 로컬 UI fixture는 제거 후 기존 쿠폰·발급·사용·주문 원장 지문과 사용자 수를 재확인했다(정리 결과 (`output/coupon-issuance-ui-qa-20261014/cleanup-result.json`)). 전체 앱의 최신 통합 build는 상위 작업의 최종 결과를 따른다.

원본 실제 발급 상세 열과 파일은 여전히 미확인이다. 발급·대상·사용 자격·만료·중복 쿠폰 정책은 바꾸지 않았다. [스토어 후속 분류](store-parity.md#남은-후속-범위)의 발급 건별 조회 한 항목을 완료한 것이며 다른 후속 정책까지 완료한 것으로 보지 않는다.
