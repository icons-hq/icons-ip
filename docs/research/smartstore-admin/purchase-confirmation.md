# 구매확정·자동 정책·요청/유예 이력

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-16 구현. 사용자 승인에 따라 자동 확정은 기본 꺼짐이고 기간은 미설정이다. 기존 고정 8일 자동 처리를 대체한다. 운영 배포·실제 결제 또는 운영 DB 변경은 하지 않았다.

## 동작

- 거래확정 내역의 **구매확정 정책 설정**에서 자동 사용, 배송완료 후 기간, 고객 1회 연장 기간과 근거를 저장한다. `sales.manage` 권한, 실제 로그인 세션, 기대 revision과 요청 ID를 검사한다.
- 첫 배송완료 시 당시 정책을 주문에 보존한다. 2026-10-27 결정(D11)에 따라 정책을 켜거나 켜진 채 저장하면 기한 없는 배송완료 주문(꺼져 있던 기간·도입 이전 배송완료)에 배송완료 시각 + 현재 기간을 저장한다. 기간을 바꿔도 이미 보존한 예정일은 유지한다. 전역 자동 설정을 끄면 이후 자동 검사에서 모두 중지하며 이미 실행 중인 트랜잭션의 완료를 취소하지는 않는다.
- 고객은 배송이 모두 완료되고 결제가 유지되며 진행 중인 클레임·보류가 없을 때 직접 구매확정할 수 있다. 자동 설정과 별개다. 자동 대상 주문은 저장된 기간만큼 1회 연장할 수 있다.
- 관리자 주문 상세에서 주문당 1회 인앱 구매확정 요청, 고객에게 표시할 사유를 포함한 보류, 보류 해제를 처리한다. 요청만으로 확정하지 않는다. 보류 해제 시 예정일을 다시 만들지 않으며 이미 기한이 지났으면 다음 자동 검사에서 확정될 수 있음을 표시한다.
- 확정은 기존 `done` 전이와 주문 당시 적립금 원장을 사용한다. 중복 호출은 같은 결과를 읽으며 지급과 확정 이력을 늘리지 않는다. 확정 후 반품/교환도 기존 배송일·사유별 기한과 실물 회수/환불 절차를 따르며, 구매확정 자체로 권리를 소멸시키지 않는다.
- 주문 행 잠금으로 클레임 접수와 확정을 직렬화한다. 자동 작업은 후보를 잠그지 않고 고른 뒤(`purchase_confirmation_candidate`), 주문마다 하위 트랜잭션에서 행위자 → 계정 작업 → 프로필 → 주문 → 확정 행을 기다리지 않고 잡는다. 못 잡거나, 확정 뒤 trigger가 100ms(`lock_timeout`) 넘게 기다리면 그 주문만 되돌리고 다음 실행에 맡긴다(2026-11-12, [ADR-0035](../../adr/0035-review-confirms-purchase.md)). 고객 잠금은 `NO KEY UPDATE`로 FK 참조 읽기를 막지 않는다. 직접 테이블 변경과 불필요한 역할의 함수 실행은 봉인한다.

## 리뷰 등록과 함께 확정 (2026-11-12, 1014-079 · [ADR-0035](../../adr/0035-review-confirms-purchase.md))

- 사용자 결정 원문: "리뷰 쓰며 함께 확정으로 진행하되 구매확정만 누를 수 있어야 하며, 일정 기간이 지나면 자동으로 확정되는것도 켜놔야함". 자동 확정 기간은 "8일 (Recommended)"이며 운영값이라 배포 뒤 이 화면에서 저장한다(migration은 정책을 켜지 않는다).
- 미확정(배송완료) 주문에 리뷰를 등록하면 고객이 [구매확정] 패널과 같은 안내를 확인·체크한 뒤 `create_good_review_v3`가 같은 트랜잭션에서 위 직접 확정(`private.change_purchase_confirmation`)을 부르고 리뷰를 저장한다. 적립금·이력·감사는 버튼 확정과 같고, 이력 메모가 "리뷰 등록과 함께 확정"이다. 리뷰 저장이 실패하면 확정도 되돌아간다.
- 확정할 수 없는 주문(진행 중 클레임·보류·배송 미완료·계정 제한·결제 원장 불일치)은 리뷰도 막고 이유를 보인다. 리뷰 없이 [구매확정]만 누르는 길, 1회 연장, 자동 작업은 그대로다. 이미 쓴 미확정 주문의 리뷰는 소급 확정하지 않는다.
- 확인 없는 기존 작성 함수(`create_good_review_v2`·`create_good_review`)는 미확정 주문을 거절한다. 리뷰는 늘 구매확정된 주문에만 남는다.
- 잠금은 행위자 → 프로필 → 계정 작업 → 주문 → 확정 행 순서다. 기존 리뷰 작성 순서(행위자 → 계정 작업 → 프로필)로 확정까지 하면 버튼·자동 작업(프로필 → 계정 작업)과 교착하는 것을 경합 시험에서 재현하고 고쳤다.
- 검증: `purchase_confirmation.sql`의 T14c 구간(확정·거절·되돌림·중복·자동 확정 상호작용·버튼 경로·소급 없음·ACL), `purchase_confirmation_concurrency.py`의 리뷰 경합(리뷰·버튼·자동 작업 12건, 같은 리뷰 6건, 리뷰·반품 접수 8건 — 격리 DB에서 6회 반복해 확정·적립 중복 0, 미확정 주문의 리뷰 0), `goods_reviews.sql`.
- 자동 작업 잠금 순서(같은 날 후속): 결제·선물·리뷰·[구매확정]·적립금 잠금을 다른 세션이 3초 쥔 채 자동 작업을 돌리면 0.2초 안에 쥔 고객만 건너뛰고 끝나며, 쥔 쪽은 모두 정상 커밋된다. 놓은 뒤 다음 실행이 나머지를 확정한다. 같은 시험에서 이전 작업은 38초를 기다렸다. 실제 결제 확정(장바구니 → 주문 → 결제 준비·승인 대기 → 확정), 선물 잠금(`gift_lock_subjects` 두 고객) 뒤 실제 결제 확정, 리뷰 등록을 자동 작업 3건과 동시에 3회 돌려 교착 0, 결제 승인 12건, 확정 누락·중복 0을 확인했다. 격리 DB에서 5회 중 4회 통과했고, 1회는 Docker VM 과부하로 상태 조회 자체가 40초 멈춘 환경 실패였다.

## 검증

- `purchase_confirmation.sql`: 꺼짐·미설정 기준, 정책 재실행/CAS, 꺼져 있던 기간 배송완료의 소급 기한(D11), 알림 중복 방지, 보류·해제, 직접 확정과 1회 적립, 1회 연장, 다른 계정/세션 거부, 확정 뒤 반품 접수, 전역 중지, 기존 기간 보존, 활성 클레임/보류 제외, ACL을 롤백 트랜잭션으로 검증했다.
- `customer_grade_rewards_checkout.sql`: 실제 v2 주문 견적·생성·결제 finalizer·배송완료 후 합성 자동 정책으로 확정했다. 배송비와 사용 적립금을 제외한 9,000원의 3%=270원 지급이 한 번뿐임을 확인했다.
- `purchase_confirmation_concurrency.py`: 동일 요청 12개, 자동 작업·구매자 요청 12개, 클레임·구매자 요청 8개를 동시 실행했다. 최종 실행 `64345e8c`에서 확정 이력·적립 중복 0, 자동 확정 4건, 클레임 4건을 확인했다. 클레임이 먼저 잠근 3건의 구매확정은 거부됐고 먼저 확정된 1건은 이후 정상 반품 접수를 허용했다. 결제 공급자를 호출하지 않는 격리 DB의 RPC 경합 검사다.
- 관련 앱 테스트 8파일 88개 통과. 타입 검사·대상 ESLint 통과. 전체 통합 빌드는 전체 어드민 후속 작업이 끝난 뒤 별도로 진행한다.
- 실제 Chrome에서 합성 정책 저장, 요청 알림, 보류·해제, 구매자 3일 연장·직접 확정·이력과 PC/390px 표시를 확인했다. 주문 `bc160000-0000-4001-8000-000000000001`의 DB 재조회는 `done`, 직접 확정, 이력 5개, 적립 100원 1회, 알림 1개다. 20일/3일/100원은 검증 전용 값이며 운영 정책으로 설정하지 않았다.
- 근거는 `output/smartstore-full-admin-20261016/`의 `confirmation-browser-readback.json`, `confirmation-concurrency.json`, SQL·앱 로그, `local-confirmation-*` 캡처와 해시다. 최초 고객 모바일 캡처는 탐색 후 viewport가 풀려 정확한 390px로 다시 촬영했다.

금전 원장의 확정·회수는 기존 전액 취소/환불 계약을 유지한다. 자동 작업의 운영 실행, 실제 PG 환불과 운영 적립금은 이번 로컬 검증의 결과가 아니다.
