# 상품 사진 로고 한 장 — 승인한 자산 수명·합성 계약

2026-10-14. 사용자가 고른 로고 한 장을 브라우저 안에서 합성한다. 구현·검증 상태는 [로고 구현 QA](product-photo-logo-implementation-qa.md)를 따른다. 기존 일반 텍스트 엔진, 자동 수평·인식, 외부 URL·별도 업로드·서버 템플릿은 추가하지 않는다.

최초 제안의 기존 bitmap 선해제·재디코드 복원 대신 **기존 로고를 유지한 단일 후보의 원자적 교체**를 승인했다. 정상 상태의 원본≤4MP + 로고≤1MP에 교체 중 후보≤1MP를 추가해 애플리케이션 소유 bitmap을 최대6MP까지 허용한다. 교체 실패는 기존 bitmap을 그대로 유지하며 복원용 재디코드·복원 실패 상태·최신 대기 요청 큐를 만들지 않는다. 이 수치는 Canvas·인코더·네이티브 디코더를 포함한 브라우저 전체 메모리 상한이 아니다.

## Module과 Interface

`PhotoEditSession`이 원본과 로고 bitmap의 소유권·직렬 렌더·교체·해제를 맡는다. `photo-editor-logo`는 로컬 파일 검사·디코드와 비율을 유지하는 배치를 숨긴다. UI는 불변 descriptor와 recipe만 보관하며 Blob·bitmap·로고용 object URL을 보관하지 않는다.

| 동작 | 호출자가 아는 계약 |
| --- | --- |
| `replaceLogo(file, signal)` | 한 번에 한 요청만 허용한다. 중복 요청은 즉시 거절한다. 성공 시 직렬 렌더가 끝난 뒤 활성 bitmap을 교체하고 이전 bitmap을 닫으며 불변 descriptor를 반환한다. 실패 시 기존 로고를 유지한다. |
| `clearLogo()` | 활성 로고와 진행 중 후보 세대를 무효화한다. 활성 bitmap은 기존 렌더가 끝난 뒤 닫고 늦은 후보는 채택하지 않는다. |
| `preview`·`render`·`dispose` | 기존 인터페이스를 유지한다. 로고 선택 중 새 preview/render는 거절한다. dispose는 원본과 소유 로고 bitmap을 닫고 모든 작업을 취소한다. |

## 불변 자산과 배치

Descriptor는 임의 `assetId`, 파일 바이트 SHA-256, 검증한 MIME, EXIF 표시 방향의 너비·높이, 표시용 파일명이다. 파일명·수정시각을 식별자로 쓰지 않으며 같은 파일을 다시 선택해도 새 ID를 발급한다. Recipe는 `logo: null | { assetId, x, y, width, opacity }`만 담는다.

- 위치는 EXIF 표시 방향을 반영한 원본 사진의 픽셀 좌표다. 원본 안에 들어가는 최대 너비의1~100%를 허용하고 높이는 자연 비율로 계산한다. 소수 픽셀을 허용하므로1px 사진·극단 비율도 비율을 깨지 않는다.
- 불투명도는 정수0~100이다. 새 로고는 최대 너비의25%, 오른쪽 아래, 짧은 변2% 여백에서 시작한다. 교체 성공 시 기존 위치·너비·불투명도를 유지하되 새 비율로 사진 안에 맞춘다.
- 좌표·너비 입력, 네 모서리/가운데 배치, 드래그, 방향키1px·Shift10px가 같은 배치 함수를 사용한다. 방향키는 화면 방향을 회전 전 원본 좌표로 바꾼다.
- 활성 자산과 recipe ID가 다르면 보이는 로고를 렌더하지 않는다. 로고 없음·불투명도0만 변경한 완료는 기존 무변경 판정에 따라 새 파일을 만들지 않는다.

## 로컬 파일 검증

입력은 정지 PNG·JPEG·WebP 한 장,5MiB 이하·100만 픽셀 이하·각 변2048px 이하다. 크기0/초과는 읽기 전에 거절한다. [기존 컨테이너 검사](../../../lib/admin/photo-editor-source.ts)의 `inspectPhotoSource`로 헤더·경계를 검증하고 더 작은 로고 치수 한도를 적용한다. 원본 사진의4MP·4096px 한도는 유지한다.

확장자 대신 실제 헤더를 사용하며 비어 있지 않은 `File.type`은 실제 MIME과 일치해야 한다. 빈 MIME은 헤더로 결정한다. APNG·애니메이션 WebP·다중 프레임·잘린 컨테이너·SVG·GIF를 거절한다. 검증한 MIME의 Blob을 `createImageBitmap(..., { imageOrientation: 'from-image' })`으로 디코드한 뒤 EXIF 기대 치수를 재확인한다. 불일치·취소 시 후보 bitmap을 닫는다.

로고용 fetch·data URL·object URL·Storage claim은 없다. 파일 선택 후 input 값을 비워 같은 파일 재선택을 허용하고 FileList 참조를 놓는다. 파일 선택창 취소는 현재 상태를 유지한다. 파일 바이트 읽기·SHA·디코드 전후에 취소를 확인한다.

## 교체·취소·메모리

1. 요청 시작 시 참조와 상태로 중복 선택을 막고 기존 미리보기를 취소한다. 파일·로고 배치·완료를 막으며 마지막 완성 미리보기는 유지한다.
2. 기존 로고를 유지한 채 후보를 검증·해시·디코드한다. 정상 상태는 원본1개 + 활성 로고1개, 교체 중에만 후보1개가 추가된다.
3. 후보가 준비되면 기존 렌더 큐에 교체 작업을 넣는다. 최신 세대와 취소 상태를 다시 확인한 뒤 활성 자산을 바꾸고 이전 bitmap을 닫는다.
4. 실패는 별도 로고 오류로 표시하며 기존 배치·미리보기·bitmap을 계속 사용한다. 실패 후 기존 로고로 완료할 수 있다.
5. 제거·재설정·창 취소·source/계정 변경·unmount는 세대를 무효화한다. 이미 시작한 네이티브 디코드는 강제로 중단하지 못하므로 반환된 후보를 닫고 새 요청은 기존 요청이 정리된 뒤 허용한다. 제거·재설정·취소는 파일 선택 중에도 가능하다.
6. bitmap 사용과 교체/일반 해제는 같은 큐를 따른다. dispose는 lifetime을 취소하고 소유 자원을 한 번만 닫는다. 렌더는 yield/await 뒤 취소를 확인한 다음 로고를 그린다.

새 파일 한 개만 처리하며 최신 대기 파일을 따로 보관하지 않는다. 기존 로고의 압축 Blob도 복원용으로 남기지 않는다. 요청의 File·바이트 배열·Blob은 단일 요청 수명 동안만 참조한다. 소유 bitmap 최대6MP는 네이티브 내부 버퍼·합성 캔버스·ImageData·인코더를 포함하지 않는다.

## 미리보기와 합성

Preview key에 asset ID와 배치를 포함한다. UI 요청 세대, preview AbortSignal, session의 활성 자산 확인을 통과한 결과만 게시한다. 같은 파일명·같은 치수도 다른 파일이거나 다시 선택했다면 별도 key다. 완료는 현재 recipe의 미리보기가 준비된 뒤 허용한다.

합성 순서는 **사진 자동/수동 보정·공간 효과 → 모자이크 → 로고 → 일반 텍스트 → 전체 회전·반전·사각 자르기 → 테두리·도형 마스크 → 미리보기 축소**다. 로고에는 사진 색 보정을 적용하지 않는다. 로고는 원본과 함께 회전·반전되고 자르기·도형 밖은 가려진다. 최종 사진 모서리에 항상 똑바로 붙는 워터마크는 범위 밖이다.

로고 alpha에 불투명도를 곱해 source-over 합성한다. 완전 투명한 로고 부분은 밑의 사진을 유지하며 로고가 사진의 투명 부분을 덮으면 alpha가 증가할 수 있다. JPEG 사진 위 투명 로고는 기존 JPEG 출력 정책을 유지하고, 도형 마스크 사용 시 PNG를 쓴다. Preview와 final은 같은 원본 해상도에서 합성한다. JPEG 재압축·Canvas 부분투명 RGB 양자화의 한계는 기존과 같다.

## 검증 기준

같은 파일명 교체·실패 보존·중복 요청·렌더 중 교체/제거·늦은 후보 취소·dispose·원본 비교·재설정·opacity0, 형식/치수/크기/EXIF 경계와 비율·키보드·드래그를 검증한다. 단위 테스트는 수명·배치·호출 순서를 검증하며 실제 픽셀·브라우저 메모리의 증거를 대신하지 않는다.

실제 브라우저에서4MP 원본+1MP 로고, 투명/부분alpha, 회전·자르기·마스크, 동일 이름 파일 교체 실패/성공, 파일 선택 취소,390px, 저장·재열기, 원본 보존을 확인한다. 검증 전에는 [구현 QA](product-photo-logo-implementation-qa.md)의 실제 UI 상태를 대기로 유지한다.
