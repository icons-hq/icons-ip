# 매니저 역할·이메일 초대 구현 검증

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

검증일: 2026-10-13. 기준은 [원본 권한표](manager-permissions.md), [ADR-0020](../../adr/0020-store-manager-capabilities.md), [운영 런북](../../runbooks/operator-access.md)이다. 네이버 계정은 읽기 전용으로 확인했다. 구현 변경과 아래 저장 검증은 격리 로컬 Supabase·합성 계정에서만 수행했다.

## 구현

- 통합 매니저·계정 주매니저·계정 부매니저·인플루언서·대행사·물류출고관리의 6역할. 담당업무 8종은 표시용이며 통합 매니저는 대표로 표시한다.
- 최초 전환은 기존 운영자 전원의 역할 또는 회수를 선택하고 통합 매니저 한 명을 명시적으로 지정한다. 자동으로 대표를 선정하지 않는다.
- 본인·통합 매니저 일반 변경 금지, 주매니저의 동급 직접 회수 금지, 통합 매니저만 다른 활성 주매니저에게 승계. 기존 소유자는 주매니저로 전환한다.
- 사용자 선택에 따라 기존 이메일 발송 경로로 초대한다. 한 번에 10명, 통합 매니저를 제외한 등록 매니저와 유효한 대기 초대를 합해 1,000명, 생성 후 7일 만료다.
- 초대 등록·이메일 접수/전달·수락을 구분한다. 재초대는 새 링크로 이전 링크를 무효화하고, 취소·초대자 권한 회수·기간 만료는 수락을 차단한다.
- 수락은 인증된 Auth 이메일과 비교한다. 수정 가능한 회원 이메일로 수락하지 않는다. 이메일 변경과 수락이 경쟁하면 행 잠금으로 순서를 정한다. 토큰 원문은 DB·감사 로그·관리자 화면에 저장하지 않는다.
- 생성·역할 변경·회수·승계의 결과 미확인은 같은 요청 ID로 재확인한다. 이미 수락한 링크는 나중에 회수한 권한을 복구하지 않는다.

## 실제 브라우저 검증

1. 기존 10명의 역할 미선택 상태에서 활성화가 차단됨을 확인했다. 통합 매니저를 직접 선택하고 기존 역할을 모두 배정한 뒤 저장했다.
2. 합성 이메일에 계정 부매니저·CS 역할을 초대했다. 등록 1건과 수락 대기가 저장되었고, 공급자 미설정은 별도 발송 상태로 표시되었다.
3. 합성 초대 링크 진입 후 주소 fragment가 제거되고 로그인·가입 복귀 경로에 토큰이 없는 것을 확인했다. 인증된 수신자 로그인 후 같은 탭에서 초대 정보가 복구되었다.
4. 390px 화면에서 역할·담당업무·만료일을 확인하고 수락했다. 완료 화면과 실제 부매니저 홈의 제한된 메뉴를 확인했다.
5. 수락 계정을 주매니저로 바꾸고 통합 매니저를 승계했다. 기존 소유자의 역할이 주매니저로 바뀌고 승계·동급 회수 버튼이 사라졌다. 새 소유자로 로그인된 화면에서 원래 소유자에게 다시 승계했다.
6. 주매니저 본인의 담당업무를 바꾸고 역할이 유지되는 것을 확인했다. 합성 계정의 권한을 회수한 뒤 기존 로그인 세션에서 매니저 화면이 404로 차단되었다. 이미 수락한 링크를 다시 열어도 권한은 복구되지 않았다.

최종 readback은 통합 매니저 1명, 기존 매니저 10명, 합성 수신자 일반 회원·membership 0건, 초대 이력 accepted다. 공급자 이벤트는 0건이며 외부 이메일을 보내지 않았다. 기존 개발 DB·운영 DB·네이버 매니저 정보는 변경하지 않았다.

## 자동 검증

- 역할 lifecycle SQL: 초기 전환 누락·중복·소유자 조건, 역할 변경·직접 회수 경계, 권한 버전 충돌, 요청 재사용, 승계 후 기존 소유자 영수증 재확인, 담당업무 경계를 검증했다.
- 초대 SQL: 비공개 ACL, 중복 수신자·대기 초대·기등록 매니저, 인증 이메일과 프로필 이메일 위조, 만료·취소·재초대, 수락 재시도·회수 후 재수락, 초대자 강등·발송 claim 재검사, 감사/이메일 원장, 999명에서 일괄 2명 전체 취소와 1,000번째 슬롯 교체를 검증했다.
- 동시성 6종: 동일 초대 수락, 취소 선행, 초대자 강등 선행, Auth 이메일 변경 선행, 수락 선행 후 이메일 변경, 마지막 인원 슬롯 경쟁을 별도 복제 DB에서 통과했다. 실제 잠금 대기를 관측한 뒤 결과와 감사 건수를 확인했다.
- 초대·기존 dispatcher·가이드 61개 단위 테스트를 통과했다. 이후 lifecycle을 포함한 묶음에서 매니저 관련 70개가 모두 통과했고 가이드 14개 중 새로 추가된 `/admin/display/stories`의 별도 문서 누락 1개를 해당 구현 담당자에게 전달했다.
- TypeScript 전체 검사와 변경 파일 ESLint를 통과했다. 동시성 shell 문법과 Python 구문 검사도 통과했다.

## 증거

`output/smartstore-reference-20261012/verification-manager-lifecycle/`에 SQL 로그, `ui-invitation-readback.json`, `ui-manager-final-readback.json`, 캡처 manifest가 있다. 화면 캡처 15개 모두 SHA-256을 대조했다. `04-activation-unknown-keeps-mapping.png`는 검수용 서버 재시작 때 임시 tsconfig 경로 매핑 누락으로 생긴 실패 증거이며 성공 증거에서 제외한다. 해당 임시 설정을 복구한 뒤 활성화부터 다시 검증했다.

주요 캡처: `06` 초대 확인, `07` 등록/발송 상태 분리, `08` 토큰 없는 로그인 경로, `09–10` 390px 수락, `11–13` 승계·반환, `14–15` 기존 세션 차단·수락 링크 재사용 제한.

운영 배포·운영 역할 활성화·실제 수신자 메일 전달은 이 검증에 포함하지 않는다. 원본 네이버의 SMS 초대·수락·회수·승계는 읽기 전용 조사 범위 밖이므로 실행 결과를 주장하지 않는다.
