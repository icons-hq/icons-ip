# 판매자 대리 클레임 접수: 현재 차이와 재사용 경계

migration 파일 경로는 [배포 매핑](../../../supabase/manifests/admin-rollout-migration-map.json)을 반영했다. 아래 과거 검증·적용 기록은 당시 원본 DRAFT 기준이며 이번 운영 배포의 성공을 뜻하지 않는다.

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-13 원본 추가 조사와 승인된 구현 범위를 반영했다. 운영 데이터 변경은 하지 않았다. 현재 구현은 판매자 직접 **취소·반품·교환 요청 접수**다. 취소는 발주확인 전 주문 전체를 대상으로 요청만 생성하며 부분 처리·환급액 입력을 받지 않는다. 아래 원본 관찰 및 첫 반품·교환 단위의 기록은 유지하고, 취소 확장은 마지막 절에 구분한다.

## 직접 확인한 원본 양식

배송현황의 배송완료 행에서 판매자 직접 반품/교환 접수 새 창을 열고, 초기 상태와 `자동수거요청`/`수거요청안함` 상태를 확인했다. 접수 버튼은 실행하지 않았다. 비공개 증거는 `output/smartstore-reference-20261012/sales/details/seller-{return,exchange}-intake*`이며 고객·주문·주소 값은 이 문서나 테스트로 복사하지 않았다.

- 두 양식 모두 구매자와 협의가 끝난 건만 접수하며 사유가 구매자에게 안내됨을 명시한다. 이 화면은 요청만 생성하고 최종 승인/후속처리는 반품관리·교환관리에서 별도로 수행한다.
- 같은 주문번호의 접수 가능 상품주문 선택, 사유, 수량, 상세 사유(500자 안내), 수거방법·택배사·송장번호를 받는다. 자동수거 선택 시 수거주소·전화·안심번호 필드가 추가된다. 교환은 재배송주소도 받는다.
- 원본은 배송중 접수·상품주문/일부 수량·조건부 배송비 재계산·택배 자동 예약을 지원한다. ICONS의 현재 주문 전체·배송완료 자격, 전액 환급, 운송사 미연동 계약과 다르므로 그대로 이식하지 않는다.
- 교환 사유 수정·수거정보 수정 별도 팝업도 확인했다. 사유 변경은 구매자 안내 대상이며 구매자 귀책으로 바꾸어도 보류가 자동 설정되지 않는다. 수거 수정은 진행 상태·택배 계약에 따라 제한된다. 실제 수정은 하지 않았다.

## 구현한 첫 완결 단위

1. 주문 상세에서 **판매자 직접 반품·교환 접수**를 연다. 주문 고객·전체 품목·현재 배송/결제 사실·활성 클레임을 읽어 보여준다. 허용된 전체 주문 유형만 선택하게 한다.
2. 고객 의사표시 근거와 대리 담당자를 분리한다. 주문의 고객 ID, 실제 접수한 staff/admin, 채널, 문의/티켓 참조, 고객 요청을 확인한 시각, 사유를 기록한다. 문의 근거를 사용하면 문의 고객과 주문 고객의 관계를 서버에서 검증한다.
3. staff 전용 RPC는 동일 요청 ID와 고정 입력으로 재생을 막고, 기존 잠금 순서·취소 가능 이력·전체 배송완료·활성 클레임·기한 검사를 공통 private helper로 재사용한다. 고객의 기존 API 동작은 변경하지 않는다.
4. 첫 단계는 `requested` 요청과 대리 접수 근거의 원자적 생성까지만 맡긴다. 기존 고객 RPC의 미결제 즉시 종결·paid 자동 승인을 대리 접수에 암묵적으로 물려주지 않는다. 이후 기존 승인→회수→환급/재출고 UI와 RPC를 사용한다. 이 차이는 버튼/결과에 분명히 표시해야 한다.
5. 요청 상세·타임라인에서 고객 요청 근거와 담당자를 확인하고, 응답이 불확실하면 같은 요청 결과를 조회한다. 중복 접수·다른 요청으로 같은 ID 재사용·권한 상실은 서버에서 거부한다.

구현한 첫 단위는 주문상세에서 반품/교환 요청만 생성한다. 고객 합의 확인·사유·수거정보·담당자/감사를 남기고 기존 승인·회수·환급 경로로 넘긴다. 고객 RPC의 자동 처리는 호출하지 않는다.

## 유지하는 경계

- **원래 고객 요청 시각과 기한.** 현재 고객 RPC는 접수 시점에 기한을 검사하고, 승인 RPC는 저장된 `requested_at`을 사용한다. 과거 문의 시각을 새 요청의 `requested_at`에 그대로 대입하면 기한 판정이 달라진다. 원문 의사표시 시각은 별도 근거로 보존하고, 임의 소급이나 기한 연장을 접수 구현에 섞지 않는다. 지연 입력의 예외 처리는 기존 CS 검토 범위와 별도로 결정한다.
- **발주확인 후~전체 배송완료 전.** 직접 신청 제한은 이번 전체·전액 결정과 별개의 기존 승인 정책이다. 이 기간의 대리 접수를 허용하려면 출고 중지·회수 대상·재고 및 결제 경합을 먼저 설계해야 한다. 현재 정책을 유지하는 첫 단위라면 접수 버튼 대신 기존 CS 검토와 증거 연결만 제공한다.
- **pending 무결제 주문.** 최초 반품/교환 단위에서는 제외했으며 아래 취소 확장에서는 `requested`만 생성한다. 고객 직접 취소의 즉시 종결과 기존 관리자 승인 경로를 구분한다.

부분취소·부분반품·환급액 입력·품목/수량 배분·유형 전환은 이 구현 단위에서 제외한다. 교환의 기존 전체 회수·같은 상품 옵션 재출고·수령 확인도 그대로 유지한다.

- 일부 배송, 교환품 미수령, 기한 경과와 고객 요청 시각 소급에 의한 기한 우회 거부를 검증했다. 이후 기존 승인에서 두 출고지 회수 원장이 만들어지고, 실제 입고 전 재출고가 거절되는 연결도 확인했다. 기존 전액 PG finalizer를 변경하지 않았고 실제 금융 처리는 실행하지 않았다.
- 2026-10-13 Chrome에서 전용 합성 주문의 반품·교환을 각각 접수하고 상세를 재조회했다. 미래 요청 시각은 거절되며 사유·문의·주소·수거 메모·선택 계좌 입력이 유지됐다. 다른 고객의 문의는 선택 목록에 나오지 않았고, 접수된 주문은 새 접수를 막고 기존 상세 링크를 표시했다. 반품 계좌 원문은 상세에 노출되지 않았다.
- 모바일 390×844에서 폼의 문서 폭/스크롤 폭은 390/390, 대화상자는 358/358이며 실제 교환 저장까지 완료했다. 같은 두 요청을 authenticated 직원으로 다시 실행한 DB readback에서 주문당 접수 1·감사 1·알림 1, 수거 계획 2, 환불/취소 실행/실제 회수 원장 0을 확인했다. 주문은 배송완료, 결제는 paid를 유지했다.
- 합성 증거는 `output/smartstore-reference-20261013/verification-seller-claim-intake/`의 화면 8장·DB readback·SHA-256 목록에 보존한다. 원본 네이버의 실제 접수·취소와 ICONS 운영 배포·PG·택배 연계는 실행하지 않았다. 동시 세션의 실제 경합이나 브라우저 전송 응답 유실을 주입한 검수는 하지 않았으며, 잠금·중복·불확실 응답 분기는 SQL 및 액션 테스트와 코드 검토로 확인했다.
