# 지정 고객·세그먼트 쿠폰 발급

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-16 로컬 구현. 혜택 조회/수정의 `발급` 또는 혜택 정보의 `지정 고객·세그먼트 발급`으로 진입한다. 쿠폰함 발급과 마케팅 알림은 별개다.

## 계약

- 지정 고객은 닉네임·고객 ID·정확한 이메일로 찾아 추가하거나 고객 ID를 입력한다. 검색 결과의 이메일은 가린다. 발급 요청에는 고객 ID만 보낸다.
- 저장한 세그먼트를 선택할 수도 있다. 현재 조건의 고객을 최대 1,000명까지 확인하고 대상 ID를 고정한다. 실행 전 새로 조건에 들어온 고객은 추가하지 않는다. 마케팅 수신 동의는 쿠폰함 발급의 필수 조건이 아니며 메시지 발송은 수행하지 않는다. 회원 행동 세그먼트는 해당 행동 동의와 관측 조건을 그대로 따른다.
- 확인 결과는 대상·새 발급 예정·기보유·오류를 구분한다. 쿠폰의 현재 발급기간·수량 한도·첫구매/재구매 조건을 유지한다. 이미 같은 쿠폰을 보유한 고객은 추가 발급하지 않는다. 사용·만료된 기존 보유분도 같은 쿠폰의 재발급 사유로 삼지 않는다.
- 실행은 확인한 운영자·실제 로그인 세션·작업 ID에 결속하며 15분 이내에만 가능하다. 쿠폰 revision, 세그먼트 정의와 고객별 현재 자격을 다시 확인한다. 기존 정책의 기간·할인·사용 자격을 바꾸지 않는다.
- 전체 발급은 한 트랜잭션이다. 중간 오류 때 새 발급과 발급수 증가가 함께 롤백되고 작업은 실패로 남는다. 동일 실행을 반복해도 새 쿠폰을 중복 생성하지 않는다. 응답이 불명확하면 새 작업으로 넘어가지 않고 현재 작업 조회·같은 요청 확인을 사용한다.
- 결과는 실제 쿠폰 발급 ID와 `admin_grant` 출처를 기록한다. 발급 후 저장된 결과를 다시 읽고 완료로 표시한다. 작업 링크로 재열람할 수 있고 기존 혜택 리포트의 발급 원장 집계에도 포함된다.

## 구현 경계

`private.coupon_issue_batches`는 확인과 실행 결과를 보존한다. 고객 프로필/탈퇴 잠금→고객별 advisory→쿠폰 행 순으로 기존 코드 등록과 직렬화한다. 코드 등록과 관리자 발급은 `private.issue_coupon_code`의 동일한 기간·자격·한도·만료일 계산을 사용한다. 잠금 획득 후 실제 시각으로 신규 발급을 판단하므로 기다리는 동안 발급기간이 끝난 쿠폰은 발급하지 않는다. 기존 보유 쿠폰의 재조회와 보유 당시 유효기간은 유지한다.

직접 테이블·내부 함수 실행은 PUBLIC·anon·authenticated·service_role에서 봉인한다. 관리자 RPC는 현재 `marketing.manage`를 검사한다. 고객 명단은 해당 관리자 화면 안에서만 표시하고 캠페인 발송이나 외부 파일로 자동 전송하지 않는다.

## 검증

- `supabase/tests/coupon_target_issuance.sql`: 확인만으로 미발급, 확인/실행 재시도, 기보유 제외, 한도 초과, 다른 계정·권한, 두 번째 INSERT 강제 실패 후 전체 롤백, 세그먼트 회원 이탈·신규 유입, 정책 변경·확인 만료·봉인 권한을 통과했다.
- 실제 HTTP 경합: 동일 실행 10개→실제 1장, 관리자 발급과 일반 코드 등록의 마지막 1장 경합→실제 1장, 행 잠금 대기 관측 후 기간 만료→실패/발급 0장. `coupon-issuance-concurrency.json`에 결과를 남겼다.
- 기존 발급기간/보유 유효기간 검증은 새 합성 운영자 멤버십만 현재 권한 계약에 맞춰 추가한 격리 harness로 통과했다. 기존 v2 장바구니 견적→주문→결제→전액 취소/쿠폰 복원 검증도 통과했다. 구형 `coupon_redemption.sql` 원문은 폐기된 authenticated `cart_items` 직접 INSERT 계약 때문에 그대로 실행할 수 없었고, 현재 v2 계약 검사를 근거로 사용한다. 권한을 다시 열지 않았다.
