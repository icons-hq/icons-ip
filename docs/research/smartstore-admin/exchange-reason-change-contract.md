# 교환 사유 정정: 공식 근거와 ICONS 적용 계약

migration 파일 경로는 [배포 매핑](../../../supabase/manifests/admin-rollout-migration-map.json)을 반영했다. 아래 과거 검증·적용 기록은 당시 원본 DRAFT 기준이며 이번 운영 배포의 성공을 뜻하지 않는다.

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-14 조사·구현. 승인된 최소 계약에 따라 교환 요청의 사유 정정 SQL·RPC·운영자 폼과 고객 이력을 구현하고, 격리된 OWN/FRESH 로컬 DB와 실제 Chrome에서 검증했다. 스마트스토어 원본과 운영 DB는 변경하지 않았으며 이메일·SMS나 결제사 요청을 보내지 않았다.

## 결론

교환 사유 수정은 기존 CS 업무에 적용할 수 있다. 다만 ICONS의 `reason_type`은 요청 기한을 결정하므로 단순 문자열 편집으로 구현하면 안 된다. 기존 두 분류와 고객에게 보이는 설명만 수정하고, 원래 접수 시각 기준 기한·현재 권한·고객 협의·행 버전·물류/환불 상태를 함께 검사하는 별도 작업으로 구현했다.

스마트스토어의 정확한 **사유 수정 허용 단계·수정 횟수는 미확인**이다. 아래 허용 단계는 기존 ICONS 계약에 맞춘 보수적인 ICONS 계약이며 네이버의 동일 동작을 확인했다는 뜻이 아니다.

## 공식 원문에서 확인한 범위

| 항목 | 확인한 사실 | 적용 판단 |
| --- | --- | --- |
| 실제 사유와 일치 | 구매자·판매자 귀책 사유를 나누며 실제 사유와 다르면 승인 전에 바로잡도록 안내한다. 판매자 귀책으로 종료하는 경우 판매관리 점수에 영향이 있을 수 있다. [귀책사유 기준](https://help.sell.smartstore.naver.com/faq/content.help?faqId=16784) | 실제 사유 정정이라는 목적만 채택한다. 판매자 귀책 전체를 ICONS의 `defect`로 변환하지 않는다. |
| 고객 안내·완료 시점 | 완료 시 최종 사유가 점수 집계에 사용되고 변경한 사유가 구매자에게 안내된다. 실제와 무관한 사유 지정 및 고객 동의 없는 임의 반품에 대한 제재를 설명한다. [판매관리 점수 FAQ](https://help.sell.smartstore.naver.com/faq/content.help?faqId=16688)의 관련 질문을 펼쳐 확인 | 모든 사유 편집에 사전동의를 요구한다는 명시적 네이버 규칙으로 확대하지 않는다. ICONS에는 기존 대리 접수·유형 전환과 일관되게 고객 협의 근거를 요구한다. |
| 사유 수정 폼 | 동일 주문 하위 상품주문 선택, 사유 선택, 상세 설명 500자, 입력한 사유의 구매자 안내 문구를 확인했다. 판매자→구매자 귀책 변경만으로 보류되지 않는다는 안내가 있다. 원본 경로는 `/o/claim/exchange/pop/modifyReasonBySelection` | 폼의 존재·문구만 확인했다. 모든 선택지·단계별 진입 허용·저장 결과는 미확인이다. ICONS의 기존 설명 한도 200자를 유지한다. |
| 비용과 보류 | 구매자 변심 분류에서 교환배송비 청구가 가능하며, 사유 확인/수정 뒤 별도로 보류 사유·고객 안내를 입력한다. [교환배송비 청구](https://help.sell.smartstore.naver.com/faq/content.help?faqId=3847) | 사유 수정만으로 비용 부과·환불 차감·보류 설정 또는 해제를 실행하지 않는다. |
| 교환→반품 | 재배송 전만 직접 변경할 수 있다. 이미 결제한 교환배송비가 있으면 거부·재접수 절차를 안내하며, 원본 사진 삭제 규칙도 있다. [교환에서 반품으로 변경](https://help.sell.smartstore.naver.com/faq/content.help?faqId=3872) | 기존 ICONS 유형 전환은 별도 작업으로 유지한다. ICONS 운영 비용 기록을 Npay 선결제 비용으로 취급하지 않으며 사진·접수 근거도 삭제하지 않는다. |
| 반품→교환 | 사전 고객 동의와 반품 완료 전 조건을 명시한다. [반품에서 교환으로 변경](https://help.sell.smartstore.naver.com/faq/content.help?faqId=3833) | 이 명시적 동의 규칙은 유형 전환에 관한 것이다. 사유 편집의 공식 단계 조건과 혼동하지 않는다. |
| 재교환/반품 횟수 | ‘재교환 접수 방법’은 교환/반품이 최대 두 차례까지 가능한 예를 설명한다. [교환요청 처리](https://help.sell.smartstore.naver.com/faq/content.help?faqId=4481)의 해당 항목을 펼쳐 확인 | 재접수 횟수다. 사유 수정의 최대 횟수가 두 번이라는 근거로 사용하지 않는다. |
| 재교환 중 반품 | 요청/수거중/수거완료는 유형 변경, 재배송중은 교환상품 반품 요청, 완료 후에는 별도 취소 흐름을 안내한다. [재교환 중 반품 변경](https://help.sell.smartstore.naver.com/faq/content.help?faqId=15333) | 이 역시 유형 전환/새 요청의 단계다. 사유 수정 허용 단계의 증거로 쓰지 않는다. |

공식 FAQ 검색 두 페이지와 위 원문을 좁혀 확인했지만 사유 수정의 전체 단계표·횟수 제한·완료 후 수정 가능 여부는 확인하지 못했다. 원본 팝업의 선택 범위도 현재 ICONS의 주문 전체 처리 계약을 부분 처리로 바꾸는 근거가 아니다.

## 구현한 최소 계약

| 항목 | 구현 계약 |
| --- | --- |
| 범위 | 우선 `exchange` 요청의 분류·고객용 설명 정정만 다룬다. 취소/반품 전체 확대, 신규 귀책 분류, 비용 부담자 모델은 별도 설계다. |
| 허용 단계 | `requested`, `in_review`, `collecting`, `collected` 및 이 단계에서 보류된 건. `on_hold`인데 이전 단계가 없거나 알 수 없으면 차단한다. |
| 차단 | 재발송 시각/송장/재출고 품목 중 하나라도 존재, 주문 취소 실행 원장 또는 환불 원장 존재, 주문 취소, 완료/거절/철회 등 종결 단계. 현재 금전·실물 가드를 잠금 획득 후 다시 확인한다. |
| 분류 변경 | 새 분류가 원래 공급일·원래 요청일에서 유효한지 기존 함수로 검사한다. 편집일을 새 접수일로 사용하지 않는다. 검증 실패 시 기존 분류·설명·이력을 그대로 두고 별도 상담 근거 기록으로 해결한다. |
| 설명 정정 | 기존 1~200자 한도와 제어문자 차단을 유지한다. 분류와 설명이 모두 같으면 새 변경 이력이나 고객 알림을 만들지 않는다. |
| 고객 협의 | 협의 여부 확인과 2~500자의 내부 근거를 요구한다. 고객의 실제 요청·합의 내용을 기록하고, 민감한 내부 근거를 고객 알림이나 일반 감사 로그에 복사하지 않는다. |
| 보존 | 최초 사유·분류와 변경 전/후, 담당자, 시각, 협의 근거를 별도 보호된 이력으로 보존한다. 요청자·접수일·기한/SLA·회수 계획/입고 증거·보류·결정 담당자·기존 비용 기록을 유지한다. |
| 비용 | 기록이 있으면 기존 비용을 화면에 보여 주고 정합성 확인을 요구한다. 사유 편집과 동시에 금액을 재계산하거나 재확정하지 않는다. 후속 비용 정정은 기존 별도 작업과 새 감사 근거를 사용한다. |
| 권한·경합 | 컨텍스트 조회/변경/결과 재조회마다 현재 `sales.manage`를 검사한다. 담당자·고객 권한 잠금→요청 UUID 잠금→주문→배송건→클레임→회수행의 기존 순서를 유지하고 `claim_revision`으로 충돌을 검출한다. |
| 멱등·응답 유실 | 서버 행위자·요청 UUID·클레임·예상 버전·분류·설명·협의 근거를 고정한다. 동일 요청은 저장된 결과 재조회, 다른 입력/계정 재사용은 충돌이다. 응답 유실 시 새 요청을 만들기 전에 결과를 확인한다. |
| 고객 이력 | 주문 소유자만 변경 시각·분류·고객용 설명을 읽게 하고 앱 내 알림을 변경당 한 번 기록한다. 최초 요청 내용과 현재 정정 내용을 구별한다. 이메일/SMS 전송은 이 작업에 포함하지 않는다. |
| 유형 전환 연계 | 교환→반품은 기존 별도 액션으로 실행한다. 서로 먼저 완료한 변경이 행 버전을 증가시키므로 두 번째 작업은 새 상태를 확인해야 한다. 사유 정정이 유형을 바꾸거나 환불계좌를 수정하지 않는다. |
| 횟수 | 공식 제한이 확인되지 않았으므로 임의의 네이버 ‘1회/2회’ 제한을 만들지 않는다. 후속 정정도 매번 새 UUID·새 행 버전·고객 협의·전체 가드를 충족해야 한다. |

예를 들어 공급 후 10일에 접수한 하자 요청을 단순 변심으로 바꾸면 기존 7일 조건을 만족하지 않아 저장이 차단된다. 5일째 접수한 단순 변심을 실제 확인된 하자로 정정하는 경우에도 원래 요청일과 증거를 유지한다. 접수일을 오늘로 다시 써서 기간을 늘리는 구현은 허용하지 않는다.

## 구현과 검증

- [SQL migration](../../../supabase/migrations/20261020085323_order_claim_reason_changes.sql)은 별도 보호 테이블에 최초/변경 전후 사유·행위자·협의 근거·원래 접수일을 보존한다. 세 운영자 RPC와 주문 소유자 전용 이력 RPC를 추가하고 기존 승인·철회·보류·유형 전환·비용 RPC는 변경하지 않았다. OWN/FRESH에 적용한 최종 SHA-256은 `2c438d2a7e0efeb1b612f4faefdadd0f977c04a4cfdfe762669b4de543e7f9cb`다. 적용 전후 기존 함수 정의·소유자·ACL이 동일하고 새 함수 소유자는 `supabase_admin`이다.
- [운영자 패널](../../../components/admin/ClaimReasonChange.tsx)은 현재 사유·최초 사유·원래 접수일·기존 비용을 보여 준다. 버전 충돌 후 입력을 보존하고 현재 내용 재확인을 요구하며, 응답 유실은 기존 행위자·UUID·입력을 고정해 결과 조회 또는 같은 요청 재시도로 해결한다. 현재 계정이나 요청 유형이 바뀌면 내부 협의 입력을 초기화한다. 실제 변경 없이 저장한 요청은 멱등 영수증만 만들고 버전·변경 이력·감사·고객 알림을 늘리지 않는다.
- [기능 SQL](../../../supabase/tests/order_claim_reason_changes.sql)은 원래 접수일의 7일/3개월 경계, 동일 분류 설명 정정, 보류·회수·비용·금전·재고 보존, 허용/차단 단계, 입력 길이·제어문자·협의·권한·소유권·재생 충돌과 민감 근거 미노출을 OWN/FRESH에서 통과했다. 기존 유형 전환·보류 SQL 및 운영자 RPC 권한 범위 검사도 통과했다.
- [동시성 검사](../../../supabase/tests/order_claim_reason_changes_concurrency.sh)는 명시된 로컬 DB를 임시 복제한 뒤 25개 실제 잠금 경합을 실행하고 복제본을 제거한다. 같은 UUID 재생, 다른 입력/행위자, 결과 재조회, 승인·검토·보류·철회·유형 전환·회수·재발송·권한 회수의 양쪽 순서를 통과했다. 금전 시작은 결제사 호출 없이 주문 잠금 아래 합성 취소/환불 원장 삽입으로 독립 가드를 검증한다. 사유 변경 14건·무변경 영수증 1건·감사/고객 알림 각 14건이며 차단된 수정과 주문 금액은 그대로였다.
