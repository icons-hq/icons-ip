# 프로모션 배너 딤·텍스트색·삭제와 복구

migration 파일 경로는 [배포 매핑](../../../supabase/manifests/admin-rollout-migration-map.json)을 반영했다. 아래 과거 검증·적용 기록은 당시 원본 DRAFT 기준이며 이번 운영 배포의 성공을 뜻하지 않는다.

이 문서의 `output/`·임시 경로는 내부에 보존한 로컬 검수 근거의 파일 참조이며, 해당 자료와 비공개 원본 캡처는 저장소에 첨부하지 않는다.

2026-10-14 KST. [원본 조사와 승인된 계약](home-banner-style-removal-proposal.md)을 구현했다. `hero` 배너의 표시 옵션과 보관·비노출 복구를 추가했고 OWN/FRESH 및 독립 체인 DB `59922`, 별도 로컬 런타임 `4322`에서 검증했다. 운영·Preview에는 적용하지 않았다.

## 표시와 보관 계약

- 새 배너는 딤 `적용안함`, 텍스트 `흰색`을 저장한다. 딤은 `none|white|black`, 텍스트는 `white|black`만 허용하며 다른 종류의 큐레이션에 이 payload 키를 쓰지 못한다.
- 기존 배너의 스타일 키 생략은 그대로 유지한다. `기존 표시 유지`에서는 문구가 있을 때 하단 그라데이션을 쓰고, 명시적 `none`은 그라데이션까지 끈다. migration이나 저장 정규화가 기본 키를 과거 payload·영수증에 주입하지 않는다.
- 흰색·검정색 딤은 이미지 전체에 opacity `0.35`로 적용한다. **0.35는 ICONS 고정 정책이며 스마트스토어에서 실측한 값이 아니다.** 문구가 없어도 명시한 딤을 표시한다. 텍스트색은 제목·내용에만 적용하고 이미지 원본·크롭·PC/MO 선택·캐러셀 조작은 유지한다.
- 저장된 배너의 `배너 삭제`는 `archived_at`을 기록하고 `enabled=false`로 바꾼다. 이미지·문구·링크·기간·개별 순서·기존 감사와 ID를 보존한다. 미저장 변경은 삭제 확인창에서 경고하고 저장하지 않는다.
- 보관된 행은 공개 홈과 일반 편집 목록에서 제외한다. 공개 RLS와 스태프도 사용하는 공개 loader에 각각 `archived_at is null`을 적용한다. 삭제한 배너는 별도 20개 페이지 목록으로 읽고 복구할 수 있다.
- 등록 10개는 보관되지 않은 배너를 센다. 비노출·예약·종료는 여전히 포함한다. 삭제는 자리를 비우고 복구는 같은 공통 잠금 아래 한도를 다시 확인한다. 기존 10개 초과 행의 수정·비노출·삭제를 허용하지만 추가·복구는 한도 아래에서만 허용한다.
- 복구는 같은 ID를 **비노출**로 되돌린다. 홈 전체의 `hero` 영역 순서·노출·revision은 바꾸지 않는다. Storage와 `attached` claim은 그대로 두며 PC/MO 경로가 공용 사진 참조 검사에서 계속 보인다. 영구 삭제·자동 만료는 없다.

## 저장·재시도 경계

현재 `store.manage`와 활성 운영자 상태를 영수증 조회보다 먼저 확인한다. 기존 writer와 새 `admin_set_home_banner_archived`는 operation ID → 구성 ID → 구성 행 → 배너 개수 풀의 잠금 순서를 공유한다. 개수 풀 진입과 이탈 모두 같은 잠금을 쓰며, 풀을 가진 요청은 다른 구성 행을 잠그지 않는다.

오래된 저장본은 `PT409`로 거절한다. 보관 행을 새 작업 ID로 일반 저장하면 구·신 RPC 모두 `curation_archived`를 반환한다. 이전 저장·삭제·복구 영수증의 정확한 재확인은 UUID만 반환하고 현재 행을 다시 변경하지 않는다. 성공 후 화면은 현재 목록을 다시 읽는다.

응답 유실 시 최초 FormData·UUID·마이크로초 단위 CAS를 고정한다. 후속 재확인이 권한 거절이나 충돌을 반환해도 첫 응답의 결과가 확정된 것은 아니므로 요청과 닫기 차단을 유지한다. 이 경계를 삭제·복구 확인창과 기존 구성 저장에 모두 적용했다. 복구 확인창이 열려 있으면 바깥 휴지통 창의 닫기·Escape로 고정 요청을 버릴 수 없다.

## 실제 검증

- 관련 9개 파일 **182개 테스트**, 대상 ESLint, 전체 `tsconfig.test.json` 타입검사를 통과했다. 독립 검토에서 찾은 응답 유실 후 거절과 부모 dialog 닫기 우회는 클라이언트 회귀 테스트로 검증했다.
- OWN/FRESH에서 새 기능 SQL·기존 배너·자유상품·operator coverage를 통과했다. 세 딤×두 텍스트색, 타입/열거형 거절, 보관·복구·정확한 영수증 재생, 현재 권한 회수, 10개 복구 한도, 이미지 claim·기존 감사·홈 순서 불변을 확인했다. 함수 정의·owner·ACL 10개가 양쪽에서 일치한다.
- 서로 다른 실제 DB 연결의 **12개 경합**에서 `pg_blocking_pids`로 대기를 확인했다. 저장↔삭제, 복구↔추가, 개수 풀 진입↔이탈, 동일 삭제 요청, 권한 회수↔복구를 검증했다. 별도 복제에서 기존 11개 배너의 수정·보관과 한도 초과 복구 거절도 통과했다.
- 실제 Chrome에서 기존 스타일 키 생략 저장과 하단 그라데이션, 흰 딤/검정 문구, 검정 딤/흰 문구, 딤 없음의 저장·공개 반영을 확인했다. PC/MO `currentSrc`가 다르고 로드가 완료됐으며 딤 전체 크기와 opacity `0.35`를 실측했다. 390px의 최종 공개·관리 문서 폭은 380px로 가로 넘침이 없었다.
- 미저장 제목을 가진 상태의 삭제 확인에서 저장된 제목과 경고를 표시했다. 삭제 뒤 등록 수가 줄고 공개 배너가 0개가 됐다. 휴지통 21개를 2페이지로 읽고, 마지막 페이지의 한 건을 복구하면 20개·1페이지로 자동 보정됐다. 원본 배너 복구 후 비노출·제목·PC/MO 이미지·스타일을 DB에서 다시 읽었다.
- 두 창에서 먼저 저장한 뒤 오래된 삭제를 보내 `curation_conflict`를 받았다. 취소하면 입력을 유지하고, 명시적 최신 저장본 불러오기는 현재 저장값을 표시했다. 모바일 복구창과 휴지통의 폭·세로 스크롤도 확인했다.
- 소유 합성 배너 21개, 관련 감사·claim, Storage 복사본 22개를 정리해 각각 0건을 확인했다. 기존 큐레이션 전체 행과 홈 layout은 seed 전과 동일했다. 소유 탭 3개와 `4322` 런타임을 종료하고 뷰포트를 복원했다.

구형 `home_layout_order` 전체 SQL은 named DB의 operator fixture가 없어 권한 단계에서 중단했다. 해당 DB에 임시 권한 helper를 설치하지 않았으며, 이번 변경의 홈 순서 불변과 이미지 참조는 새 기능 SQL·브라우저 전후 readback으로 검증했다. 실제 권한 없는 별도 브라우저와 응답 유실 네트워크 재현은 사용하지 않았고 SQL·액션·클라이언트 테스트로 확인했다. 콘솔에서는 기존 확장 출처 hydration 경고와 `chrome-extension://` TypeError가 관측됐다. 실제 스크린리더 기기 낭독과 운영·Preview 배포는 실행하지 않았다.
