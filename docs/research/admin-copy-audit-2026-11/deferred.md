## DEFERRED (예약판매·상세 이미지·상품 목록)

범위: `area-DEFER2.txt`의 31개 파일 + 그 문구를 검사하는 테스트 + 예약판매 런북 버튼 이름 인용. 문구·표시만 바꿨고 data-* 속성·상태 값·함수·저장 값·RPC 이름은 그대로다. `lib/admin/guide/topics/goods-sales.ts`는 `id: 'preorders'` 섹션만 고쳤다.

### 공통으로 맞춘 말

- **'할당' → '입고 확인'.** 예약판매의 할당(`admin_allocate_goods_preorders`)은 물건이 들어온 뒤 결제된 예약 주문을 골라 옵션 재고수량에서 빼고 그 주문을 출고할 수 있게 만드는 일이다(배송 건의 예약 품목이 모두 `allocated`여야 출고 가능 — `private.shipment_preorder_allocation_ready`). 화면에서 이 동작은 이미 '입고 확인'으로 불렸고(버튼 앞부분, 근거 칸 '입고 확인 근거', 안내 '입고 확인(예약 주문 할당)'), 상태 이름도 '입고 전 취소·입고 후 환불'이었다. 그래서 '할당'을 걷어 내고 '입고 확인'으로 통일했다(미할당 → 입고 확인 전, 할당 완료 → 입고 확인 완료).
  - '배정'을 쓰지 않은 이유: 같은 예약판매 화면·가이드에서 '배정'은 랜덤 판매의 옵션 무작위 배정 뜻으로 쓰인다("입고 할당은 … 배정된 옵션별로", 런북 "준비 상태로 배정을 짐작"). 둘 다 '배정'이면 한 문장 안에서 뜻이 갈린다.
  - 예약 밖의 '할당 재고'(상품 재고 뜻)는 1차와 같게 '재고수량'.
- '미설정' → 입력칸 예시 글은 '예: 100', 값이 없을 때는 '없음'(예전 '미설정개' 표기 오류도 함께 고침).
- 결과를 모를 때: 그 화면에 있는 버튼 이름을 [ ]로 부르고, 다시 눌러도 한 번만 처리되는지는 코드·런북으로 확인한 곳에만 씀(입고 확인 재처리는 재고를 다시 빼지 않음 — 런북·성공 문구, 일정 일괄 변경 재확정은 두 번 바뀌지 않음 — 가이드, 영상 저장은 같은 operationId).
- 이메일 준비 안 됨: 발송관리 지연 안내(1차)와 같은 말 '메일 발송 서비스 연결(발송 키·서명 설정) … 개발 담당자에게 메일 발송 설정을 요청', 이메일 상태 '공급자 접수' → '발송 서비스 접수'(OrderDelayNoticePanel과 같은 이름).
